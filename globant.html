How do you think about auth and security in PHP apps?

Validate input, least privilege for DB users, don't trust the client, protect secrets, and use proper session/token checks on APIs. For sensitive flows like tax or HR data, authorization matters as much as authentication — can this user see this record?

What do you mean by pure PHP, without a framework?

Pure PHP means writing the app with PHP language features and standard extensions — no Laravel/Symfony doing routing, ORM, and auth for you. You still use Composer sometimes, but you own routing, request/response, DB access with PDO, sessions, and structure yourself. How do you talk to MySQL in pure PHP?

I use PDO with prepared statements — never concatenate user input into SQL. That prevents SQL injection. You prepare, bind values, execute, fetch. Same idea whether you're in Laravel's query builder or pure PHP — the safe pattern is parameterized queries.

Trong PHP thuần bạn nói chuyện với MySQL thế nào?

Tôi dùng PDO với prepared statement — không nối chuỗi input user vào SQL. Như vậy tránh SQL injection. Prepare, bind value, execute, fetch. Cùng ý tưởng dù Laravel query builder hay PHP thuần — pattern an toàn là parameterized query.

Know: PDO + prepared statements = baseline.

Trap: mysqli_query with string concat from $_GET.

Follow-up: Show a safe SELECT with a user id parameter.

How do sessions work in PHP?

session_start() starts a session; PHP stores session data on the server and gives the browser a session cookie. You keep login state in $_SESSION, not only in localStorage. Cookies can also hold preferences, but sensitive auth should stay server-side. Frameworks wrap this; in pure PHP you call it yourself and protect against session fixation/hijacking basics.

Session trong PHP hoạt động thế nào?

session_start() bắt đầu session; PHP lưu data session trên server và gửi cookie session cho browser. Trạng thái login để trong $_SESSION, không chỉ localStorage. Cookie có thể giữ preference, nhưng auth nhạy cảm nên ở server. Framework bọc sẵn; PHP thuần bạn tự gọi và chú ý session fixation/hijacking cơ bản.

Know: Server-side session + session cookie.

Trap: Storing passwords in cookies.

Do you use Composer in pure PHP projects?

Yes — pure PHP doesn't mean old-style everything in one file. Composer manages dependencies and PSR-4 autoloading so classes load by namespace. You still write plain PHP classes; Composer just removes require_once hell. That's standard even without Laravel.

Explain class, interface, and trait in PHP.

A class is a blueprint with properties and methods. An interface defines a contract — methods a class must implement, without the code. A trait is reusable method chunks you paste into classes — useful when you want shared behavior without deep inheritance. In real apps I use classes and interfaces a lot; traits when several classes need the same helper behavior.

Giải thích class, interface và trait trong PHP.

Class là bản thiết kế với property và method. Interface là hợp đồng — method class phải implement, không chứa code. Trait là khối method tái sử dụng gắn vào class — hữu ích khi muốn share behavior mà không kế thừa sâu. Trong app thật tôi dùng class và interface nhiều; trait khi nhiều class cần helper giống nhau.

Know: Class = implementation; interface = contract; trait = reusable methods.

Trap: Confusing interface with abstract class details you can't explain.

Follow-up: When would you use an interface?

What is the React component lifecycle?

In class components there are phases: mounting (constructor, render, componentDidMount), updating (render, componentDidUpdate), and unmounting (componentWillUnmount). How does useEffect relate to the lifecycle?

useEffect runs after the browser paints. With [] it runs once after mount — good for subscribe, initial fetch, or third-party chart init. With [a, b] it re-runs when a or b change. 28. Virtual DOM

Classic concept.

Question EN

What is the Virtual DOM, and why does React use it?

The Virtual DOM is React's in-memory description of the UI — a lightweight tree of React elements. When state changes, React creates a new virtual tree, diffs it with the previous one (reconciliation), and updates only the real DOM nodes that changed. That is usually cheaper than rewriting the whole page by hand. It is not “always faster than raw DOM”; it is a productive model so we describe UI as a function of state and let React apply the minimal updates.

Virtual DOM là gì và vì sao React dùng?

Virtual DOM là mô tả UI trong memory của React — cây element nhẹ. Khi state đổi, React tạo virtual tree mới, diff với tree trước (reconciliation), và chỉ update node DOM thật thay đổi. Thường rẻ hơn tự viết lại cả trang. Không phải “luôn nhanh hơn raw DOM”; đó là model hiệu quả: UI = f(state), React apply cập nhật tối thiểu.

Know: Describe UI → diff → patch real DOM. Not magic always-faster.

Why use Zustand instead of useState?

useState is perfect for local state inside one component — open/closed modal, input draft, one toggle. The pain starts when many distant components need the same state: dashboard filters shared by chart + AG-Grid + workflow panel. With only useState you lift state to a parent and prop-drill, or wrap a huge tree in Context and often re-render too much. So: useState for local; Zustand when shared UI state crosses many siblings without a clean parent.

Vì sao dùng Zustand thay vì chỉ useState?

useState hoàn hảo cho state cục bộ trong một component — mở/đóng modal, draft input, một toggle. Đau bắt đầu khi nhiều component xa nhau cần cùng state: filter dashboard dùng chung bởi chart + AG-Grid + panel workflow. Chỉ dùng useState thì phải lift lên parent và prop-drill, hoặc bọc Context cả cây và hay re-render nhiều. Zustand giữ shared client state trong một store ngoài tree; widget nào cũng subscribe đúng slice cần. Vậy: useState cho local; Zustand khi UI state share xuyên nhiều sibling mà không có parent gọn.

137. Synchronous vs asynchronous

Core concept — memorize.

Question EN
Answer EN
Question VI

What is the difference between synchronous and asynchronous processing?

Synchronous means the caller waits for the work to finish before continuing — like a React page waiting for a PHP API response. Asynchronous means you accept the work and continue; the result comes later — like queueing a heavy export and notifying when it is done. Sync is simpler; async is better when work is slow or spiky and you do not want to block the user request.

Khác nhau giữa xử lý synchronous và asynchronous?

Synchronous nghĩa là caller chờ việc xong mới đi tiếp — như trang React chờ response API PHP. Asynchronous nghĩa là nhận việc rồi đi tiếp; kết quả đến sau — như xếp hàng export nặng và báo khi xong. Sync đơn giản hơn; async tốt hơn khi việc chậm hoặc spike và bạn không muốn block request user.

Problem-solving + async.

Answer VI

How would you design around an unreliable third-party API?

Do not put the third-party call on the critical user path if you can avoid it. Use timeouts, clear errors, retries with backoff for safe operations, and logging with request IDs. For sync jobs, make them re-runnable and visible when they fail — like the job-board integrations on E-Hiring. The UI should show failure honestly, not spin forever.

Bạn thiết kế khi API bên thứ ba không ổn định thế nào?

Đừng đặt gọi bên thứ ba trên đường critical của user nếu tránh được. Dùng timeout, lỗi rõ, retry có backoff cho thao tác an toàn, và log kèm request ID. Với job sync, làm chúng chạy lại được và hiện rõ khi fail — như tích hợp job board ở E-Hiring. UI phải nói thất bại thật, không spin mãi.

Know: Timeouts, retries, visibility, isolate from critical path.

Trap: Infinite retries with no backoff.

Follow-up: How do you avoid duplicate side effects on retry?
