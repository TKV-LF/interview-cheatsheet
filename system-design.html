Architecture

01Client-side vs server-side architectureJD: design client-side and server-side architecture.

How do you split client-side and server-side architecture?

The client owns UI state, routing, and how the screen feels — React/React Native, responsive layout. The server owns truth: authz, validation, business rules, persistence, and anything secret. I don't put prices, permissions, or 'is admin' only in the frontend. APIs are the contract. If a feature needs a background job — export, sync, email — that stays server-side so a closed laptop doesn't kill it. I draw the boundary early with the PM: what the user sees vs what must be correct even if someone tampers with the client.

Bạn tách kiến trúc client và server thế nào?

Client own UI state, routing, cảm giác màn hình — React/React Native, layout responsive. Server own sự thật: authz, validation, business rule, persistence, và mọi thứ secret. Tôi không để giá, quyền, hay 'is admin' chỉ ở frontend. API là contract. Feature cần job nền — export, sync, email — để server, laptop tắt không được giết việc. Tôi vẽ ranh giới sớm với PM: user thấy gì vs cái phải đúng dù ai đó sửa client.

Know: UI on client · truth and secrets on server · API is the contract

Trap: Hiding a button as authorization.

Follow-up: What must never live only in React state?

How you design

02How you approach system designFullstack level — not FAANG mega-scale.

How do you approach a system design question?

I start with requirements and constraints — users, reads/writes, consistency needs, and what can fail. Then I sketch the simple path: React client → PHP API → MySQL. After that I ask what breaks when traffic or data grows — slow queries, long requests, spikes — and only then add caching, jobs, or split services. I do not jump to microservices first.

Bạn tiếp cận câu hỏi system design thế nào?

Tôi bắt đầu từ requirements và ràng buộc — user, đọc/ghi, cần consistency thế nào, và chỗ nào có thể fail. Rồi phác đường đơn giản: React client → PHP API → MySQL. Sau đó hỏi cái gì gãy khi traffic hoặc data tăng — query chậm, request dài, spike — rồi mới thêm cache, job, hoặc tách service. Tôi không nhảy microservices ngay.

Know: Requirements → simple path → bottlenecks → scale carefully.

Trap: Designing Kubernetes for a small CRUD tool on day one.

Follow-up: What questions do you ask before drawing boxes?

03Design a reporting dashboardUse a familiar shape.

Design a feature: a reporting dashboard that loads data from PHP and shows it in React.

I would keep a clear API contract — filters in, paginated JSON out. React handles UI state and loading/error. PHP validates input, queries MySQL with indexes and pagination, returns stable shapes. Heavy exports like Excel/XML I would move off the click-path into a background job if they get slow. Auth on every request. That is the same shape I have used in enterprise reporting UIs.

Thiết kế feature: dashboard report load từ PHP hiện trên React.

Tôi giữ contract API rõ — filter vào, JSON có phân trang ra. React lo UI state và loading/error. PHP validate input, query MySQL có index và pagination, trả shape ổn định. Export nặng như Excel/XML nếu chậm thì đưa khỏi click-path sang background job. Auth mỗi request. Đó là shape tôi dùng cho UI reporting enterprise.

Know: Contract + pagination + auth; heavy work async.

Trap: Loading hundreds of thousands of rows into the browser at once.

Follow-up: How do you paginate large reports?

04What is scalability?Plain language.

What does scalability mean to you?

It means the system still behaves acceptably when load grows — more users, more data, more requests — without rewriting everything overnight. For my work that usually starts with good schema/indexes, pagination, avoiding N+1, and not doing heavy work inside a user request. Horizontal scaling and caches come after you know the real bottleneck.

Scalability với bạn nghĩa là gì?

Nghĩa là hệ thống vẫn chấp nhận được khi tải tăng — nhiều user, nhiều data, nhiều request — mà không phải viết lại hết trong một đêm. Với việc của tôi thường bắt đầu từ schema/index tốt, pagination, tránh N+1, và không nhét việc nặng trong request user. Scale ngang và cache đến sau khi biết bottleneck thật.

Know: Grow load without collapse; measure bottleneck first.

Trap: Scalability means only add more servers.

Follow-up: Vertical vs horizontal scaling?

05Scale PHP + MySQL + ReactPractical fullstack answer.

How would you scale a PHP + MySQL + React application?

First measure: is it CPU, DB, or network? For MySQL: indexes, query shape, read replicas if reads dominate. For PHP: keep requests short, cache hot reads when safe, move slow jobs out of the request. For React: paginate, do not over-fetch, avoid huge re-renders. I have felt this on large-record products like Base PIT — the database and query design mattered before fancy architecture.

Bạn scale app PHP + MySQL + React thế nào?

Đo trước: CPU, DB, hay mạng? MySQL: index, dạng query, read replica nếu đọc chiếm đa số. PHP: giữ request ngắn, cache đọc nóng khi an toàn, đưa job chậm ra khỏi request. React: phân trang, đừng over-fetch, tránh re-render khổng lồ. Tôi từng thấy điều này ở sản phẩm nhiều bản ghi như Base PIT — database và query quan trọng trước kiến trúc hoa mỹ.

Know: Measure → DB → request time → FE fetch size.

Trap: Caching before fixing a missing index.

Follow-up: What would you cache vs always read fresh?

06Bottlenecks checklistInterview checklist.

What bottlenecks do you look for in a web system?

Slow SQL, N+1 queries, huge payloads to the browser, synchronous third-party API calls in the middle of a request, missing indexes, and lock contention on writes. Also frontend: blocking the main thread with big lists. I use Network timing and backend logs/SQL to see which layer is actually slow.

Bạn tìm bottleneck nào trong hệ thống web?

SQL chậm, N+1, payload khổng lồ xuống browser, gọi API bên thứ ba đồng bộ giữa request, thiếu index, và tranh chấp lock khi ghi. Frontend nữa: block main thread vì list lớn. Tôi dùng timing Network và log/SQL backend để xem tầng nào thật sự chậm.

Know: DB, payload size, sync external calls, FE render.

Trap: Guessing without timing data.

Follow-up: How do you prove the DB is the bottleneck?

07Synchronous vs asynchronousCore concept — memorize.

What is the difference between synchronous and asynchronous processing?

Synchronous means the caller waits for the work to finish before continuing — like a React page waiting for a PHP API response. Asynchronous means you accept the work and continue; the result comes later — like queueing a heavy export and notifying when it is done. Sync is simpler; async is better when work is slow or spiky and you do not want to block the user request.

Khác nhau giữa xử lý synchronous và asynchronous?

Synchronous nghĩa là caller chờ việc xong mới đi tiếp — như trang React chờ response API PHP. Asynchronous nghĩa là nhận việc rồi đi tiếp; kết quả đến sau — như xếp hàng export nặng và báo khi xong. Sync đơn giản hơn; async tốt hơn khi việc chậm hoặc spike và bạn không muốn block request user.

Know: Sync = wait now; async = do later / elsewhere.

Trap: Calling everything async with no need.

Follow-up: Give one example of each in a web app.

08When sync vs async in real appsTie to CV.

When do you choose synchronous vs asynchronous in a real app?

For normal CRUD and screen loads, I stay synchronous — user clicks, API returns, UI updates. For heavy exports, big sync between systems, or slow third-party calls, I prefer async jobs so the HTTP request stays fast and failures can retry. At BaseVN, sync pipelines and Excel/XML flows are exactly the kind of work that can hurt if you force everything into one request.

Khi nào chọn sync hay async trong app thật?

CRUD và load màn hình bình thường thì sync — user bấm, API trả, UI cập nhật. Export nặng, đồng bộ lớn giữa hệ thống, hoặc gọi bên thứ ba chậm thì nên async job để HTTP request còn nhanh và fail có thể retry. Ở BaseVN, pipeline sync và flow Excel/XML đúng kiểu việc dễ đau nếu ép hết vào một request.

Know: UI path sync; heavy/retryable work async.

Trap: Making login async for no reason.

Follow-up: How do you show progress for an async export?

09Queues and background jobsConcept level — honest.

What are background jobs or queues for?

They are for work you do not want inside the user request — emails, big imports/exports, syncing to another system, generating files. The API enqueues a job and returns quickly; a worker processes it later, with retries if something fails. I understand the pattern from enterprise sync/export work; the exact queue tool depends on the team stack.

Background job hoặc queue dùng để làm gì?

Cho việc không muốn nhét trong request user — email, import/export lớn, sync sang hệ khác, tạo file. API xếp job và trả nhanh; worker xử lý sau, retry nếu fail. Tôi hiểu pattern từ việc sync/export enterprise; tool queue cụ thể tùy stack team.

Know: Decouple slow work from HTTP; retry failures.

Trap: Claiming deep RabbitMQ or Kafka ownership if you have not run it.

Follow-up: What happens if a job fails halfway?

10Consistency tradeoffsLight system-design vocab.

Have you heard of consistency tradeoffs when scaling?

At a practical level: if everything must be correct immediately — like tax or payroll numbers — I stay closer to strong consistency in the database and careful transactions. If the UI can show slightly delayed status — like a sync job progress — eventual consistency is OK. I do not pretend I am designing Google-scale CAP systems; I choose based on whether wrong data is worse than slow data.

Bạn biết tradeoff consistency khi scale không?

Ở mức thực tế: nếu mọi thứ phải đúng ngay — như số thuế hay payroll — tôi gần strong consistency trong DB và transaction cẩn thận. Nếu UI chấp nhận status hơi trễ — như tiến độ sync job — eventual consistency ổn. Tôi không giả vờ thiết kế hệ CAP quy mô Google; tôi chọn theo việc data sai có tệ hơn data chậm hay không.

Know: Money/compliance → stronger consistency; progress/status can lag.

Trap: Throwing CAP theorem buzzwords with no example.

Follow-up: Give a feature that can be eventually consistent.

11Traffic spike 10xScalability scenario.

What would you do if traffic suddenly spiked 10x?

I would protect the core path first — make sure the app stays up for critical actions. Check DB connections, slow queries, and error rates. Add caching for hot read endpoints if safe, rate-limit abusive traffic if needed, and shed non-critical work. Longer term: capacity planning, better indexes, and moving heavy jobs off the request path. I start with evidence, not a full rewrite.

Nếu traffic đột ngột tăng 10 lần bạn làm gì?

Tôi bảo vệ đường critical trước — giữ app sống cho hành động quan trọng. Kiểm tra DB connection, slow query và error rate. Cache endpoint đọc nóng nếu an toàn, rate-limit nếu bị abuse, và giảm việc không critical. Dài hạn: capacity planning, index tốt hơn, và đưa job nặng khỏi request path. Bắt đầu từ bằng chứng, không viết lại hết.

Know: Stabilize → measure → cache/limit → structural fixes.

Trap: Premature microservices during an incident.

Follow-up: What metrics do you watch during a spike?

12Unreliable third-party APIProblem-solving + async.

How would you design around an unreliable third-party API?

Do not put the third-party call on the critical user path if you can avoid it. Use timeouts, clear errors, retries with backoff for safe operations, and logging with request IDs. For sync jobs, make them re-runnable and visible when they fail — like the job-board integrations on E-Hiring. The UI should show failure honestly, not spin forever.

Bạn thiết kế khi API bên thứ ba không ổn định thế nào?

Đừng đặt gọi bên thứ ba trên đường critical của user nếu tránh được. Dùng timeout, lỗi rõ, retry có backoff cho thao tác an toàn, và log kèm request ID. Với job sync, làm chúng chạy lại được và hiện rõ khi fail — như tích hợp job board ở E-Hiring. UI phải nói thất bại thật, không spin mãi.

Know: Timeouts, retries, visibility, isolate from critical path.

Trap: Infinite retries with no backoff.

Follow-up: How do you avoid duplicate side effects on retry?

13How would you design an AI learning feature? · 26. Hallucinations · 27. EvaluationKeep this practical. A learning product’s problem is similar: recommend or explain learning without inventing unsafe or irrelevant content. the in-product assistant has to stay grounded in their library and assignments.

How would you design an AI learning feature? · 26. Hallucinations · 27. Evaluation.

Design: Start with the learner job — understand, practice, get feedback, or find a course. Ship a narrow first use case. Then auth, permissions, validation, rate limits, logging, fallbacks. If we have approved content, retrieve it and keep the model inside that box. Measure latency, errors, cost, and whether the learner actually continues.

Hallucinations: Not only a better prompt. Give trusted content, constrain the output, allow “I don’t know,” and fall back to a catalog item or a human path. Watch real traces. That is why I used Langfuse.

Evaluate: Technical health plus product quality. A fast 200 can still be a useless or wrong lesson. I want golden questions, reviewer checks, and after-release behavior: repeat questions, drop-off, thumbs-down patterns.

Bạn thiết kế một tính năng học bằng AI thế nào? Ảo giác và cách đánh giá?

Thiết kế: bắt đầu từ việc của người học — hiểu, luyện, nhận góp ý, hoặc tìm khóa. Ship một case đầu hẹp. Rồi auth, quyền, validation, rate limit, log, fallback. Nếu có nội dung đã duyệt, lấy nội dung đó và giữ model trong cái hộp ấy. Đo độ trễ, lỗi, chi phí, và người học có tiếp tục không.

Ảo giác: không chỉ là prompt hay hơn. Đưa nội dung tin được, ràng output, cho phép "tôi không biết", và fallback sang catalog hoặc người. Xem trace thật. Vì vậy tôi dùng Langfuse.

Đánh giá: sức khỏe kỹ thuật cộng chất lượng sản phẩm. Một 200 nhanh vẫn có thể là bài vô ích hoặc sai. Tôi muốn câu hỏi vàng, người review, và hành vi sau release: hỏi lại, bỏ giữa chừng, kiểu thumbs-down.

Keep this practical. A learning product’s problem is similar: recommend or explain learning without inventing unsafe or irrelevant content. the in-product assistant has to stay grounded in their library and assignments.

Common questions

14Webhook retriesCommon design prompt. Use E-Hiring and IAP, not a URL shortener.

Design retries for a third-party webhook or API.

I retry only when the call is safe to repeat. Timeout and 429 and 5xx can retry. A 4xx usually means my request is wrong, so retrying will not help. I use backoff, a max number of attempts, and a dead letter so a poison message does not loop forever. I store the external id so a retry is idempotent. E-Hiring taught me job-board APIs time out and change their JSON. IELTS taught me a store webhook can arrive twice. Loud failure, a request id in the logs, and a sample I can re-check beat a silent success.

Thiết kế retry cho webhook hoặc API bên thứ ba.

Tôi chỉ retry khi gọi lại là an toàn. Timeout, 429 và 5xx có thể retry. 4xx thường là request của tôi sai, retry không giúp. Tôi dùng backoff, số lần tối đa, và dead letter để message độc không lặp mãi. Tôi lưu external id để retry idempotent. E-Hiring dạy tôi API job board timeout và đổi JSON. IELTS dạy tôi webhook của store có thể đến hai lần. Lỗi phải ồn, request id trong log, và một sample kiểm lại — hơn một success thầm lặng.
