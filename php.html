02Building APIs in PHPREST mindset.

How do you design a backend API in PHP?

I start from the use case: what the React client needs. Then I define clear endpoints, request/response shapes, validation, auth, and error codes. I keep controllers thin, put business rules in services, and make sure MySQL queries are intentional. Good APIs are boring and predictable.

Bạn thiết kế API PHP thế nào?

Tôi bắt đầu từ use case: React client cần gì. Rồi định nghĩa endpoint rõ, shape request/response, validation, auth và mã lỗi. Controller mỏng, business rule ở service, query MySQL có chủ đích. API tốt thì nhàm chán và dễ đoán.

Know: Contract-first thinking between FE and BE.

Trap: Fat controllers with SQL everywhere.

03MySQL and performancePIT 500k story hook.

How do you handle MySQL performance in PHP apps?

I look at the query plan and indexes first, not micro-optimizing PHP loops. On Base PIT we dealt with 500,000+ records, so schema design and query shape mattered for reports and sync. I also avoid N+1 patterns and heavy work inside request cycles when a job/queue is better.

Bạn xử lý hiệu năng MySQL trong app PHP thế nào?

Tôi xem query plan và index trước, không tối ưu vòng lặp PHP trước. Ở Base PIT có 500,000+ bản ghi, nên schema và dạng query quan trọng cho report/sync. Tôi cũng tránh N+1 và việc nặng trong request cycle khi job/queue hợp hơn.

Know: Index + query shape + avoid N+1.

Trap: Caching everything before measuring.

04Auth and security basicsEnterprise awareness.

How do you think about auth and security in PHP apps?

Validate input, least privilege for DB users, don't trust the client, protect secrets, and use proper session/token checks on APIs. For sensitive flows like tax or HR data, authorization matters as much as authentication — can this user see this record?

Bạn nghĩ về auth và bảo mật trong app PHP thế nào?

Validate input, least privilege cho DB user, không tin client, bảo vệ secret, và check session/token đúng trên API. Với luồng nhạy cảm như thuế/HR, authorization quan trọng không kém authentication — user này có được xem bản ghi này không?

Know: Authn vs authz; never trust FE-only checks.

Trap: Hiding a button is not security.

Follow-up: SQL injection — how do you prevent it?

05Testing PHP codeHonest practical level.

How do you test PHP backend code?

I focus on the risky paths: API contracts, validation, and critical business rules. Unit tests for pure logic, and integration-style checks for DB/API when needed. I'm not dogmatic about 100% coverage — I care that the money/compliance/data paths are safe.

Bạn test PHP backend thế nào?

Tôi tập trung đường rủi ro: contract API, validation và business rule quan trọng. Unit cho logic thuần, integration khi cần DB/API. Không cố 100% coverage — quan tâm các luồng tiền/compliance/data phải an toàn.

Know: Test risk, not vanity coverage.

Pure PHP

06What is PHP thuần / pure PHP?Interviewer asked to review this carefully.

What do you mean by pure PHP, without a framework?

Pure PHP means writing the app with PHP language features and standard extensions — no Laravel/Symfony doing routing, ORM, and auth for you. You still use Composer sometimes, but you own routing, request/response, DB access with PDO, sessions, and structure yourself. Frameworks speed you up; pure PHP shows you understand what happens under the hood. At BaseVN I worked on a custom PHP platform — so I'm used to PHP beyond only Laravel helpers.

PHP thuần nghĩa là gì, không dùng framework?

PHP thuần là viết app bằng ngôn ngữ PHP và extension chuẩn — không có Laravel/Symfony lo routing, ORM, auth giúp bạn. Đôi khi vẫn dùng Composer, nhưng bạn tự own routing, request/response, DB bằng PDO, session và cấu trúc. Framework giúp nhanh; PHP thuần chứng tỏ bạn hiểu thứ xảy ra bên dưới. Ở BaseVN tôi làm trên nền tảng PHP custom — nên tôi quen PHP, không chỉ helper của Laravel.

Know: Own routing/DB/session yourself; frameworks hide that.

Trap: Saying pure PHP means no Composer and no OOP.

Follow-up: What does a framework give you that pure PHP does not?

07PDO and SQL safelyCore pure PHP skill.

How do you talk to MySQL in pure PHP?

I use PDO with prepared statements — never concatenate user input into SQL. That prevents SQL injection. You prepare, bind values, execute, fetch. Same idea whether you're in Laravel's query builder or pure PHP — the safe pattern is parameterized queries.

Trong PHP thuần bạn nói chuyện với MySQL thế nào?

Tôi dùng PDO với prepared statement — không nối chuỗi input user vào SQL. Như vậy tránh SQL injection. Prepare, bind value, execute, fetch. Cùng ý tưởng dù Laravel query builder hay PHP thuần — pattern an toàn là parameterized query.

Know: PDO + prepared statements = baseline.

Trap: mysqli_query with string concat from $_GET.

Follow-up: Show a safe SELECT with a user id parameter.

08Sessions and cookiesAuth without a framework.

How do sessions work in PHP?

session_start() starts a session; PHP stores session data on the server and gives the browser a session cookie. You keep login state in $_SESSION, not only in localStorage. Cookies can also hold preferences, but sensitive auth should stay server-side. Frameworks wrap this; in pure PHP you call it yourself and protect against session fixation/hijacking basics.

Session trong PHP hoạt động thế nào?

session_start() bắt đầu session; PHP lưu data session trên server và gửi cookie session cho browser. Trạng thái login để trong $_SESSION, không chỉ localStorage. Cookie có thể giữ preference, nhưng auth nhạy cảm nên ở server. Framework bọc sẵn; PHP thuần bạn tự gọi và chú ý session fixation/hijacking cơ bản.

Know: Server-side session + session cookie.

Trap: Storing passwords in cookies.

Follow-up: What's the difference between session and cookie?

09Composer, autoload, namespacesModern pure PHP still uses these.

Do you use Composer in pure PHP projects?

Yes — pure PHP doesn't mean old-style everything in one file. Composer manages dependencies and PSR-4 autoloading so classes load by namespace. You still write plain PHP classes; Composer just removes require_once hell. That's standard even without Laravel.

Trong dự án PHP thuần có dùng Composer không?

Có — PHP thuần không có nghĩa kiểu cũ nhét hết một file. Composer quản lý dependency và PSR-4 autoload để class load theo namespace. Bạn vẫn viết class PHP thường; Composer bỏ cảnh require_once loạn. Đó là chuẩn kể cả không dùng Laravel.

Know: Composer + PSR-4 autoload is modern PHP.

Trap: Pure PHP = no namespaces / no Composer.

10OOP in PHP: class, interface, traitThey may quiz basics.

Explain class, interface, and trait in PHP.

A class is a blueprint with properties and methods. An interface defines a contract — methods a class must implement, without the code. A trait is reusable method chunks you paste into classes — useful when you want shared behavior without deep inheritance. In real apps I use classes and interfaces a lot; traits when several classes need the same helper behavior.

Giải thích class, interface và trait trong PHP.

Class là bản thiết kế với property và method. Interface là hợp đồng — method class phải implement, không chứa code. Trait là khối method tái sử dụng gắn vào class — hữu ích khi muốn share behavior mà không kế thừa sâu. Trong app thật tôi dùng class và interface nhiều; trait khi nhiều class cần helper giống nhau.

Know: Class = implementation; interface = contract; trait = reusable methods.

Trap: Confusing interface with abstract class details you can't explain.

11Request lifecycle in pure PHPHow a page runs without Laravel.

What happens when a request hits a pure PHP app?

The web server points to an entry file, often index.php. That script reads the URL/method, routes to a controller or include, talks to the database, then echoes HTML or JSON. There's no magic router unless you write one or use a small router package. Understanding this helps when debugging Laravel too — the framework still ends at request in, response out.

Khi một request vào app PHP thuần thì chuyện gì xảy ra?

Web server trỏ vào file entry, thường index.php. Script đọc URL/method, route tới controller hoặc include, nói chuyện database, rồi echo HTML hoặc JSON. Không có router thần kỳ trừ khi bạn tự viết hoặc dùng package router nhỏ. Hiểu điều này cũng giúp debug Laravel — framework vẫn là request vào, response ra.

Know: Entry script → route → logic/DB → response.

Trap: Thinking Laravel has no request lifecycle.

12Superglobals: GET POST SERVERDaily pure PHP.

What are PHP superglobals you use often?

$_GET and $_POST for input, $_SERVER for method/URL/headers, $_SESSION for server session data, $_COOKIE for cookies, and sometimes $_FILES for uploads. I never trust them raw — validate and sanitize before use. In APIs I also read JSON from php://input.

Các superglobal PHP bạn hay dùng?

$_GET và $_POST cho input, $_SERVER cho method/URL/header, $_SESSION cho data session server, $_COOKIE cho cookie, đôi khi $_FILES cho upload. Không tin raw — phải validate/sanitize trước khi dùng. Với API tôi cũng đọc JSON từ php://input.

Know: Input via superglobals; always validate.

Trap: Echoing $_GET straight into HTML/SQL.

13Errors and exceptions in PHPDebugging pure PHP.

How do you handle errors in PHP?

For expected failures I use exceptions and try/catch. For logging I avoid showing sensitive details to users — log server-side, return a safe message. In pure PHP you configure error_reporting and display_errors carefully: off in production, detailed in local. Same discipline as in Laravel, just more manual.

Bạn xử lý lỗi trong PHP thế nào?

Với lỗi预期 đoán được tôi dùng exception và try/catch. Log thì không show chi tiết nhạy cảm cho user — log phía server, trả message an toàn. PHP thuần cần chỉnh error_reporting và display_errors cẩn thận: tắt trên production, chi tiết ở local. Cùng kỷ luật như Laravel, chỉ thủ công hơn.

Know: Exceptions + safe user messages + no display_errors in prod.

Trap: var_dump in production.

14Security basics in pure PHPThey care about this.

What security basics do you apply in pure PHP?

Prepared statements for SQL, htmlspecialchars or escaping for HTML output against XSS, CSRF tokens on state-changing forms, password_hash/password_verify for passwords, and never commit secrets. Frameworks give helpers; in pure PHP you must remember to apply them yourself.

Bảo mật cơ bản trong PHP thuần bạn áp dụng gì?

Prepared statement cho SQL, htmlspecialchars hoặc escape HTML chống XSS, CSRF token cho form đổi dữ liệu, password_hash/password_verify cho mật khẩu, và không commit secret. Framework có helper; PHP thuần bạn phải tự nhớ áp dụng.

Know: SQLi, XSS, CSRF, password hashing.

Trap: md5 for passwords.

15Laravel vs pure PHPHonest comparison.

When do you use Laravel vs pure PHP?

Pure PHP or a thin custom stack is fine for small APIs or when you already have an in-house framework — like at BaseVN. Laravel is faster for full apps: routing, auth, Eloquent, validation, queues. For enterprise products I'd expect a framework or structured codebase, but I still want strong pure PHP fundamentals so I'm not lost when the framework doesn't hide the problem.

Khi nào dùng Laravel, khi nào PHP thuần?

PHP thuần hoặc stack custom mỏng ổn cho API nhỏ hoặc khi đã có framework nội bộ — như ở BaseVN. Laravel nhanh hơn cho app đầy đủ: routing, auth, Eloquent, validation, queue. Với sản phẩm enterprise tôi expect framework hoặc codebase có cấu trúc, nhưng vẫn cần nền PHP thuần vững để không lạc khi framework không che được vấn đề.

Know: Framework for speed; pure PHP for fundamentals and custom platforms.

Trap: Saying you never need frameworks / never need pure PHP.

How do you connect a PHP backend with a React frontend?

PHP exposes a clear JSON API. React fetches it, types the response, renders UI, and sends mutations back with validation both sides. I care about consistent error shapes, auth headers/cookies, and loading/empty/error states in the UI so users aren't stuck on a spinner forever.

18Error handling across stackUser-visible quality.

How do you handle errors across frontend and backend?

Backend returns meaningful status codes and a stable error payload. Frontend maps that to user messages and logs details for developers. I don't show raw stack traces to users, and I don't swallow errors silently. For retries, only idempotent-safe calls.

Bạn xử lý lỗi xuyên frontend và backend thế nào?

Backend trả status có nghĩa và payload lỗi ổn định. Frontend map thành message cho user và log chi tiết cho dev. Không show stack trace cho user, không nuốt lỗi im lặng. Retry chỉ khi call an toàn idempotent.

Know: Stable error contract + honest UX.

Trap: Alert with secret details.

Common questions

19== versus ===Common PHP quiz. Say the rule, then one surprise.

What is the difference between == and === in PHP?

I use === by default. == compares after type coercion, so "0" == false and 0 == "foo" can both surprise you. === checks value and type. I only reach for == when I explicitly want coercion, which is rare in application code.

Khác nhau giữa == và === trong PHP?

Tôi mặc định dùng ===. == so sánh sau khi ép kiểu, nên "0" == false và 0 == "foo" đều có thể bất ngờ. === kiểm tra cả giá trị lẫn kiểu. Tôi chỉ dùng == khi cố ý muốn ép kiểu — trong code ứng dụng thì hiếm.

20N+1 queriesCommon performance question. Use BaseVN, not a textbook.

What is the N+1 query problem, and how do you fix it?

N+1 is one query for the list, then one more query per row inside a loop. On a large employee or tax table that dies. I look for a query in a loop, then I join or batch-load the related rows. On IELTS I hit the same idea from the other side: hydrate the progress the screen needs instead of fetching every topic one by one. The fix is fewer round trips, and then I re-check the result on a known sample so I did not just make a wrong query faster.

N+1 query là gì và bạn sửa thế nào?

N+1 là một query cho danh sách, rồi thêm một query mỗi dòng trong vòng lặp. Bảng nhân viên hoặc thuế lớn sẽ chết. Tôi tìm query nằm trong loop, rồi join hoặc load theo lô. Bên IELTS tôi gặp cùng ý từ phía kia: hydrate đúng phần progress màn hình cần, không fetch từng topic. Sửa là giảm round trip, rồi kiểm lại trên sample đã biết để không làm một query sai chạy nhanh hơn.

21Database transactionsCommon when they ask about money or sync.

When do you use a database transaction?

When several writes must succeed or fail together. A sync that updates HR data and a payroll row is a good example: a half-written result is worse than a failed job. I open a transaction, do the writes, commit if every step is valid, and roll back if one fails. I keep the transaction short. I do not hold it open across an HTTP call to a third party.

Khi nào bạn dùng database transaction?

Khi nhiều lệnh ghi phải cùng thành công hoặc cùng thất bại. Sync vừa sửa dữ liệu HR vừa sửa dòng payroll là ví dụ: ghi nửa chừng tệ hơn một job fail. Tôi mở transaction, ghi, commit khi mọi bước hợp lệ, rollback nếu một bước lỗi. Transaction phải ngắn. Tôi không giữ nó mở trong lúc gọi HTTP sang bên thứ ba.

22Idempotent APIsCommon follow-up after retries, webhooks, or payments.

What is an idempotent API request?

Calling it twice has the same effect as calling it once. GET should be idempotent. A payment, a webhook, or a sync often is not, unless I design it that way. I store an external id or an idempotency key and I check it before insert. On IELTS, Apple and Google purchase notifications hit Express. A repeated notification must not grant the purchase twice. The server is the source of truth, and the unique store transaction id is the guard.

Request API idempotent là gì?

Gọi hai lần cho cùng kết quả như gọi một lần. GET nên idempotent. Thanh toán, webhook, hoặc sync thường không — trừ khi tôi thiết kế vậy. Tôi lưu external id hoặc idempotency key và kiểm tra trước khi insert. Trên IELTS, thông báo mua của Apple và Google vào Express. Notification lặp không được cấp quyền mua hai lần. Server là nguồn sự thật, và transaction id của store là chốt chặn.

23REST and GraphQLCommon awareness question. Stay honest about what you shipped.

REST or GraphQL — which do you choose?

I have shipped REST. The client and server share a JSON contract, status codes mean something, and errors have a stable shape. GraphQL is one endpoint where the client asks for the fields it needs. That helps when many clients need very different shapes. I would use it if the team already runs it. I would not introduce it for a small PHP API. My default is a clear REST contract.

REST hay GraphQL — bạn chọn cái nào?

Tôi đã ship REST. Client và server dùng contract JSON, status code có nghĩa, lỗi có shape ổn định. GraphQL là một endpoint, client xin đúng field nó cần. Hợp khi nhiều client cần shape rất khác nhau. Tôi dùng nếu team đã chạy sẵn. Tôi không đưa vào một API PHP nhỏ. Mặc định của tôi là REST contract rõ.

24Where you cacheCommon, and easy to oversell. Say what you would not cache.

What do you cache, and what do you refuse to cache?

I cache work that is expensive and safe to be slightly stale: a dashboard aggregate, a config, a rendered report that we can invalidate. I do not cache a tax or payroll figure for a specific period unless invalidation is obvious, because fast and wrong is a bad launch. Redis is the usual tool. I know the pattern — key, TTL, invalidate on write — and I would follow the team's setup instead of inventing one in the interview.

Bạn cache gì, và từ chối cache gì?

Tôi cache việc đắt và chấp nhận hơi cũ: số tổng dashboard, config, report có thể invalidate. Tôi không cache số thuế hoặc payroll của một kỳ nếu chưa rõ cách xóa cache, vì nhanh mà sai là launch tệ. Redis là tool thường gặp. Tôi biết pattern — key, TTL, xóa khi ghi — và tôi theo setup của team thay vì bịa một cái trong interview.
