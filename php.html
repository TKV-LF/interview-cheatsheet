01== versus ===Say the rule, then one PHP 8 surprise. Know what changed in PHP 8.~51s✓

What is the difference between == and === in PHP?

I use === by default. Triple equals checks the value and the type. Double equals converts types first, and those rules are easy to forget.

PHP 8 made them saner. 0 == "foo" is now false, because a non-numeric string is compared as a string. In PHP 7 it was true, and that caused real bugs. Some surprises are still there in PHP 8: "0" == false is true, null == false is true, and "1e3" == "1000" is true because both are numeric strings.

So in application code I write ===, and I pass true as the strict flag to in_array and array_search. I only use == when I really want the conversion, and that is rare.

Khác nhau giữa == và === trong PHP là gì?

Tôi mặc định dùng ===. Ba dấu bằng so cả giá trị lẫn kiểu. Hai dấu bằng đổi kiểu trước rồi mới so, và luật đổi kiểu rất dễ quên.

PHP 8 đã sửa cho hợp lý hơn. 0 == "foo" giờ là false, vì chuỗi không phải số sẽ được so như chuỗi. Ở PHP 7 nó là true, và từng gây bug thật. PHP 8 vẫn còn vài chỗ bất ngờ: "0" == false là true, null == false là true, và "1e3" == "1000" là true vì cả hai đều là chuỗi số.

Nên trong code ứng dụng tôi viết ===, và truyền true vào tham số strict của in_array và array_search. Tôi chỉ dùng == khi thật sự muốn đổi kiểu, mà việc đó hiếm.

Know: PHP 8.0 “saner string to number comparisons”: a number compared with a non-numeric string is now compared as strings. match always compares strictly.

Trap: Saying 0 == "foo" is true without adding “before PHP 8”.

Follow-up: What does match use to compare? Strict ===, unlike switch.

02Interface versus abstract classA contract versus shared code. Give one example of each.~60s✓

What is the difference between an interface and an abstract class in PHP?

An interface is a contract: method signatures and constants, no state. A class can implement many interfaces. An abstract class is a partly built class. It can have properties, a constructor, and real methods, plus abstract methods the child must write. A class can extend only one parent.

I use an interface when different implementations must be swappable. A PaymentGateway interface can have a Stripe class and a fake class for tests. Laravel binds the interface in the container, and the controller never knows which one it got.

I use an abstract class when several classes share real code and state. For example, a base importer opens the file, loops over the rows, and logs errors, and each child only maps one row. If I am not sure, I start with an interface, because inheritance is harder to undo later.

Interface và abstract class trong PHP khác nhau thế nào?

Interface là một hợp đồng: chỉ có chữ ký method và hằng số, không có state. Một class có thể implement nhiều interface. Abstract class là một class mới làm một phần. Nó có property, constructor, method có code thật, cộng các method abstract mà class con phải viết. Một class chỉ extends được một class cha.

Tôi dùng interface khi nhiều cách cài đặt phải thay được cho nhau. Interface PaymentGateway có thể có một class Stripe và một class giả để test. Laravel bind interface đó trong container, và controller không cần biết nó nhận được bản nào.

Tôi dùng abstract class khi nhiều class dùng chung code và state thật. Ví dụ một importer gốc lo mở file, duyệt từng dòng và ghi lỗi, còn mỗi class con chỉ map một dòng. Khi phân vân, tôi bắt đầu bằng interface, vì kế thừa về sau khó gỡ hơn.

Know: Interface: no properties, all methods public, constants allowed. Abstract class: can have a constructor, properties, protected methods. You cannot instantiate either.

Trap: Saying an abstract class cannot have a constructor or implemented methods. It can.

Follow-up: Where does a trait fit? See the next card.

03TraitsShared methods without a shared parent. Not a type.~59s✓

What is a trait in PHP, and when do you use one?

A trait is a group of methods that PHP copies into a class. PHP has single inheritance, so a trait is how two unrelated classes share code without a common parent. Laravel uses traits everywhere: HasFactory, SoftDeletes, and Notifiable on a model.

I write one when the behavior is small and really the same in each class, like a HasUuid trait that fills the id when a model is created. A trait is not a type. You cannot type-hint it, so if callers need to rely on that behavior, I pair it with an interface.

If two traits define the same method, I resolve it with insteadof, or I take it as a sign the design is wrong. I avoid traits that use properties the class might not have, because that hides a dependency.

Trait trong PHP là gì, và khi nào bạn dùng?

Trait là một nhóm method mà PHP chép vào class. PHP chỉ cho kế thừa đơn, nên trait là cách để hai class không liên quan dùng chung code mà không cần chung class cha. Laravel dùng trait ở khắp nơi: HasFactory, SoftDeletes, Notifiable trên model.

Tôi viết trait khi hành vi nhỏ và thật sự giống nhau ở mỗi class, như trait HasUuid tự điền id khi tạo model. Trait không phải là một kiểu. Không type-hint được, nên nếu nơi gọi cần dựa vào hành vi đó, tôi đi kèm một interface.

Nếu hai trait có method trùng tên, tôi xử lý bằng insteadof, hoặc coi đó là dấu hiệu thiết kế có vấn đề. Tôi tránh trait dùng property mà class có thể không có, vì như vậy là giấu một phụ thuộc.

Know: Traits can have properties, abstract methods, and static methods. Conflict syntax: use A, B { A::hello insteadof B; }.

Trap: Building a giant trait as a way around single inheritance.

04SOLID, with a PHP exampleOne line per letter, then one real refactor. Do not recite.~68s✓

What is SOLID? Give an example in PHP.

SOLID is five rules for keeping classes easy to change. Single responsibility: a class has one reason to change. Open/closed: you add behavior by adding a class, not by editing a growing switch. Liskov substitution: a child class must work anywhere its parent works. Interface segregation: keep interfaces small, so a class does not implement methods it ignores. Dependency inversion: depend on an interface, not on a concrete class.

One example covers most of them. Picture an export controller that builds the Excel file, sends the email, and switches on the format. I would split it. The controller validates and dispatches a job. An ExportService builds the rows. Each format is a class behind an Exporter interface, so adding CSV is a new class, not a new case. The job gets the Exporter from the container, so a test can pass a fake.

I apply this when a class starts to hurt, not as a checklist on day one.

SOLID là gì? Cho một ví dụ bằng PHP.

SOLID là năm nguyên tắc giúp class dễ sửa. Single responsibility: mỗi class chỉ có một lý do để thay đổi. Open/closed: thêm hành vi bằng cách thêm class, không phải sửa một switch ngày càng dài. Liskov substitution: class con phải chạy được ở mọi chỗ class cha chạy. Interface segregation: interface nhỏ, để class không phải implement method nó không dùng. Dependency inversion: phụ thuộc vào interface, không phụ thuộc vào class cụ thể.

Một ví dụ là đủ cho hầu hết các ý. Giả sử một controller export vừa tạo file Excel, vừa gửi email, vừa switch theo định dạng. Tôi sẽ tách ra. Controller chỉ validate và dispatch một job. ExportService tạo các dòng dữ liệu. Mỗi định dạng là một class sau interface Exporter, nên thêm CSV là thêm một class, không phải thêm một case. Job lấy Exporter từ container, nên khi test có thể truyền bản giả.

Tôi áp dụng khi một class bắt đầu khó sửa, không phải làm theo checklist từ ngày đầu.

Know: The most common break in Laravel apps is single responsibility: fat controllers and fat models.

Trap: Reciting the acronym with no example, or wrapping a 20-line class in three interfaces.

Follow-up: Which principle do you see broken most often? Single responsibility, in controllers.

05PHP 8 features you actually useTypes, enums, match, readonly. Be honest about JIT.~62s✓

Which PHP 8 features do you use?

The ones I use most make types clearer. Constructor property promotion and readonly properties turn a small DTO into a few lines, and readonly stops someone changing it later. Enums, since PHP 8.1, replace status strings. An OrderStatus enum backed by a string can be cast directly on an Eloquent model.

match replaces a long switch. It compares strictly, returns a value, and throws if nothing matches. The nullsafe operator, $order?->customer?->name, replaces nested null checks. Named arguments help at a call with several booleans, and union types say int|string when a value really can be both.

About JIT, I am honest: it helps CPU-heavy loops, but a normal web request spends its time waiting on MySQL and the network, so JIT barely changes it. OPcache is what matters for web PHP. For a new project today I would target PHP 8.3 or newer.

Bạn dùng những tính năng nào của PHP 8?

Những cái tôi dùng nhiều nhất là giúp kiểu dữ liệu rõ hơn. Constructor property promotion và readonly property làm một DTO nhỏ chỉ còn vài dòng, và readonly chặn việc ai đó sửa giá trị về sau. Enum, từ PHP 8.1, thay cho chuỗi trạng thái. Enum OrderStatus có giá trị string có thể cast thẳng trên model Eloquent.

match thay cho switch dài. Nó so sánh chặt, trả về giá trị, và báo lỗi nếu không nhánh nào khớp. Toán tử nullsafe, $order?->customer?->name, thay cho nhiều lớp kiểm tra null. Named argument giúp chỗ gọi hàm có nhiều tham số boolean, và union type ghi rõ int|string khi giá trị thật sự có thể là cả hai.

Về JIT, tôi nói thật: nó giúp vòng lặp nặng CPU, nhưng một request web bình thường chủ yếu chờ MySQL và mạng, nên JIT gần như không đổi gì. Với PHP web, OPcache mới là thứ quan trọng. Dự án mới hôm nay tôi sẽ chọn PHP 8.3 trở lên.

Know: 8.0: match, nullsafe, named args, union types, promotion, JIT. 8.1: enums, readonly properties, never, fibers. 8.2: readonly classes. 8.3: typed class constants, json_validate. 8.4: property hooks, asymmetric visibility.

Trap: Claiming JIT made your API faster.

Follow-up: What happens when no match arm matches? An UnhandledMatchError is thrown.

06Errors and exceptionsThrowable, Error versus Exception, and one handler at the edge.~58s✓

How do you handle errors in PHP? What is the difference between an Error and an Exception?

Since PHP 7, both Error and Exception implement Throwable. An Exception is for things the code can expect and handle: a validation failure, a missing record, a partner API that timed out. An Error comes from the engine, like calling a method on null or a TypeError, and it usually means a bug.

I catch specific exceptions where I can do something useful, like retry or return a clear message. I do not catch Throwable everywhere and carry on. At the edge, one handler logs the details and returns a safe message, so users never see a stack trace. In production display_errors is off and log_errors is on.

In Laravel 11 and 12 that handler is configured in bootstrap/app.php, and errors go to the log or to an error tracker like Sentry.

Bạn xử lý lỗi trong PHP thế nào? Error và Exception khác nhau ra sao?

Từ PHP 7, cả Error và Exception đều implement Throwable. Exception dành cho lỗi mà code có thể lường trước và xử lý: validation sai, không tìm thấy bản ghi, API đối tác bị timeout. Error đến từ engine, như gọi method trên null hay TypeError, và thường có nghĩa là có bug.

Tôi bắt những exception cụ thể ở chỗ tôi làm được gì đó có ích, như retry hoặc trả thông báo rõ ràng. Tôi không bắt Throwable ở mọi nơi rồi chạy tiếp như không có gì. Ở lớp ngoài cùng, một handler ghi log chi tiết và trả thông báo an toàn, nên người dùng không bao giờ thấy stack trace. Trên production display_errors tắt và log_errors bật.

Trong Laravel 11 và 12, handler đó cấu hình trong bootstrap/app.php, và lỗi được ghi vào log hoặc gửi tới công cụ theo dõi lỗi như Sentry.

Know: Throwable → Error (TypeError, ValueError, ArithmeticError) and Exception. Custom domain exceptions make catch blocks readable. finally always runs.

Trap: An empty catch block, or var_dump left in production.

Follow-up: Where have you used an error tracker? Sentry on Aquanix and PhysioFix (Express).

07What happens when a request hits PHPWeb server, PHP-FPM, superglobals, then everything is thrown away.~63s✓

What happens when a request reaches a PHP app? Which superglobals do you use?

Nginx or Apache receives the request and hands it to PHP-FPM, which runs one entry file, usually public/index.php. PHP fills the superglobals: $_GET, $_POST, $_SERVER for the method and headers, $_COOKIE, and $_FILES. A JSON body is not in $_POST, so I read php://input and decode it. None of that input is trusted until it is validated.

The script routes, runs the logic, queries MySQL, outputs HTML or JSON, and ends. Then PHP throws everything away. Nothing in memory survives to the next request, which is why sessions, cache, and locks live in files, Redis, or the database.

Laravel is the same path with more layers: index.php boots the app, the request passes through middleware to the router and the controller, and the response goes back out. OPcache keeps the compiled code, so booting on every request is cheaper than it sounds.

Khi một request tới app PHP thì chuyện gì xảy ra? Bạn hay dùng superglobal nào?

Nginx hoặc Apache nhận request và chuyển cho PHP-FPM, PHP-FPM chạy một file đầu vào, thường là public/index.php. PHP điền sẵn các superglobal: $_GET, $_POST, $_SERVER cho method và header, $_COOKIE, và $_FILES. Body JSON không nằm trong $_POST, nên tôi đọc php://input rồi decode. Mọi input đó đều chưa đáng tin cho tới khi được validate.

Script định tuyến, chạy logic, truy vấn MySQL, trả HTML hoặc JSON, rồi kết thúc. Sau đó PHP bỏ hết. Không có gì trong bộ nhớ còn lại cho request sau, nên session, cache và lock phải nằm ở file, Redis hoặc database.

Laravel đi đúng đường đó nhưng nhiều lớp hơn: index.php khởi động app, request đi qua middleware tới router và controller, rồi response đi ngược ra. OPcache giữ code đã biên dịch, nên việc khởi động mỗi request rẻ hơn nhiều người nghĩ.

Know: Share-nothing per request. Laravel Octane is the exception: long-running workers, so static state can leak between requests.

Trap: Echoing $_GET straight into HTML or SQL.

Follow-up: How do you return JSON in pure PHP? header('Content-Type: application/json'), then echo json_encode($data, JSON_THROW_ON_ERROR).

08What a mutex is, in PHPShare-nothing. Use a database or Redis lock instead.~63s✓

Explain what a mutex is, and why it is uncommon in PHP.

A mutex is a lock that stops two threads from entering the same critical section at the same time. In a normal PHP-FPM or Laravel queue setup, each request or job runs in its own process, so a mutex inside one process does not stop the others. That is why you rarely see one in application PHP.

When two jobs must not run the same export at once, I take a lock that every process can see: GET_LOCK in MySQL, SELECT … FOR UPDATE on a row, or a Redis lock with a TTL, which is what Cache::lock gives you in Laravel. The TTL means a dead worker cannot hold it forever. flock is fine for one cron on one machine, but not across two Cloud Run instances. PHP is share-nothing on purpose, so cross-process locks live in the database or in Redis, never in a static variable.

Mutex là gì, và vì sao ít gặp trong PHP?

Mutex là một cái khóa để hai thread không cùng lúc chạy vào một đoạn code nhạy cảm. Với PHP-FPM hoặc queue Laravel thông thường, mỗi request hoặc job chạy trong một process riêng, nên mutex trong một process không chặn được các process khác. Vì vậy code ứng dụng PHP hiếm khi có mutex.

Khi hai job không được chạy cùng một lần export, tôi lấy một khóa mà mọi process đều thấy: GET_LOCK trong MySQL, SELECT … FOR UPDATE trên một dòng, hoặc khóa Redis có TTL, chính là Cache::lock trong Laravel. TTL để worker chết giữa chừng không giữ khóa mãi. flock ổn cho một cron trên một máy, nhưng không dùng được giữa hai instance Cloud Run. PHP cố ý không chia sẻ bộ nhớ, nên khóa giữa các process phải nằm ở database hoặc Redis, không bao giờ ở biến static.

Know: PHP processes do not share memory. Lock in MySQL or Redis, with a timeout.

Trap: A static $locked flag in a controller.

Follow-up: How do you stop the same queued job overlapping? ShouldBeUnique or the WithoutOverlapping job middleware, both backed by a cache lock.

09Composer, autoload, namespacesModern PHP uses Composer with or without a framework.~40s✓

Do you use Composer? What does autoloading do?

Yes, in every project. Composer installs the dependencies and generates a PSR-4 autoloader, so a class like App\Services\TaxReport loads from app/Services/TaxReport.php the first time it is used, without a pile of require_once lines. Namespaces keep my class names from colliding with a library's.

I commit composer.lock, so every machine and every deploy installs exactly the same versions. Production runs composer install --no-dev with an optimized autoloader. Updating a package is a deliberate change with its own review, not a side effect of a deploy. This is standard PHP, with or without Laravel.

Bạn có dùng Composer không? Autoload làm gì?

Có, ở mọi dự án. Composer cài dependency và tạo autoloader theo PSR-4, nên một class như App\Services\TaxReport được nạp từ app/Services/TaxReport.php ngay lần đầu được dùng, không cần một đống dòng require_once. Namespace giúp tên class của tôi không trùng với class của thư viện.

Tôi commit composer.lock, để mọi máy và mọi lần deploy cài đúng cùng phiên bản. Production chạy composer install --no-dev với autoloader đã tối ưu. Nâng cấp package là một thay đổi có chủ đích và được review riêng, không phải tác dụng phụ của một lần deploy. Đây là chuẩn của PHP, dù có Laravel hay không.

Know: PSR-4 maps a namespace prefix to a folder. composer install follows the lock file; composer update changes it.

Trap: Running composer update on the production server.

Follow-up: What is PSR-4? A standard that maps namespaces to file paths for autoloading.

10Arrays and common PHP functionsEveryday PHP. Know map versus filter and the strict flag.~47s✓

Which PHP array functions do you use often?

Arrays are everywhere in PHP, both lists and associative arrays. Every day I use array_map to transform each item, array_filter to keep the items that pass a check, array_column to pull one field out of rows, array_merge, in_array with the strict flag, isset, count, and usort with the spaceship operator. For APIs it is json_encode and json_decode, with JSON_THROW_ON_ERROR so bad JSON fails loudly.

In Laravel I mostly reach for Collections, like map, filter, pluck, and groupBy, which read better in a chain. When the shape matters, I use a small typed DTO instead of passing an array with ten keys around.

Bạn hay dùng những hàm array nào trong PHP?

Array có ở khắp nơi trong PHP, cả dạng danh sách lẫn mảng kết hợp. Hằng ngày tôi dùng array_map để biến đổi từng phần tử, array_filter để giữ phần tử thỏa điều kiện, array_column để lấy một trường từ các dòng, array_merge, in_array có bật strict, isset, count, và usort với toán tử spaceship. Với API là json_encode và json_decode, kèm JSON_THROW_ON_ERROR để JSON sai thì báo lỗi rõ.

Trong Laravel tôi chủ yếu dùng Collection, như map, filter, pluck, groupBy, viết thành chuỗi dễ đọc hơn. Khi cấu trúc dữ liệu quan trọng, tôi dùng một DTO nhỏ có kiểu rõ ràng thay vì truyền một array mười key đi khắp nơi.

Know: array_map returns the same number of items, changed. array_filter returns fewer items, unchanged, and keeps the keys.

Trap: Forgetting that array_filter preserves keys, then json_encode outputs an object instead of a list. Wrap it in array_values.

Follow-up: Difference between array_merge and the + operator? + keeps the left side's keys.

11Pure PHP or Laravel?Know what the framework does for you, and when you do not need it.~46s✓

What does pure PHP mean, and when would you use it instead of Laravel?

Pure PHP means no framework doing routing, the ORM, validation, and auth for me. I still use Composer and classes, but I own the router, the PDO queries, the sessions, and the folder structure myself.

It is fine for a small API, a script, or when a company already has its own codebase. For a full product I pick Laravel, because routing, validation, Eloquent, queues, and auth are already solved, and every new developer knows where things go.

Knowing pure PHP still matters. When Laravel behaves strangely, the answer is usually in the plain request, the session, or the SQL underneath, and I can read those directly.

PHP thuần là gì, và khi nào bạn dùng nó thay vì Laravel?

PHP thuần là không có framework lo routing, ORM, validation và auth cho tôi. Tôi vẫn dùng Composer và class, nhưng tự lo router, query PDO, session và cấu trúc thư mục.

Nó hợp với một API nhỏ, một script, hoặc khi công ty đã có codebase riêng. Với một sản phẩm đầy đủ tôi chọn Laravel, vì routing, validation, Eloquent, queue và auth đã có sẵn, và lập trình viên mới vào đều biết thứ gì nằm ở đâu.

Hiểu PHP thuần vẫn quan trọng. Khi Laravel chạy lạ, câu trả lời thường nằm ở request, session, hoặc câu SQL bên dưới, và tôi đọc được trực tiếp những thứ đó.

Know: A framework gives you routing, middleware, validation, ORM, queues, auth, and conventions. Pure PHP gives you control and no hidden layers.

Trap: Saying pure PHP means no Composer, no namespaces, or no OOP.

Follow-up: What Laravel feature would you miss most? Validation and queues.

12Service container and dependency injectionThe class asks for what it needs. A provider decides what it gets.~62s✓

What is the Laravel service container? How does dependency injection work there?

The service container builds objects and their dependencies for me. If a controller's constructor asks for a ReportService, Laravel reads the type hint, builds the service and whatever it needs, and passes it in. That is dependency injection: the class says what it needs instead of creating it with new.

What is middleware in Laravel? When do you write your own?

Middleware is a layer every matching request passes through before it reaches the controller, and the response passes back through it on the way out. 14Eloquent relationships and N+1Name the relations, then show with() and preventLazyLoading.~56s✓

How do Eloquent relationships work, and how do you avoid N+1 queries?

Relations are methods on the model: hasMany, belongsTo, belongsToMany with a pivot table, and hasManyThrough. Reading $order->customer runs a query the first time. That is lazy loading, and in a loop over fifty orders it becomes fifty-one queries. That is N+1.

The fix is eager loading. Order::with(['customer', 'items'])->paginate(50) runs one extra query per relation using WHERE IN. withCount('items') gives a count without loading the rows. To catch it early I turn on Model::preventLazyLoading() outside production, so a lazy load throws in development instead of slowing down production. Debugbar or Telescope locally shows the query count per page.

The idea is the same outside Laravel. On IELTS AI Tutor I fixed the same shape from the client side: progress loads once at sign-in, not one request per topic.

Quan hệ trong Eloquent hoạt động thế nào, và bạn tránh N+1 ra sao?

Quan hệ là các method trên model: hasMany, belongsTo, belongsToMany qua bảng trung gian, và hasManyThrough. Đọc $order->customer sẽ chạy một query ở lần đầu. Đó là lazy loading, và trong vòng lặp năm mươi đơn hàng nó thành năm mươi mốt query. Đó là N+1.

Cách sửa là eager loading. Order::with(['customer', 'items'])->paginate(50) chỉ chạy thêm một query cho mỗi quan hệ, dùng WHERE IN. withCount('items') cho số lượng mà không cần tải các dòng. Để bắt sớm, tôi bật Model::preventLazyLoading() ngoài production, để lazy load báo lỗi ngay lúc phát triển thay vì làm chậm production. Ý này giống hệt khi không dùng Laravel. Trên IELTS AI Tutor tôi sửa đúng dạng này từ phía client: tiến độ học được tải một lần khi đăng nhập, không phải một request cho mỗi chủ đề.

How do you validate input in Laravel?

17Migrations and safe schema changesAdditive changes, expand then contract. Rollback is not a backup.~74s✓

How do you use migrations, and how do you change a schema safely on a live system?

A migration is a versioned PHP file that changes the schema, with an up and a down. Everyone runs the same files in the same order, and the migrations table records which ones already ran. On a live system I treat migrate as a deploy step, not a casual command.

Rollback is not my safety net, because a down that drops a column also drops its data. So I keep changes additive. To rename a column, I add the new one, write to both, backfill in chunks, switch the reads, and drop the old column in a later release. A new index on a big MySQL table I check first: InnoDB can usually build it online, but it still costs IO.

I never edit a migration that already ran in production; I write a new one. And I take a backup before anything destructive. That is the habit I kept when I migrated a legacy database to MySQL at Akktis: backup first, then check the application's reads and writes after the cutover.

Bạn dùng migration thế nào, và đổi schema an toàn trên hệ thống đang chạy ra sao?

Migration là một file PHP có phiên bản dùng để đổi schema, gồm up và down. Mọi người chạy cùng các file theo cùng thứ tự, và bảng migrations ghi lại file nào đã chạy. Trên hệ thống đang chạy, tôi coi migrate là một bước của deploy, không phải lệnh chạy tùy tiện.

Rollback không phải là lưới an toàn của tôi, vì một down xóa cột thì cũng xóa luôn dữ liệu trong cột đó. Nên tôi giữ thay đổi theo kiểu chỉ thêm. Muốn đổi tên cột, tôi thêm cột mới, ghi vào cả hai, chép dữ liệu cũ theo từng đợt, chuyển phần đọc sang cột mới, rồi xóa cột cũ ở bản phát hành sau. Thêm index trên bảng MySQL lớn thì tôi kiểm tra trước: InnoDB thường tạo được mà không khóa bảng, nhưng vẫn tốn IO.

Tôi không bao giờ sửa migration đã chạy trên production, tôi viết migration mới. Và tôi backup trước mọi thay đổi có thể mất dữ liệu. Đó là thói quen tôi giữ khi chuyển một database cũ sang MySQL ở Akktis: backup trước, rồi kiểm tra đọc và ghi của ứng dụng sau khi chuyển.

Know: Expand, migrate, contract. migrate --pretend shows the SQL. migrate --force is needed in production. Old code must work with the new schema during a rolling deploy.

Trap: migrate:fresh anywhere near production, or a NOT NULL column with no default on a big table in one step.

18Queues, jobs, and failed jobsDispatch, tries, backoff, failed_jobs. A job can run twice.~72s✓

How do Laravel queues work? What happens when a job fails?

A job is a class with a handle method. I dispatch it from the request, the request returns, and a worker running queue:work picks it up later from Redis, the database, or SQS. Each job sets its tries, a backoff, and a timeout. When it runs out of tries, Laravel writes it to the failed_jobs table, and once the cause is fixed I can retry it with queue:retry.

Delivery is at least once, so a job can run twice. I make it idempotent: check a unique key before writing, or use ShouldBeUnique for jobs that must not overlap. I pass ids, not big models, and the job reloads fresh state. If I dispatch inside a transaction, I use afterCommit, or the worker may look for a row that does not exist yet. Workers are long-running processes, so a deploy runs queue:restart.

The shape I know from BaseVN integrations, with retries, request logging, and job monitoring, is what failed_jobs and Horizon give you in Laravel.

Queue trong Laravel hoạt động thế nào? Job lỗi thì sao?

Job là một class có method handle. Tôi dispatch nó trong request, request trả về ngay, và một worker chạy queue:work lấy job ra xử lý sau, từ Redis, database hoặc SQS. Mỗi job đặt số lần thử, thời gian chờ giữa các lần thử, và timeout. Khi hết số lần thử, Laravel ghi nó vào bảng failed_jobs, và khi đã sửa nguyên nhân thì tôi chạy lại bằng queue:retry.

Job được giao ít nhất một lần, nên có thể chạy hai lần. Tôi làm job idempotent: kiểm tra một khóa unique trước khi ghi, hoặc dùng ShouldBeUnique cho job không được chạy chồng. Tôi truyền id, không truyền model lớn, và job tự tải lại dữ liệu mới. Nếu dispatch trong transaction, tôi dùng afterCommit, không thì worker có thể đi tìm một dòng chưa tồn tại. Worker là process chạy lâu, nên mỗi lần deploy phải chạy queue:restart.

Cách làm tôi quen từ các tích hợp ở BaseVN, gồm retry, log request và theo dõi job, chính là những gì failed_jobs và Horizon cung cấp trong Laravel.

Know: Job chains and batches, failed() method on the job, rate-limited job middleware, WithoutOverlapping. Horizon is a dashboard for Redis queues.

Trap: Dispatching inside a transaction without afterCommit, or forgetting to restart workers after a deploy.

21When do you add an index?Index the query you have. Equality columns first, range or sort last.~67s✓

When do you add an index, and how do you choose the column order?

I add an index for a slow query that people actually run, not for a column that might be useful later, because every index slows down writes. For a composite index the rule is: equality columns first, then the range or ORDER BY column last. Take an orders list filtered by customer and status, newest first:

SELECT id, status, created_at FROM orders
WHERE customer_id = 42 AND status = 'open'
ORDER BY created_at DESC LIMIT 50;

That wants (customer_id, status, created_at). The two equality columns narrow the rows, and inside them created_at is already sorted, so there is no filesort. If I put a range column in the middle, the columns after it cannot be used to seek. An index on status alone barely helps, because status has only a few values. I confirm with EXPLAIN. On Base PIT, with more than 500,000 records, a missing index was a real delay, not a textbook note.

Khi nào bạn thêm index, và chọn thứ tự cột thế nào?

Tôi thêm index cho một query chậm mà người dùng thật sự chạy, không phải cho một cột có thể sau này cần, vì mỗi index đều làm chậm việc ghi. Với index nhiều cột, quy tắc là: cột so sánh bằng đứng trước, cột so sánh khoảng hoặc cột ORDER BY đứng cuối. Ví dụ danh sách đơn hàng lọc theo khách hàng và trạng thái, mới nhất trước:

SELECT id, status, created_at FROM orders
WHERE customer_id = 42 AND status = 'open'
ORDER BY created_at DESC LIMIT 50;

Query này cần (customer_id, status, created_at). Hai cột so sánh bằng thu hẹp số dòng, và trong phạm vi đó created_at đã được sắp sẵn, nên không phải filesort. Nếu đặt cột so sánh khoảng ở giữa, các cột phía sau nó không dùng để tìm được nữa. Index chỉ trên status gần như không giúp gì, vì status chỉ có vài giá trị. Tôi kiểm tra lại bằng EXPLAIN. Ở Base PIT, với hơn 500.000 bản ghi, thiếu index là chậm thật, không phải lý thuyết trong sách.

Know: Equality, then range or sort. A covering index holds every column the query reads, so MySQL never touches the table (Extra: Using index).

Trap: Saying the column order must follow the order of the WHERE clause. The optimizer does not care about that order; it cares about equality versus range.

22Composite index, leftmost prefixRead from the left. A leading % kills a B-tree, and FULLTEXT is not substring search.~61s✓

You have INDEX (warehouse_id, sku). Which queries can use it?

A composite index is sorted by the first column, then by the second inside it. So (warehouse_id, sku) works for WHERE warehouse_id = 3, and for warehouse_id = 3 AND sku = 'A-451'. For WHERE sku = 'A-451' alone it normally cannot seek, because those SKUs are scattered across every warehouse. MySQL 8.0.13 added skip scan, which can help when the first column has very few values, but I do not design around it. If people search by SKU across all warehouses, I add an index that starts with sku.

LIKE '%451%', with a leading wildcard, cannot use a B-tree at all. A FULLTEXT index does not fix that either, because it matches whole words, not substrings, unless you use the ngram parser. For real substring or fuzzy search at scale, I put a search engine next to MySQL.

Có INDEX (warehouse_id, sku). Những query nào dùng được index này?

Index nhiều cột được sắp theo cột đầu, rồi theo cột thứ hai bên trong cột đầu. Nên (warehouse_id, sku) dùng được cho WHERE warehouse_id = 3, và cho warehouse_id = 3 AND sku = 'A-451'. Với WHERE sku = 'A-451' đứng một mình thì thường không tìm theo index được, vì các SKU đó nằm rải ở mọi kho. MySQL 8.0.13 có thêm skip scan, giúp được khi cột đầu có rất ít giá trị, nhưng tôi không thiết kế dựa vào nó. Nếu người dùng tìm SKU trên mọi kho, tôi thêm một index bắt đầu bằng sku.

LIKE '%451%', có ký tự đại diện ở đầu, hoàn toàn không dùng được B-tree. FULLTEXT cũng không giải quyết được, vì nó tìm theo từ nguyên vẹn, không tìm chuỗi con, trừ khi dùng ngram parser. Muốn tìm chuỗi con hoặc tìm gần đúng ở quy mô lớn, tôi đặt một search engine bên cạnh MySQL.

Know: Leftmost prefix. LIKE 'A-4%' (no leading wildcard) can use the index as a range.

Trap: Claiming one composite index covers every filter, or that FULLTEXT does substring search.

23Finding a slow query and reading EXPLAINSlow query log first. Then type, key, rows, Extra.~69s✓

How do you find a slow MySQL query, and what do you look for in EXPLAIN?

First I find the query. In production that is the slow query log or the APM, not a guess. Then I run EXPLAIN on it with realistic values.

I read four columns. type: ALL is a full table scan, while ref, eq_ref, or range means an index is used. key: which index MySQL actually chose. rows: how many rows it expects to read. 400,000 for a page of 50 means the index is wrong. Extra: Using filesort or Using temporary usually means the ORDER BY or GROUP BY has no matching index, and Using index means a covering index. On MySQL 8, EXPLAIN ANALYZE gives real timings, because it actually runs the query.

Then I change one thing, the index or the query, and run EXPLAIN again. I do not put a cache on top of a table scan. This is the loop I used when tuning tax and reporting queries on Base PIT.

Bạn tìm query MySQL chậm thế nào, và nhìn gì trong EXPLAIN?

Trước hết tôi tìm ra query đó. Trên production là nhờ slow query log hoặc APM, không phải đoán. Rồi tôi chạy EXPLAIN với giá trị giống thật.

Tôi đọc bốn cột. type: ALL là quét toàn bảng, còn ref, eq_ref hoặc range nghĩa là có dùng index. key: index mà MySQL thật sự chọn. rows: số dòng nó dự kiến đọc. Đọc 400.000 dòng cho một trang 50 dòng nghĩa là index sai. Extra: Using filesort hoặc Using temporary thường là ORDER BY hoặc GROUP BY không có index phù hợp, còn Using index là covering index. Trên MySQL 8, EXPLAIN ANALYZE cho thời gian thật, vì nó chạy thật câu query.

Rồi tôi đổi một thứ, index hoặc câu query, và chạy EXPLAIN lại. Tôi không đặt cache lên trên một lần quét toàn bảng. Đây là vòng lặp tôi dùng khi tối ưu các query thuế và báo cáo ở Base PIT.

Know: Slow query log (long_query_time), EXPLAIN columns, EXPLAIN ANALYZE. Fix the index or the query before adding a cache.

Trap: EXPLAIN on a tiny local dump, then claiming production is fine.

Follow-up: How do you prove the database is the bottleneck? Request timing in the logs, then the slow query log for that endpoint.

24INNER JOIN versus LEFT JOINSay which rows disappear. Watch the WHERE on the right table.~64s✓

When do you use INNER JOIN, and when LEFT JOIN?

INNER JOIN keeps only rows that match on both sides. LEFT JOIN keeps every row from the left table and fills the right side with NULL when there is no match. A list of open orders with the customer name is an inner join, because an order without a customer should not appear:

SELECT o.id, c.name, o.status
FROM orders o
INNER JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'open';

A report of every customer, including those who never ordered, is a LEFT JOIN from customers to orders. With an inner join there, customers without orders vanish and the report is wrong. One trap: if I filter the right-hand table in the WHERE clause, the LEFT JOIN quietly becomes an inner join, so that condition belongs in the ON clause. And I join in SQL, not by loading rows into PHP and matching them in a loop.

Khi nào dùng INNER JOIN, khi nào dùng LEFT JOIN?

INNER JOIN chỉ giữ những dòng khớp ở cả hai bên. LEFT JOIN giữ mọi dòng của bảng bên trái, và điền NULL cho bên phải khi không khớp. Danh sách đơn hàng đang mở kèm tên khách là inner join, vì đơn không có khách thì không nên hiện:

SELECT o.id, c.name, o.status
FROM orders o
INNER JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'open';

Báo cáo mọi khách hàng, kể cả người chưa từng đặt đơn, là LEFT JOIN từ customers sang orders. Nếu dùng inner join ở đây, khách chưa có đơn sẽ biến mất và báo cáo bị sai. Một cái bẫy: nếu lọc bảng bên phải trong WHERE, LEFT JOIN sẽ lặng lẽ thành inner join, nên điều kiện đó phải đặt trong ON. Và tôi join bằng SQL, không kéo dữ liệu về PHP rồi ghép trong vòng lặp.

Know: INNER drops unmatched rows. LEFT keeps the left side. Right-table filters go in ON.

Trap: LEFT JOIN orders o … WHERE o.status = 'open', which drops customers with no orders.

Follow-up: How do you find customers with no orders? LEFT JOIN … WHERE o.id IS NULL, or NOT EXISTS.

25Database transactionsAll or nothing. Short, and no HTTP call inside.~45s✓

When do you use a database transaction?

When several writes must succeed or fail together. A sync that updates HR data and a payroll row is a good example: a half-written result is worse than a failed job. I open a transaction, do the writes, commit when every step is valid, and roll back if one fails. In Laravel, DB::transaction() with a closure does that, and it can retry on a deadlock.

I keep the transaction short. I do not hold it open across an HTTP call to a third party, because the locks stay held the whole time and other requests queue up behind them. Emails and notifications go after the commit.

Khi nào bạn dùng database transaction?

Khi nhiều lệnh ghi phải cùng thành công hoặc cùng thất bại. Một lần sync vừa sửa dữ liệu HR vừa sửa dòng lương là ví dụ tốt: ghi được một nửa còn tệ hơn job thất bại hẳn. Tôi mở transaction, ghi, commit khi mọi bước hợp lệ, và rollback nếu một bước lỗi. Trong Laravel, DB::transaction() với một closure làm đúng việc đó, và có thể tự chạy lại khi gặp deadlock.

Tôi giữ transaction thật ngắn. Tôi không để nó mở trong lúc gọi HTTP sang bên thứ ba, vì khóa bị giữ suốt thời gian đó và các request khác phải xếp hàng chờ. Email và thông báo gửi sau khi commit.

Know: ACID. DB::transaction(fn () => …, attempts: 3). Queue jobs dispatched inside use afterCommit.

Trap: Calling a payment or email API while the transaction holds row locks.

Follow-up: What isolation level does MySQL use? See Isolation levels.

26MySQL isolation levelsFour levels. InnoDB default is REPEATABLE READ. A plain SELECT reads a snapshot.~69s✓

What are transaction isolation levels? Which one does MySQL use by default?

Isolation says how much one transaction can see of others running at the same time. There are four levels. READ UNCOMMITTED can see writes that are not committed yet, a dirty read. READ COMMITTED sees only committed data, but reading the same row twice can give two different answers. REPEATABLE READ, the InnoDB default, gives each transaction a consistent snapshot, so plain SELECTs return the same result. SERIALIZABLE behaves as if transactions ran one at a time, at the cost of much more locking.

The trap with the default is that a plain SELECT reads the snapshot, so it can be stale for a check-then-write. When I decide based on current data, I use SELECT … FOR UPDATE, which locks the rows and reads the latest version. In REPEATABLE READ, locking reads on a range also take gap locks, which block inserts into that range and can cause deadlocks. I rarely change the level. I fix the specific query instead.

Isolation level của transaction là gì? MySQL mặc định dùng mức nào?

Isolation cho biết một transaction thấy được bao nhiêu của các transaction khác đang chạy cùng lúc. Có bốn mức. READ UNCOMMITTED thấy cả dữ liệu chưa commit, gọi là dirty read. READ COMMITTED chỉ thấy dữ liệu đã commit, nhưng đọc cùng một dòng hai lần có thể ra hai kết quả khác nhau. REPEATABLE READ, mức mặc định của InnoDB, cho mỗi transaction một bản chụp nhất quán, nên các câu SELECT thường trả về cùng kết quả. SERIALIZABLE chạy như thể các transaction lần lượt từng cái một, đổi lại là khóa nhiều hơn hẳn.

Cái bẫy của mức mặc định là SELECT thường đọc từ bản chụp, nên có thể đã cũ khi kiểm tra rồi mới ghi. Khi cần quyết định dựa trên dữ liệu hiện tại, tôi dùng SELECT … FOR UPDATE, nó khóa các dòng và đọc phiên bản mới nhất. Ở REPEATABLE READ, đọc có khóa trên một khoảng còn lấy thêm gap lock, chặn insert vào khoảng đó và có thể gây deadlock. Tôi hiếm khi đổi mức isolation. Tôi sửa đúng câu query có vấn đề.

Know: Phenomena: dirty read, non-repeatable read, phantom. InnoDB uses MVCC snapshots. PostgreSQL defaults to READ COMMITTED.

Trap: Saying REPEATABLE READ prevents every race condition. It does not stop a lost update from a plain read followed by a write.

Follow-up: How do you change it for one transaction? SET TRANSACTION ISOLATION LEVEL READ COMMITTED before it starts.

27Deadlocks: how to read and fix themRetry the transaction, read INNODB STATUS, then fix the lock order.~68s✓

You see deadlocks in MySQL. How do you investigate and fix them?

A deadlock is two transactions each holding a lock the other needs. InnoDB detects it, rolls one back with error 1213, and lets the other finish. So the first rule is that the application catches that error and retries the whole transaction, a few times with a short pause. Laravel's DB::transaction takes an attempts argument for that.

To find the cause I run SHOW ENGINE INNODB STATUS and read the LATEST DETECTED DEADLOCK section. It shows both transactions, the statement each was running, the lock each held, and the lock each was waiting for.

The fixes are usually simple. Touch rows in the same order everywhere, for example always the lower id first. Keep transactions short, with no HTTP call inside. Make sure the WHERE uses an index, because without one InnoDB locks every row it scans, plus the gaps. A rare deadlock with a retry is normal. One that repeats every hour means the access order is wrong.

MySQL bị deadlock. Bạn điều tra và sửa thế nào?

Deadlock là khi hai transaction mỗi bên giữ một khóa mà bên kia đang cần. InnoDB phát hiện ra, rollback một bên với lỗi 1213, và cho bên kia chạy xong. Nên quy tắc đầu tiên là ứng dụng phải bắt lỗi đó và chạy lại cả transaction, vài lần, mỗi lần chờ một chút. DB::transaction của Laravel có tham số số lần thử cho việc này.

Để tìm nguyên nhân, tôi chạy SHOW ENGINE INNODB STATUS và đọc phần LATEST DETECTED DEADLOCK. Nó cho thấy cả hai transaction, câu lệnh mỗi bên đang chạy, khóa mỗi bên đang giữ, và khóa mỗi bên đang chờ.

Cách sửa thường đơn giản. Mọi chỗ đều đụng tới các dòng theo cùng một thứ tự, ví dụ luôn khóa id nhỏ trước. Giữ transaction ngắn, không gọi HTTP bên trong. Đảm bảo WHERE dùng được index, vì nếu không InnoDB sẽ khóa mọi dòng nó quét qua, cả các khoảng trống. Thỉnh thoảng một deadlock có retry là bình thường. Nếu nó lặp lại mỗi giờ thì thứ tự truy cập đang sai.

Know: Error 1213 is a deadlock; error 1205 is a lock wait timeout, a different problem. innodb_print_all_deadlocks = ON logs every deadlock, not just the latest.

Trap: Raising innodb_lock_wait_timeout and calling it fixed.

Follow-up: Why does a missing index cause more deadlocks? The update scans and locks far more rows and gaps than it changes.

28Race condition on the last unitMake the check and the write one step. Then read the affected rows.~68s✓

Two users reserve the last unit at the same time. What happens, and how do you stop it?

If both requests read quantity 1 and both then write 0, the same unit is sold twice. The check and the write must be one atomic step. The simplest way is to put the check inside the UPDATE:

UPDATE stock SET qty = qty - 1
WHERE sku = 'A-451' AND qty >= 1;

Then I read the affected rows. One means I got it, and I insert the reservation in the same transaction. Zero means it is sold out. InnoDB locks the row during the update, so the second request waits, re-checks the condition, and changes nothing.

When the decision needs more than one condition, I use a short transaction with SELECT … FOR UPDATE, decide in PHP, then update. Either way sku must be indexed, or the lock covers every row InnoDB scans. I never hold the lock while calling an email or payment API, and I test with two parallel requests, not one click.

Hai người cùng lúc giữ chiếc cuối cùng. Chuyện gì xảy ra, và bạn chặn thế nào?

Nếu cả hai request đều đọc thấy số lượng 1 rồi cùng ghi 0, một chiếc bị bán hai lần. Bước kiểm tra và bước ghi phải là một thao tác nguyên tử. Cách đơn giản nhất là đưa điều kiện vào ngay câu UPDATE:

UPDATE stock SET qty = qty - 1
WHERE sku = 'A-451' AND qty >= 1;

Rồi tôi xem số dòng bị ảnh hưởng. Bằng một là tôi giữ được, và tôi insert bản ghi đặt chỗ trong cùng transaction. Bằng không là đã hết hàng. InnoDB khóa dòng trong lúc update, nên request thứ hai phải chờ, kiểm tra lại điều kiện, và không đổi gì.

Khi quyết định cần nhiều hơn một điều kiện, tôi dùng một transaction ngắn với SELECT … FOR UPDATE, quyết định trong PHP, rồi mới update. Cách nào thì sku cũng phải có index, nếu không khóa sẽ trùm lên mọi dòng InnoDB quét qua. Tôi không bao giờ giữ khóa trong lúc gọi API gửi mail hay thanh toán, và tôi test bằng hai request song song, không phải một cú click.

Know: Atomic conditional UPDATE plus affected rows, or FOR UPDATE in a short transaction. In Laravel: ->where('qty', '>=', 1)->decrement('qty') returns the affected row count.

Trap: Checking the quantity in PHP, then running an UPDATE with no condition and no lock.

Follow-up: What if two different SKUs are locked in different orders? That is a deadlock. See Deadlocks.

29Pagination: offset versus cursorPage 1 is fine. Page 2,000 is not. Cursor for feeds and APIs.~63s✓

Offset or cursor pagination? Why is LIMIT 50 OFFSET 100000 slow?

Offset pagination is LIMIT 50 OFFSET 100000. It is simple and lets a user jump to page 7, but MySQL still reads the 100,000 rows it skips, so deep pages get slow. And if rows are inserted while someone is paging, they see duplicates or miss rows.

Cursor pagination, also called keyset, remembers the last row shown:

SELECT id, total FROM orders
WHERE id < 18420
ORDER BY id DESC
LIMIT 50;

With an index on the sort key, every page costs the same. The API returns a next_cursor instead of a page number, and Laravel has cursorPaginate for it. The trade-off is no jumping to page 500. My rule: offset for admin tables where people want page numbers and the data is small, cursor for feeds, infinite scroll, and public APIs. A job that visits every row walks by id ranges, which is what chunkById does.

Phân trang bằng offset hay cursor? Vì sao LIMIT 50 OFFSET 100000 lại chậm?

Phân trang offset là LIMIT 50 OFFSET 100000. Nó đơn giản và cho người dùng nhảy tới trang 7, nhưng MySQL vẫn phải đọc 100.000 dòng bị bỏ qua, nên trang càng sâu càng chậm. Và nếu có dòng mới được thêm trong lúc ai đó đang lật trang, họ sẽ thấy dòng trùng hoặc bị sót dòng.

Phân trang cursor, còn gọi là keyset, nhớ dòng cuối cùng đã hiện:

SELECT id, total FROM orders
WHERE id < 18420
ORDER BY id DESC
LIMIT 50;

Có index trên cột sắp xếp thì trang nào cũng tốn như nhau. API trả về next_cursor thay vì số trang, và Laravel có cursorPaginate cho việc này. Đổi lại là không nhảy thẳng tới trang 500 được. Quy tắc của tôi: offset cho bảng quản trị cần số trang và dữ liệu nhỏ, cursor cho feed, cuộn vô hạn và API public. Job phải đi qua mọi dòng thì đi theo khoảng id, chính là cách chunkById làm.

Know: Sort by a unique key, or add id as a tie-breaker: ORDER BY created_at DESC, id DESC with a matching index.

Trap: Paginating in PHP after SELECT *.

Follow-up: How does the client know there is a next page? The API returns next_cursor, or null on the last page.

30Second-highest salarySay what “second” means when two people share the top. Handle NULL.~53s✓

Write a query for the second-highest salary.

First I ask what “second” means. If two people share the top salary, OFFSET 1 without DISTINCT returns the top number again. So I take the next distinct salary, and I leave out NULLs:

SELECT DISTINCT salary FROM employees
WHERE salary IS NOT NULL
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

If they want everyone on the second tier, I use a rank:

SELECT * FROM (
  SELECT name, salary,
    DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees WHERE salary IS NOT NULL
) ranked WHERE rnk = 2;

Both run on MySQL 8 and PostgreSQL. The NULL filter matters on PostgreSQL in particular, because it sorts NULL first in descending order, so OFFSET 1 would return the wrong row.

Viết query lấy mức lương cao thứ hai.

Trước hết tôi hỏi “thứ hai” nghĩa là gì. Nếu hai người cùng mức cao nhất, OFFSET 1 không có DISTINCT sẽ trả lại đúng mức cao nhất. Nên tôi lấy mức lương khác tiếp theo, và loại bỏ NULL:

SELECT DISTINCT salary FROM employees
WHERE salary IS NOT NULL
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

Nếu họ muốn mọi người ở bậc thứ hai, tôi dùng rank:

SELECT * FROM (
  SELECT name, salary,
    DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees WHERE salary IS NOT NULL
) ranked WHERE rnk = 2;

Cả hai chạy được trên MySQL 8 và PostgreSQL. Lọc NULL đặc biệt quan trọng trên PostgreSQL, vì nó xếp NULL lên đầu khi sắp giảm dần, nên OFFSET 1 sẽ trả sai dòng.

Know: DISTINCT plus OFFSET, or DENSE_RANK. MySQL puts NULL last in DESC; PostgreSQL puts it first unless you write NULLS LAST.

Trap: ORDER BY salary DESC LIMIT 1 OFFSET 1 with no DISTINCT.

Follow-up: Second-highest per department? DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC).

31Write an UPDATESELECT the WHERE first. Then the transaction.~49s✓

Write an update query. What do you check first?

I write the WHERE as a SELECT and read the row count before I change anything. Then the same filter goes into the UPDATE, inside a transaction.

BEGIN;
SELECT id, salary FROM employees
WHERE department_id = 4 AND salary < 2000;

UPDATE employees
SET salary = salary * 1.1
WHERE department_id = 4 AND salary < 2000;
COMMIT;

No WHERE means every row, and I do not run that. PostgreSQL can add RETURNING id, salary, so I see what changed. On MySQL I check the affected row count and run the SELECT again. On payroll data at BaseVN, a wrong update was worse than a slow one, so the preview is the point.

Viết một câu UPDATE. Bạn kiểm tra gì trước?

Tôi viết điều kiện WHERE thành một câu SELECT và xem số dòng trước khi sửa bất cứ thứ gì. Rồi đúng điều kiện đó đưa vào UPDATE, trong một transaction.

BEGIN;
SELECT id, salary FROM employees
WHERE department_id = 4 AND salary < 2000;

UPDATE employees
SET salary = salary * 1.1
WHERE department_id = 4 AND salary < 2000;
COMMIT;

Không có WHERE là sửa cả bảng, và tôi không chạy câu đó. PostgreSQL thêm được RETURNING id, salary để thấy dòng nào vừa đổi. Trên MySQL tôi xem số dòng bị ảnh hưởng và chạy lại câu SELECT. Với dữ liệu lương ở BaseVN, update sai còn tệ hơn update chậm, nên bước xem trước mới là điểm chính.

Know: Preview, WHERE, transaction, affected rows. MySQL Workbench's safe update mode refuses an UPDATE without a key in the WHERE.

Trap: UPDATE with no WHERE, then COMMIT.

Follow-up: Update from another table? UPDATE a JOIN b ON … SET a.x = b.y in MySQL.

32Delete duplicate rowsKeep one id per email. Then add a unique key.~46s✓

Delete duplicate rows and keep one row per email.

First I decide which row survives, usually the smallest id. A window function makes that explicit in both PostgreSQL and MySQL 8:

DELETE FROM employees
WHERE id IN (
  SELECT id FROM (
    SELECT id,
      ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM employees
  ) ranked
  WHERE rn > 1
);

I run the inner SELECT first and read how many rows would go. After the delete I add UNIQUE (email), or the duplicates come back with the next import. I do it in a transaction, and I do not delete from a table I have not backed up when the data is payroll.

Xóa các dòng trùng và giữ lại một dòng cho mỗi email.

Trước hết tôi quyết định dòng nào được giữ, thường là dòng có id nhỏ nhất. Window function nói rõ điều đó trên cả PostgreSQL và MySQL 8:

DELETE FROM employees
WHERE id IN (
  SELECT id FROM (
    SELECT id,
      ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM employees
  ) ranked
  WHERE rn > 1
);

Tôi chạy câu SELECT bên trong trước và xem bao nhiêu dòng sẽ bị xóa. Xóa xong tôi thêm UNIQUE (email), không thì lần import sau dữ liệu trùng lại quay về. Tôi làm trong transaction, và không xóa trên bảng lương khi chưa backup.

Know: ROW_NUMBER, keep one, then a unique constraint. The extra derived table avoids MySQL error 1093 (cannot select from the table you are deleting from).

Trap: Deleting the duplicates and leaving the door open for new ones.

33Designing an API for a web or mobile clientContract first, thin controllers, stable JSON, paginated lists.~61s✓

How do you design a backend API for a React or mobile client?

I start from what the client screen needs, then write the contract before the code: resource URLs like /api/orders and /api/orders/{id}, methods, request and response shapes, validation rules, auth, and the error format. In Laravel responses go through an API Resource class, so the JSON shape does not change when someone renames a column.

On the client I handle loading, empty, and error states, so a failed call never leaves someone on a spinner.

My recent APIs are Express in TypeScript for React and Expo clients, and the rules are the same in Laravel.

Bạn thiết kế API backend cho client React hoặc mobile thế nào?

34REST status codes and the error shapeA small set of codes used the same way everywhere, and one error format.~67s✓

Which HTTP status codes do you use, and how do you return errors?

A small set, used consistently. 200 for a normal read or update, 201 Created after a POST, 204 No Content after a delete. 400 for a malformed request. 401 when you are not authenticated, 403 when you are but are not allowed. 404 when the record does not exist, or you should not know it exists. 409 for a conflict, like a duplicate or a stale version. 422 for validation errors, which is Laravel's default. 429 for rate limiting, with Retry-After. 500 means my bug; 502 or 503 means something upstream failed or is overloaded.

Every error has the same JSON shape: a code, a message that is safe to show, and field errors when there are any. The client maps that to a message, and the details go to the log with a request id, never a stack trace to the user. Clients retry only on 429, 503, and timeouts, and only for idempotent calls.

Bạn dùng những status code HTTP nào, và trả lỗi thế nào?

Một nhóm nhỏ, dùng nhất quán. 200 cho đọc hoặc cập nhật bình thường, 201 Created sau POST, 204 No Content sau khi xóa. 400 cho request sai định dạng. 401 khi chưa xác thực, 403 khi đã xác thực nhưng không có quyền. 404 khi bản ghi không tồn tại, hoặc người gọi không nên biết nó tồn tại. 409 cho xung đột, như trùng dữ liệu hoặc phiên bản đã cũ. 422 cho lỗi validate, là mặc định của Laravel. 429 cho rate limit, kèm Retry-After. 500 là bug của tôi, 502 hoặc 503 là phía sau bị lỗi hoặc quá tải.

Mọi lỗi có cùng một cấu trúc JSON: mã lỗi, thông báo an toàn để hiển thị, và lỗi theo từng trường nếu có. Client chuyển nó thành thông báo cho người dùng, còn chi tiết nằm trong log kèm request id, không bao giờ đưa stack trace cho người dùng. Client chỉ retry với 429, 503 và timeout, và chỉ với các lời gọi idempotent.

Know: 401 versus 403 is the classic. 404 instead of 403 hides that another tenant's record exists. Idempotency: see The Pay button clicked twice.

Trap: 200 with {"error": …} in the body, or a stack trace in the JSON.

Follow-up: PUT versus PATCH? PUT replaces the resource and is idempotent; PATCH changes some fields.

35REST or GraphQLSay what you shipped. GraphQL has a cost.~50s✓

REST or GraphQL: which do you choose?

I have shipped REST. The client and server share a JSON contract, status codes mean something, errors have a stable shape, and HTTP caching works out of the box. GraphQL is one endpoint where the client asks for exactly the fields it needs. That helps when many clients need very different shapes of the same data.

It also has costs: N+1 problems inside resolvers, harder caching, and the need to limit query depth and cost so one query cannot ask for the whole database. I would use it if the team already runs it well. I would not introduce it for a small API with one or two clients. My default is a clear REST contract.

REST hay GraphQL, bạn chọn cái nào?

Tôi đã ship REST. Client và server dùng chung hợp đồng JSON, status code có ý nghĩa, lỗi có cấu trúc ổn định, và cache HTTP dùng được ngay. GraphQL là một endpoint duy nhất, client xin đúng những trường nó cần. Nó hữu ích khi nhiều client cần những dạng dữ liệu rất khác nhau từ cùng một nguồn.

Nó cũng có giá: N+1 bên trong resolver, cache khó hơn, và phải giới hạn độ sâu và chi phí query để một câu không xin cả database. Tôi sẽ dùng nếu team đã vận hành tốt. Tôi không đưa nó vào một API nhỏ chỉ có một hai client. Mặc định của tôi là hợp đồng REST rõ ràng.

Know: GraphQL: schema, resolvers, DataLoader for batching, persisted queries. REST: resources, HTTP semantics, caching.

Trap: Claiming GraphQL experience you do not have.

Follow-up: How would you avoid N+1 in GraphQL? A DataLoader that batches lookups per request.

36SQL injection, XSS, and CSRFThree attacks, three defenses. Know where Laravel stops protecting you.~69s✓

How do you defend a PHP app against SQL injection, XSS, and CSRF?

Three different attacks, three defenses. SQL injection is when user input changes the SQL. The fix is prepared statements: PDO with bound parameters in plain PHP, or Eloquent and the query builder in Laravel, which bind for you. The danger spots are DB::raw, whereRaw, and a column name or sort direction taken from the request, which I check against an allow-list.

XSS is when user input runs as a script in someone else's browser. I escape on output: htmlspecialchars in plain PHP, double curly braces in Blade, and I am careful with Blade's unescaped syntax. A Content Security Policy is a second layer.

CSRF is when another site makes the user's browser send a request with their cookie. Laravel's web middleware checks a CSRF token on every POST, PUT, and DELETE, and SameSite cookies help too. An API that uses a bearer token in a header is not exposed the same way. And passwords use password_hash, never md5.

Bạn bảo vệ app PHP khỏi SQL injection, XSS và CSRF thế nào?

Ba kiểu tấn công khác nhau, ba cách phòng khác nhau. SQL injection là khi input của người dùng làm thay đổi câu SQL. Cách chặn là prepared statement: PDO với tham số bind trong PHP thuần, hoặc Eloquent và query builder trong Laravel, vốn tự bind. Chỗ nguy hiểm là DB::raw, whereRaw, và tên cột hay chiều sắp xếp lấy từ request, những thứ đó tôi kiểm tra theo một danh sách cho phép.

XSS là khi input của người dùng chạy thành script trong trình duyệt của người khác. Tôi escape khi xuất ra: htmlspecialchars trong PHP thuần, cặp ngoặc nhọn đôi trong Blade, và cẩn thận với cú pháp không escape của Blade. Content Security Policy là lớp bảo vệ thứ hai.

CSRF là khi một trang khác khiến trình duyệt của người dùng gửi request kèm cookie của họ. Middleware web của Laravel kiểm tra CSRF token trên mọi POST, PUT và DELETE, và cookie SameSite cũng giúp thêm. API dùng bearer token trong header thì không bị theo cách đó. Còn mật khẩu thì dùng password_hash, không bao giờ dùng md5.

Know: Bind values; allow-list identifiers. Escape on output, not on input. CSRF token plus SameSite. password_hash uses bcrypt or Argon2.

Trap: "… WHERE id = " . $_GET['id'], or {!! $comment !!} on user content.

Follow-up: Can you bind a column name? No. Placeholders are for values only, so identifiers need an allow-list.

37Authorization: Policies and GatesAuthentication is who. Authorization is what, on this record.~67s✓

How do you handle authorization in Laravel? What are Policies and Gates?

Authentication says who you are. Authorization says what you may do with this record, and that is where real leaks happen. In Laravel a Gate is a closure for a general ability, like viewing reports. A Policy is a class for one model, with methods like view, update, and delete that receive the user and the record.

In the controller I call $this->authorize('update', $order), or use the can middleware, and a failure becomes 403. What matters is that the check uses the actual record: this order belongs to this user's company. Hiding a button does nothing if the API still answers. I also scope list queries by tenant, so the index endpoint cannot return another company's rows, and I test the deny case, not just the allow.

On Aquanix, which is Express, pond routes reject a member who is not assigned to that pond. In Laravel that rule would be a PondPolicy.

Bạn xử lý phân quyền trong Laravel thế nào? Policy và Gate là gì?

Xác thực cho biết bạn là ai. Phân quyền cho biết bạn được làm gì với bản ghi này, và đó là chỗ dữ liệu thật sự bị lộ. Trong Laravel, Gate là một closure cho một quyền chung, như xem báo cáo. Policy là một class cho một model, có các method như view, update, delete, nhận vào user và bản ghi.

Trong controller tôi gọi $this->authorize('update', $order), hoặc dùng middleware can, và nếu không đạt thì trả 403. Điều quan trọng là phải kiểm tra trên bản ghi thật: đơn hàng này thuộc công ty của user này. Ẩn một nút bấm không có tác dụng gì nếu API vẫn trả lời. Tôi cũng giới hạn query danh sách theo tenant, để endpoint danh sách không trả dòng của công ty khác, và tôi test cả trường hợp bị từ chối, không chỉ trường hợp được phép.

Trên Aquanix, viết bằng Express, các route của ao từ chối thành viên không được gán vào ao đó. Trong Laravel, quy tắc đó sẽ là một PondPolicy.

Know: Gate::define, Gate::before for a super admin, policy auto-discovery, @can in Blade. A global scope can enforce the tenant filter.

Trap: Checking only the role, not ownership. That is an IDOR: change the id in the URL and read someone else's record.

Follow-up: Gate or Policy? Policy when the rule is about one model; Gate for an ability not tied to a model.

38Sanctum versus PassportSanctum for your own clients. Passport only if you need an OAuth 2 server.~62s✓

Sanctum or Passport for API authentication in Laravel?

Sanctum is the simple choice, and the default I would pick. It does two things. For a first-party SPA on the same top-level domain, it uses the normal cookie session with CSRF protection. For a mobile app or a script, it issues personal access tokens, which are stored hashed, can carry abilities, and can be revoked one by one.

Passport is a full OAuth 2 server. You need it when third parties build apps against your API and users grant them access, with authorization codes, refresh tokens, and client credentials. For one company's own web and mobile clients, Passport is more moving parts than you need.

My own token work is JWT on Express: on Aquanix the phone login issues a JWT carrying the role and partnership. A Sanctum token is different, an opaque string checked against the database, so revoking it takes effect immediately.

Dùng Sanctum hay Passport để xác thực API trong Laravel?

Sanctum là lựa chọn đơn giản, và là mặc định tôi sẽ chọn. Nó làm hai việc. Với SPA do chính công ty làm, chạy cùng tên miền gốc, nó dùng session cookie bình thường kèm bảo vệ CSRF. Với app mobile hoặc script, nó cấp personal access token, được lưu dạng hash, có thể gắn quyền, và thu hồi được từng cái một.

Passport là một OAuth 2 server đầy đủ. Bạn cần nó khi bên thứ ba xây app trên API của bạn và người dùng cấp quyền cho họ, với authorization code, refresh token và client credentials. Với web và mobile của chính một công ty, Passport có quá nhiều thành phần không cần thiết.

Kinh nghiệm token của tôi là JWT trên Express: ở Aquanix, đăng nhập bằng số điện thoại cấp một JWT mang role và partnership. Token của Sanctum thì khác, là một chuỗi ngẫu nhiên được kiểm tra với database, nên thu hồi là có hiệu lực ngay.

Know: Sanctum SPA mode needs stateful domains configured and a call to /sanctum/csrf-cookie first. Passport is built on league/oauth2-server.

Trap: Picking Passport for a single first-party app, or storing SPA tokens in localStorage when cookie mode is available.

Follow-up: JWT versus an opaque token? JWT needs no lookup but is hard to revoke before it expires; an opaque token needs a lookup but revokes instantly.

39Sessions and cookiesData on the server, a random id in the cookie. HttpOnly, Secure, SameSite, regenerate on login.~60s✓

How do sessions work in PHP, and how do you keep them safe?

session_start() gives the browser a cookie with a random session id. The data itself stays on the server in $_SESSION, stored in files, Redis, or the database. The cookie should be HttpOnly, so JavaScript cannot read it, Secure, so it only travels over HTTPS, and SameSite Lax or Strict, which blocks most cross-site requests.

After a successful login I call session_regenerate_id(true), so an id an attacker planted before login becomes useless. That attack is session fixation. On logout I destroy the session, not just clear one field. With more than one server, sessions must live in Redis or the database, not on one machine's disk.

Laravel does all of this through its session config, and it regenerates the session on login. A cookie can hold harmless preferences, but never a password or a role the server trusts.

Session trong PHP hoạt động thế nào, và bạn giữ nó an toàn ra sao?

session_start() gửi cho trình duyệt một cookie chứa session id ngẫu nhiên. Còn dữ liệu nằm trên server trong $_SESSION, lưu ở file, Redis hoặc database. Cookie nên có HttpOnly để JavaScript không đọc được, Secure để chỉ đi qua HTTPS, và SameSite Lax hoặc Strict để chặn phần lớn request từ trang khác.

Sau khi đăng nhập thành công, tôi gọi session_regenerate_id(true), để một id mà kẻ tấn công cài sẵn trước lúc đăng nhập trở nên vô dụng. Kiểu tấn công đó gọi là session fixation. Khi đăng xuất, tôi hủy cả session, không chỉ xóa một trường. Khi có nhiều hơn một server, session phải nằm ở Redis hoặc database, không nằm trên ổ đĩa của một máy.

Laravel làm hết những việc này qua cấu hình session, và tự regenerate khi đăng nhập. Cookie có thể giữ những tùy chọn vô hại, nhưng không bao giờ chứa mật khẩu hay một role mà server tin theo.

Know: Session versus cookie: the session is server-side data; the cookie only carries the id. session.cookie_httponly, session.cookie_secure, session.cookie_samesite.

Trap: Storing a password, or is_admin=1, in a cookie.

Follow-up: What is session fixation? An attacker sets a known session id before login; regenerating the id on login defeats it.

40Magic link loginOne-time, hashed, short-lived. Same response whether the email exists or not.~63s✓

How would you implement a magic-link login?

The user types an email, and there is no password on this flow. I create a random token, store only a hash of it, and set a short expiry, minutes, not days. The email carries a link with the raw token once. When they click, I hash what arrived, find a row that is unused and not expired, start a session, and invalidate the token so it cannot be replayed.

HTTPS only. I rate-limit the “send link” endpoint, so nobody can mail a stranger a thousand times. The response is the same whether the email exists or not, so the form does not reveal who has an account. I log each send and each use with the IP, so a compromised mailbox leaves a trail.

In Laravel, Mail plus a temporary signed URL can carry this. The important part is one-time, hashed, and short-lived, not the helper's name.

Bạn làm đăng nhập bằng magic link thế nào?

Người dùng nhập email, và luồng này không có mật khẩu. Tôi tạo một token ngẫu nhiên, chỉ lưu bản hash của nó, và đặt hạn ngắn, vài phút, không phải vài ngày. Chỉ dùng HTTPS. Tôi rate-limit endpoint “gửi link”, để không ai gửi một nghìn email cho người lạ được. Response giống nhau dù email có tồn tại hay không, để form không làm lộ ai có tài khoản. Tôi ghi log mỗi lần gửi và mỗi lần dùng, kèm IP, để nếu hộp thư bị chiếm thì vẫn còn dấu vết.

Trap: Storing the raw token, or a link that lasts a week.
