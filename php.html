03MySQL and performancePIT 500k story hook.

How do you handle MySQL performance in PHP apps?

I look at the query plan and indexes first, not micro-optimizing PHP loops. On Base PIT we dealt with 500,000+ records, so schema design and query shape mattered for reports and sync. I also avoid N+1 patterns and heavy work inside request cycles when a job/queue is better.

Bạn xử lý hiệu năng MySQL trong app PHP thế nào?

Tôi xem query plan và index trước, không tối ưu vòng lặp PHP trước. Ở Base PIT có 500,000+ bản ghi, nên schema và dạng query quan trọng cho report/sync. Tôi cũng tránh N+1 và việc nặng trong request cycle khi job/queue hợp hơn.

Know: Index + query shape + avoid N+1.

Trap: Caching everything before measuring.

04Auth and security basicsEnterprise awareness.

How do you think about auth and security in PHP apps?

Validate input, least privilege for DB users, don't trust the client, protect secrets, and use proper session/token checks on APIs. For sensitive flows like tax or HR data, authorization matters as much as authentication — can this user see this record?

Bạn nghĩ về auth và bảo mật trong app PHP thế nào?

Validate input, least privilege cho DB user, không tin client, bảo vệ secret, và check session/token đúng trên API. Với luồng nhạy cảm như thuế/HR, authorization quan trọng không kém authentication — user này có được xem bản ghi này không?

Know: Authn vs authz; never trust FE-only checks.

Trap: Hiding a button is not security.

06What is PHP thuần / pure PHP?Interviewer asked to review this carefully.

What do you mean by pure PHP, without a framework?

Pure PHP means writing the app with PHP language features and standard extensions — no Laravel/Symfony doing routing, ORM, and auth for you. You still use Composer sometimes, but you own routing, request/response, DB access with PDO, sessions, and structure yourself. Frameworks speed you up; pure PHP shows you understand what happens under the hood. At BaseVN I worked on a custom PHP platform — so I'm used to PHP beyond only Laravel helpers.

PHP thuần nghĩa là gì, không dùng framework?

PHP thuần là viết app bằng ngôn ngữ PHP và extension chuẩn — không có Laravel/Symfony lo routing, ORM, auth giúp bạn. Đôi khi vẫn dùng Composer, nhưng bạn tự own routing, request/response, DB bằng PDO, session và cấu trúc. Framework giúp nhanh; PHP thuần chứng tỏ bạn hiểu thứ xảy ra bên dưới. Ở BaseVN tôi làm trên nền tảng PHP custom — nên tôi quen PHP, không chỉ helper của Laravel.

Know: Own routing/DB/session yourself; frameworks hide that.

Trap: Saying pure PHP means no Composer and no OOP.

07PDO and SQL safelyCore pure PHP skill.

How do you talk to MySQL in pure PHP?

I use PDO with prepared statements — never concatenate user input into SQL. That prevents SQL injection. You prepare, bind values, execute, fetch. Same idea whether you're in Laravel's query builder or pure PHP — the safe pattern is parameterized queries.

Trong PHP thuần bạn nói chuyện với MySQL thế nào?

Tôi dùng PDO với prepared statement — không nối chuỗi input user vào SQL. Như vậy tránh SQL injection. Prepare, bind value, execute, fetch. Cùng ý tưởng dù Laravel query builder hay PHP thuần — pattern an toàn là parameterized query.

Know: PDO + prepared statements = baseline.

Trap: mysqli_query with string concat from $_GET.

Follow-up: Show a safe SELECT with a user id parameter.

08Sessions and cookiesAuth without a framework.

How do sessions work in PHP?

session_start() starts a session; PHP stores session data on the server and gives the browser a session cookie. You keep login state in $_SESSION, not only in localStorage. Cookies can also hold preferences, but sensitive auth should stay server-side. Frameworks wrap this; in pure PHP you call it yourself and protect against session fixation/hijacking basics.

Session trong PHP hoạt động thế nào?

session_start() bắt đầu session; PHP lưu data session trên server và gửi cookie session cho browser. Trạng thái login để trong $_SESSION, không chỉ localStorage. Cookie có thể giữ preference, nhưng auth nhạy cảm nên ở server. Framework bọc sẵn; PHP thuần bạn tự gọi và chú ý session fixation/hijacking cơ bản.

Know: Server-side session + session cookie.

Trap: Storing passwords in cookies.

Follow-up: What's the difference between session and cookie?

09Composer, autoload, namespacesModern pure PHP still uses these.

Do you use Composer in pure PHP projects?

Yes — pure PHP doesn't mean old-style everything in one file. Composer manages dependencies and PSR-4 autoloading so classes load by namespace. You still write plain PHP classes; Composer just removes require_once hell. That's standard even without Laravel.

Trong dự án PHP thuần có dùng Composer không?

Có — PHP thuần không có nghĩa kiểu cũ nhét hết một file. Composer quản lý dependency và PSR-4 autoload để class load theo namespace. Bạn vẫn viết class PHP thường; Composer bỏ cảnh require_once loạn. Đó là chuẩn kể cả không dùng Laravel.

Know: Composer + PSR-4 autoload is modern PHP.

Trap: Pure PHP = no namespaces / no Composer.

10OOP in PHP: class, interface, traitThey may quiz basics.

Explain class, interface, and trait in PHP.

A class is a blueprint with properties and methods. An interface defines a contract — methods a class must implement, without the code. A trait is reusable method chunks you paste into classes — useful when you want shared behavior without deep inheritance. In real apps I use classes and interfaces a lot; traits when several classes need the same helper behavior.

Giải thích class, interface và trait trong PHP.

Class là bản thiết kế với property và method. Interface là hợp đồng — method class phải implement, không chứa code. Trait là khối method tái sử dụng gắn vào class — hữu ích khi muốn share behavior mà không kế thừa sâu. Trong app thật tôi dùng class và interface nhiều; trait khi nhiều class cần helper giống nhau.

Know: Class = implementation; interface = contract; trait = reusable methods.

Trap: Confusing interface with abstract class details you can't explain.

11Request lifecycle in pure PHPHow a page runs without Laravel.

What happens when a request hits a pure PHP app?

The web server points to an entry file, often index.php. That script reads the URL/method, routes to a controller or include, talks to the database, then echoes HTML or JSON. There's no magic router unless you write one or use a small router package. Understanding this helps when debugging Laravel too — the framework still ends at request in, response out.

Khi một request vào app PHP thuần thì chuyện gì xảy ra?

Web server trỏ vào file entry, thường index.php. Script đọc URL/method, route tới controller hoặc include, nói chuyện database, rồi echo HTML hoặc JSON. Không có router thần kỳ trừ khi bạn tự viết hoặc dùng package router nhỏ. Hiểu điều này cũng giúp debug Laravel — framework vẫn là request vào, response ra.

Know: Entry script → route → logic/DB → response.

Trap: Thinking Laravel has no request lifecycle.

12Superglobals: GET POST SERVERDaily pure PHP.

What are PHP superglobals you use often?

$_GET and $_POST for input, $_SERVER for method/URL/headers, $_SESSION for server session data, $_COOKIE for cookies, and sometimes $_FILES for uploads. I never trust them raw — validate and sanitize before use. In APIs I also read JSON from php://input.

Các superglobal PHP bạn hay dùng?

$_GET và $_POST cho input, $_SERVER cho method/URL/header, $_SESSION cho data session server, $_COOKIE cho cookie, đôi khi $_FILES cho upload. Không tin raw — phải validate/sanitize trước khi dùng. Với API tôi cũng đọc JSON từ php://input.

Know: Input via superglobals; always validate.

Trap: Echoing $_GET straight into HTML/SQL.

What security basics do you apply in pure PHP?

Prepared statements for SQL, htmlspecialchars or escaping for HTML output against XSS, CSRF tokens on state-changing forms, password_hash/password_verify for passwords, and never commit secrets. Frameworks give helpers; in pure PHP you must remember to apply them yourself.

Bảo mật cơ bản trong PHP thuần bạn áp dụng gì?

Prepared statement cho SQL, htmlspecialchars hoặc escape HTML chống XSS, CSRF token cho form đổi dữ liệu, password_hash/password_verify cho mật khẩu, và không commit secret. Framework có helper; PHP thuần bạn phải tự nhớ áp dụng.

19When do you add an index?Say the query, then the columns. Not every column.

When do you add an index, and when do you refuse?

I add an index for a query that is slow and that people actually run. The columns match the WHERE and the JOIN, in that order, then the ORDER BY if it still fits. Writes pay for every index, so I do not index a column because it “might be useful later”.

Example: the sales list of partner cases, always filtered by partner and status, newest first:

SELECT id, status, created_at
FROM cases
WHERE partner_id = 42 AND status = 'open'
ORDER BY created_at DESC
LIMIT 50;

That wants (partner_id, status, created_at). A separate index on status alone does not help this query much. At Base the tax and payroll tables were large enough that a missing index was a real delay, not a textbook note.

Khi nào bạn thêm index, và khi nào thì không?

Tôi thêm index cho query chậm mà người ta thật sự chạy. Cột khớp WHERE và JOIN, theo thứ tự đó, rồi ORDER BY nếu còn vừa. Mỗi index làm chậm ghi, nên tôi không index một cột vì “sau này có thể cần”.

Ví dụ: danh sách case của sales, lúc nào cũng lọc theo đối tác và trạng thái, mới nhất trước:

SELECT id, status, created_at
FROM cases
WHERE partner_id = 42 AND status = 'open'
ORDER BY created_at DESC
LIMIT 50;

Cần (partner_id, status, created_at). Một index chỉ trên status hầu như không giúp query này. Ở Base, bảng thuế và lương đủ lớn để thiếu index là chậm thật, không phải ghi chú trong sách.

Know: Index the query you have, not every column.

Trap: Adding five indexes before EXPLAIN.

20Composite index, leftmost prefixWalk a warehouse lookup. They will ask why the second column is unused.

You have INDEX (warehouse_id, sku). Which queries use it?

A composite index is read from the left. (warehouse_id, sku) is useful when warehouse_id is in the WHERE. It is not useful when you only filter by SKU.

-- uses the index
WHERE warehouse_id = 3 AND sku = 'TS-451'
WHERE warehouse_id = 3

-- does not use this index
WHERE sku = 'TS-451'

-- also does not use a normal B-tree
WHERE sku LIKE '%451%'

If partners search by SKU across every warehouse, they need an index that starts with sku, or a separate one. I would look at EXPLAIN before I add the second index. A leading % in LIKE will not use a B-tree either. That search belongs in a search engine, or at least a full-text index, not a hope.

Có INDEX (warehouse_id, sku). Query nào dùng được?

Index kép đọc từ trái sang. (warehouse_id, sku) hữu ích khi WHERE có warehouse_id. Chỉ lọc SKU thì không dùng được.

-- dùng index
WHERE warehouse_id = 3 AND sku = 'TS-451'
WHERE warehouse_id = 3

-- không dùng index này
WHERE sku = 'TS-451'

-- B-tree thường cũng không dùng
WHERE sku LIKE '%451%'

Nếu đối tác tìm SKU trên mọi kho, cần index bắt đầu bằng sku, hoặc một index riêng. Tôi xem EXPLAIN trước khi thêm index thứ hai. LIKE với % đứng đầu không dùng B-tree. Kiểu tìm đó thuộc search engine, hoặc full-text, không phải hy vọng.

Know: Leftmost prefix. LIKE '%x' is not an index lookup.

Trap: Claiming one composite index covers every filter.

21INNER JOIN versus LEFT JOINUse a case list. Say which rows disappear.

When do you INNER JOIN, and when do you LEFT JOIN?

INNER JOIN keeps rows that match on both sides. LEFT JOIN keeps every row on the left, and fills the right with NULL when there is no match.

A sales list of open cases with the partner name is an inner join. A case without a partner should not show up:

SELECT cases.id, partners.name, cases.status
FROM cases
INNER JOIN partners ON partners.id = cases.partner_id
WHERE cases.status = 'open'
ORDER BY cases.created_at DESC
LIMIT 50;

A report of every partner, including partners who have never opened a case, is a left join from partners to cases. If I INNER JOIN there, silent partners vanish and the report lies. I put the filter in SQL. I do not load every case into PHP and join in a loop. That is how N+1 starts.

Khi nào INNER JOIN, khi nào LEFT JOIN?

INNER JOIN giữ dòng khớp cả hai bên. LEFT JOIN giữ mọi dòng bên trái, bên phải thành NULL khi không khớp.

Danh sách case đang mở kèm tên đối tác là inner join. Case không có đối tác thì không hiện:

SELECT cases.id, partners.name, cases.status
FROM cases
INNER JOIN partners ON partners.id = cases.partner_id
WHERE cases.status = 'open'
ORDER BY cases.created_at DESC
LIMIT 50;

Báo cáo mọi đối tác, kể cả người chưa mở case, là left join từ partners sang cases. Nếu INNER JOIN ở đó, đối tác im lặng biến mất và báo cáo nói dối. Filter để trong SQL. Tôi không kéo hết case vào PHP rồi join trong vòng lặp. Đó là chỗ N+1 bắt đầu.

Know: INNER drops unmatched rows. LEFT keeps the left side.

Trap: Joining in PHP after SELECT *.

22How you read EXPLAINtype ALL versus ref. Then Extra.

A query is slow. What do you look for in EXPLAIN?

I run EXPLAIN on the real query, with realistic values, not WHERE id = 1. I look at three things. type: ALL is a table scan. At hundreds of thousands of rows that is the bug. ref or range means it is using an index. rows: how many rows MySQL thinks it will read. If it says 400,000 for a page of 50, the index is wrong. Extra: Using filesort or Using temporary often means ORDER BY or GROUP BY has no matching index.

Then I change one thing — the index or the query — and I EXPLAIN again. I do not add a cache on top of a scan. On Base PIT this is how a report stopped reading the whole tax table for one company.

Query chậm. Bạn nhìn gì trong EXPLAIN?

Tôi chạy EXPLAIN trên query thật, với giá trị giống production, không phải WHERE id = 1. Tôi nhìn ba thứ. type: ALL là quét bảng. Hàng trăm nghìn dòng thì đó là bug. ref hoặc range nghĩa là đang dùng index. rows: MySQL nghĩ sẽ đọc bao nhiêu dòng. Nếu nó nói 400.000 cho một trang 50, index sai. Extra: Using filesort hoặc Using temporary thường là ORDER BY hoặc GROUP BY không có index khớp.

Rồi tôi đổi một thứ — index hoặc query — và EXPLAIN lại. Tôi không phủ cache lên một lần quét. Ở Base PIT, cách này khiến report thôi đọc cả bảng thuế cho một công ty.

Know: type, rows, Extra. Change one thing, EXPLAIN again.

Trap: EXPLAIN on a tiny local dump, then claiming production is fine.

23Race condition on the last unitTwo requests. One stock row. Speak the SQL.

Two sales users reserve the last unit at the same time. What happens?

If each request reads quantity 1, then both write 0, you sold the same unit twice. The check and the write have to be one transaction, with a lock on that row:

START TRANSACTION;
SELECT qty FROM stock WHERE sku = 'TS-451' FOR UPDATE;
-- if qty >= 1
UPDATE stock SET qty = qty - 1 WHERE sku = 'TS-451';
INSERT INTO reservations (sku, case_id) VALUES ('TS-451', 88);
COMMIT;

Without FOR UPDATE, both SELECTs see 1. I keep the transaction short. I do not call an email API while the lock is held. The same shape fits partner approval: lock the application, refuse a second approve. I would test with two parallel requests, not one happy click. I have not run a warehouse at QNAP’s scale. I have seen the same class of bug on workflow status and on payroll rows that must not be written twice.

Hai sales giữ chiếc cuối cùng cùng lúc. Chuyện gì xảy ra?

Nếu mỗi request đọc quantity 1, rồi cả hai ghi 0, bạn bán cùng một chiếc hai lần. Bước kiểm tra và bước ghi phải nằm trong một transaction, và lock đúng dòng đó:

START TRANSACTION;
SELECT qty FROM stock WHERE sku = 'TS-451' FOR UPDATE;
-- nếu qty >= 1
UPDATE stock SET qty = qty - 1 WHERE sku = 'TS-451';
INSERT INTO reservations (sku, case_id) VALUES ('TS-451', 88);
COMMIT;

Không có FOR UPDATE, cả hai SELECT đều thấy 1. Transaction để ngắn. Tôi không gọi API gửi mail khi đang giữ lock. Cùng hình dạng cho duyệt hồ sơ: lock đơn, từ chối lần duyệt thứ hai. Tôi sẽ test bằng hai request song song, không phải một cú click đúng đường. Tôi chưa chạy kho ở quy mô QNAP. Tôi đã gặp cùng loại bug trên trạng thái workflow và trên dòng lương không được ghi hai lần.

Know: FOR UPDATE inside a short transaction.

Trap: Check in PHP, then UPDATE with no lock.

24OFFSET pagination versus keysetPage 1 is fine. Page 2000 is not.

Why is LIMIT 50 OFFSET 100000 slow?

MySQL still walks those 100,000 rows, then throws them away, then returns 50. Page one of a sales list is fine with OFFSET. A deep page, or an export that “pages” through the whole table, is not.

-- cheap for page 1
LIMIT 50 OFFSET 0

-- expensive at scale
LIMIT 50 OFFSET 100000

-- keyset: remember the last id you showed
WHERE id > 18420
ORDER BY id
LIMIT 50;

For a UI I keep OFFSET for the first few pages and I disable “jump to page 500”. For a job that must visit every row, I walk by id ranges, the same way I chunked payroll and tax work at Base. I do not load 500,000 rows into PHP to paginate there.

Vì sao LIMIT 50 OFFSET 100000 chậm?

MySQL vẫn đi qua 100.000 dòng đó, rồi bỏ, rồi trả 50. Trang một của danh sách sales thì OFFSET ổn. Trang sâu, hoặc export “lật trang” cả bảng, thì không.

-- rẻ ở trang 1
LIMIT 50 OFFSET 0

-- đắt khi lớn
LIMIT 50 OFFSET 100000

-- keyset: nhớ id cuối cùng đã hiện
WHERE id > 18420
ORDER BY id
LIMIT 50;

Với UI tôi giữ OFFSET vài trang đầu và không cho “nhảy tới trang 500”. Với job phải đi hết từng dòng, tôi đi theo khoảng id, cùng cách tôi cắt nhỏ việc lương và thuế ở Base. Tôi không kéo 500.000 dòng vào PHP để phân trang ở đó.

Know: OFFSET scans and discards. Keyset walks from the last key.

Trap: Paginate in PHP after SELECT *.

25Second-highest salarySay what 'second' means when two people share the top.

Write a query for the second-highest salary.

I have run this shape on MySQL, not on a Postgres cluster. The SQL is the same idea. 'Second' has to mean the next distinct salary, or two people on the top salary make OFFSET 1 return the same number.

SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

If they want everyone on the second tier, I use a rank:

SELECT salary
FROM (
  SELECT salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;

LIMIT and OFFSET work in MySQL and PostgreSQL. I would confirm NULL salaries are excluded, because NULL sorts first or last depending on the engine.

Viết query lấy lương cao thứ hai.

Em đã chạy dạng này trên MySQL, chưa vận hành một cụm Postgres. SQL cùng một ý. 'Thứ hai' phải là mức lương khác tiếp theo, nếu không hai người cùng mức cao nhất khiến OFFSET 1 trả lại đúng số đó.

SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;

Nếu họ muốn mọi người ở bậc thứ hai, em dùng rank:

SELECT salary
FROM (
  SELECT salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;

LIMIT và OFFSET chạy được trên MySQL và PostgreSQL. Em sẽ hỏi lương NULL có bị loại không, vì NULL sắp đầu hoặc cuối tùy engine.

Know: DISTINCT or DENSE_RANK. OFFSET 1 without DISTINCT can repeat the top salary.

Trap: Claiming a Postgres-only career. You have operated MySQL.

26Write an UPDATESELECT the WHERE first. Then the transaction.

Write an update query. What do you check first?

I write the WHERE as a SELECT and read the row count before I change anything. Then the same filter goes into the UPDATE, inside a transaction.

BEGIN;
SELECT id, salary FROM employees
WHERE department_id = 4 AND salary < 2000;

UPDATE employees
SET salary = salary * 1.1
WHERE department_id = 4 AND salary < 2000;
COMMIT;

No WHERE means every row. I do not run that. PostgreSQL can add RETURNING id, salary so I see what changed. MySQL I follow with a SELECT. On payroll data at Base, a wrong update is worse than a slow one, so the preview is the point.

Viết một câu UPDATE. Bạn kiểm tra gì trước?

Em viết WHERE thành SELECT và xem số dòng trước khi sửa. Rồi đúng filter đó vào UPDATE, trong một transaction.

BEGIN;
SELECT id, salary FROM employees
WHERE department_id = 4 AND salary < 2000;

UPDATE employees
SET salary = salary * 1.1
WHERE department_id = 4 AND salary < 2000;
COMMIT;

Không có WHERE là sửa cả bảng. Em không chạy câu đó. PostgreSQL thêm được RETURNING id, salary để thấy dòng vừa đổi. MySQL thì em SELECT lại. Với dữ liệu lương ở Base, update sai tệ hơn update chậm, nên bước xem trước mới là điểm chính.

Know: Preview, WHERE, transaction.

Trap: UPDATE with no WHERE, then COMMIT.

27Delete duplicate rowsKeep one id per email. Then add a unique key.

Delete duplicate rows and leave one row per email.

I decide which row survives. Usually the smallest id. A window makes that obvious in both PostgreSQL and MySQL 8:

DELETE FROM employees
WHERE id IN (
  SELECT id FROM (
    SELECT id,
           ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM employees
  ) ranked
  WHERE rn > 1
);

I run the inner SELECT first and read how many rows would go. After the delete I add UNIQUE (email), or the duplicates come back on the next import. I do this in a transaction, and I do not delete from a table I have not backed up when the data is payroll.

Xóa dòng trùng và giữ một dòng cho mỗi email.

Em chọn dòng nào được giữ. Thường là id nhỏ nhất. Window function nói rõ điều đó trên cả PostgreSQL và MySQL 8:

DELETE FROM employees
WHERE id IN (
  SELECT id FROM (
    SELECT id,
           ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM employees
  ) ranked
  WHERE rn > 1
);

Em chạy SELECT bên trong trước và xem bao nhiêu dòng sẽ mất. Xóa xong em thêm UNIQUE (email), không thì lần import sau trùng lại. Làm trong transaction, và em không xóa bảng chưa backup khi data là lương.

Know: ROW_NUMBER, keep one, then a unique constraint.

Trap: DELETE the duplicates and leave the door open.

Common questions

28== versus ===Common PHP quiz. Say the rule, then one surprise.

What is the difference between == and === in PHP?

I use === by default. == compares after type coercion, so "0" == false and 0 == "foo" can both surprise you. === checks value and type. I only reach for == when I explicitly want coercion, which is rare in application code.

Khác nhau giữa == và === trong PHP?

Tôi mặc định dùng ===. == so sánh sau khi ép kiểu, nên "0" == false và 0 == "foo" đều có thể bất ngờ. === kiểm tra cả giá trị lẫn kiểu. Tôi chỉ dùng == khi cố ý muốn ép kiểu — trong code ứng dụng thì hiếm.

29N+1 queriesCommon performance question. Use BaseVN, not a textbook.

What is the N+1 query problem, and how do you fix it?

N+1 is one query for the list, then one more query per row inside a loop. On a large employee or tax table that dies. I look for a query in a loop, then I join or batch-load the related rows. On IELTS I hit the same idea from the other side: hydrate the progress the screen needs instead of fetching every topic one by one. The fix is fewer round trips, and then I re-check the result on a known sample so I did not just make a wrong query faster.

N+1 query là gì và bạn sửa thế nào?

N+1 là một query cho danh sách, rồi thêm một query mỗi dòng trong vòng lặp. Bảng nhân viên hoặc thuế lớn sẽ chết. Tôi tìm query nằm trong loop, rồi join hoặc load theo lô. Bên IELTS tôi gặp cùng ý từ phía kia: hydrate đúng phần progress màn hình cần, không fetch từng topic. Sửa là giảm round trip, rồi kiểm lại trên sample đã biết để không làm một query sai chạy nhanh hơn.

30Database transactionsCommon when they ask about money or sync.

When do you use a database transaction?

When several writes must succeed or fail together. A sync that updates HR data and a payroll row is a good example: a half-written result is worse than a failed job. I open a transaction, do the writes, commit if every step is valid, and roll back if one fails. I keep the transaction short. I do not hold it open across an HTTP call to a third party.

Khi nào bạn dùng database transaction?

Khi nhiều lệnh ghi phải cùng thành công hoặc cùng thất bại. Sync vừa sửa dữ liệu HR vừa sửa dòng payroll là ví dụ: ghi nửa chừng tệ hơn một job fail. Tôi mở transaction, ghi, commit khi mọi bước hợp lệ, rollback nếu một bước lỗi. Transaction phải ngắn. Tôi không giữ nó mở trong lúc gọi HTTP sang bên thứ ba.

31Idempotent APIsCommon follow-up after retries, webhooks, or payments.

What is an idempotent API request?

Calling it twice has the same effect as calling it once. GET should be idempotent. A payment, a webhook, or a sync often is not, unless I design it that way. I store an external id or an idempotency key and I check it before insert. On IELTS, Apple and Google purchase notifications hit Express. A repeated notification must not grant the purchase twice. The server is the source of truth, and the unique store transaction id is the guard.

Request API idempotent là gì?

Gọi hai lần cho cùng kết quả như gọi một lần. GET nên idempotent. Thanh toán, webhook, hoặc sync thường không — trừ khi tôi thiết kế vậy. Tôi lưu external id hoặc idempotency key và kiểm tra trước khi insert. Trên IELTS, thông báo mua của Apple và Google vào Express. Notification lặp không được cấp quyền mua hai lần. Server là nguồn sự thật, và transaction id của store là chốt chặn.

32REST and GraphQLCommon awareness question. Stay honest about what you shipped.

REST or GraphQL — which do you choose?

I have shipped REST. The client and server share a JSON contract, status codes mean something, and errors have a stable shape. GraphQL is one endpoint where the client asks for the fields it needs. That helps when many clients need very different shapes. I would use it if the team already runs it. I would not introduce it for a small PHP API. My default is a clear REST contract.

REST hay GraphQL — bạn chọn cái nào?

Tôi đã ship REST. Client và server dùng contract JSON, status code có nghĩa, lỗi có shape ổn định. GraphQL là một endpoint, client xin đúng field nó cần. Hợp khi nhiều client cần shape rất khác nhau. Tôi dùng nếu team đã chạy sẵn. Tôi không đưa vào một API PHP nhỏ. Mặc định của tôi là REST contract rõ.

33Where you cacheCommon, and easy to oversell. Say what you would not cache.

What do you cache, and what do you refuse to cache?

I cache work that is expensive and safe to be slightly stale: a dashboard aggregate, a config, a rendered report that we can invalidate. I do not cache a tax or payroll figure for a specific period unless invalidation is obvious, because fast and wrong is a bad launch. Redis is the usual tool. I know the pattern — key, TTL, invalidate on write — and I would follow the team's setup instead of inventing one in the interview.

Bạn cache gì, và từ chối cache gì?

Tôi cache việc đắt và chấp nhận hơi cũ: số tổng dashboard, config, report có thể invalidate. Tôi không cache số thuế hoặc payroll của một kỳ nếu chưa rõ cách xóa cache, vì nhanh mà sai là launch tệ. Redis là tool thường gặp. Tôi biết pattern — key, TTL, xóa khi ghi — và tôi theo setup của team thay vì bịa một cái trong interview.

34Magic link loginEngineering prompt. Security first, Laravel second.

How would you implement a magic-link login?

The user types an email. I do not put a password on that flow. I create a random token, I store only a hash of it, I set a short expiry — minutes, not days — and I email a link that carries the raw token once. When they click, I hash what arrived, find a row that is unused and not expired, start a session, and I invalidate the token so it cannot be replayed. HTTPS only. Rate-limit the “send link” endpoint so nobody mails a stranger a thousand times. The response is the same whether the email exists or not, so I do not leak accounts. I log the send and the consume, with an ip, so a stolen mailbox is visible. Laravel Mail plus a signed URL can carry this. The important part is one-time, hashed, short-lived, not the helper name.

Bạn làm đăng nhập magic link thế nào?

User nhập email. Flow này không có password. Tôi tạo token ngẫu nhiên, chỉ lưu bản hash, hạn ngắn — vài phút, không phải vài ngày — và gửi mail một link mang token thô một lần. Khi họ bấm, tôi hash cái nhận được, tìm dòng chưa dùng và chưa hết hạn, mở session, rồi hủy token để không dùng lại. Chỉ HTTPS. Rate-limit endpoint “gửi link” để không ai gửi một nghìn mail cho người lạ. Response giống nhau dù email có tồn tại hay không, để không lộ tài khoản. Tôi log lần gửi và lần dùng, kèm ip, để hộp thư bị lấy vẫn nhìn thấy. Laravel Mail cộng signed URL làm được. Phần quan trọng là một lần, đã hash, sống ngắn, không phải tên helper.

Know: Hash the token, short TTL, one-time, same response if the email is unknown.

Trap: Storing the raw token, or a link that lasts a week.

35Stop people abusing a public APIRate limit, cache, cheap queries. Not a captcha speech.

A public stats API is free. How do you stop people abusing it?

Assume it will be scraped. I put a key even on a “free” API so I can revoke one client. I rate-limit by key and by ip, and I return 429 with a Retry-After. The handler is a cache of a precomputed number, not a live scan of the cases table on every anonymous hit. I page and I cap the window they can query. I log volume per key. If a key is clearly a bot I disable it. Auth and cost belong in the design, not in a later firewall ticket. I have not run an open API at internet scale. The same idea showed up on IELTS: untrusted clients, a tight endpoint, and the server as the source of truth.

API thống kê public, miễn phí. Làm sao để không bị lạm dụng?

Giả định sẽ bị scrape. Tôi vẫn cấp key cho API “free” để thu hồi được một client. Rate-limit theo key và theo ip, trả 429 kèm Retry-After. Handler đọc cache một số đã tính sẵn, không quét bảng cases mỗi lần hit ẩn danh. Có phân trang và khống chế khoảng thời gian họ được hỏi. Tôi log sản lượng theo key. Key rõ là bot thì tắt. Auth và chi phí nằm trong thiết kế, không phải ticket firewall về sau. Tôi chưa chạy API mở ở quy mô internet. Cùng ý đó xuất hiện trên IELTS: client không tin được, endpoint hẹp, server là nguồn sự thật.

Know: Key, rate limit, cache, cap the query, revoke.

Trap: Running an unbounded GROUP BY on every public GET.

36A six-hour Artisan commandChunk, queue, do not load the table into PHP.

An Artisan command reads MySQL and computes analytics. It takes six hours. Most steps do not depend on each other. How do you speed it up?

First I ask whether SQL can do the aggregation. A GROUP BY in MySQL is faster than fetching every row into PHP. If the work is still per row and independent, I stop using one process. I chunk by id, I push many jobs onto a queue, and workers run them in parallel. Each job selects a range, only the columns it needs, and writes its result. I do not Model::all(). I do not wrap the whole six hours in one transaction. I make the job idempotent so a retry does not double-count. At Base, payroll export and sync jobs were this shape: chunk, queue, log the failures, do not hold the browser. I have not had a job that truly needed six hours after that treatment. If it still does, the next question is a warehouse or a replica, not a bigger PHP memory_limit.

Một lệnh Artisan đọc MySQL và tính analytics, chạy sáu giờ. Hầu hết bước không phụ thuộc nhau. Làm sao cho nhanh?

Trước hết tôi hỏi SQL có làm được phần gộp không. GROUP BY trong MySQL nhanh hơn kéo từng dòng vào PHP. Nếu việc vẫn theo từng dòng và độc lập, tôi không dùng một process. Tôi cắt theo id, đẩy nhiều job vào queue, worker chạy song song. Mỗi job chọn một khoảng, chỉ cột cần, rồi ghi kết quả. Tôi không Model::all(). Tôi không bọc cả sáu giờ trong một transaction. Job phải idempotent để retry không đếm hai lần. Ở Base, export lương và job sync là hình dạng này: cắt nhỏ, queue, ghi lỗi, không giữ trình duyệt. Tôi chưa gặp job nào vẫn cần sáu giờ sau cách đó. Nếu vẫn cần, câu tiếp theo là warehouse hoặc replica, không phải memory_limit PHP to hơn.

Know: SQL first, then chunked queue jobs, idempotent writes.

Trap: Raising memory_limit and selecting the whole table.

37What a mutex is, in PHPShare-nothing. Use a DB or Redis lock instead.

Explain what a mutex is, and why it is uncommon in PHP.

A mutex is a lock so two threads do not enter the same critical section. In a typical PHP-FPM or Laravel queue setup, each request is its own process. A mutex inside one process does not stop the other workers. That is why you rarely see one in application PHP. When two jobs must not run the same partner export, I take a lock they can all see: GET_LOCK in MySQL, SELECT … FOR UPDATE on a row, or a Redis/cache lock with a TTL so a dead worker cannot hold it forever. flock is fine for one cron on one machine. It is not fine across two Cloud Run instances. PHP is share-nothing on purpose. Cross-process locks live in the database or in Redis, not in a static variable.

Mutex là gì, và vì sao ít gặp trong PHP?

Mutex là khóa để hai thread không vào cùng một đoạn nguy hiểm. PHP-FPM hoặc queue Laravel thường mỗi request một process. Mutex trong một process không chặn worker khác. Vì vậy code ứng dụng PHP ít khi có mutex. Khi hai job không được chạy cùng một lần export đối tác, tôi lấy khóa cả hai đều thấy: GET_LOCK trong MySQL, SELECT … FOR UPDATE trên một dòng, hoặc lock Redis/cache có TTL để worker chết không giữ mãi. flock ổn cho một cron trên một máy. Không ổn trên hai instance Cloud Run. PHP cố ý share-nothing. Khóa xuyên process nằm ở database hoặc Redis, không nằm ở biến static.

Know: PHP processes do not share memory. Lock in MySQL or Redis.

Trap: A static $locked flag in a controller.

38Fuzzy search on 50 million rowsHonesty first. MySQL LIKE will not do 50–300ms.

You have 50 million rows in MySQL. How do you do fuzzy search and faceting in 50–300ms?

Not with LIKE '%qnap%' on that table. A B-tree cannot help a leading wildcard, and faceting — counts per warehouse, per status, per product line — wants aggregations a primary MySQL node should not recompute on every keystroke. The usual architecture is a search engine next to MySQL: Elasticsearch, OpenSearch, or Meilisearch. MySQL stays the source of truth. A worker writes to the index when a row changes. The search box and the facet counts hit the engine. I have not operated 50 million rows. At Base the heavy tables were hundreds of thousands, and the fix was indexes, pagination, and not selecting columns we did not render. If this portal’s inventory search is thousands of SKUs, MySQL is enough. If they truly have tens of millions and type-ahead, I would say so, and I would not pretend I have already built that cluster.

50 triệu dòng trong MySQL. Làm fuzzy search và facet trong 50–300ms thế nào?

Không phải bằng LIKE '%qnap%' trên bảng đó. B-tree không giúp ký tự % đứng đầu, và facet — đếm theo kho, theo trạng thái, theo dòng sản phẩm — là phép gộp mà node MySQL chính không nên tính lại mỗi lần gõ. Kiến trúc thường gặp là một search engine cạnh MySQL: Elasticsearch, OpenSearch, hoặc Meilisearch. MySQL vẫn là nguồn sự thật. Worker ghi vào index khi một dòng đổi. Ô tìm và số facet đánh vào engine. Tôi chưa vận hành 50 triệu dòng. Ở Base bảng nặng là hàng trăm nghìn, và cách sửa là index, phân trang, và không select cột không vẽ. Nếu ô tìm tồn kho của portal này là vài nghìn SKU, MySQL đủ. Nếu họ thật sự có hàng chục triệu và type-ahead, tôi sẽ nói vậy, và tôi không giả vờ đã dựng cluster đó.

Know: Search engine beside MySQL. MySQL remains the source of truth.

Trap: Claiming 50 million LIKE queries at 50ms.

39High traffic and 99.9% uptimeShape, then honesty. You have not run millions of visitors.

How would you keep a high-traffic site up around 99.9% of the time, even if one server dies?

I have not run millions of visitors a day. The shape I would start from is still simple. More than one app server behind a load balancer, so one box can die. The database is not on the web box. Health checks remove a bad instance. Sessions and uploads live in Redis or object storage, not on local disk. Hot reads can be cached. Writes and reports that take seconds leave the request and go to a queue. If the primary database dies, a replica can serve reads; failover of writes is a runbook, not a hope. 99.9% is about eight hours of downtime a year, so deploys and migrations have to be boring. I would measure error rate and latency before I buy a more exotic topology. At Akktis and on the tutor, Cloud Run already gave me more than one instance. I would not invent Kubernetes in the interview to sound senior.

Giữ site traffic lớn quanh 99.9% uptime, kể cả khi một server chết, thế nào?

Tôi chưa chạy hàng triệu khách mỗi ngày. Hình dạng tôi bắt đầu vẫn đơn giản. Nhiều hơn một app server sau load balancer, để một máy chết được. Database không nằm trên máy web. Health check gỡ instance hỏng. Session và file upload nằm ở Redis hoặc object storage, không nằm đĩa local. Đọc nóng có thể cache. Ghi và report mất vài giây rời request, vào queue. Primary database chết thì replica phục vụ đọc; failover ghi là runbook, không phải hy vọng. 99.9% là khoảng tám giờ downtime một năm, nên deploy và migration phải nhàm chán. Tôi đo error rate và latency trước khi mua topology cầu kỳ hơn. Ở Akktis và trên tutor, Cloud Run đã cho tôi hơn một instance. Tôi không bịa Kubernetes trong interview để nghe như senior.

Know: Redundant app, DB off the web box, cache, queue, boring deploys.

Trap: Claiming an HA story you have not operated.

40Queue versus the HTTP requestIf the user should not wait, it is a job.

What belongs in the HTTP request, and what belongs on a queue?

The request does the thing the user is staring at: validate, authorize, write the case, return the id. Mail, Excel export, partner notify, analytics, and sync with another system go on a queue. If it can take more than a second, or if it can fail and retry, it is a job. At Base, VSS sync and payroll export were jobs. A partner-application approval should commit the status in the request, then queue the email. I do not start a six-minute report inside index() and hope the proxy timeout is kind.

Cái gì nằm trong HTTP request, cái gì nằm trên queue?

Request làm việc user đang nhìn: validate, authorize, ghi case, trả id. Mail, export Excel, báo đối tác, analytics, và đồng bộ hệ thống khác đi vào queue. Nếu có thể hơn một giây, hoặc có thể fail rồi retry, đó là job. Ở Base, sync VSS và export lương là job. Duyệt hồ sơ đối tác nên commit trạng thái trong request, rồi queue email. Tôi không mở report sáu phút trong index() rồi hy vọng timeout của proxy tử tế.

Know: User-facing write in the request. Slow or retryable work on a queue.

41Eloquent versus the query builderModels for one record. SQL you can see for a report.

When do you use Eloquent, and when do you use the query builder?

Eloquent is for one model and its relations: load a case, with(['partner', 'warehouse']), update status, fire the usual events. A report that joins five tables, or a batch that must show me the SQL, I write with the query builder. I can paste that SQL into EXPLAIN. I use raw SQL only when the builder cannot say it, and I still bind the values. I do not put a 40-line query in a Blade file. I do not disable the query log in production and then guess.

Khi nào dùng Eloquent, khi nào dùng query builder?

Eloquent cho một model và quan hệ của nó: load một case, with(['partner', 'warehouse']), đổi trạng thái, bắn event bình thường. Report join năm bảng, hoặc batch mà tôi phải nhìn thấy SQL, tôi viết query builder. Tôi dán SQL đó vào EXPLAIN. Raw SQL chỉ khi builder không nói được, và tôi vẫn bind giá trị. Tôi không nhét query 40 dòng vào file Blade. Tôi không tắt query log trên production rồi đoán.

Know: Eloquent for the unit of work. Builder when you need to see the SQL.

Trap: Eloquent in a loop, which is N+1 with nicer syntax.
