07Microservices, or modules firstYou have not run a microservice estate. Say the shape.~64s✓

Do you understand microservices or scalable design?

I have not operated a microservice platform, and I would not start there with a small team. I start with modules in one app: the API, background jobs, and the two clients. A piece gets split out when it has its own traffic or its own team. If the user is waiting, I call HTTP with a timeout. If the fact has already happened, like a report being ready, that goes on a queue.

I have done this inside one codebase. At BaseVN the sync between the social-insurance system, HR, and payroll ran as jobs with a fixed order and validation. The hiring integration retried failed calls to the job boards and logged every request. On PhysioFix, each call’s events run through one queue so they stay in order. On a health product the same rule holds: a retry must not create a second charge or a second record.

Bạn hiểu microservices hoặc thiết kế scale chứ?

Tôi chưa vận hành một hệ thống microservice, và với team nhỏ tôi cũng không bắt đầu từ đó. Tôi bắt đầu bằng các module trong một app: API, job chạy nền, và hai client. Một phần chỉ được tách ra khi nó có lưu lượng riêng hoặc team riêng. Nếu người dùng đang chờ, tôi gọi HTTP có timeout. Nếu sự việc đã xảy ra rồi, ví dụ báo cáo đã sẵn sàng, thì đưa vào queue.

Tôi đã làm như vậy trong một codebase. Ở BaseVN, việc đồng bộ giữa hệ thống bảo hiểm xã hội, nhân sự và lương chạy bằng job có thứ tự cố định và có validate. 09Vue 3: Options API vs Composition APIBoth supported. Composition groups by feature and reuses through composables.~62s✓

What is the difference between the Options API and the Composition API in Vue 3?

Both are supported in Vue 3. The Options API puts a component into fixed slots: data, methods, computed, watch, and lifecycle hooks like mounted, and you reach everything through this. It is easy to read in a small component.

The Composition API, usually written with <script setup>, lets you group code by feature instead of by option type. You declare state with ref, derive values with computed, and react to changes with watch or onMounted. The big gain is reuse: a composable like useCase(id) returns its own refs and can be shared between components, which replaces mixins and their name collisions. It also works better with TypeScript.

In a new Vue 3 codebase I would expect <script setup> and composables. If the existing code uses the Options API, I follow it rather than mixing both styles in one file.

Options API và Composition API trong Vue 3 khác nhau thế nào?

Vue 3 hỗ trợ cả hai. Options API chia component thành các ô cố định: data, methods, computed, watch, và các lifecycle hook như mounted, và mọi thứ được truy cập qua this. Với component nhỏ thì cách này dễ đọc.

Composition API, thường viết bằng <script setup>, cho phép gom code theo tính năng thay vì theo loại option. Mình khai báo state bằng ref, tính giá trị dẫn xuất bằng computed, và phản ứng với thay đổi bằng watch hoặc onMounted. Lợi ích lớn nhất là tái sử dụng: một composable như useCase(id) trả về các ref riêng và dùng chung được giữa nhiều component, thay cho mixin và chuyện trùng tên. Nó cũng hợp với TypeScript hơn.

Với codebase Vue 3 mới, tôi nghĩ team sẽ dùng <script setup> và composable. Nếu code đang có dùng Options API, tôi làm theo, không trộn hai kiểu trong cùng một file.

Know: A composable is the Vue version of a custom hook, but it runs once inside setup, not on every render.

Trap: Saying the Options API is deprecated. It is not.

Follow-up: “How do you share logic between components?” → composables, not mixins.

10ref vs reactiveref for most state. reactive loses reactivity when destructured or replaced.~55s✓

When do you use ref and when do you use reactive?

ref wraps any value, including a string or a number. In script you read and write it through .value, and in the template it is unwrapped for you. reactive takes an object and returns a proxy, so you write state.count without .value.

reactive has two traps. You cannot replace the whole object, because the proxy you hold is the reactive one. And if you destructure it, the values stop being reactive unless you use toRefs. The Vue docs recommend ref as the default for that reason.

So I would use ref for most state, maybe reactive for a form object that stays the same object, and computed for anything derived, instead of copying values into a second ref and keeping them in sync by hand.

Khi nào dùng ref, khi nào dùng reactive?

ref bọc được mọi giá trị, kể cả string hay number. Trong script mình đọc và ghi qua .value, còn trong template Vue tự mở ra. reactive nhận một object và trả về một Proxy, nên mình viết state.count mà không cần .value.

reactive có hai cái bẫy. Không thể gán lại cả object, vì cái Proxy mình đang giữ mới là cái reactive. Và nếu destructure thì các giá trị mất reactivity, trừ khi dùng toRefs. Vì thế tài liệu Vue khuyên dùng ref làm mặc định.

Nên tôi dùng ref cho phần lớn state, có thể dùng reactive cho một object form không bị thay thế, và dùng computed cho mọi giá trị dẫn xuất, thay vì copy sang một ref khác rồi tự đồng bộ bằng tay.

Know: A ref holding an object makes it deeply reactive. shallowRef skips that for large data. Refs inside a reactive object are unwrapped.

Trap: const { count } = reactive({ count: 0 }) — count is now a plain number.

Follow-up: “How do you watch a prop?” watch(() => props.id, load), a getter, not props.id itself.

11Pinia vs VuexPinia is the official store now. No mutations, typed, one store per domain.~59s✓

Pinia or Vuex? What is the difference?

Pinia is the official store for Vue 3. Vuex is the older one and is in maintenance mode. The difference you feel is less ceremony. In Vuex you change state through mutations and call actions through dispatch with string names. In Pinia you define a store with defineStore, state is plain reactive state, actions are normal functions that can be async, and TypeScript infers the types. Each store is its own module, so a case store and a user store do not live in one big tree. If I destructure a store in a component, I use storeToRefs to keep reactivity.

What goes in a store is the same rule I use in React: data many screens share, like the signed-in user. Data for one screen stays with that screen, and permission still lives on the API.

Pinia hay Vuex? Khác nhau ở đâu?

Pinia là store chính thức cho Vue 3. Vuex là thư viện cũ hơn và đang ở chế độ bảo trì. Khác biệt rõ nhất là ít thủ tục hơn. Với Vuex, mình đổi state qua mutation và gọi action bằng dispatch với tên dạng chuỗi. Với Pinia, mình định nghĩa store bằng defineStore, state là state reactive bình thường, action là hàm thường và có thể async, và TypeScript tự suy ra kiểu. Mỗi store là một module riêng, nên store cho case và store cho user không bị nhét chung vào một cây lớn. Nếu destructure store trong component, tôi dùng storeToRefs để giữ reactivity.

Cái gì nên vào store thì vẫn theo nguyên tắc tôi dùng ở React: dữ liệu nhiều màn hình dùng chung, như người dùng đang đăng nhập. Dữ liệu của một màn thì để ở màn đó, và quyền vẫn do API quyết định.

12Vue Router basicsRoutes, lazy pages, params, guards. The guard is UX; the API still checks.~60s✓

How does routing work in a Vue app? How would you protect a page?

You create the router with a list of routes and a history mode, usually createWebHistory. Each route maps a path to a component, and big pages load lazily with a dynamic import, so the first bundle stays small. Params like /cases/:id come in through useRoute, and you navigate in code with useRouter().push. Nested routes render into a nested RouterView, which suits a layout with a sidebar.

For auth I would add a beforeEach guard that checks route meta, like requiresAuth, and sends the user to login. That guard is only for user experience. The API still checks the token on every request, because anyone can call it directly.

One thing to watch: when only the param changes, Vue reuses the same component, so I watch the param instead of loading data once on mount.

Routing trong app Vue hoạt động thế nào? Bạn bảo vệ một trang ra sao?

Mình tạo router với danh sách route và một chế độ history, thường là createWebHistory. Mỗi route gắn một đường dẫn với một component, và trang lớn thì lazy load bằng dynamic import để bundle đầu tiên nhỏ. Tham số như /cases/:id lấy qua useRoute, còn chuyển trang trong code thì dùng useRouter().push. Route lồng nhau render vào một RouterView lồng bên trong, hợp với layout có sidebar.

Với auth, tôi thêm guard beforeEach kiểm tra meta của route, ví dụ requiresAuth, rồi chuyển người dùng sang trang đăng nhập. Guard đó chỉ phục vụ trải nghiệm người dùng. API vẫn kiểm tra token ở mọi request, vì ai cũng có thể gọi API trực tiếp.

Một điểm cần để ý: khi chỉ tham số thay đổi, Vue dùng lại đúng component đó, nên tôi watch tham số thay vì chỉ tải dữ liệu một lần lúc mount.

14Ionic and Capacitor basics: plugins and native buildsStudied, not shipped. cap sync, native projects in the repo, plugins, permissions, real device.~61s✓

How does an Ionic app with Capacitor get native features and reach the stores?

Capacitor is the native runtime under an Ionic app. You build the web app, then npx cap sync copies the build into native iOS and Android projects and updates the plugins. Those native projects live in the repo, and you open them in Xcode or Android Studio to sign and build for the stores. Native features come from plugins, for example Camera, Push Notifications, and Preferences for small key-value storage. Each plugin needs its permissions declared, like the camera usage text on iOS.

For daily work you can run the app on a device with live reload, so a code change shows on the phone without a full rebuild. What I know from Expo still applies: test on a real device, keep tokens out of plain storage, and remember that store review can add days to any release that changes native code.

App Ionic dùng Capacitor lấy tính năng native và lên store như thế nào?

Capacitor là lớp runtime native bên dưới app Ionic. Mình build web app, rồi npx cap sync chép bản build vào project native iOS và Android và cập nhật plugin. Hai project native đó nằm trong repo, và mình mở bằng Xcode hoặc Android Studio để ký và build lên store. Tính năng native đến từ plugin, ví dụ Camera, Push Notifications, và Preferences để lưu dữ liệu key-value nhỏ. Mỗi plugin cần khai báo quyền, như dòng mô tả quyền dùng camera trên iOS.

Khi làm hằng ngày, có thể chạy app trên máy thật với live reload, nên sửa code là thấy ngay trên điện thoại mà không phải build lại toàn bộ. Những gì tôi học từ Expo vẫn đúng: test trên máy thật, không để token trong bộ nhớ thường, và nhớ rằng duyệt store có thể mất vài ngày với mọi bản release có thay đổi phần native.

How would you handle several languages?

Strings live in keyed files, not inside a component, for example with vue-i18n on the web and the same keys in the mobile app. The locale sits on the user or the device, and the API returns dates and copy in that locale. Vet.AI’s public site lists Chinese, English, Japanese, and Vietnamese, so I would expect that set, and I would confirm which ones a new screen must ship with on day one.
