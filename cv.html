02IELTS Express API mapJD: write APIs. Name real modules.

How is the IELTS Node API structured?

server.js is the Express entry: CORS, JSON parser, then route modules under src/api. Public: Google/Apple auth, IAP webhooks, some audio. Authenticated: TTS, transcribe, agent, practice, translation, storage, study-plan, writing assess, speaking, words, assignment-portal, feature flags. Auth middleware checks an X-Username header before those routes. Tracing boots first so Langfuse sees OpenAI calls. I add a feature by a new router file and app.use — not one giant server.js. Same idea as PHP controllers, just Express.

API Node của IELTS được cấu trúc thế nào?

server.js là entry Express: CORS, parser JSON, rồi router trong src/api. Public: auth Google/Apple, webhook IAP, một phần audio. Cần auth: TTS, transcribe, agent, practice, translation, storage, study-plan, chấm writing, speaking, words, assignment-portal, feature flag. Middleware kiểm header X-Username trước các route đó. Tracing bật trước để Langfuse thấy lệnh OpenAI. Feature mới là file router rồi app.use — không nhét hết vào server.js. Cùng ý controller PHP, chỉ là Express.

Know: One router per domain · auth on most /api · tracing before routes

Trap: Memorizing every path. Name 4–5 domains, then go deep on one.

Follow-up: Which routes must stay public, and why?

03IELTS auth: Google, Apple, headerReal flow. Don't upgrade it to JWT-everywhere.

How does the IELTS app authenticate to the Node API?

Sign-in is Google or Apple on the device. Express verifies the Google token or authorization code with google-auth-library, or Apple's identity token, then upserts the user in Firebase. After that the API client sends X-Username. That's identity, not a signed session on every call — I'd say so in an interview. Purchases are stricter: Apple JWS verified with the cert chain, Google Play via service account. Admin portal uses its own cookie/session. If they ask how I'd harden it: signed tokens with expiry, still authorize per resource.

App IELTS authenticate với API Node thế nào?

Đăng nhập Google hoặc Apple trên máy. Express verify token/code Google bằng google-auth-library, hoặc identity token Apple, rồi upsert user trên Firebase. Sau đó API client gửi X-Username. Đó là identity, chưa phải session ký trên mọi call — tôi nói thẳng. Mua hàng chặt hơn: JWS Apple verify chuỗi cert, Google Play qua service account. Portal admin có cookie/session riêng. Nếu hỏi cách siết: token ký có hạn, vẫn authorize theo resource.

Know: OAuth verify on server · X-Username is simple · IAP uses real crypto

Trap: Calling the username header 'OAuth' or 'JWT'.

Follow-up: Why can't IAP webhooks use the same auth as the mobile app?

04Firestore on IELTS vs MySQL at BaseVNPick the store from the product, not the JD buzzword.

Why Firestore on IELTS if you are strong at MySQL?

IELTS progress is per-user documents — topic keys, settings, entitlements — not payroll joins. Firestore fits that; Cloud Run talks through firebase-admin. Base PIT and VSS needed MySQL: related tables, 500k rows, Excel/XML, transactions. I don't force Firestore onto tax data or MySQL onto a phone's nested progress blob. For a Node JD that lists MySQL, I bring BaseVN. For documents, I bring IELTS. Mongo would be the middle cousin of Firestore, not something I operated as a cluster.

Vì sao IELTS dùng Firestore trong khi bạn mạnh MySQL?

Tiến độ IELTS là document theo user — key topic, setting, entitlement — không phải join payroll. Firestore hợp; Cloud Run nói qua firebase-admin. Base PIT và VSS cần MySQL: bảng liên quan, 500k row, Excel/XML, transaction. Không nhét Firestore vào data thuế hay MySQL vào blob tiến độ trên điện thoại. JD liệt MySQL thì tôi mang BaseVN. Document thì mang IELTS. Mongo là họ hàng của Firestore, không phải cluster tôi đã operate.

Know: Document store for app state · MySQL for related business records

Trap: Saying Firestore and MySQL are interchangeable.

Follow-up: Would you migrate IELTS progress to MySQL? When yes / no?

41You wrote “optimized queries for 500,000+ records.” Walk me through it.This is the money story from Base PIT (personal income tax). Correctness matters more than speed — wrong tax/payroll is worse than a slow screen. Follow-ups: EXPLAIN, indexes, why not load all rows in PHP, how you proved it.

You wrote “optimized queries for 500,000+ records.” Walk me through it..

Base PIT is a personal income tax product. It sat on more than 500,000 records and had to talk to HRM and Payroll. The painful parts were reporting and export — Excel and XML for tax-style compliance — plus screens that loaded or filtered a lot of employee and period data.

The first rule: I do not run a 500k-row report inside a user request. That will time out or blow memory. I treat heavy export and sync as a job path: chunk the work, write the file, then let the user download it.

Then I find the real slow query. I look at the slow query log or the query behind the slow screen, run EXPLAIN, and check whether it is a full scan, a bad join, or a missing index on the columns we actually filter — company, employee, period, that kind of key. I also look for SELECT * and N+1: one query per row in a loop will die at this size.

What I change is usually boring and safe: add or fix indexes that match the WHERE and JOIN, rewrite the query so it only fetches the columns and rows the report needs, and process in batches instead of loading everything into PHP memory. Sometimes the schema itself was the problem — types, keys, or a table that mixed too many concerns — so I adjust that carefully and re-test the export.

I always re-check correctness, not only speed. For tax data I compare a small known sample: same employees, same period, Excel/XML still matches HRM/Payroll. Fast and wrong is a worse launch than slow and right.

What I learned: at this size, schema and queries are infrastructure. “It works on my laptop” is not a plan.

Bạn viết đã tối ưu query cho hơn 500.000 bản ghi. Kể lại.

Base PIT là sản phẩm thuế thu nhập cá nhân. Hơn 500.000 bản ghi, phải nói chuyện với HRM và Payroll. Chỗ đau là report và export — Excel và XML cho tuân thủ — cộng các màn load hoặc lọc nhiều dữ liệu nhân viên và kỳ.

Rồi tôi tìm query chậm thật. Slow query log hoặc query sau màn hình chậm, chạy EXPLAIN, xem full scan, join xấu, hoặc thiếu index trên cột thật sự lọc — công ty, nhân viên, kỳ. Tôi cũng tìm SELECT * và N+1.

Cái tôi đổi thường nhàm và an toàn: index khớp WHERE và JOIN, viết lại query chỉ lấy cột và dòng report cần, xử lý theo lô thay vì nhét cả bảng vào memory PHP. Đôi khi schema là vấn đề — kiểu, khóa, bảng gộp quá nhiều việc — tôi sửa cẩn thận và test lại export.

If they ask “what index?” Say: indexes on the columns we filter and join — typically company / employee / tax period — so EXPLAIN stops doing a full table scan. I do not add an index on every column; unused indexes slow writes.

Speed without a matching file is a failure.

42How do you find a slow query? What does EXPLAIN tell you?

How do you find a slow query? What does EXPLAIN tell you?

I start from the user symptom: which screen, which export, which company and period. Then I get the SQL — from logs, from the ORM, or by reproducing the action. I run EXPLAIN.

I look for type ALL or a huge rows count, no useful key, or a join that explodes. That usually means a missing index or a filter that cannot use an index — function on the column, bad types, or SELECT * plus a sort of the whole table.

I change one thing, measure again, and keep a copy of the old query. I do not “tune production” by guessing.

Bạn tìm query chậm thế nào? EXPLAIN cho biết gì?

Tôi bắt đầu từ triệu chứng của user: màn nào, export nào, công ty và kỳ nào. Rồi tôi lấy SQL — từ log, từ ORM, hoặc bằng cách làm lại thao tác. Tôi chạy EXPLAIN.

What is the most important issue you caught, and how did you fix it?

The most important class of issue I have caught is a silent data mismatch, not a crash.

On Base VSS we synced Vietnam Social Security data with HRM and Payroll, and we exported Excel/XML for compliance. A crash is obvious. A sync that “succeeds” with the wrong mapping is worse — counts look fine until finance or the tax path notices.

How I catch it: I do not trust the job’s success log. I take a small known sample — a few employees I can check by hand — and I compare source fields vs destination fields vs the export. I check job order too: if Payroll reads before HRM has finished, you get yesterday’s truth.

How I fix it: correct the mapping or the transform rule, or fix the job order, then add a clearer validation step — row counts, required fields, or a checksum-style check on the sample — so the next failure is loud. Then I re-run on the sample before I touch the full set.

That is the issue I care about most: wrong money or compliance data that looks green. I would rather catch it on ten rows than explain it on 500,000.

47How do you test a report, export, or schema change?

How do you test a report, export, or schema change?

I keep a fixture: a small company or a few employees whose numbers I already know. I run the old path and the new path and compare. For Excel/XML I check totals and a few line items, not only “file downloaded.”

For a schema or index change I check the write path too — inserts and the sync job — because a new index can slow writes. Then I run the heavy export once on a realistic volume if I have a staging dump, not first in production.

Bạn test một report, một export, hoặc một đổi schema thế nào?

Tôi giữ một fixture: một công ty nhỏ hoặc vài nhân viên có số tôi đã biết. Tôi chạy đường cũ và đường mới rồi so. Với Excel/XML tôi kiểm tổng và vài dòng, không chỉ "file đã tải".

Với đổi schema hoặc index tôi kiểm cả đường ghi — insert và job sync — vì index mới có thể làm chậm ghi. Rồi tôi chạy export nặng một lần trên volume thật nếu có dump staging, không phải lần đầu trên production.

A production issue you fixed · Something you caught in staging.

Staging green, prod red: I diff commits, env vars, secrets, and service versions before I change code. Usually a missing variable, different web-server config, or a dependency only installed in one environment. Fix the config, redeploy, add it to the checklist.

Cloud Run up, DB down: Logs, then connection string, then network/socket, then service account permissions. Often identity or host setup, not “Node died.”

Linux disk full: df/du, free space safely, rotate logs, restart the service, then make disk visible in monitoring. I do not delete blindly under /var.

Pipeline red mid-release: Stop retry spam. Read which stage failed. Smallest fix. Promote only when green. Then make that failure louder earlier.

Một sự cố production bạn đã sửa. Một thứ bạn bắt ở staging.

Staging xanh, prod đỏ: tôi so commit, biến env, secret, và phiên bản service trước khi sửa code. Thường là thiếu biến, config web server khác, hoặc dependency chỉ cài một môi trường. Sửa config, deploy lại, thêm vào checklist.

Cloud Run lên, DB xuống: log, rồi connection string, rồi mạng hoặc socket, rồi quyền service account. Thường là identity hoặc host, không phải "Node chết".
