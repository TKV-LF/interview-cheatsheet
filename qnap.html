10How would you build case registration?~60s✓

How would you build case registration?

A partner submits a case: who they are, which customer, which product, and what they need. I keep the controller thin. A Form Request checks required fields and formats, and a Policy checks that this partner may open that kind of case. The service creates one row with a status, for example draft or submitted, and writes an audit row for who did it. The response is the case id and the status, not the whole database row. How would you do warehouse and inventory lookup?

13How do you handle batch operations?~55s✓

How do you handle batch operations?

A batch is a job, not a request that holds the browser. Sales uploads a file or selects many rows. I validate the file first and reject it with row numbers if the columns are wrong. Then a queue worker chunks the rows, one transaction per chunk, and records failures instead of rolling back the whole file. The screen shows queued, running, and done, and offers a download of the failed rows. Running the same file twice must not create duplicates, so each row has a natural key. At BaseVN I did this kind of work on the tax export and on the sync jobs between social insurance, HR, and payroll, where job order and validation mattered. I would not run an unbounded update in the web process.

Xử lý thao tác hàng loạt thế nào?

How do you keep MVC from turning into a fat controller?

The controller knows HTTP. It does not know the approval rules. If I can describe the method as “validate, authorize, call one service, return a resource”, it is the right size. 24Two people reserve the last unit. What happens?~63s✓

Two people reserve the last unit. What happens?

Without a lock, both requests read one unit available and both reserve it. So the check and the write go in one short transaction, with the stock row locked: SELECT … FOR UPDATE in SQL, or lockForUpdate() in Laravel. The second request waits, then reads zero and gets a clear 409 instead of a half-written case. Another option is a conditional update, WHERE id = ? AND available > 0, and check that one row changed.

I keep the transaction short and never call an external API while I hold the lock. If two transactions lock rows in a different order, MySQL can deadlock and roll one of them back, so I lock in a consistent order and retry once. The same pattern fits approval: lock the application and refuse a second approve. I would test it with two parallel requests, not one happy click.

Hai người giữ chiếc cuối cùng. Chuyện gì xảy ra?

Nếu không lock, cả hai request cùng đọc thấy còn một chiếc và cùng giữ nó. Vì vậy bước kiểm tra và bước ghi phải nằm trong một transaction ngắn, có lock dòng tồn kho: SELECT … FOR UPDATE trong SQL, hoặc lockForUpdate() trong Laravel. Request thứ hai phải chờ, rồi đọc ra số không và nhận một lỗi 409 rõ ràng, thay vì để lại một case ghi dở. Cách khác là update có điều kiện, WHERE id = ? AND available > 0, rồi kiểm tra đúng một dòng bị thay đổi.

I use Cursor and Claude Code every day, with a fixed workflow, so the model works from a spec and not from a vague chat.
