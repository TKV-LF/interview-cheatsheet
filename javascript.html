01ClosuresSay the rule, then show debounce. That is the real use.~60s✓

What is a closure, and where have you actually used one?

A closure is a function that keeps access to the variables of the scope where it was created, even after that outer function has returned. The variables are not copied. The inner function holds a live reference to them.

The clearest real use is debounce. The timer variable lives in the closure, so every call sees the same timer and can cancel the last one.

function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

React hooks are closures too. Every render creates new functions that capture that render's state. That is why a stale closure happens: a setInterval set up once in an effect keeps reading the first value of state. I fix it with the functional updater, setCount(c => c + 1), or with the right dependency array.

Closure là gì, và bạn đã dùng nó thật ở đâu?

Closure là một function vẫn giữ được quyền truy cập vào biến của scope nơi nó được tạo ra, kể cả khi function bên ngoài đã return. Biến không bị copy. Function bên trong giữ tham chiếu sống tới biến đó.

Ví dụ thực tế rõ nhất là debounce. Biến timer nằm trong closure, nên mọi lần gọi đều thấy cùng một timer và hủy được lần trước.

function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

React hook cũng là closure. Mỗi lần render tạo function mới, giữ state của lần render đó. Vì thế mới có stale closure: một setInterval tạo một lần trong effect sẽ cứ đọc giá trị state đầu tiên. Tôi sửa bằng functional updater, setCount(c => c + 1), hoặc dependency array đúng.

Know: Function + the scope it was born in · live reference, not a copy · stale closure in hooks.

Trap: Saying a closure 'copies' the variables. It does not; a later change is visible.

02this and arrow functionsthis depends on how a function is called, except for arrows.~62s✓

How does this work, and how are arrow functions different?

For a normal function, this is decided by how the function is called, not where it is written. Called as obj.method(), it is obj. Called as a plain function, it is undefined in strict mode and in modules. Called with new, it is the new object. call, apply and bind set it by hand.

An arrow function has no this of its own. It takes this from the surrounding scope, the same way it would take any other variable. That makes arrows good for callbacks inside a class method, and bad as object methods.

const btn = { label: 'Save', click() {
  setTimeout(() => console.log(this.label), 0); // 'Save'
}};

The common bug is passing obj.method as a callback. It loses obj. I wrap it in an arrow or use bind. In function components I rarely touch this at all.

this hoạt động thế nào, và arrow function khác gì?

Với function thường, this được quyết định bởi cách gọi, không phải chỗ viết. Gọi kiểu obj.method() thì là obj. Gọi như function trơn thì là undefined trong strict mode và trong module. Gọi bằng new thì là object mới. call, apply, bind gán nó bằng tay.

Arrow function không có this riêng. Nó lấy this từ scope bên ngoài, giống như lấy một biến bình thường. Nên arrow hợp làm callback trong method của class, và không hợp làm method của object.

const btn = { label: 'Save', click() {
  setTimeout(() => console.log(this.label), 0); // 'Save'
}};

Lỗi hay gặp là truyền obj.method làm callback. Nó mất obj. Tôi bọc bằng arrow hoặc dùng bind. Trong function component tôi gần như không đụng tới this.

Know: Call site decides · arrow = lexical this · no own arguments, cannot be used with new.

Trap: Saying this in a plain call is window. Only in sloppy-mode scripts; modules are strict.

03Hoisting and the TDZEverything is hoisted; only var is initialised.~57s✓

What is hoisting, and what is the temporal dead zone?

Before code runs, JavaScript registers every declaration in its scope. That is hoisting. The difference is what each declaration starts as.

A var starts as undefined, so reading it early gives undefined and no error. A function declaration is hoisted with its body, so I can call it above where it is written. let, const and class are hoisted too, but not initialised. From the start of the block until the declaration line, touching them throws a ReferenceError. That window is the temporal dead zone.

console.log(a); // undefined
var a = 1;
console.log(b); // ReferenceError
let b = 2;

The TDZ is a feature. It turns a silent undefined bug into a loud error. A function expression assigned to const follows the const rule, so it cannot be called before its line.

Hoisting là gì, và temporal dead zone là gì?

Trước khi code chạy, JavaScript đăng ký mọi khai báo trong scope. Đó là hoisting. Khác nhau ở chỗ mỗi khai báo bắt đầu với giá trị gì.

var bắt đầu là undefined, nên đọc sớm thì ra undefined và không lỗi. Function declaration được hoist cả thân, nên tôi gọi được nó ở trên dòng khai báo. let, const và class cũng được hoist, nhưng chưa được khởi tạo. Từ đầu block tới dòng khai báo, đụng vào là ném ReferenceError. Khoảng đó gọi là temporal dead zone.

console.log(a); // undefined
var a = 1;
console.log(b); // ReferenceError
let b = 2;

TDZ là tính năng có chủ đích. Nó biến một lỗi undefined âm thầm thành lỗi rõ ràng. Function expression gán vào const theo luật của const, nên không gọi được trước dòng của nó.

Know: All declarations hoisted · var = undefined · let/const/class = TDZ · function declaration = full body.

Trap: Saying let and const are 'not hoisted'. They are; they are uninitialised.

04var, let, constDefault to const, let when you reassign, never var.~60s✓

What is the difference between var, let and const?

Three differences. Scope: var is function-scoped, let and const are block-scoped, so a variable inside an if or a loop stays there. Hoisting: var is undefined before its line, the other two are in the temporal dead zone. Reassignment: const cannot be reassigned.

The trap is that const is not immutable. It fixes the binding, not the value.

const user = { name: 'Thuy' };
user.name = 'An';   // fine
user = {};          // TypeError

The loop case shows block scope. With let, each iteration gets a fresh i, so callbacks see 0, 1, 2. With var they all share one i and see 3.

My rule in TypeScript code is const by default, let only when I really reassign, and no var. ESLint enforces it, so I do not have to argue about it in review.

var, let và const khác nhau thế nào?

Ba điểm khác. Scope: var theo function, let và const theo block, nên biến khai báo trong if hay vòng lặp chỉ sống trong đó. Hoisting: var là undefined trước dòng khai báo, hai cái kia nằm trong temporal dead zone. Gán lại: const không gán lại được.

Bẫy là const không có nghĩa là bất biến. Nó cố định binding, không cố định giá trị.

const user = { name: 'Thuy' };
user.name = 'An';   // fine
user = {};          // TypeError

Vòng lặp cho thấy block scope. Với let, mỗi vòng có một i mới, nên callback thấy 0, 1, 2. Với var tất cả dùng chung một i và thấy 3.

Quy tắc của tôi trong code TypeScript: mặc định const, let chỉ khi thật sự gán lại, và không dùng var. ESLint bắt luật đó, nên không phải tranh luận trong review.

Know: Scope · hoisting · reassignment. const binds, does not freeze (Object.freeze is shallow).

Trap: 'const means immutable'.

05== vs ===Use ===. Know the one place == null is handy.~55s✓

What is the difference between == and ===?

=== is strict equality: same type and same value, no conversion. == converts types first, and the conversion rules are surprising.

0 == ''          // true
'1' == 1        // true
null == undefined // true
NaN === NaN     // false

So I use === everywhere, and the linter enforces it. The one idiom some teams allow is x == null, which matches both null and undefined. In TypeScript I usually write x ?? fallback or optional chaining instead.

Two edge cases are worth knowing. NaN is not equal to itself, so I check it with Number.isNaN. Objects and arrays compare by reference, so two arrays with the same items are not equal. For that I compare an id or a field, not the whole object.

== và === khác nhau thế nào?

=== là so sánh chặt: cùng kiểu và cùng giá trị, không ép kiểu. == ép kiểu trước rồi mới so, và luật ép kiểu rất dễ gây bất ngờ.

0 == ''          // true
'1' == 1        // true
null == undefined // true
NaN === NaN     // false

Nên tôi dùng === ở mọi chỗ, và linter bắt luật đó. Ngoại lệ duy nhất một số team cho phép là x == null, khớp cả null lẫn undefined. Trong TypeScript tôi thường viết x ?? fallback hoặc optional chaining.

Có hai trường hợp cần biết. NaN không bằng chính nó, nên tôi kiểm tra bằng Number.isNaN. Object và array so sánh theo tham chiếu, nên hai array cùng phần tử vẫn không bằng nhau. Lúc đó tôi so id hoặc một field, không so cả object.

Know: === no coercion · == null idiom · NaN · reference equality · Object.is treats NaN as equal and +0/-0 as different.

Trap: Claiming === compares objects 'by content'.

06Prototypes and classesclass is syntax over prototypes.~64s✓

How does prototypal inheritance work, and what does class add?

Every object has a hidden link to another object, its prototype. When I read a property that is not on the object, JavaScript walks up that chain until it finds it or reaches null. Methods are shared this way: they live once on the prototype, not on every instance.

class is mostly syntax over the same mechanism. Methods in the class body go on ClassName.prototype, and extends links one prototype to another.

class ApiError extends Error {
  constructor(status, msg) { super(msg); this.status = status; }
}
const e = new ApiError(404, 'Not found');
e instanceof Error; // true

A custom error class like this is where I use classes most, because an Express error handler can check the status. Classes do add real things: private #fields, static members, and they throw if called without new. For UI I use functions and hooks, not class components.

Kế thừa prototype hoạt động thế nào, và class thêm được gì?

Mỗi object có một liên kết ẩn tới object khác, gọi là prototype. Khi đọc một property không có trên object, JavaScript đi ngược chuỗi đó cho tới khi tìm thấy hoặc gặp null. Method được dùng chung theo cách này: nằm một lần trên prototype, không nằm trên từng instance.

class phần lớn là cú pháp trên cùng cơ chế đó. Method trong thân class nằm trên ClassName.prototype, và extends nối prototype này với prototype kia.

class ApiError extends Error {
  constructor(status, msg) { super(msg); this.status = status; }
}
const e = new ApiError(404, 'Not found');
e instanceof Error; // true

Class lỗi tự định nghĩa như thế này là chỗ tôi dùng class nhiều nhất, vì error handler của Express kiểm tra được status. Class cũng thêm vài thứ thật: field private #field, member static, và báo lỗi nếu gọi mà không có new. Với UI tôi dùng function và hook, không dùng class component.

Know: Prototype chain lookup · methods shared on prototype · class = syntax + #private + static.

Trap: Saying JS classes work like Java classes with copied methods.

07The browser event loopCall stack, then all microtasks, then one macrotask.~68s✓

Explain the event loop in the browser. What prints first, a promise or a setTimeout?

JavaScript runs on one call stack. When the stack is empty, the event loop picks the next job. There are two queues that matter. Macrotasks are things like setTimeout, a click event, or a network callback. Microtasks are promise callbacks, await continuations, and queueMicrotask.

The rule: run one macrotask, then drain all microtasks, then let the browser render if it needs to, then take the next macrotask.

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// A D C B

A and D are synchronous. C is a microtask, so it runs as soon as the stack is empty. B is a macrotask, so it waits, even with zero delay.

The practical point is that a long synchronous loop or an endless microtask chain blocks rendering, and the page freezes. I split heavy work or move it to a Web Worker. The Node event loop has extra phases, but the micro-before-macro rule is the same.

Giải thích event loop trong trình duyệt. Promise hay setTimeout in ra trước?

JavaScript chạy trên một call stack. Khi stack trống, event loop lấy việc tiếp theo. Có hai hàng đợi quan trọng. Macrotask là setTimeout, sự kiện click, hay callback mạng. Microtask là callback của promise, phần tiếp theo sau await, và queueMicrotask.

Luật là: chạy một macrotask, rồi chạy hết microtask, rồi trình duyệt render nếu cần, rồi mới lấy macrotask tiếp theo.

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// A D C B

A và D chạy đồng bộ. C là microtask, nên chạy ngay khi stack trống. B là macrotask, nên phải đợi, dù delay bằng 0.

Ý thực tế là một vòng lặp đồng bộ dài hoặc một chuỗi microtask không dứt sẽ chặn render, và trang bị đơ. Tôi chia nhỏ việc nặng hoặc chuyển sang Web Worker. Event loop của Node có thêm các phase, nhưng luật microtask trước macrotask vẫn giống.

Know: One stack · macrotask → all microtasks → render · requestAnimationFrame runs before paint.

Trap: Saying setTimeout(fn, 0) runs 'immediately'. It runs after microtasks and at least one loop turn.

08async/await in the browserSequential awaits are the usual hidden slowness.~69s✓

How do you use async/await well on the client, including errors and cancellation?

async/await is syntax over promises. An async function always returns a promise, and await pauses only that function, not the page. The Node side, with unhandled rejections and error middleware, is on this card. On the client three things matter.

First, independent requests should not wait for each other.

// sequential: about 2 x the time
const user = await getUser(id);
const plan = await getPlan(id);
// parallel: both start now
const [u, p] = await Promise.all([getUser(id), getPlan(id)]);

Second, errors: fetch only rejects on a network failure. A 404 or a 500 still resolves, so I check res.ok and throw. Third, cancellation: when the user leaves a screen or types a new search, I pass an AbortController signal so an old response cannot overwrite the new one.

On the IELTS app, sign-in originally fetched progress topic by topic. I replaced that loop with one progress fetch into local storage, which is the same idea: fewer awaits in a row.

Bạn dùng async/await thế nào cho tốt ở client, kể cả lỗi và hủy request?

async/await là cú pháp trên promise. Function async luôn trả về promise, và await chỉ tạm dừng function đó, không dừng cả trang. Phía Node, với unhandled rejection và error middleware, ở card này. Ở client có ba điều quan trọng.

Thứ nhất, các request độc lập thì không nên đợi nhau.

// sequential: about 2 x the time
const user = await getUser(id);
const plan = await getPlan(id);
// parallel: both start now
const [u, p] = await Promise.all([getUser(id), getPlan(id)]);

Thứ hai, lỗi: fetch chỉ reject khi lỗi mạng. 404 hay 500 vẫn resolve, nên tôi kiểm tra res.ok rồi throw. Thứ ba, hủy request: khi user rời màn hình hoặc gõ tìm kiếm mới, tôi truyền signal của AbortController để response cũ không ghi đè response mới.

Trên app IELTS, lúc đăng nhập ban đầu progress được tải theo từng topic. Tôi thay vòng lặp đó bằng một lần fetch progress vào local storage, cũng cùng ý: bớt các await nối đuôi nhau.

Know: Sequential vs parallel · res.ok · AbortController · async always returns a promise.

Trap: await inside forEach. It does not wait; use for...of or Promise.all.

09Promise.all, allSettled, race, anyPick by what one failure should mean.~63s✓

What is the difference between Promise.all, allSettled, race and any?

All four take a list of promises. The difference is what counts as done.

Promise.all resolves with every result, in order, and rejects as soon as one rejects. I use it when I need all the pieces, like a screen that needs the user and the plan.

Promise.allSettled never rejects. It waits for all and gives each a status. I use it when partial success is fine, like a dashboard where one widget may fail.

Promise.race settles with the first one to settle, success or failure. The usual use is a timeout.

Promise.any resolves with the first success, and rejects with an AggregateError only if all fail. That fits trying two mirrors.

const results = await Promise.allSettled(urls.map(u => fetch(u)));
const ok = results.filter(r => r.status === 'fulfilled');

One thing people miss: when all rejects, the other requests keep running. To really stop them I need an AbortController.

Promise.all, allSettled, race và any khác nhau thế nào?

Cả bốn đều nhận một danh sách promise. Khác nhau ở chỗ thế nào thì coi là xong.

Promise.all resolve với mọi kết quả, đúng thứ tự, và reject ngay khi có một cái reject. Tôi dùng khi cần đủ mọi phần, ví dụ một màn hình cần cả user và plan.

Promise.allSettled không bao giờ reject. Nó đợi tất cả rồi trả status cho từng cái. Tôi dùng khi thành công một phần vẫn chấp nhận được, như dashboard mà một widget có thể lỗi.

Promise.race settle theo cái settle đầu tiên, dù thành công hay lỗi. Hay dùng để làm timeout.

Promise.any resolve với cái thành công đầu tiên, và chỉ reject bằng AggregateError khi tất cả đều lỗi. Hợp khi thử hai nguồn dự phòng.

const results = await Promise.allSettled(urls.map(u => fetch(u)));
const ok = results.filter(r => r.status === 'fulfilled');

Điều hay bị quên: khi all reject, các request còn lại vẫn chạy tiếp. Muốn dừng thật thì phải dùng AbortController.

Know: all = fail fast · allSettled = never rejects · race = first settled · any = first fulfilled.

Trap: Thinking Promise.all cancels the rest. Promises are not cancellable.

10Debounce vs throttleDebounce waits for quiet; throttle caps the rate.~69s✓

What is the difference between debounce and throttle, and when do you use each?

Both limit how often a function runs when an event fires a lot.

Debounce waits until the events stop for a set time, then runs once. Every new event restarts the timer. That fits a search box: I do not want a request on every key, only when the user pauses for about 300 milliseconds. It also fits auto-saving a draft or reacting to a window resize when it ends.

Throttle runs at most once per interval while events keep coming. That fits scroll position, infinite scroll checks, or tracking a drag, where I want regular updates but not sixty a second.

// debounce: one call after 300 ms of quiet
const onSearch = debounce(q => fetchResults(q), 300);

In React the trap is creating the debounced function on every render, which creates a new timer each time. I keep it stable with useMemo or useRef, or debounce the value with a small useDebouncedValue hook, and clear the timer on unmount.

Debounce và throttle khác nhau thế nào, khi nào dùng cái nào?

Cả hai đều giới hạn số lần một function chạy khi sự kiện bắn liên tục.

Debounce đợi tới khi sự kiện ngừng trong một khoảng thời gian, rồi chạy một lần. Mỗi sự kiện mới khởi động lại timer. Hợp với ô tìm kiếm: tôi không muốn gửi request mỗi lần gõ phím, chỉ khi user dừng khoảng 300 mili giây. Cũng hợp với auto-save bản nháp, hoặc xử lý resize khi đã kéo xong.

Throttle chạy nhiều nhất một lần trong mỗi khoảng thời gian, trong lúc sự kiện vẫn tới. Hợp với vị trí scroll, kiểm tra infinite scroll, hoặc theo dõi thao tác kéo, khi tôi cần cập nhật đều đặn nhưng không phải sáu mươi lần một giây.

// debounce: one call after 300 ms of quiet
const onSearch = debounce(q => fetchResults(q), 300);

Bẫy trong React là tạo function debounce mới ở mỗi lần render, mỗi lần lại một timer mới. Tôi giữ nó ổn định bằng useMemo hoặc useRef, hoặc debounce giá trị bằng một hook nhỏ useDebouncedValue, và clear timer khi unmount.

Know: Debounce = after quiet · throttle = steady rate · stable reference in React · clear on unmount.

Trap: Debouncing a search and still not cancelling the old request. Debounce reduces calls; it does not fix out-of-order responses.

11Shallow vs deep copySpread copies one level. structuredClone goes all the way.~59s✓

What is the difference between a shallow and a deep copy? How do you deep copy?

A shallow copy creates a new outer object, but nested objects are still shared. Spread, Object.assign and Array.slice are all shallow.

const a = { user: { name: 'Thuy' } };
const b = { ...a };
b.user.name = 'An';   // a.user.name is 'An' too
const c = structuredClone(a); // fully separate

For a deep copy I use structuredClone, which is built into modern browsers and Node. It handles nested objects, arrays, Dates, Maps, Sets and circular references. It does not copy functions, DOM nodes or class prototypes.

The old trick, JSON.parse(JSON.stringify(x)), drops undefined and functions and turns a Date into a string. I avoid it now.

In React I rarely need a full deep copy. I copy only the path I change, so unchanged parts keep their reference and memoised children do not re-render.

Shallow copy và deep copy khác nhau thế nào? Deep copy bằng cách nào?

How do you use map, filter and reduce, and why does immutability matter?

map turns each item into a new item, same length. filter keeps items that pass a test. reduce folds the list into one value, like a total or a lookup object. All three return something new and leave the original array alone.

const total = costs
  .filter(c => c.pondId === pondId)
  .reduce((sum, c) => sum + c.amount, 0);

That is the shape of a per-pond cost total, like the season costs on Aquanix.

Immutability matters because React decides whether to re-render by comparing references. If I push into a state array, the reference is the same and the screen may not update. So I write [...items, newItem], or the newer toSorted, toReversed and with, which return copies. sort and reverse mutate in place, which surprises people.

I use reduce when it is clearer than a loop, not to show off. A plain for...of is fine.

Bạn dùng map, filter, reduce thế nào, và vì sao immutability quan trọng?

map biến mỗi phần tử thành phần tử mới, giữ nguyên độ dài. filter giữ phần tử thỏa điều kiện. reduce gộp cả danh sách thành một giá trị, như một tổng hoặc một object tra cứu. Cả ba đều trả về thứ mới và không đụng vào array gốc.

  .reduce((sum, c) => sum + c.amount, 0);

Đó là dạng tổng chi phí theo từng ao, giống phần chi phí mùa vụ trên Aquanix.

Tôi dùng reduce khi nó rõ hơn vòng lặp, không phải để khoe. Một vòng for...of bình thường cũng được.

13ES modules vs CommonJSimport/export is the standard; require is Node's older system.~64s✓

What is the difference between ES modules and CommonJS?

CommonJS is Node's original system: require and module.exports. It loads synchronously at runtime, so require can sit inside an if. ES modules are the language standard: import and export. Imports are static, so tools can see the whole dependency graph before running anything. That is what makes tree shaking work in a bundler.

// CommonJS
const express = require('express');
module.exports = { router };
// ESM
import express from 'express';
export { router };

Other differences: ESM is always strict mode, supports top-level await, and a dynamic import() returns a promise, which is how code splitting works.

In practice I write import syntax in all my TypeScript, on the Express APIs and in the Expo apps. What it compiles to depends on module in tsconfig and "type" in package.json. Current Node can also require a synchronous ES module, so mixing hurts less than it used to.

ES modules và CommonJS khác nhau thế nào?

CommonJS là hệ module gốc của Node: require và module.exports. Nó load đồng bộ lúc runtime, nên require đặt được trong if. ES modules là chuẩn của ngôn ngữ: import và export. Import là tĩnh, nên tool thấy được toàn bộ cây phụ thuộc trước khi chạy. Nhờ vậy bundler mới tree shaking được.

// CommonJS

// ESM

export { router };

Khác biệt khác: ESM luôn ở strict mode, hỗ trợ await ở top-level, và import() động trả về promise, đó là cách code splitting hoạt động.

Thực tế tôi viết cú pháp import trong toàn bộ code TypeScript, cả ở API Express lẫn app Expo. Nó được compile ra gì phụ thuộc vào module trong tsconfig và "type" trong package.json. Node hiện tại cũng require được ES module đồng bộ, nên trộn hai loại đỡ đau hơn trước.

14Garbage collection and memory leaksUnreachable is collected; leaks are things still reachable by mistake.~66s✓

How does garbage collection work in JavaScript, and what causes memory leaks in the browser?

The engine frees memory that nothing can reach any more. It starts from roots, like globals and the current call stack, marks everything reachable, and collects the rest. So a leak is not forgotten memory. It is something still reachable that I no longer need.

The common causes in a single-page app are listeners and timers that are never removed, a setInterval that keeps running after the component is gone, a subscription that is not closed, a cache or Map that only grows, and detached DOM nodes still held by a variable.

useEffect(() => {
  const id = setInterval(poll, 5000);
  window.addEventListener('resize', onResize);
  return () => { clearInterval(id); window.removeEventListener('resize', onResize); };
}, []);

The cleanup function is my main defence. To find a leak I take heap snapshots in Chrome DevTools before and after repeating an action, and compare what grew. For caches keyed by objects, a WeakMap lets entries go when the key goes.

Garbage collection trong JavaScript hoạt động thế nào, và cái gì gây memory leak trên trình duyệt?

Engine giải phóng vùng nhớ mà không còn gì truy cập tới được. Nó bắt đầu từ root, như biến global và call stack hiện tại, đánh dấu mọi thứ còn với tới được, rồi thu hồi phần còn lại. Nên leak không phải là bộ nhớ bị quên. Đó là thứ vẫn còn được tham chiếu dù tôi không cần nữa.

Nguyên nhân hay gặp trong single-page app là listener và timer không bao giờ được gỡ, setInterval vẫn chạy sau khi component đã mất, subscription không đóng, cache hay Map chỉ lớn lên, và DOM node đã bị gỡ nhưng vẫn bị một biến giữ.

useEffect(() => {
  const id = setInterval(poll, 5000);
  window.addEventListener('resize', onResize);
  return () => { clearInterval(id); window.removeEventListener('resize', onResize); };
}, []);

Hàm cleanup là cách phòng chính của tôi. Để tìm leak tôi chụp heap snapshot trong Chrome DevTools trước và sau khi lặp lại một thao tác, rồi so xem cái gì tăng. Với cache dùng object làm key, WeakMap cho phép entry tự mất khi key mất.

15Event bubbling and delegationOne listener on the parent instead of one per row.~65s✓

What is event bubbling, and what is event delegation?

When I click an element, the event first travels down from the window to the target, the capture phase, and then bubbles back up through every ancestor. Most listeners run in the bubble phase.

Event delegation uses bubbling. Instead of a listener on every row of a long list, I put one listener on the parent and check event.target to see which row was clicked. It uses less memory, and rows added later work without new listeners.

list.addEventListener('click', (e) => {
  const row = e.target.closest('[data-id]');
  if (row) openItem(row.dataset.id);
});

target is what was actually clicked, maybe an icon inside the row. currentTarget is the element the listener sits on. That is why I use closest.

stopPropagation stops the bubbling, and preventDefault stops the browser's default action, like a form submit. They are different things. React already delegates: it attaches listeners at the root, so I mostly use this in plain JavaScript.

Event bubbling là gì, và event delegation là gì?

Khi tôi click một phần tử, sự kiện đi xuống từ window tới phần tử đích, gọi là capture phase, rồi nổi ngược lên qua từng phần tử cha, gọi là bubbling. Phần lớn listener chạy ở pha bubble.

Event delegation tận dụng bubbling. Thay vì gắn listener cho từng dòng của một danh sách dài, tôi gắn một listener ở phần tử cha và kiểm tra event.target để biết dòng nào được click. Tốn ít bộ nhớ hơn, và dòng thêm vào sau vẫn chạy mà không cần listener mới.

  const row = e.target.closest('[data-id]');
  if (row) openItem(row.dataset.id);
});

target là thứ thực sự được click, có thể là icon bên trong dòng. currentTarget là phần tử gắn listener. Vì thế tôi dùng closest.

stopPropagation chặn bubbling, còn preventDefault chặn hành vi mặc định của trình duyệt, như submit form. Hai cái khác nhau. React đã tự delegate: nó gắn listener ở root, nên tôi chủ yếu dùng kỹ thuật này trong JavaScript thuần.

17type vs interfaceMostly interchangeable. Know the two real differences.~67s✓

When do you use type and when interface?

For describing an object shape they are nearly the same, and both can be extended. There are two real differences.

An interface can be declared twice and the two merge. That is useful for extending a library type, like adding user to Express's Request. A type alias cannot merge, but it can name anything: unions, tuples, primitives, mapped and conditional types.

interface Pond { id: string; name: string }
interface Pond { zoneId: string }        // merges
type Status = 'active' | 'harvested';     // only type can do this
type PondRow = Pond & { status: Status };

My habit is type by default, because most of my types are unions or built from other types, and interface when I need merging or when I write a public shape that others will extend. Some teams prefer interface for every object. That is fine. I follow the codebase rather than mixing both for the same thing.

Khi nào bạn dùng type, khi nào dùng interface?

Để mô tả shape của object thì hai cái gần như giống nhau, và đều mở rộng được. Có hai khác biệt thật.

interface khai báo hai lần thì hai lần đó gộp lại. Hữu ích khi mở rộng type của thư viện, ví dụ thêm user vào Request của Express. type alias không gộp được, nhưng đặt tên được cho mọi thứ: union, tuple, kiểu nguyên thủy, mapped type và conditional type.

18Unions and narrowingA union is 'one of these'; narrowing is how you prove which.~70s✓

What is a union type, and how does narrowing work?

A union says a value is one of several types, like string | number | null. On its own I can only use what all members share. Narrowing is how I prove to the compiler which member I have, using ordinary JavaScript checks.

function label(v: string | number | null) {
  if (v == null) return '-';
  if (typeof v === 'number') return v.toFixed(1);
  return v.trim();          // v is string here
}

The checks the compiler understands are typeof for primitives, instanceof for classes, in for a property, equality checks, truthiness, and Array.isArray. After each check, TypeScript knows the type in that branch.

When the logic is more complex, I write a type guard, a function that returns value is Pond. That is handy when filtering a list where some items failed to load.

What I avoid is as. A cast does not check anything. It just tells the compiler to trust me, and it moves the bug to runtime.

Union type là gì, và narrowing hoạt động thế nào?

Union nói rằng một giá trị là một trong nhiều kiểu, như string | number | null. Bản thân nó chỉ cho tôi dùng những gì mọi thành phần đều có. Narrowing là cách tôi chứng minh với compiler là tôi đang có thành phần nào, bằng chính các phép kiểm tra JavaScript bình thường.

function label(v: string | number | null) {
  if (v == null) return '-';
  if (typeof v === 'number') return v.toFixed(1);
  return v.trim();          // v is string here
}

Những phép kiểm tra compiler hiểu là typeof cho kiểu nguyên thủy, instanceof cho class, in cho property, so sánh bằng, kiểm tra truthy, và Array.isArray. Sau mỗi phép kiểm tra, TypeScript biết kiểu trong nhánh đó.

Khi logic phức tạp hơn, tôi viết type guard, một function trả về value is Pond. Rất tiện khi lọc một danh sách mà vài phần tử load lỗi.

Thứ tôi tránh là as. Ép kiểu không kiểm tra gì cả. Nó chỉ bảo compiler tin tôi, và đẩy lỗi sang runtime.

What is a discriminated union, and where is it useful?

What is the difference between any, unknown and never?

any switches type checking off for that value. I can call anything on it, and the compiler stays quiet, so errors spread silently. I treat it as a last resort.

unknown also accepts any value, but I cannot use it until I narrow it. It is the honest type for data from outside: JSON.parse, a request body, a caught error.

try { await save(); }
catch (err: unknown) {
  const msg = err instanceof Error ? err.message : String(err);
}

never is the type with no values. A function that always throws returns never. Its most useful job is the exhaustive check: in the default branch of a switch over a discriminated union, I assign the value to never.

default: {
  const unreachable: never = r; // error if a case is missing
  throw new Error('unhandled');
}

If someone adds a new status later, that line stops compiling. To keep myself honest I enable noImplicitAny through strict, and in catch blocks I use unknown.

any, unknown và never khác nhau thế nào?

any tắt kiểm tra kiểu cho giá trị đó. Tôi gọi gì trên nó cũng được và compiler im lặng, nên lỗi lan ra mà không ai biết. Tôi coi nó là lựa chọn cuối cùng.

unknown cũng nhận mọi giá trị, nhưng tôi không dùng được cho tới khi narrow nó. Đó là kiểu đúng cho dữ liệu từ bên ngoài: JSON.parse, request body, lỗi bắt được trong catch.

try { await save(); }
catch (err: unknown) {
  const msg = err instanceof Error ? err.message : String(err);
}

never là kiểu không có giá trị nào. Function luôn throw thì trả về never. Việc hữu ích nhất của nó là kiểm tra vét cạn: ở nhánh default của switch trên một discriminated union, tôi gán giá trị vào biến kiểu never.

default: {
  const unreachable: never = r; // error if a case is missing
  throw new Error('unhandled');
}

Nếu sau này có người thêm status mới, dòng đó sẽ không compile được. Để giữ kỷ luật, tôi bật noImplicitAny qua strict, và trong catch tôi dùng unknown.

22Utility typesDerive types from one source instead of copying fields.~76s✓

Which utility types do you use, and why?

Utility types build new types from existing ones, so I keep one source of truth instead of copying fields into five similar types.

type User = { id: string; name: string; role: Role; createdAt: Date };
type UpdateUser = Partial<Pick<User, 'name' | 'role'>>;
type NewUser    = Omit<User, 'id' | 'createdAt'>;
type ByRole     = Record<Role, User[]>;
type Session    = Awaited<ReturnType<typeof loadSession>>;

Partial makes every field optional, which fits a PATCH body. Pick keeps some fields and Omit removes some. A create body is usually the entity without id and timestamps. Record types an object map, like items grouped by role. ReturnType takes the type a function returns, and with Awaited it unwraps the promise, so I do not have to write the type twice.

Others I reach for are Required, Readonly, NonNullable and Parameters.

One caution. Partial on a PATCH says every field may be missing, but it still allows undefined values, and it says nothing about which fields a member is allowed to change. That rule belongs in the API, not in the type.

Bạn dùng những utility type nào, vì sao?

Utility type tạo type mới từ type có sẵn, nên tôi giữ một nguồn sự thật duy nhất thay vì copy field sang năm type na ná nhau.

type User = { id: string; name: string; role: Role; createdAt: Date };
type UpdateUser = Partial<Pick<User, 'name' | 'role'>>;
type NewUser    = Omit<User, 'id' | 'createdAt'>;
type ByRole     = Record<Role, User[]>;
type Session    = Awaited<ReturnType<typeof loadSession>>;

Partial làm mọi field thành tùy chọn, hợp với body của PATCH. Pick giữ một vài field, Omit bỏ một vài field. Body tạo mới thường là entity bỏ id và timestamp. Record định kiểu cho object dạng map, như danh sách nhóm theo role. ReturnType lấy kiểu mà function trả về, kết hợp với Awaited thì bóc luôn promise, nên tôi không phải viết type hai lần.

Những cái khác tôi hay dùng là Required, Readonly, NonNullable và Parameters.

Một lưu ý. Partial cho PATCH nói rằng field nào cũng có thể thiếu, nhưng vẫn cho phép giá trị undefined, và không nói gì về việc một member được sửa field nào. Luật đó thuộc về API, không thuộc về type.

Know: Partial · Pick · Omit · Record · ReturnType + Awaited · Readonly is shallow.

Trap: Omit with a misspelled key compiles silently; it does not check keys exist.

23Enums vs as constPrefer a const array or object plus a union.~66s✓

Do you use TypeScript enums, or something else?

I mostly use an as const array or object with a union type instead of enum.

export const ROLES = ['owner', 'manager', 'member'] as const;
export type Role = (typeof ROLES)[number]; // 'owner' | 'manager' | 'member'

Three reasons. It is plain JavaScript, so nothing extra is generated, and it works with tools that only strip types, like Node's built-in type stripping or isolatedModules builds. I get a real array to loop over, for a dropdown or for validation. And the values are the actual strings that go to the API and into Firestore, so there is no mapping layer.

Enums have quirks. A numeric enum accepts any number, and it creates a reverse mapping object at runtime. const enum has problems across module boundaries.

An enum is still fine in a codebase that already uses them, and string enums are not dangerous. I just would not start a new one with them.

Bạn có dùng enum của TypeScript không, hay dùng cách khác?

Tôi chủ yếu dùng array hoặc object as const kèm một union type thay cho enum.

export const ROLES = ['owner', 'manager', 'member'] as const;
export type Role = (typeof ROLES)[number]; // 'owner' | 'manager' | 'member'

Ba lý do. Đó là JavaScript thuần, nên không sinh thêm code gì, và chạy được với các tool chỉ xóa type, như type stripping có sẵn của Node hay build dùng isolatedModules. Tôi có một array thật để lặp, cho dropdown hoặc để validate. Và giá trị chính là chuỗi thật gửi lên API và lưu vào Firestore, nên không cần lớp ánh xạ.

Enum vẫn ổn trong codebase đã dùng sẵn, và string enum không nguy hiểm. Chỉ là tôi sẽ không bắt đầu dự án mới bằng enum.

24strict mode and strictNullChecksstrict is a bundle; strictNullChecks is the one that matters most.~69s✓

What does strict do in tsconfig, and why does strictNullChecks matter?

strict: true turns on a group of checks. The two that matter most are noImplicitAny, so a missing type is an error instead of silently becoming any, and strictNullChecks.

Without strictNullChecks, null and undefined fit into every type, so the compiler never warns about the most common runtime crash, reading a property of undefined. With it on, a value that may be missing has to be handled.

const user = users.find(u => u.id === id); // User | undefined
user.name;            // error under strictNullChecks
user?.name ?? 'Guest'; // fine

That forces the question at the right moment: what should the screen show when there is no user, or when a Firestore document does not exist yet?

I keep strict on in new projects. I also like noUncheckedIndexedAccess, which makes arr[0] possibly undefined. On an old codebase I would turn flags on one at a time and fix folder by folder, rather than one huge pull request.

strict trong tsconfig làm gì, và vì sao strictNullChecks quan trọng?

strict: true bật một nhóm kiểm tra. Hai cái quan trọng nhất là noImplicitAny, để thiếu type thì báo lỗi thay vì âm thầm thành any, và strictNullChecks.

Không có strictNullChecks, null và undefined lọt vào mọi kiểu, nên compiler không bao giờ cảnh báo lỗi runtime phổ biến nhất: đọc property của undefined. Bật lên thì giá trị có thể thiếu bắt buộc phải được xử lý.

const user = users.find(u => u.id === id); // User | undefined
user.name;            // error under strictNullChecks
user?.name ?? 'Guest'; // fine

Nó buộc tôi trả lời câu hỏi đúng lúc: màn hình nên hiện gì khi không có user, hoặc khi document Firestore chưa tồn tại?

Tôi luôn bật strict ở dự án mới. Tôi cũng thích noUncheckedIndexedAccess, làm cho arr[0] có thể là undefined. Với codebase cũ, tôi bật từng flag một và sửa theo từng thư mục, thay vì một pull request khổng lồ.

25Typing an API boundaryTypes vanish at runtime. Validate, then infer the type from the schema.~66s✓

How do you type data coming into your API or from another service?

TypeScript types are erased when the code is compiled. At runtime, req.body is whatever the client sent, and writing req.body as CreatePond checks nothing. So at every boundary, request bodies, webhook payloads, third-party responses, I validate at runtime with a schema library like zod, and I let the type come from the schema.

import { z } from 'zod';
const CreatePond = z.object({ name: z.string().min(1), zoneId: z.string() });
type CreatePond = z.infer<typeof CreatePond>;

const parsed = CreatePond.safeParse(req.body);
if (!parsed.success) return res.status(400).json(parsed.error.flatten());

Now there is one source of truth. If the schema changes, the type changes with it, and bad input gets a clear 400 instead of crashing three functions later.

Validation is one layer. On Aquanix, after the body is valid, the pond route still checks that this member is assigned to this pond. On PhysioFix, the inbound webhook is verified before anything else runs. Shape, then identity and access, then business rules.

Bạn định kiểu dữ liệu đi vào API hoặc từ service khác thế nào?

Type của TypeScript bị xóa khi compile. Lúc runtime, req.body là bất cứ gì client gửi lên, và viết req.body as CreatePond không kiểm tra gì cả. Nên ở mọi biên, request body, payload webhook, response của bên thứ ba, tôi validate lúc runtime bằng thư viện schema như zod, và để type sinh ra từ schema.

import { z } from 'zod';

Giờ chỉ có một nguồn sự thật. Schema đổi thì type đổi theo, và input sai nhận 400 rõ ràng thay vì làm sập ở ba function sau.

Validate chỉ là một lớp. Ở Aquanix, sau khi body hợp lệ, route ao vẫn kiểm tra member này có được gán vào ao này không. Ở PhysioFix, webhook gọi vào được xác thực trước khi làm bất cứ việc gì. Kiểm shape, rồi danh tính và quyền, rồi mới tới luật nghiệp vụ.

26Declaration merging and .d.ts filesBrief: .d.ts describes types for code that has none.~63s✓

What is a .d.ts file, and what is declaration merging?

A .d.ts file holds only types, no runtime code. It describes the shape of JavaScript that has no types of its own. Most libraries ship one, or there is a @types package. If neither exists, I write a small declare module 'lib-name' with just the parts I use.

Declaration merging is when two declarations with the same name combine. Interfaces merge, and so do namespaces. The practical use is adding a field to a library type.

// types/express.d.ts
declare global {
  namespace Express { interface Request { user?: { uid: string; role: Role } } }
}
export {};

After auth middleware verifies a token, the handler can read req.user with a type, instead of casting in every route. That fits the APIs I build, where the token carries a role.

I keep these augmentations few and in one folder, because a global type change affects every file.

File .d.ts là gì, và declaration merging là gì?

File .d.ts chỉ chứa type, không có code chạy. Nó mô tả shape của code JavaScript vốn không có type. Phần lớn thư viện có sẵn file này, hoặc có package @types. Nếu không có cả hai, tôi viết một declare module 'lib-name' nhỏ chỉ cho phần tôi dùng.

Declaration merging là khi hai khai báo cùng tên gộp lại với nhau. Interface gộp được, namespace cũng vậy. Ứng dụng thực tế là thêm field vào type của thư viện.

// types/express.d.ts
declare global {
  namespace Express { interface Request { user?: { uid: string; role: Role } } }
}

Sau khi middleware auth xác thực token, handler đọc được req.user có type, thay vì ép kiểu ở mọi route. Hợp với các API tôi làm, nơi token mang theo role.

Tôi giữ những phần mở rộng này ít và gom vào một thư mục, vì đổi type global ảnh hưởng tới mọi file.

27Cookies vs localStorage vs sessionStorageWhere the token lives is the real question.~73s✓

What is the difference between cookies, localStorage and sessionStorage? Where would you keep an auth token?

localStorage keeps data per origin until it is cleared. sessionStorage is the same, but per tab, and it is gone when the tab closes. Both are synchronous, hold a few megabytes, and are readable by any JavaScript on the page. Cookies are small, and the browser sends them with every matching request.

That last point decides where a token goes. Anything in localStorage can be stolen by one XSS bug. An HttpOnly cookie cannot be read by JavaScript at all.

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600

So in a browser app my preference is a session or refresh token in an HttpOnly, Secure, SameSite cookie, with a short-lived access token kept in memory. Because cookies are sent automatically, I then have to think about CSRF. SameSite covers most of it, and a CSRF token covers the rest.

A mobile app is different. There is no shared page script, and the OS keychain is the right place. The JWT checks on the server side are on this card.

Cookie, localStorage và sessionStorage khác nhau thế nào? Bạn sẽ giữ token đăng nhập ở đâu?

localStorage giữ dữ liệu theo origin cho tới khi bị xóa. sessionStorage cũng vậy, nhưng theo từng tab, và mất khi đóng tab. Cả hai đều đồng bộ, chứa vài megabyte, và mọi JavaScript trên trang đều đọc được. Cookie thì nhỏ, và trình duyệt tự gửi kèm với mọi request khớp điều kiện.

Điểm cuối cùng quyết định token nên nằm ở đâu. Thứ gì trong localStorage cũng có thể bị lấy mất chỉ bằng một lỗi XSS. Cookie HttpOnly thì JavaScript hoàn toàn không đọc được.

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600

Nên với app trên trình duyệt, tôi chọn để session hoặc refresh token trong cookie HttpOnly, Secure, SameSite, còn access token ngắn hạn giữ trong bộ nhớ. Vì cookie được gửi tự động, tôi phải tính tới CSRF. SameSite lo phần lớn, CSRF token lo phần còn lại.

App mobile thì khác. Không có script trang dùng chung, và keychain của hệ điều hành là chỗ đúng. Phần kiểm tra JWT phía server nằm ở card này.

Know: Storage = readable by JS · HttpOnly cookie = not readable · cookie brings CSRF · SameSite=Lax default in modern browsers.

Trap: Saying HttpOnly 'prevents XSS'. It stops token theft; an XSS can still make requests as the user.

28CORS and the preflightA browser rule. The server opts in with headers.~72s✓

What is CORS, and what is a preflight request?

The browser's same-origin policy stops a page from reading responses from another origin, meaning another scheme, host or port. CORS is how a server opts in. It sends headers saying which origins may read its responses.

For a simple GET, the browser sends the request and then checks Access-Control-Allow-Origin on the response. For anything else, a PATCH, a JSON body, an Authorization header, it first sends a preflight: an OPTIONS request asking for permission.

OPTIONS /api/ponds
Origin: https://admin.example.com
Access-Control-Request-Method: PATCH

204  Access-Control-Allow-Origin: https://admin.example.com
     Access-Control-Allow-Methods: GET, PATCH
     Access-Control-Allow-Headers: Authorization, Content-Type

Two points people get wrong. CORS is enforced by the browser, not the server. curl and Postman ignore it, and the request may already have reached the server. So CORS is not security for the API. Auth is. And with cookies, the origin must be exact, not *, plus Access-Control-Allow-Credentials: true.

On an Express API, the cors middleware takes an allowlist of origins per environment. How I debug a CORS error is on this card.

CORS là gì, và preflight request là gì?

Same-origin policy của trình duyệt chặn một trang đọc response từ origin khác, tức là khác scheme, host hoặc port. CORS là cách server đồng ý cho phép. Nó gửi header nói origin nào được đọc response.

Với GET đơn giản, trình duyệt gửi request rồi kiểm tra Access-Control-Allow-Origin trên response. Với các trường hợp khác, PATCH, body JSON, header Authorization, nó gửi preflight trước: một request OPTIONS để xin phép.

OPTIONS /api/ponds
Origin: https://admin.example.com
Access-Control-Request-Method: PATCH

204  Access-Control-Allow-Origin: https://admin.example.com
     Access-Control-Allow-Methods: GET, PATCH
     Access-Control-Allow-Headers: Authorization, Content-Type

Có hai điểm hay bị hiểu sai. CORS do trình duyệt thực thi, không phải server. curl và Postman bỏ qua nó, và request có thể đã tới server rồi. Nên CORS không phải là bảo mật cho API. Auth mới là bảo mật. Và khi dùng cookie, origin phải ghi chính xác, không được *, kèm Access-Control-Allow-Credentials: true.

Với API Express, middleware cors nhận danh sách origin được phép theo từng môi trường. Cách tôi debug lỗi CORS nằm ở card này.

Know: Same-origin policy · server opts in · preflight = OPTIONS for non-simple requests · browser-only.

Trap: 'Fixing' CORS with * on an API that uses cookies. It will not work, and it is the wrong instinct.

29What happens when you load a pageDNS to pixels, then name what blocks rendering.~70s✓

What happens when you type a URL and press Enter? What is the critical rendering path?

The browser resolves the domain with DNS, opens a TCP or QUIC connection, does the TLS handshake, and sends the HTTP request. The server, or a CDN, returns the HTML.

Then the critical rendering path. The browser parses HTML into the DOM. When it meets CSS, it builds the CSSOM, and it will not paint until that CSS is ready, so CSS is render-blocking. A plain <script> stops HTML parsing until it is downloaded and run. That is why I use defer or modules. DOM and CSSOM combine into the render tree, then layout works out sizes and positions, then paint and compositing put pixels on screen.

After that, JavaScript runs and the app fetches data, which can change the layout again.

To make the first view faster: keep critical CSS small, defer scripts, preload the main image or font, and send less JavaScript. For a single-page app, rendering the first view on the server, like Next.js does, shortens the time to first content.

Chuyện gì xảy ra khi bạn gõ URL và nhấn Enter? Critical rendering path là gì?

Trình duyệt phân giải tên miền qua DNS, mở kết nối TCP hoặc QUIC, bắt tay TLS, rồi gửi HTTP request. Server, hoặc CDN, trả về HTML.

Sau đó là critical rendering path. Trình duyệt parse HTML thành DOM. Gặp CSS thì nó dựng CSSOM, và sẽ không vẽ gì cho tới khi CSS sẵn sàng, nên CSS chặn render. Thẻ <script> thường dừng việc parse HTML cho tới khi tải và chạy xong. Vì thế tôi dùng defer hoặc module. DOM và CSSOM ghép thành render tree, rồi layout tính kích thước và vị trí, rồi paint và composite đưa pixel lên màn hình.

Sau đó JavaScript chạy và app lấy dữ liệu, có thể làm layout thay đổi lần nữa.

Để màn hình đầu hiện nhanh hơn: giữ CSS quan trọng nhỏ, defer script, preload ảnh chính hoặc font, và gửi ít JavaScript hơn. Với single-page app, render màn hình đầu ở server như Next.js giúp rút ngắn thời gian tới nội dung đầu tiên.

Know: DNS → connect → TLS → HTML → DOM + CSSOM → render tree → layout → paint → composite.

Trap: Saying async and defer are the same. defer keeps order and runs after parsing.

30Core Web VitalsLCP, INP, CLS: what each means and one fix for each.~78s✓

What are Core Web Vitals, and how would you improve one?

Three metrics Google uses for real user experience, measured at the 75th percentile.

LCP, Largest Contentful Paint: when the biggest thing in view, usually a hero image or a heading, appears. Good is under 2.5 seconds. INP, Interaction to Next Paint: how long the page takes to respond visually to a click or a key. It replaced FID. Good is under 200 milliseconds. CLS, Cumulative Layout Shift: how much the page jumps while loading. Good is under 0.1.

For LCP, I find the LCP element, make sure it is not lazy-loaded, give it high priority, and serve it compressed and sized. For CLS, every image and embed gets width and height so space is reserved.

<img src="hero.webp" fetchpriority="high" width="1200" height="600" alt="">
<img src="row.webp" loading="lazy" width="400" height="300" alt="">

INP is about long tasks on the main thread. I break up heavy handlers, debounce input, and in React move non-urgent updates into startTransition.

I measure first, with Lighthouse for lab data and the web-vitals library or Search Console for real users. Lab numbers on a fast laptop hide what a cheap phone sees.

Core Web Vitals là gì, và bạn sẽ cải thiện một chỉ số như thế nào?

Ba chỉ số Google dùng để đo trải nghiệm người dùng thật, tính ở phân vị 75.

LCP, Largest Contentful Paint: lúc phần tử lớn nhất trong khung nhìn, thường là ảnh banner hoặc tiêu đề, hiện ra. Tốt là dưới 2,5 giây. INP, Interaction to Next Paint: trang mất bao lâu để phản hồi trên màn hình sau một cú click hay phím bấm. Nó thay thế FID. Tốt là dưới 200 mili giây. CLS, Cumulative Layout Shift: trang bị nhảy bao nhiêu trong lúc tải. Tốt là dưới 0,1.

Với LCP, tôi tìm phần tử LCP, đảm bảo nó không bị lazy-load, cho nó độ ưu tiên cao, và phục vụ ảnh đã nén, đúng kích thước. Với CLS, mọi ảnh và phần nhúng đều có width và height để giữ chỗ trước.

How do HTTP caching headers work? Explain Cache-Control and ETag.

Cache-Control tells the browser and any CDN how long a response stays fresh. max-age is the lifetime in seconds. no-cache means the cache may keep it but must check with the server before using it. no-store means do not keep it at all, which is for private data. private means only the browser may cache it, not a shared CDN.

An ETag is a version tag for the content. When the cached copy needs checking, the browser sends If-None-Match with that tag. If nothing changed, the server answers 304 Not Modified with no body, which saves the download.

# app.3f9a1c.js (hashed file name)
Cache-Control: public, max-age=31536000, immutable
# index.html
Cache-Control: no-cache
ETag: "v42"
# next visit: If-None-Match: "v42"  ->  304 Not Modified

That pattern is how I think about a frontend deploy. Bundled files have a content hash in their name, so they can be cached for a year. index.html must be revalidated, or users keep loading an old bundle. When users still see old data after a deploy, I go through these checks.

Header cache HTTP hoạt động thế nào? Giải thích Cache-Control và ETag.

Cache-Control cho trình duyệt và CDN biết response còn mới trong bao lâu. max-age là thời gian sống tính bằng giây. no-cache nghĩa là cache được giữ, nhưng phải hỏi lại server trước khi dùng. no-store nghĩa là không được giữ gì cả, dành cho dữ liệu riêng tư. private nghĩa là chỉ trình duyệt được cache, CDN dùng chung thì không.

ETag là nhãn phiên bản của nội dung. Khi bản cache cần kiểm tra lại, trình duyệt gửi If-None-Match kèm nhãn đó. Nếu không có gì thay đổi, server trả 304 Not Modified không có body, đỡ phải tải lại.

# app.3f9a1c.js (hashed file name)
Cache-Control: public, max-age=31536000, immutable
# index.html
Cache-Control: no-cache
ETag: "v42"
# next visit: If-None-Match: "v42"  ->  304 Not Modified

Đó là cách tôi nghĩ về một lần deploy frontend. File đã bundle có hash nội dung trong tên, nên cache một năm được. index.html thì phải được kiểm tra lại, nếu không user cứ tải bundle cũ. Khi user vẫn thấy dữ liệu cũ sau deploy, tôi đi qua các bước kiểm tra này.

Know: max-age · no-cache = revalidate · no-store = never keep · private vs public · ETag + If-None-Match → 304.

32XSS and CSP on the frontendNever turn user text into HTML; CSP is the second wall.~74s✓

What is XSS, and how do you prevent it on the frontend? What does a CSP do?

XSS is when an attacker gets their script to run on my page, usually by getting user-controlled text inserted as HTML. Once it runs, it acts as the user: it can read anything JavaScript can read and call the API with the user's session.

The first defence is not creating HTML from strings. React escapes text in JSX by default, so the risky spots are dangerouslySetInnerHTML, innerHTML, and URLs like javascript: in an href. If I must render user HTML, for example rich text, I sanitise it with a library like DOMPurify first.

The second defence is a Content Security Policy, a response header that tells the browser which sources may run scripts.

Content-Security-Policy: default-src 'self';
  script-src 'self'; object-src 'none'; base-uri 'self';
  connect-src 'self' https://api.example.com

With no inline scripts allowed, an injected <script> simply does not run. A strict CSP with nonces is stronger than a long domain allowlist. I start with Content-Security-Policy-Report-Only to see what would break, then enforce. Keeping tokens in HttpOnly cookies limits the damage too.

XSS là gì, và bạn phòng nó ở frontend thế nào? CSP làm gì?

XSS là khi kẻ tấn công làm cho script của họ chạy trên trang của tôi, thường bằng cách đưa đoạn text do user kiểm soát vào trang dưới dạng HTML. Khi đã chạy, nó hành động như chính user: đọc được mọi thứ JavaScript đọc được và gọi API bằng session của user.

Lớp phòng thủ đầu tiên là không tạo HTML từ chuỗi. React mặc định escape text trong JSX, nên chỗ rủi ro là dangerouslySetInnerHTML, innerHTML, và URL kiểu javascript: trong href. Nếu bắt buộc phải render HTML của user, ví dụ rich text, tôi sanitize trước bằng thư viện như DOMPurify.

Lớp thứ hai là Content Security Policy, một header của response cho trình duyệt biết nguồn nào được phép chạy script.

Content-Security-Policy: default-src 'self';
  script-src 'self'; object-src 'none'; base-uri 'self';
  connect-src 'self' https://api.example.com

Khi không cho phép inline script, thẻ <script> bị chèn vào đơn giản là không chạy. CSP chặt dùng nonce mạnh hơn một danh sách domain dài. Tôi bắt đầu bằng Content-Security-Policy-Report-Only để xem cái gì sẽ hỏng, rồi mới bật thật. Giữ token trong cookie HttpOnly cũng giới hạn thiệt hại.

Know: Stored, reflected, DOM-based · React escapes by default · sanitise rich HTML · CSP with nonces · report-only first.

Trap: Thinking server-side validation alone stops XSS. Output encoding at render time is what stops it.
