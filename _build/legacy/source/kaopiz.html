11. VM vs Cloud Run vs GKE

Show decision thinking.

Question EN
Answer EN
Question VI
Answer VI

When would you choose a VM, Cloud Run, or Kubernetes?

I think in tradeoffs. A VM is simple when you need full control or long-running custom setups. Cloud Run is great for containerized apps that scale with traffic and you don’t want to manage nodes. Kubernetes or GKE fits when you have many services, complex networking, and a team ready to operate the cluster. For many web backends I’ve worked with, Cloud Run hits a sweet spot.

Khi nào chọn VM, Cloud Run hay Kubernetes?

Tôi nghĩ theo tradeoff. VM hợp khi cần kiểm soát đầy đủ hoặc setup lâu dài, tùy biến. Cloud Run hợp app container, scale theo traffic và không muốn quản lý node. Kubernetes/GKE hợp khi nhiều service, networking phức tạp và team sẵn sàng vận hành cluster. Với nhiều web backend tôi từng làm, Cloud Run là điểm cân bằng tốt.

Know: Match runtime needs to ops cost: control vs convenience vs complexity.

Trap: Saying “Kubernetes always” without ops cost is a red flag.

Follow-up: What are Cloud Run’s limitations?

VPC vocabulary.

Explain VPC, subnet, firewall, and load balancer.

A VPC is your private network in the cloud. Subnets split that network, usually by region or tier. Firewall rules control what traffic is allowed. A load balancer distributes traffic to healthy backends. In interviews I keep it practical: isolate environments, open only needed ports, and put public entry points behind a load balancer when needed.

Giải thích VPC, subnet, firewall và load balancer.

VPC là mạng riêng trên cloud. Subnet chia mạng đó, thường theo region hoặc tầng. Firewall rule quyết định traffic nào được phép. Load balancer phân phối traffic tới backend khỏe. Trong interview tôi nói thực tế: tách môi trường, chỉ mở port cần thiết, và đặt cổng vào public sau load balancer khi cần.

Know: Private network + segmentation + allow rules + traffic distribution.

Trap: Don’t say firewall = security complete. IAM and app auth still matter.

What is IAM and least privilege?

IAM decides who can do what on which resource. Least privilege means giving only the permissions needed for the job — no more. In practice I prefer service accounts for apps, human users with limited roles, and reviewing wide roles like Owner or Admin carefully.

IAM và least privilege là gì?

IAM quyết định ai được làm gì trên resource nào. Least privilege nghĩa là chỉ cấp đúng quyền cần cho việc — không hơn. Thực tế tôi ưu tiên service account cho app, user người với role giới hạn, và thận trọng với role rộng như Owner/Admin.

Know: Identity + permission binding on resources.

Trap: Using Owner everywhere “to make it work” is a common trap.

Follow-up: What’s the difference between a user account and a service account?

15. Serverless concepts

Pros and ops tradeoffs.

Question EN
Answer EN
Question VI
Answer VI

What is serverless, and when is it a good fit?

Serverless means you deploy code or containers and the platform handles most scaling and server management. Cloud Run is close to that model for containers. It’s great for variable traffic and faster ops. The tradeoff is less low-level control, cold starts in some cases, and you need to design for request-driven or event-driven limits.

Serverless là gì và khi nào hợp?

Serverless là bạn deploy code hoặc container, còn platform lo phần lớn scale và quản lý server. Cloud Run gần với model đó cho container. Hợp traffic biến động và giảm ops. Tradeoff là ít kiểm soát tầng thấp, đôi khi cold start, và phải thiết kế theo giới hạn request/event-driven.

Know: Managed scale + less server babysitting.

Trap: Serverless ≠ zero ops. Still need IAM, networking, monitoring, cost control.

Follow-up: How do you debug a serverless service in production?

Walk me through a basic Terraform workflow.

Usually: write config, run terraform init to set up providers and backend, terraform plan to preview changes, then terraform apply after review. In a team, plan output matters a lot — you want people to see what will change before it hits prod.

Quy trình Terraform cơ bản thế nào?

Thường là: viết config, terraform init để setup provider và backend, terraform plan để xem trước thay đổi, rồi terraform apply sau khi review. Trong team, output của plan rất quan trọng — mọi người cần thấy sẽ đổi gì trước khi đụng prod.

Know: init sets up; plan previews; apply changes real infra.

What is Terraform state, and why does remote state matter?

State is Terraform’s memory of what it manages and the real resource IDs. Local state is fine for learning, but teams need remote state — usually in object storage with locking — so people don’t overwrite each other and so CI can use the same source of truth.

State của Terraform là gì và vì sao cần remote state?

State là bộ nhớ của Terraform về những gì nó quản lý và ID resource thật. Local state ổn để học, nhưng team cần remote state — thường trên object storage kèm locking — để không ghi đè nhau và CI dùng chung một nguồn sự thật.

Know: State maps config to real cloud resources.

Trap: Editing state by hand or sharing local state files casually is dangerous.

Follow-up: What is state locking and why does it matter?

What are Terraform modules?

Modules are reusable packages of Terraform config — like functions for infra. You put common patterns in a module, then call it for each environment or project with different variables. It helps keep things consistent and avoids copy-paste.

Module trong Terraform là gì?

Module là gói config Terraform tái sử dụng — giống hàm cho hạ tầng. Bạn gom pattern chung vào module, rồi gọi cho từng môi trường hoặc dự án với biến khác nhau. Giúp đồng nhất và tránh copy-paste.

Know: Reusable building blocks with inputs/outputs.

Trap: Giant modules that do everything become hard to change.

Can you explain Docker?

Docker packages an app with its dependencies into an image. A container is a running instance of that image. So instead of “works on my machine,” the team shares a more reproducible runtime. In cloud work it makes builds and deploys more predictable.

Bạn giải thích Docker thế nào?

Docker đóng gói app cùng dependency thành image. Container là instance đang chạy của image đó. Thay vì “máy tôi chạy được,” team có runtime dễ tái tạo hơn. Trong cloud, nó giúp build và deploy dễ dự đoán hơn.

Know: Image = package; container = running process from image.

Trap: Docker ≠ Kubernetes. Docker is packaging/runtime; K8s orchestrates.

How do volumes and networking work in Docker, at a practical level?

Volumes keep data outside the container lifecycle — useful for databases or files you don’t want to lose when the container restarts. Networking lets containers talk to each other and to the host. In real work I care most about: what must persist, which ports are exposed, and how services find each other.

Volume và networking trong Docker thực tế thế nào?

Volume giữ data ngoài vòng đời container — hữu ích cho database hoặc file không muốn mất khi restart. Networking để container nói chuyện với nhau và với host. Thực tế tôi quan tâm nhất: cái gì phải persist, port nào expose, và service tìm nhau thế nào.

Know: Persist data with volumes; connect services with networks/ports.

Trap: Storing important data only in the writable container layer.

Follow-up: How would you give one container access to another’s port?

What is CI/CD?

CI is continuously integrating and verifying changes — usually build and test on every push. CD is getting those verified changes to environments in a repeatable way. The point isn’t the tool name. It’s fewer manual mistakes and faster, safer releases.

CI/CD là gì?

CI là liên tục tích hợp và kiểm tra thay đổi — thường build/test mỗi lần push. CD là đưa thay đổi đã verify lên môi trường một cách lặp lại được. Điểm chính không phải tên tool. Là giảm lỗi tay và release nhanh, an toàn hơn.

Know: CI = verify often; CD = deliver repeatably.

Trap: Calling any deploy script “full CI/CD” without tests or promotion rules.

Follow-up: What’s the difference between continuous delivery and continuous deployment?

What is multi-environment deployment and why does it matter?

It means separate environments like dev, staging, and production. You promote changes instead of developing straight on prod. That reduces risk and makes debugging easier, because you can compare “works in staging, fails in prod” with config and data differences in mind.

Multi-environment deployment là gì và vì sao quan trọng?

Nghĩa là có các môi trường tách như dev, staging, production. Bạn promote thay đổi thay vì code thẳng lên prod. Giảm rủi ro và debug dễ hơn, vì có thể so “staging chạy, prod lỗi” với khác biệt config và data.

Know: Promote through environments to reduce blast radius.

Trap: Same names, different hidden config — silent drift.

Follow-up: How do you keep env parity without making staging identical to prod data?

What’s the difference between monitoring, logging, and tracing?

Monitoring watches health with metrics and alerts — CPU, latency, error rate. Logging records detailed events for investigation. Tracing follows a request across services. Monitoring tells you something’s wrong; logs and traces help explain why.

Khác nhau giữa monitoring, logging và tracing?

Monitoring theo dõi sức khỏe bằng metric và alert — CPU, latency, error rate. Logging ghi sự kiện chi tiết để điều tra. Tracing lần theo một request qua các service. Monitoring nói có vấn đề; log và trace giúp giải thích vì sao.

Know: Metrics detect; logs explain; traces connect the path.

Trap: Only collecting logs with no alerts — you find out from users.

Follow-up: What is observability vs traditional monitoring?

What metrics would you alert on?

It depends on the service, but I usually start with: is it up, error rate, latency, and saturation — CPU, memory, disk, connection pools. For user-facing apps I’d also watch request success rate. Alerts should be actionable. Too many noisy alerts and people ignore them.

Bạn sẽ alert những metric nào?

Tùy service, nhưng tôi thường bắt đầu: còn sống không, error rate, latency, và saturation — CPU, memory, disk, connection pool. App user-facing thì thêm tỉ lệ request thành công. Alert phải actionable. Nhiễu quá thì mọi người bỏ qua.

Know: Golden signals mindset: latency, traffic, errors, saturation.

Trap: Alerting on every tiny CPU blip.

How do you choose between Cloud Logging, Loki, ELK, or Graylog?

How do you handle an incident?

Detect, triage impact, mitigate first if users are hurting, then find root cause. After recovery I like a short write-up: what happened, what we changed, and how to prevent it. Blameless is important — fix the system, not the person.

Bạn xử lý incident thế nào?

Phát hiện, đánh giá impact, giảm thiệt hại trước nếu user đang bị ảnh hưởng, rồi tìm root cause. Sau khi phục hồi tôi thích ghi ngắn: chuyện gì xảy ra, đã đổi gì, và cách phòng. Blameless quan trọng — sửa hệ thống, không đổ lỗi người.

Know: Mitigate impact before perfect root cause.

Trap: Debugging forever while users stay down.

Follow-up: What’s the difference between an incident and a known bug?

How do you debug a network connectivity issue?

I ask: can we resolve DNS, can we reach the IP, is the port open, and is the app listening? Tools like ping, curl, dig or nslookup, and checking firewall rules help narrow it. A lot of “network bugs” are actually DNS, TLS, or security group mistakes.

Bạn debug lỗi kết nối mạng thế nào?

Tôi hỏi: resolve DNS được không, tới được IP không, port mở không, app có đang listen không? ping, curl, dig/nslookup và kiểm tra firewall giúp thu hẹp. Nhiều “lỗi mạng” thực ra là DNS, TLS, hoặc security group.

Know: DNS → route → port → process listening.

Trap: Blaming the network before checking the app is down.

How do you use SSH, file permissions, and systemd in daily work?

SSH is how I get onto servers securely — keys preferred over passwords. Permissions and ownership matter so services can read configs but random users can’t. systemd manages services: start, stop, enable on boot, and inspect status. Together they’re the basics of keeping a Linux box operable.

SSH, permission và systemd dùng thế nào trong việc hằng ngày?

SSH để vào server an toàn — ưu tiên key hơn password. Permission và ownership để service đọc được config nhưng user linh tinh thì không. systemd quản lý service: start, stop, enable lúc boot, xem status. Đó là nền tảng giữ Linux vận hành được.

Know: Access + permission boundary + service lifecycle.

How should secrets be managed?

Don’t put secrets in git or plain env files that get copied around. Prefer a secret manager or at least encrypted CI secrets, rotate when people leave, and give apps only what they need. If something leaks, rotate first, then investigate.

Nên quản lý secret thế nào?

Đừng để secret trong git hay file env plaintext chuyền tay. Ưu tiên secret manager hoặc ít nhất secret mã hóa trên CI, rotate khi người nghỉ, và app chỉ nhận đúng thứ cần. Nếu lộ, rotate trước rồi mới điều tra.

Know: Store secrets centrally; inject at runtime; rotate.

Trap: Committing .env with production credentials.

Follow-up: Where would you store a database password for Cloud Run?
