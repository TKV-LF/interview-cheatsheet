05Migrating a legacy database to MySQLBackup, cutover, validate reads and writes, document.~60s✓

Tell me about the database migration you did at Akktis.

At Akktis, one client system ran on a legacy custom database that was hard to support. I migrated it to MySQL on an Apache Linux server. I treated it as an operations change more than a data copy. Before the cutover I took backups, so we had a known point to go back to. After the cutover I validated that the application could still read and write the data it needed, on the paths users actually take, not just that the tables existed. Then I wrote down the new ops path: where the database lives, how it is backed up, and how to restart and check it, so support did not depend on one person. The lesson I took from it is that a migration is finished when someone else can run the new system, not when the data has moved.

Bạn kể về lần migrate database ở Akktis.

Ở Akktis, một hệ thống của khách hàng chạy trên một database tự xây đã cũ và khó hỗ trợ. Tôi migrate nó sang MySQL trên server Linux chạy Apache. Tôi coi đây là một thay đổi vận hành hơn là chỉ chép dữ liệu. Trước khi cutover, tôi backup để có một điểm chắc chắn có thể quay về. Sau khi cutover, tôi kiểm tra ứng dụng vẫn đọc và ghi được đúng dữ liệu cần thiết, trên chính những luồng người dùng hay đi, chứ không chỉ kiểm tra là bảng đã tồn tại. Sau đó tôi viết lại cách vận hành mới: database nằm ở đâu, backup thế nào, restart và kiểm tra ra sao, để việc hỗ trợ không phụ thuộc vào một người. Bài học tôi rút ra là một lần migrate chỉ xong khi người khác vận hành được hệ thống mới, chứ không phải khi dữ liệu đã chuyển xong.

06PhysioFix: a VM and Cloud RunCloud Build to a VM and to Cloud Run. Answer the webhook first.~61s✓

How is PhysioFix deployed, and what do you check after a deploy?

PhysioFix is a phone reservation service. The call audio stays on Twilio and Grok voice, and my Express service is the control path. Cloud Build deploys the voice process to a Compute Engine VM over HTTPS, with restart on failure, and also to Cloud Run. The Next.js admin deploys separately to Cloud Run. Operationally, the one rule that matters is the webhook. The handler checks the webhook secret, answers 200 right away, and only then opens the realtime socket for the call. A wrong secret gets a 401. Express must answer the webhook before it does any other work, because webhook providers expect a fast answer and will not wait for slow setup. So when I verify a deploy, I check that the webhook still answers quickly with the right status, and that the process comes back by itself if it crashes.

PhysioFix được deploy thế nào, và sau khi deploy bạn kiểm tra gì?

PhysioFix là dịch vụ đặt lịch qua điện thoại. Âm thanh cuộc gọi nằm ở Twilio và Grok voice, còn service Express của tôi là đường điều khiển. Cloud Build deploy process giọng nói lên một VM Compute Engine qua HTTPS, có cơ chế tự khởi động lại khi lỗi, và deploy cả lên Cloud Run. Trang admin viết bằng Next.js được deploy riêng lên Cloud Run. Về vận hành, quy tắc quan trọng nhất là webhook. Handler kiểm tra webhook secret, trả 200 ngay, rồi mới mở realtime socket cho cuộc gọi. Secret sai thì trả 401. Express phải trả lời webhook trước khi làm bất cứ việc gì khác, vì bên gửi webhook cần câu trả lời nhanh và sẽ không chờ phần khởi tạo chậm. Nên khi kiểm tra một lần deploy, tôi xem webhook vẫn trả lời nhanh với đúng status, và process tự chạy lại được nếu bị crash.

Walk me through how Aquanix gets released.

Aquanix is an Expo app with an Express API for pond operations. The release has two stages. A push to the dev branch triggers Cloud Build, which deploys the API to Cloud Run and the web export to a staging Firebase Hosting site. I check the staging site against the new API. Production web, aquanix.co, is a separate, manual Hosting release that I do only after that check, so nothing reaches customers just because a commit landed. API errors go to Sentry, so after a release I watch for new error groups, not only whether the revision is up. A user token cannot start the batch worker, and the cron credential cannot act as a user.

10What is DevOps?Ownership from commit to production, plus fast feedback.~57s✓

What does DevOps mean to you?

For me DevOps means the people who build a system also own how it reaches production and how it behaves there. Tools support that: CI, automated deploys, logs, alerts. But the core is a short, safe path from commit to production, and fast feedback when something breaks. In practice I judge it with a few questions. Can we deploy on any day without a hero? Can we tell within minutes that a release is bad? Can we roll back without a meeting? Can a new person follow the runbook? That is how I worked at Akktis: I maintained the pipelines, deployed, checked the new revision, and wrote the runbook, instead of handing the release to someone else. Installing a CI product is not DevOps if nobody owns what happens after the deploy.

Với bạn, DevOps là gì?

Với tôi, DevOps nghĩa là người xây hệ thống cũng chịu trách nhiệm đưa nó lên production và cách nó chạy trên đó. Công cụ chỉ hỗ trợ: CI, deploy tự động, log, cảnh báo. Cốt lõi là một con đường ngắn và an toàn từ commit đến production, và phản hồi nhanh khi có gì hỏng. Thực tế tôi đánh giá bằng vài câu hỏi. Người mới có làm theo runbook được không? Ở Akktis tôi làm đúng như vậy: tôi duy trì pipeline, deploy, kiểm tra revision mới và viết runbook, chứ không giao release cho người khác. Cài một công cụ CI không phải là DevOps nếu không ai chịu trách nhiệm cho những gì xảy ra sau khi deploy.

Know: The DORA metrics measure this: deployment frequency, lead time for changes, change failure rate, and time to restore service.

11CI vs CD, and the stages of a pipelineIntegration, delivery, deployment. Ask which CD they mean.~63s✓

Explain CI/CD. What stages should a pipeline have?

Continuous integration means every change is merged often and verified automatically: install, build, lint, test. Continuous delivery means every green build produces an artifact that could go to production at any time, with a person pressing the button. Continuous deployment goes one step further and releases every green build without the button. So when someone says "we do CD", I ask which one. The stages I expect are: check out, install from the lockfile, lint and test, build one artifact tagged with the version, push it to a registry, deploy to staging, run a smoke check, then promote that same artifact to production. Aquanix is a good example of delivery rather than deployment: Cloud Build deploys staging automatically, and production web is a manual release after I check it. Without tests, CI is mostly packaging, so I am honest about how much testing a pipeline really has.

Bạn giải thích CI/CD. Một pipeline nên có những stage nào?

Continuous integration là mọi thay đổi được merge thường xuyên và được kiểm tra tự động: cài dependency, build, lint, test. Continuous delivery là mỗi bản build xanh tạo ra một artifact có thể lên production bất cứ lúc nào, nhưng vẫn có người bấm nút. Continuous deployment đi thêm một bước: mọi bản build xanh được release luôn, không cần bấm nút. Nên khi ai đó nói "bên tôi làm CD", tôi sẽ hỏi là loại nào. Các stage tôi mong đợi là: checkout, cài dependency theo lockfile, lint và test, build một artifact gắn tag phiên bản, push lên registry, deploy lên staging, chạy smoke check, rồi promote chính artifact đó lên production. Aquanix là ví dụ của delivery chứ không phải deployment: Cloud Build tự deploy staging, còn web production là một lần release thủ công sau khi tôi kiểm tra. Không có test thì CI chủ yếu chỉ là đóng gói, nên tôi nói thật pipeline có bao nhiêu test.

Know: Build once, promote the same artifact. Rebuilding per environment means production runs something staging never tested.

Trap: Calling any deploy script "full CI/CD".

Follow-up: "Where do cheap checks go?" First, before expensive builds, so a lint error fails in seconds.

12GitHub Actions, GitLab CI, Jenkins, Cloud BuildSame idea, different hosting. You have used all four.~64s✓

Which CI/CD tools have you used, and how do they compare?

They all run the same idea, a pipeline of jobs on runners, but they differ in where they live and who maintains them. GitHub Actions and GitLab CI sit next to the code, with YAML in the repository and hosted runners. Jenkins is self-hosted and very flexible, but you maintain the server, the plugins, and the stored credentials yourself. Cloud Build sits inside Google Cloud, so it can push to Artifact Registry and deploy to Cloud Run as a service account, without exporting keys. I have used all four. At Akktis each project used GitHub Actions, GitLab CI, or Jenkins, so I worked in whichever one the project had. On my own projects I use Cloud Build. When a team uses a tool I know less, like CircleCI or Bamboo, I learn it through the same questions: where the runners are, where secrets live, and how a build gets promoted.

Bạn đã dùng những công cụ CI/CD nào, và so sánh chúng thế nào?

Tất cả đều chạy cùng một ý tưởng, là một chuỗi job chạy trên runner, nhưng khác nhau ở chỗ nó nằm đâu và ai phải bảo trì. GitHub Actions và GitLab CI nằm cạnh code, file YAML để trong repo và có sẵn runner. Jenkins là tự host và rất linh hoạt, nhưng ta phải tự bảo trì server, plugin và các credential lưu trên đó. Cloud Build nằm trong Google Cloud, nên nó push lên Artifact Registry và deploy Cloud Run bằng service account được, không cần xuất key ra ngoài. Tôi đã dùng cả bốn. Ở Akktis mỗi dự án dùng GitHub Actions, GitLab CI hoặc Jenkins, nên dự án dùng cái nào thì tôi làm với cái đó. Dự án của riêng tôi thì dùng Cloud Build. Khi team dùng một công cụ tôi ít quen hơn, như CircleCI hay Bamboo, tôi học nó qua đúng mấy câu hỏi đó: runner ở đâu, secret nằm đâu, và một bản build được promote thế nào.

Know: Jenkins pain points: plugin upgrades, controller security, credentials on the box. Actions and GitLab: runner minutes, and third-party actions you should pin to a commit SHA.

Trap: Saying Jenkins is "not your thing". It is on the CV.

Follow-up: "How do you share steps across repos?" Reusable workflows in Actions, includes and templates in GitLab, shared libraries in Jenkins.

13Rolling, blue-green, and canaryDefine all three, then map them to Cloud Run revisions.~67s✓

Explain rolling, blue-green, and canary deployments.

Rolling replaces old instances with new ones a few at a time, so capacity stays up, but both versions serve traffic for a while. Blue-green runs two full environments and switches all traffic at once when the new one is healthy; rollback is switching back. Canary sends a small share of traffic, say five percent, to the new version, watches errors and latency, and then increases the share. Cloud Run makes these cheap because every deploy is an immutable revision. By default the new revision takes all the traffic, which is closest to blue-green, with the old revision still there to switch back to. You can also deploy with no traffic, test the new revision on its own tagged URL, and then split traffic for a canary. In my releases I check the new revision and keep the previous one ready, so rollback is one command. The right strategy is the one the team can actually undo.

Bạn giải thích rolling, blue-green và canary deployment.

Rolling là thay dần instance cũ bằng instance mới, mỗi lần vài cái, nên vẫn đủ công suất, nhưng có một khoảng thời gian cả hai phiên bản cùng nhận traffic. Blue-green là chạy hai môi trường đầy đủ, chuyển toàn bộ traffic một lần khi môi trường mới đã ổn; rollback là chuyển ngược lại. Canary là đưa một phần nhỏ traffic, ví dụ năm phần trăm, sang phiên bản mới, theo dõi lỗi và latency, rồi tăng dần. Cloud Run làm mấy việc này rất rẻ vì mỗi lần deploy là một revision không thay đổi được. Mặc định revision mới nhận toàn bộ traffic, gần với blue-green nhất, và revision cũ vẫn còn đó để chuyển về. Ta cũng có thể deploy mà không cho nhận traffic, test revision mới qua URL có tag riêng, rồi mới chia traffic để làm canary. Trong các lần release, tôi kiểm tra revision mới và giữ sẵn revision trước, nên rollback chỉ là một lệnh. Chiến lược đúng là chiến lược mà team thực sự rollback được.

Know: Kubernetes Deployments default to RollingUpdate (maxSurge and maxUnavailable 25%). Canary needs a metric to judge by, or it is just a slow rollout.

Trap: Database changes break all three if the schema is not backward compatible. Expand, migrate, then contract.

Follow-up: "How would you do a canary on Cloud Run?" --no-traffic --tag=candidate, test the tag URL, then update-traffic --to-revisions=NEW=10.

14Rolling back a bad Cloud Run releaseConfirm it is the release, roll back traffic, then debug.~67s✓

A new Cloud Run revision is throwing errors. What do you do?

First I confirm it is the release. In Cloud Logging I filter errors by revision and check that they started with the new one. If users are affected, I roll back before I debug. On Cloud Run that means sending 100 percent of traffic to the last good revision with one update-traffic command. It is fast because the old revision and its image are still there. I don't delete the bad revision, because its logs and config are my evidence. Then I compare the two revisions: image, env vars, secrets, and service account. The usual causes are a missing env var or secret, a bug that only shows with production config, or a container that does not listen on the port Cloud Run gives it. I fix forward, deploy again, and watch the error rate. This works because images are tagged by commit, not just latest, so I always know what the good revision was running.

Một revision mới trên Cloud Run đang báo lỗi. Bạn làm gì?

Đầu tiên tôi xác nhận lỗi đến từ lần release. Trong Cloud Logging, tôi lọc lỗi theo revision và kiểm tra xem lỗi có bắt đầu cùng lúc với revision mới không. Nếu người dùng đang bị ảnh hưởng, tôi rollback trước rồi mới debug. Trên Cloud Run, rollback là chuyển 100% traffic về revision tốt gần nhất bằng một lệnh update-traffic. Làm nhanh được vì revision cũ và image của nó vẫn còn. Tôi không xóa revision lỗi, vì log và cấu hình của nó là bằng chứng. Sau đó tôi so sánh hai revision: image, biến môi trường, secret và service account. Nguyên nhân hay gặp là thiếu một biến môi trường hoặc secret, một bug chỉ xuất hiện với cấu hình production, hoặc container không lắng nghe đúng port mà Cloud Run cấp. Tôi sửa, deploy lại và theo dõi tỉ lệ lỗi. Cách này chạy được vì image được gắn tag theo commit chứ không chỉ là latest, nên tôi luôn biết revision tốt đang chạy code nào.

Know: Commands are in the deploy runbook. A feature flag is the other fast rollback: turn the feature off without a deploy.

Trap: After pinning traffic to an old revision, the next deploy does not get traffic until you run update-traffic --to-latest.

Follow-up: "What if the bad release also ran a database migration?" Rolling back the code is not enough; migrations must be backward compatible so the old revision still works.

15Environment promotion: dev, staging, productionOne build, config per environment, compare config when promoting.~60s✓

How do you handle multiple environments and promotion between them?

Separate environments let me prove a change before customers see it, and promotion means moving the same tested thing forward, not rebuilding it differently at each step. My rule is one codebase and one build, with config per environment. API URLs, secrets, and service accounts come from the environment, never from Git. Each environment has its own services and its own secrets, so a mistake in staging cannot touch production data. Branches map to environments. In Aquanix, a push to the dev branch deploys the API to Cloud Run and the web app to a staging Hosting site, and production web is a separate manual release after I check staging. The trap is drift: staging is green, but production has a different secret or a different server setting. So when I promote, I compare the config, not only the commit.

Bạn xử lý nhiều môi trường và việc promote giữa chúng thế nào?

Có các môi trường riêng giúp tôi chứng minh một thay đổi chạy được trước khi khách hàng thấy nó, và promote nghĩa là đưa đúng thứ đã test sang bước tiếp theo, chứ không build lại theo kiểu khác ở mỗi bước. Nguyên tắc của tôi là một codebase, một bản build, cấu hình riêng cho từng môi trường. URL của API, secret và service account lấy từ môi trường, không bao giờ nằm trong Git. Mỗi môi trường có service riêng và secret riêng, nên lỗi ở staging không đụng được dữ liệu production. Mỗi nhánh gắn với một môi trường. Ở Aquanix, push lên nhánh dev sẽ deploy API lên Cloud Run và web app lên site Hosting staging, còn web production là một lần release thủ công riêng sau khi tôi kiểm tra staging. Cái bẫy là lệch cấu hình: staging xanh nhưng production có secret khác hoặc cấu hình server khác. Nên khi promote, tôi so sánh cấu hình chứ không chỉ so commit.

Know: This is the twelve-factor "config in the environment" rule. The others worth naming: one codebase, many deploys; logs as event streams; backing services attached by config.

Trap: One Cloud Run service shared by all environments with only an env var flipped. A staging mistake then hits production.

Follow-up: "How do you keep parity without copying production data?" Same build and same infrastructure shape; seeded or masked data in staging.

16Staging works, production failsSame commit, different config. Diff the environments.~57s✓

A release works in staging but fails in production. How do you find out why?

I assume a difference between the environments until I prove otherwise, because the code is usually the same commit. So I compare what actually differs: env vars and secrets, the service account and its permissions, the API URL a client was built with, the database or bucket it points to, and on a classic server the vhost, the PHP version, or the Apache and LiteSpeed settings. I read the production logs from the first error, which often names the missing value directly. In multi-environment work this is the shape of failure I watch for most: something set in staging and never set in production. The fix is the missing piece, and then I add that item to the promotion checklist, so it is checked before the next release instead of after it.

Một bản release chạy được ở staging nhưng lỗi ở production. Bạn tìm nguyên nhân thế nào?

Tôi giả định là hai môi trường có gì đó khác nhau cho đến khi chứng minh được điều ngược lại, vì code thường là cùng một commit. Nên tôi so sánh những gì thực sự khác: biến môi trường và secret, service account và quyền của nó, URL API mà client được build cùng, database hoặc bucket nó trỏ tới, và với server truyền thống thì là vhost, phiên bản PHP, hoặc cấu hình Apache và LiteSpeed. Tôi đọc log production từ lỗi đầu tiên, vì lỗi đầu thường nói thẳng giá trị nào đang thiếu. Khi làm với nhiều môi trường, đây là kiểu lỗi tôi để ý nhiều nhất: một thứ được cấu hình ở staging nhưng chưa bao giờ được cấu hình ở production. Cách sửa là bổ sung phần còn thiếu, rồi thêm mục đó vào checklist promote, để lần release sau nó được kiểm tra trước chứ không phải sau.

Know: gcloud run services describe api --format=yaml on both services and diff the output. Do the same for Nginx or Apache config files.

Trap: Diffing only the git SHA. The commit is the same; the config is not.

Follow-up: "How do you stop it happening again?" Config declared in one place per environment, and a checklist or a startup check that fails fast when a required variable is missing.

17A pipeline is red in the middle of a releaseFirst error, what changed, flaky or deterministic.~60s✓

The pipeline goes red in the middle of a release. What do you do?

I open the first failing job and read its log from the first error, not the last line, because the last line is usually just the job exiting. Then I ask what changed since the last green run: a commit, a dependency in the lockfile, the runner image, a tool version, or an expired credential such as a signing certificate. If the failure is flaky, like a network timeout while fetching packages, one re-run is fair. If it is deterministic, re-running only wastes time. I fix the smallest cause, pin a version or revert the commit if the release is blocked, and tell the team what is happening. The release moves forward only when the run is green, and I never disable a check to get there. That was the rule on every Akktis project, whatever the CI tool was.

Pipeline chuyển đỏ giữa lúc đang release. Bạn làm gì?

Tôi mở job đầu tiên bị lỗi và đọc log từ lỗi đầu tiên, không phải dòng cuối, vì dòng cuối thường chỉ là job thoát ra. Rồi tôi hỏi: từ lần chạy xanh gần nhất đến giờ, cái gì đã thay đổi? Một commit, một dependency trong lockfile, image của runner, phiên bản một công cụ, hay một credential đã hết hạn như chứng chỉ ký app. Nếu lỗi kiểu chập chờn, như timeout mạng khi tải package, thì chạy lại một lần là hợp lý. Nếu lỗi lặp lại được, chạy lại chỉ tốn thời gian. Tôi sửa nguyên nhân nhỏ nhất, pin phiên bản hoặc revert commit nếu release đang bị chặn, và báo cho team biết tình hình. Release chỉ đi tiếp khi pipeline xanh, và tôi không bao giờ tắt một bước kiểm tra để qua được. Đó là quy tắc ở mọi dự án tại Akktis, dù dùng công cụ CI nào.

Know: Reproduce with the same versions as the runner: same Node, same JDK, same image. A dependency that floated is fixed by the lockfile, not by retrying.

Trap: Re-running three times without reading the log, or merging red "because it is flaky".

Follow-up: "How do you reduce flaky jobs?" Cache dependencies, pin images and actions, retry only the network step, and quarantine flaky tests with an owner.

18Release under time pressureMake it smaller, keep it reversible, say the risk out loud.~57s✓

The business wants a release today, but things are unstable. What do you do?

I separate what must ship from what is nice to have, and I keep the steps that make a release reversible. I won't skip the pipeline, push an unsigned mobile build, or deploy something I cannot roll back. What I can do is make the release smaller. I take the smallest change that already passed its checks, smoke the critical path on staging, deploy with the previous revision ready, and watch it right after. I also tell the person asking exactly what the risk is. If the risk is too high, I give options instead of silent hope: ship a reduced scope, ship only the hotfix, or move the date. Most people accept a clear "not today, and here is why" much more easily than a broken release on a Friday evening.

Bên kinh doanh muốn release trong hôm nay nhưng hệ thống đang chưa ổn. Bạn làm gì?

Tôi tách phần bắt buộc phải lên khỏi phần có thì tốt, và giữ lại những bước giúp release có thể quay lui. Tôi sẽ không bỏ qua pipeline, không đẩy bản build mobile chưa ký, và không deploy thứ gì mà tôi không rollback được. Việc tôi làm được là làm cho bản release nhỏ lại. Tôi lấy thay đổi nhỏ nhất đã qua kiểm tra, chạy thử luồng quan trọng trên staging, deploy khi đã có sẵn revision trước để quay về, và theo dõi ngay sau đó. Tôi cũng nói rõ với người yêu cầu rủi ro là gì. Nếu rủi ro quá cao, tôi đưa ra lựa chọn thay vì im lặng và hy vọng: release phạm vi nhỏ hơn, chỉ release bản hotfix, hoặc dời ngày. Phần lớn mọi người dễ chấp nhận một câu "hôm nay chưa được, lý do là thế này" hơn nhiều so với một bản release lỗi vào tối thứ Sáu.

Know: Options plus risk, in writing. Name a rollback owner and a time to check.

Trap: "I just push it and fix later." Or the opposite: a flat no with no options.

Follow-up: "What if your manager insists?" Write down the risk and the rollback plan, then ship the smallest safe version.

19Mobile store builds and signingAAB is required. The CI key is the upload key.~65s✓

How do Android and iOS builds get signed and uploaded to the stores?

On Android, Google Play has required the AAB bundle format for new apps since August 2021. With Play App Signing, the key you keep in CI is only the upload key. Google holds the app signing key and re-signs what users download, so if the upload key leaks or is lost, you can reset it through Play without losing the app. On iOS you need a distribution certificate and a provisioning profile, the build has to run on macOS, and it goes to App Store Connect, usually through TestFlight first. In both cases the keys never live in Git. They sit in the CI secret store or a credentials service, and only the signing step can read them. For Expo apps, EAS Build can manage these credentials and EAS Submit can upload. If a team uses Fastlane, match, gym, and pilot are actions called inside the team's own lanes, not lanes themselves.

Bản build Android và iOS được ký và đưa lên store thế nào?

Với Android, từ tháng 8/2021 Google Play bắt buộc app mới phải dùng định dạng AAB. Khi dùng Play App Signing, key để trong CI chỉ là upload key. Google giữ app signing key và ký lại bản mà người dùng tải về, nên nếu upload key bị lộ hoặc bị mất, ta có thể yêu cầu đặt lại qua Play mà không mất app. Với iOS, cần distribution certificate và provisioning profile, bản build phải chạy trên macOS, và được đưa lên App Store Connect, thường qua TestFlight trước. Ở cả hai nền tảng, key không bao giờ nằm trong Git. Nó nằm trong kho secret của CI hoặc một dịch vụ quản lý credential, và chỉ bước ký app mới đọc được. Với app Expo, EAS Build quản lý được các credential này và EAS Submit có thể upload lên store. Nếu team dùng Fastlane, thì match, gym và pilot là các action được gọi bên trong lane của team, chứ bản thân chúng không phải là lane.

Know: A red mobile build is debugged like any red pipeline: first error, what changed. Android: ./gradlew bundleRelease gives the AAB; APKs are for sideloading and testing. Play tracks: internal, closed, open, production. iOS: upload_to_testflight is the action alias for pilot, build_app for gym. Certificates and profiles expire, so expiry is a common cause of a red mobile build.

Trap: "Play prefers AAB." It is required for new apps. And losing the upload key is recoverable; losing a self-managed app signing key is not.

Follow-up: "What happens when the iOS certificate expires?" Builds fail to sign; installed apps keep working for App Store builds. Renew, update the profile, re-run.

20Merge and rebaseMerge shared history, rebase your own local branch.~63s✓

When do you merge, and when do you rebase?

I merge when the branch is shared or already on the remote where other people work from it. Rewriting that history makes their next pull painful. I rebase my own local branch onto the latest main before I open or update a pull request, so the review shows the real change and not a stale conflict. I don't rebase a branch that someone else is committing to. For releases, I like the main branch to stay deployable: every merge has passed CI, and a release is a commit or a tag I can point to. During an incident, Git is also forensics. git log and git diff tell me what changed and in which commit, and whether that commit is the one running in production. A git revert is a safe undo on a shared branch, because it adds a new commit instead of rewriting history.

Khi nào bạn dùng merge, khi nào dùng rebase?

Tôi dùng merge khi nhánh đã được chia sẻ hoặc đã nằm trên remote và người khác đang làm việc từ nó. Viết lại lịch sử của nhánh đó sẽ làm lần pull tiếp theo của họ rất khổ. Tôi rebase nhánh local của tôi lên main mới nhất trước khi mở hoặc cập nhật pull request, để phần review chỉ là thay đổi thật chứ không phải xung đột cũ. Tôi không rebase một nhánh mà người khác đang commit vào. Với release, tôi muốn nhánh main luôn deploy được: mỗi lần merge đều đã qua CI, và một bản release là một commit hoặc một tag tôi chỉ ra được. Khi có sự cố, Git còn là công cụ điều tra. git log và git diff cho tôi biết cái gì đã thay đổi, ở commit nào, và commit đó có đang chạy trên production không. git revert là cách hoàn tác an toàn trên nhánh chung, vì nó thêm một commit mới chứ không viết lại lịch sử.

Know: git pull --rebase for your own work, --force-with-lease if you must push a rebased branch you alone own.

Trap: Force-pushing a shared main.

21Container vs virtual machineShared kernel, namespaces, cgroups.~63s✓

What is the difference between a container and a virtual machine?

A virtual machine virtualizes hardware. Each VM boots its own kernel and a full operating system on a hypervisor, so it is strongly isolated but heavy: gigabytes of disk and a boot that takes a while. A container shares the host's kernel. It is a normal process tree that the kernel isolates with namespaces, which give it its own view of processes, network, mounts, and hostname, and limits with cgroups, which cap its CPU and memory. That is why a container starts in about a second and an image can be tens of megabytes. The tradeoff is weaker isolation, because a kernel bug affects every container on that host, and you cannot run a different kernel inside. I run both. The PhysioFix voice process runs on a Compute Engine VM, and my APIs run as containers on Cloud Run, which adds its own sandbox around each container.

Container khác máy ảo ở điểm nào?

Máy ảo là ảo hóa phần cứng. Mỗi VM khởi động kernel riêng và cả một hệ điều hành đầy đủ trên hypervisor, nên cách ly rất tốt nhưng nặng: tốn vài GB ổ đĩa và khởi động mất một lúc. Container dùng chung kernel với máy chủ. Nó là một cây process bình thường, được kernel cách ly bằng namespace, tức là có góc nhìn riêng về process, mạng, mount và hostname, và bị giới hạn bằng cgroup, tức là bị chặn mức CPU và bộ nhớ. Vì vậy container khởi động trong khoảng một giây và image có thể chỉ vài chục MB. Đổi lại thì cách ly yếu hơn, vì một lỗi kernel ảnh hưởng mọi container trên máy đó, và không chạy được kernel khác bên trong. Tôi dùng cả hai. Process giọng nói của PhysioFix chạy trên VM Compute Engine, còn các API của tôi chạy dạng container trên Cloud Run, nơi mỗi container còn được bọc thêm một lớp sandbox.

Know: Namespaces: pid, net, mnt, uts, ipc, user. cgroups v2 is the default on current distros. Cloud Run gen1 uses gVisor; gen2 runs in a microVM.

Trap: "Containers are lightweight VMs." They are processes; there is no guest kernel.

Follow-up: "When would you pick a VM?" A different kernel or OS, strong isolation between tenants, or a long-lived process that needs the whole machine.

22Docker: image vs containerImage is the package, container is the running instance.~61s✓

Explain Docker. What is the difference between an image and a container?

An image is a read-only package: a filesystem built in layers, plus metadata like the default command, environment, and user. A container is a running instance of that image, with a thin writable layer on top that disappears when the container is removed. The value is that the same image runs on my laptop, in CI, and in production, so "works on my machine" becomes a much smaller problem. In practice I build one image per commit, tag it with the commit SHA, push it to Artifact Registry, and deploy that exact image to Cloud Run. Before I deploy, I run it locally with the same port and env that Cloud Run will give it, which catches most startup mistakes. What a local run cannot prove is the cloud wiring: IAM, secrets, and network access. Those I check on the new revision.

Bạn giải thích Docker. Image khác container thế nào?

Image là một gói chỉ đọc: hệ thống file được xây theo từng layer, kèm metadata như lệnh mặc định, biến môi trường và user. Container là một instance đang chạy của image đó, có thêm một lớp ghi mỏng ở trên, lớp này mất khi container bị xóa. Giá trị của nó là cùng một image chạy trên máy tôi, trong CI và trên production, nên chuyện "máy tôi chạy được" nhỏ đi rất nhiều. Thực tế tôi build một image cho mỗi commit, gắn tag bằng commit SHA, push lên Artifact Registry, và deploy đúng image đó lên Cloud Run. Trước khi deploy, tôi chạy thử ở local với đúng port và env mà Cloud Run sẽ cấp, cách này bắt được hầu hết lỗi lúc khởi động. Điều mà chạy local không chứng minh được là phần kết nối trên cloud: IAM, secret và quyền truy cập mạng. Mấy phần đó tôi kiểm tra trên revision mới.

Know: Local parity check: docker run --rm -p 8080:8080 -e PORT=8080 api:local, then curl localhost:8080/health.

Trap: Docker is not Kubernetes. Docker builds and runs containers; Kubernetes schedules them across machines.

Follow-up: "What is in an image?" Layers plus a config (entrypoint, cmd, env, user, exposed ports). See layers and multi-stage builds.

23Image layers and multi-stage buildsOrder for cache, slim final stage, non-root, listen on $PORT.~64s✓

How do you write a good production Dockerfile? What is a multi-stage build?

Each Dockerfile instruction makes a layer, and Docker reuses a cached layer until something it depends on changes. So order matters: copy package.json and the lockfile first, install dependencies, and copy the source last. Then a code change does not reinstall everything. A .dockerignore keeps node_modules, .git, and .env files out of the build context. A multi-stage build uses one stage with the full toolchain to compile, for example TypeScript to JavaScript, and a second, slim stage that copies only the built output and the production dependencies. The final image is smaller, has fewer packages to patch, and has no build tools in it. I also add a USER line so the process does not run as root. For Cloud Run, EXPOSE is only documentation. Cloud Run ignores it and sends traffic to the port in the PORT environment variable, 8080 by default, so the app must listen there.

Bạn viết một Dockerfile production tốt thế nào? Multi-stage build là gì?

Mỗi lệnh trong Dockerfile tạo một layer, và Docker dùng lại layer đã cache cho đến khi thứ nó phụ thuộc thay đổi. Nên thứ tự rất quan trọng: copy package.json và lockfile trước, cài dependency, rồi mới copy source. Như vậy sửa code không làm cài lại toàn bộ. File .dockerignore giữ node_modules, .git và các file .env ra khỏi build context. Multi-stage build dùng một stage có đủ công cụ để biên dịch, ví dụ TypeScript sang JavaScript, và một stage thứ hai gọn nhẹ, chỉ copy phần đã build và dependency production. Image cuối nhỏ hơn, ít package phải vá hơn, và không có công cụ build bên trong. Tôi cũng thêm dòng USER để process không chạy bằng root. Với Cloud Run, EXPOSE chỉ mang tính tài liệu. Cloud Run bỏ qua nó và gửi traffic đến port trong biến môi trường PORT, mặc định là 8080, nên app phải lắng nghe ở đó.

FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build && npm prune --omit=dev

FROM node:22-slim
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]

Know: Listen on process.env.PORT and on 0.0.0.0, not localhost.

Trap: Baking a production .env into an image. Every layer is readable by anyone who can pull the image, even if a later layer deletes the file.

Follow-up: "How do you keep the image patched?" Rebuild on a schedule from an updated base, and let Artifact Registry vulnerability scanning flag old layers.

24CMD vs ENTRYPOINTENTRYPOINT is the program, CMD the default args. Use exec form.~63s✓

What is the difference between CMD and ENTRYPOINT?

ENTRYPOINT is the executable the container always runs. CMD gives the default arguments, or the default command if there is no ENTRYPOINT. Anything you pass after the image name in docker run replaces CMD, but not ENTRYPOINT, unless you use the --entrypoint flag. So a common pattern is ENTRYPOINT for the program and CMD for its default flags. The detail that matters in production is the form. The exec form, written as a JSON array, runs your process directly as PID 1, so it receives SIGTERM when the platform stops the container. The shell form wraps it in sh -c, and the shell may not pass the signal on, so the app never shuts down cleanly and gets killed after the grace period. For a Node API on Cloud Run, I use the exec form and handle SIGTERM, so in-flight requests can finish before the instance stops.

CMD và ENTRYPOINT khác nhau thế nào?

ENTRYPOINT là chương trình mà container luôn chạy. CMD là tham số mặc định, hoặc là lệnh mặc định nếu không có ENTRYPOINT. Những gì ta truyền sau tên image trong docker run sẽ thay thế CMD, nhưng không thay ENTRYPOINT, trừ khi dùng cờ --entrypoint. Nên cách hay dùng là ENTRYPOINT cho chương trình và CMD cho các cờ mặc định. Chi tiết quan trọng trên production là cách viết. Dạng exec, viết bằng mảng JSON, chạy process trực tiếp với PID 1, nên nó nhận được SIGTERM khi nền tảng dừng container. Dạng shell bọc nó trong sh -c, và shell có thể không chuyển tín hiệu xuống, nên app không bao giờ tắt gọn gàng và bị kill sau thời gian chờ. Với API Node trên Cloud Run, tôi dùng dạng exec và xử lý SIGTERM, để các request đang chạy kịp hoàn thành trước khi instance dừng.

Know: Cloud Run sends SIGTERM and waits 10 seconds before SIGKILL. PID 1 gets no default signal handlers, so either handle SIGTERM in the app or run with docker run --init or tini.

Trap: CMD npm start in shell form: npm may not forward the signal either.

Follow-up: "How do you shut down a Node server gracefully?" On SIGTERM, stop accepting connections with server.close(), finish in-flight work, close the database, then exit.

25Volumes, networking, and Docker ComposePersist in volumes, reach services by name, one file for the stack.~63s✓

How do Docker volumes and networking work? When do you use Docker Compose?

A container's writable layer is gone when the container is removed, so anything that must survive goes in a volume. A named volume is managed by Docker and is the right choice for, say, a local MySQL. A bind mount maps a host folder into the container, which is handy for live code in development. For networking, containers on the same user-defined network reach each other by service name through Docker's DNS, and the -p flag publishes a container port on the host. Docker Compose puts all of that in one file: the API, MySQL with a named volume, and a shared network, started with one command. That is how I'd give a developer a full local stack. On Cloud Run none of this applies. Instances are stateless and the local disk is in memory, so files go to Cloud Storage and data goes to a database.

Volume và networking trong Docker hoạt động thế nào? Khi nào bạn dùng Docker Compose?

Lớp ghi của container sẽ mất khi container bị xóa, nên cái gì cần giữ lại phải để trong volume. Named volume do Docker quản lý, phù hợp cho kiểu MySQL chạy ở local. Bind mount gắn một thư mục trên máy vào container, tiện để sửa code trực tiếp khi phát triển. Về mạng, các container trong cùng một network do ta tạo sẽ gọi nhau bằng tên service qua DNS của Docker, còn cờ -p mở port của container ra máy chủ. Docker Compose gom tất cả vào một file: API, MySQL với named volume, và một network chung, chạy lên bằng một lệnh. Đó là cách tôi sẽ cho một developer có đủ cả hệ thống ở local. Trên Cloud Run thì không có những thứ này. Instance không giữ trạng thái và ổ đĩa local nằm trong bộ nhớ, nên file để ở Cloud Storage và dữ liệu để trong database.

Know: In Compose, the API connects to mysql:3306, not localhost. depends_on with a healthcheck condition waits for MySQL to be ready, not just started.

Trap: Docker-published ports bypass UFW rules on a Linux host, because Docker writes its own iptables rules.

Follow-up: "Can Cloud Run mount storage?" Yes, Cloud Storage or NFS volume mounts exist, but they are not a local disk; I keep the app stateless.

26Kubernetes basicsStudied, not operated. Pod, Deployment, Service, Ingress, desired state.~65s✓

Do you know Kubernetes? Explain the main objects.

I'll be clear first: I have studied Kubernetes, and I have not operated a cluster in production. My production containers run on Cloud Run. The core objects are these. A Pod is the smallest unit: one or more containers that share a network and storage. A Deployment declares how many replicas of a Pod template you want and rolls out changes, by default as a rolling update. A Service gives those Pods one stable name and virtual IP, because Pods come and go. An Ingress, or the newer Gateway API, routes HTTP from outside to Services by host and path. ConfigMaps and Secrets hold config. The idea that ties it together is desired state: you declare what you want, and controllers keep correcting the cluster toward it. If I joined a team on GKE, I'd start from their manifests and their deploy and rollback path, and practice on a staging cluster.

Bạn có biết Kubernetes không? Bạn giải thích các object chính.

Tôi nói rõ trước: tôi đã học Kubernetes nhưng chưa vận hành cluster nào trên production. Container production của tôi chạy trên Cloud Run. Các object cốt lõi là thế này. Pod là đơn vị nhỏ nhất, gồm một hoặc vài container dùng chung mạng và storage. Deployment khai báo muốn bao nhiêu bản sao của một Pod template và thực hiện việc rollout thay đổi, mặc định là rolling update. Service cho các Pod đó một tên và một IP ảo cố định, vì Pod có thể bị tạo mới hoặc mất đi bất cứ lúc nào. Ingress, hoặc Gateway API mới hơn, định tuyến HTTP từ bên ngoài vào Service theo host và path. ConfigMap và Secret chứa cấu hình. Ý tưởng xuyên suốt là desired state: ta khai báo trạng thái mong muốn, và các controller liên tục kéo cluster về trạng thái đó. Nếu vào một team dùng GKE, tôi sẽ bắt đầu từ manifest của họ, cách họ deploy và rollback, và thực hành trên một cluster staging.

Know: Service types: ClusterIP (internal), NodePort, LoadBalancer. Kubernetes Secrets are only base64-encoded by default; enable encryption at rest or use an external secret manager. Ingress NGINX was retired in 2026; Gateway API is the current direction.

Trap: Claiming cluster operations you have not done.

Follow-up: "What does Kubernetes solve that Docker alone does not?" Scheduling across machines, self-healing, rollouts, service discovery, and autoscaling.

27Liveness, readiness, and startup probesLiveness restarts, readiness removes from traffic.~63s✓

What is the difference between a liveness probe and a readiness probe?

Liveness asks whether the container is stuck. If it fails, the kubelet restarts the container. Readiness asks whether the Pod can take traffic right now. If it fails, the Pod is taken out of the Service endpoints, but it is not restarted. A startup probe protects slow starters: until it succeeds, the other probes do not run. The classic mistake is making liveness check a dependency, like the database. Then a short database outage makes every Pod fail liveness, Kubernetes restarts all of them, and a small problem becomes a full outage. So liveness should check only the process itself, and readiness can check whether it is able to serve. This is knowledge from study, not from running a cluster, but Cloud Run uses the same idea. It supports startup and liveness probes on the container, and it only sends traffic once the container is ready.

Liveness probe và readiness probe khác nhau thế nào?

Liveness hỏi xem container có bị treo không. Nếu thất bại, kubelet sẽ restart container. Readiness hỏi xem Pod lúc này có nhận traffic được không. Nếu thất bại, Pod bị gỡ khỏi danh sách endpoint của Service, nhưng không bị restart. Startup probe bảo vệ những app khởi động chậm: khi nó chưa thành công thì các probe khác chưa chạy. Lỗi kinh điển là cho liveness kiểm tra một dependency, ví dụ database. Khi đó database chập chờn một chút là mọi Pod đều fail liveness, Kubernetes restart tất cả, và một vấn đề nhỏ thành sự cố toàn hệ thống. Nên liveness chỉ nên kiểm tra chính process đó, còn readiness có thể kiểm tra xem nó có phục vụ được không. Đây là kiến thức tôi học, chưa phải từ vận hành cluster, nhưng Cloud Run cũng dùng ý tưởng tương tự. Nó hỗ trợ startup probe và liveness probe cho container, và chỉ gửi traffic khi container đã sẵn sàng.

livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 2

Know: Probe types: httpGet, tcpSocket, exec, grpc.

Trap: A liveness probe with no startup probe on a slow app: it gets killed before it finishes starting, which shows up as CrashLoopBackOff.

Follow-up: "What should /ready check?" That the app has loaded config and can reach what it needs to serve; keep it cheap.

28Debugging CrashLoopBackOffdescribe, logs --previous, exit code, what changed.~72s✓

A Pod is in CrashLoopBackOff. How do you debug it?

CrashLoopBackOff means the container starts, exits, and Kubernetes keeps restarting it with a growing delay. It is a symptom, not a cause. I'd go in this order. kubectl describe pod shows the events and the last state: the exit code, and whether the reason was OOMKilled. Exit code 137 with OOMKilled means the memory limit is too low or the app leaks. Then kubectl logs with --previous, because the current container may have just restarted and has nothing yet, while the previous one has the crash. Common causes are a missing env var or secret, a wrong command, an app that exits on startup because it cannot reach a dependency, or a liveness probe that kills a slow-starting app. I'd also check what changed in the last rollout: the image tag and the config. I have not debugged this on a real cluster, but it is the same habit I use when a Cloud Run revision fails to start: read why the container exited before changing anything.

Một Pod đang ở trạng thái CrashLoopBackOff. Bạn debug thế nào?

CrashLoopBackOff nghĩa là container khởi động, thoát ra, và Kubernetes cứ restart nó với khoảng chờ ngày càng dài. Đó là triệu chứng, không phải nguyên nhân. Tôi sẽ đi theo thứ tự này. kubectl describe pod cho thấy các event và trạng thái lần cuối: exit code, và lý do có phải OOMKilled không. Exit code 137 kèm OOMKilled nghĩa là giới hạn bộ nhớ quá thấp hoặc app bị rò bộ nhớ. Sau đó là kubectl logs với --previous, vì container hiện tại có thể vừa restart và chưa có log gì, còn container trước đó mới có lỗi crash. Nguyên nhân hay gặp là thiếu biến môi trường hoặc secret, sai lệnh chạy, app thoát ngay khi khởi động vì không kết nối được dependency, hoặc liveness probe kill một app khởi động chậm. Tôi cũng kiểm tra lần rollout gần nhất đã thay đổi gì: image tag và cấu hình. Tôi chưa debug lỗi này trên cluster thật, nhưng đó cũng là thói quen tôi dùng khi một revision Cloud Run không khởi động được: đọc lý do container thoát trước khi sửa bất cứ thứ gì.

kubectl get pods
kubectl describe pod api-7d9f-abc      # Events, Last State, Exit Code, Reason
kubectl logs api-7d9f-abc --previous   # logs of the crashed container
kubectl get events --sort-by=.lastTimestamp
kubectl rollout history deploy/api
kubectl rollout undo deploy/api        # back to the previous ReplicaSet

Know: Exit 1 is usually an app error, 137 is SIGKILL (often OOM), 143 is SIGTERM.

Trap: Deleting the Pod and hoping. The Deployment recreates it with the same bug.

Follow-up: "ImagePullBackOff instead?" Wrong image name or tag, or the node cannot authenticate to the registry.

29Horizontal Pod AutoscalerReplicas follow a metric; needs requests. Cloud Run does this for you.~63s✓

How does autoscaling work in Kubernetes?

The Horizontal Pod Autoscaler changes the number of replicas in a Deployment to keep a metric near a target, usually average CPU utilization, for example 70 percent of what the Pods requested. It needs resource requests set, because utilization is measured against the request, and it needs the metrics server. You set minimum and maximum replicas, so it never drops below what you need or grows past the cost you planned. It scales up quickly and scales down slowly, to avoid flapping. The HPA only adds Pods. If the nodes are full, the cluster autoscaler has to add nodes, which is slower. On Cloud Run I get similar behavior without configuring it. It scales instances on incoming requests and CPU, and I control it with min instances, max instances, and concurrency per instance. I know the HPA from study; Cloud Run autoscaling is what I have actually run.

Autoscaling trong Kubernetes hoạt động thế nào?

Horizontal Pod Autoscaler thay đổi số bản sao của một Deployment để giữ một chỉ số gần mức mục tiêu, thường là mức sử dụng CPU trung bình, ví dụ 70% so với lượng Pod đã request. Nó cần đặt resource request, vì mức sử dụng được tính so với request, và cần có metrics server. Ta đặt số bản sao tối thiểu và tối đa, để nó không bao giờ xuống dưới mức cần thiết hay vượt quá chi phí đã tính. Nó tăng nhanh và giảm chậm, để tránh dao động liên tục. HPA chỉ thêm Pod. Nếu các node đã đầy thì cluster autoscaler phải thêm node, việc này chậm hơn. Trên Cloud Run tôi có hành vi tương tự mà không cần cấu hình. Nó tự tăng giảm instance theo request đến và CPU, còn tôi điều khiển bằng min instances, max instances và concurrency của mỗi instance. HPA là kiến thức tôi học, còn autoscaling của Cloud Run là thứ tôi đã thực sự vận hành.

Know: kubectl autoscale deploy api --cpu-percent=70 --min=2 --max=10. Vertical Pod Autoscaler changes requests instead of replica count. KEDA scales on queue length and other events.

Trap: No resource requests: the HPA cannot compute utilization and does nothing.

Follow-up: "What does max instances protect on Cloud Run?" Cost, and downstream systems like a database with a connection limit.

30What happens when you type a URLDNS, TCP, TLS, HTTP, edge, app, render.~75s✓

What happens when you type a URL into the browser and press Enter?

First the browser needs an IP address for the hostname. It checks its own cache, then the operating system, then asks a DNS resolver, which, if it has no cached answer, walks from the root servers to the .com servers to the domain's own name servers. Then the browser opens a TCP connection to that IP on port 443, with a three-way handshake. Then comes TLS: the two sides agree on a cipher, the server proves its identity with a certificate the browser checks, and they derive session keys. With TLS 1.3 that takes one round trip. Now the browser sends the HTTP request. On the way it may hit a CDN or a load balancer, which terminates TLS and forwards the request to a backend, maybe through a reverse proxy like Nginx to the app. The app does its work, perhaps queries a database, and returns a response. The browser parses the HTML, fetches the CSS, JavaScript, and images, and renders the page. With HTTP/3, QUIC over UDP replaces the TCP and TLS steps.

Chuyện gì xảy ra khi bạn gõ một URL vào trình duyệt và nhấn Enter?

Đầu tiên trình duyệt cần địa chỉ IP của hostname. Nó xem cache của chính nó, rồi đến hệ điều hành, rồi hỏi một DNS resolver. Nếu resolver chưa có sẵn câu trả lời, nó đi từ root server đến server của đuôi .com rồi đến name server của chính tên miền đó. Sau đó trình duyệt mở kết nối TCP đến IP đó ở port 443, qua bắt tay ba bước. Tiếp theo là TLS: hai bên thống nhất thuật toán mã hóa, server chứng minh danh tính bằng certificate mà trình duyệt kiểm tra, rồi hai bên tạo ra khóa phiên. Với TLS 1.3, việc này mất một vòng đi về. Giờ trình duyệt mới gửi request HTTP. Trên đường đi, request có thể qua CDN hoặc load balancer, nơi kết thúc TLS và chuyển tiếp đến backend, có thể qua một reverse proxy như Nginx rồi mới đến app. App xử lý, có thể truy vấn database, rồi trả response. Trình duyệt phân tích HTML, tải CSS, JavaScript, ảnh, rồi hiển thị trang. Với HTTP/3, QUIC chạy trên UDP thay cho các bước TCP và TLS.

Know: Go one layer deeper wherever the interviewer stops you: DNS, TCP and TLS, HTTP versions, load balancers, CDN.

Trap: Skipping the TLS step, or saying the browser asks the root servers directly.

Follow-up: "Where can this be slow?" DNS lookup, connection setup on a far server, a slow backend (TTFB), or a heavy page to render.

31DNS, and debugging a service you cannot reachRecord types and TTL, then resolve, reach, listen, firewall.~71s✓

How does DNS work, and how do you debug a service you cannot reach?

DNS maps names to records. An A record points to an IPv4 address, AAAA to IPv6, a CNAME aliases one name to another, MX is for mail, and TXT carries things like domain verification. Each answer has a TTL, which is how long resolvers may cache it, so lowering the TTL before a migration makes the switch faster. When a service is unreachable, I go layer by layer. Does the name resolve, and to the right IP? dig answers that. Can I reach the IP and the port? curl -v or nc. Is the process actually listening, and on which address? ss -tlnp on the server. Is a firewall rule blocking it? If curl works by IP but not by hostname, I suspect DNS, or a Host header that does not match any vhost. If it fails only over HTTPS, I suspect the certificate. For a new site, DNS has to point at the server before a certificate can be issued by an HTTP check.

DNS hoạt động thế nào, và bạn debug một service không truy cập được ra sao?

DNS ánh xạ tên miền sang các bản ghi. Bản ghi A trỏ đến địa chỉ IPv4, AAAA trỏ đến IPv6, CNAME là bí danh từ tên này sang tên khác, MX dành cho mail, còn TXT chứa những thứ như xác minh tên miền. Mỗi câu trả lời có TTL, là thời gian resolver được phép cache, nên hạ TTL trước khi chuyển server sẽ giúp chuyển đổi nhanh hơn. Khi một service không truy cập được, tôi đi từng lớp. Tên miền có phân giải ra không, và có đúng IP không? Lệnh dig trả lời câu đó. Có tới được IP và port không? Dùng curl -v hoặc nc. Process có thực sự đang lắng nghe không, và trên địa chỉ nào? Chạy ss -tlnp trên server. Có rule firewall nào chặn không? Nếu curl bằng IP thì được mà bằng tên miền thì không, tôi nghi DNS, hoặc header Host không khớp với vhost nào. Nếu chỉ lỗi với HTTPS, tôi nghi certificate. Với một site mới, DNS phải trỏ về server trước thì mới xin được certificate qua bước kiểm tra HTTP.

dig +short example.com A
dig example.com @8.8.8.8          # compare with a public resolver
curl -v https://example.com/health
nc -vz 10.0.0.5 443
sudo ss -tlnp | grep :443          # listening on 127.0.0.1 only?

Know: A CNAME cannot sit at the zone apex; providers offer ALIAS or flattening. Negative answers are cached too.

Trap: An app listening on 127.0.0.1 works with curl on the box and fails from outside.

Follow-up: "DNS was changed an hour ago but some users still see the old IP. Why?" Cached by resolvers until the old TTL expires.

32TCP and TLS handshakesSYN, SYN-ACK, ACK; then TLS 1.3 in one round trip.~63s✓

Explain the TCP handshake and the TLS handshake.

TCP gives a reliable, ordered stream of bytes. To open a connection, the client sends SYN, the server answers SYN-ACK, and the client sends ACK. That costs one round trip before any data moves. After that, TCP handles retransmission, ordering, and flow control. TLS runs on top to add encryption and identity. In TLS 1.3, the client's hello already includes its key share. The server replies with its own share, its certificate, and a signature proving it holds the certificate's private key, and both sides derive the same session keys. That is one round trip, versus two in TLS 1.2. The browser checks that the certificate chains to a trusted authority, is within its validity period, and matches the hostname. The TLS problems I'd expect on a server are an expired certificate, a missing intermediate certificate in the chain, or a hostname that does not match the certificate.

Bạn giải thích bắt tay TCP và bắt tay TLS.

TCP cung cấp một luồng byte tin cậy và đúng thứ tự. Để mở kết nối, client gửi SYN, server trả SYN-ACK, rồi client gửi ACK. Việc này mất một vòng đi về trước khi có dữ liệu nào được gửi. Sau đó TCP lo việc gửi lại gói bị mất, sắp xếp thứ tự và điều khiển luồng. TLS chạy bên trên để thêm mã hóa và xác thực danh tính. Với TLS 1.3, lời chào của client đã gửi kèm phần khóa của nó. Server trả lời bằng phần khóa của nó, certificate, và một chữ ký chứng minh nó giữ private key của certificate đó, rồi hai bên cùng tạo ra một bộ khóa phiên giống nhau. Tổng cộng một vòng đi về, so với hai vòng ở TLS 1.2. Trình duyệt kiểm tra certificate có chuỗi tin cậy về một nhà phát hành đáng tin không, còn hạn không, và có khớp hostname không. Các lỗi TLS tôi hay nghĩ đến trên server là certificate hết hạn, thiếu certificate trung gian trong chuỗi, hoặc hostname không khớp với certificate.

Know: Check a server: openssl s_client -connect example.com:443 -servername example.com shows the chain and expiry. SNI lets one IP serve many certificates. TLS 1.3 can resume with 0-RTT, which is replayable, so only for safe requests.

Trap: Saying TLS encrypts with the certificate. The certificate proves identity; the session keys come from the key exchange.

Follow-up: "Works in Chrome, fails in curl or an old Android device?" A missing intermediate: browsers can fetch it, other clients cannot.

33HTTP/1.1 vs HTTP/2 vs HTTP/3One at a time, multiplexed on TCP, multiplexed on QUIC.~65s✓

What are the differences between HTTP/1.1, HTTP/2, and HTTP/3?

HTTP/1.1 sends one request at a time per connection, so browsers open several connections, and a slow response blocks the ones queued behind it. HTTP/2 keeps one connection and multiplexes many requests as streams, with binary framing and compressed headers. But it still runs on TCP, so one lost packet stalls every stream; the head-of-line blocking just moved down into TCP. HTTP/3 runs on QUIC over UDP. Each stream recovers from loss on its own, the transport and TLS 1.3 handshakes are combined, and a connection can survive a network change, like a phone moving from wifi to mobile data. In practice, the version is mostly decided at the edge. The load balancer or CDN speaks HTTP/2 or 3 to browsers, and often HTTP/1.1 to the backend. Google's front end in front of Cloud Run and Firebase Hosting already speaks HTTP/2 to browsers, so my apps get it without code changes.

HTTP/1.1, HTTP/2 và HTTP/3 khác nhau thế nào?

HTTP/1.1 gửi mỗi lần một request trên một kết nối, nên trình duyệt phải mở nhiều kết nối, và một response chậm sẽ chặn các request xếp hàng phía sau. HTTP/2 giữ một kết nối và ghép nhiều request thành các stream chạy song song, với khung dữ liệu nhị phân và header được nén. Nhưng nó vẫn chạy trên TCP, nên mất một gói tin là mọi stream đều phải chờ; vấn đề chặn đầu hàng chỉ chuyển xuống tầng TCP. HTTP/3 chạy trên QUIC qua UDP. Mỗi stream tự phục hồi khi mất gói, bắt tay của tầng truyền tải và TLS 1.3 được gộp làm một, và kết nối có thể giữ được khi đổi mạng, như điện thoại chuyển từ wifi sang 4G. Thực tế, phiên bản HTTP chủ yếu do tầng biên quyết định. Load balancer hoặc CDN nói HTTP/2 hoặc 3 với trình duyệt, và thường dùng HTTP/1.1 với backend. Lớp front end của Google đứng trước Cloud Run và Firebase Hosting đã nói HTTP/2 với trình duyệt, nên app của tôi có sẵn mà không cần sửa code.

Know: HTTP/2 made old HTTP/1.1 tricks (domain sharding, sprite sheets, heavy bundling) less useful. HTTP/3 needs UDP 443 open; clients fall back to HTTP/2 when it is blocked.

Trap: Saying HTTP/2 removed head-of-line blocking entirely. It removed it at the HTTP layer, not at TCP.

Follow-up: "How do you check the version?" Browser dev tools Protocol column, or curl -I --http2.

34L4 vs L7 load balancers and reverse proxiesConnections vs requests. Health checks decide who gets traffic.~73s✓

What is the difference between a layer 4 and a layer 7 load balancer? Where does a reverse proxy fit?

A layer 4 load balancer works on TCP or UDP. It sees IP addresses and ports and forwards connections without reading the request. It is fast and works for any protocol, but it cannot route by URL. A layer 7 load balancer understands HTTP. It terminates TLS, reads the host, path, headers, and cookies, and can send /api to one backend and static files to another, retry a failed request, add headers, or apply a WAF. A reverse proxy like Nginx is a layer 7 component on one server. It sits in front of the app, terminates TLS, serves static files, and forwards dynamic requests to PHP-FPM or a Node process. At Akktis I configured Nginx, Apache, and LiteSpeed in front of PHP and CMS applications, with TLS on the server. The key part of any load balancer is the health check: a backend that fails it is taken out of rotation. On Google Cloud, the Application Load Balancer is layer 7 and the Network Load Balancer is layer 4.

Load balancer tầng 4 và tầng 7 khác nhau thế nào? Reverse proxy nằm ở đâu?

Load balancer tầng 4 làm việc với TCP hoặc UDP. Nó chỉ thấy địa chỉ IP và port, và chuyển tiếp kết nối mà không đọc nội dung request. Nó nhanh và dùng được cho mọi giao thức, nhưng không định tuyến theo URL được. Load balancer tầng 7 hiểu HTTP. Nó kết thúc TLS, đọc host, path, header và cookie, và có thể gửi /api đến một backend còn file tĩnh đến backend khác, thử lại request lỗi, thêm header, hoặc áp dụng WAF. Reverse proxy như Nginx là một thành phần tầng 7 trên một server. Nó đứng trước app, kết thúc TLS, phục vụ file tĩnh, và chuyển request động đến PHP-FPM hoặc process Node. Ở Akktis tôi cấu hình Nginx, Apache và LiteSpeed đứng trước các ứng dụng PHP và CMS, có TLS ngay trên server. Phần quan trọng nhất của mọi load balancer là health check: backend nào không qua health check sẽ bị đưa ra khỏi vòng phân phối. Trên Google Cloud, Application Load Balancer là tầng 7, còn Network Load Balancer là tầng 4.

Know: Algorithms: round robin, least connections, hashing for stickiness. Behind an L7 proxy the client IP arrives in X-Forwarded-For; trust it only from your own proxy.

Trap: Sticky sessions hide state on one server; better to keep sessions in a shared store or a token.

Follow-up: "Why put Nginx in front of Node at all?" TLS, static files, buffering slow clients, rate limits, and one place for access logs.

35How a CDN worksEdge cache, Cache-Control, hashed assets, stale HTML after deploy.~70s✓

What is a CDN, and what problems does it cause?

A CDN is a network of edge servers that cache content close to users. The first request in a region goes to your origin; later requests are served from the edge, so latency drops and the origin sees much less traffic. What gets cached, and for how long, is controlled mostly by the Cache-Control headers from the origin. Static assets with a content hash in the filename can be cached for a year as immutable. HTML and API responses usually get short caching or none, because they change. The classic problem is stale content after a deploy: users see an old page because it was cached. The fix is hashed asset names plus a short cache on the HTML, or a purge. Firebase Hosting, which I use for the Aquanix web app, serves through Google's CDN, so this applies to me directly. A new release only shows up quickly if the HTML that points to the new bundle is not cached for long.

CDN là gì, và nó gây ra những vấn đề gì?

CDN là mạng lưới các server ở biên, cache nội dung gần người dùng. Request đầu tiên ở một khu vực sẽ đi về server gốc; các request sau được phục vụ ngay từ biên, nên độ trễ giảm và server gốc nhận ít traffic hơn nhiều. Cái gì được cache và trong bao lâu chủ yếu do header Cache-Control từ server gốc quyết định. File tĩnh có mã hash trong tên file có thể cache cả năm, đánh dấu immutable. HTML và response của API thường cache ngắn hoặc không cache, vì chúng thay đổi. Vấn đề kinh điển là nội dung cũ sau khi deploy: người dùng thấy trang cũ vì nó đang bị cache. Cách xử lý là đặt tên file theo hash cộng với cache ngắn cho HTML, hoặc xóa cache. Firebase Hosting, nơi tôi chạy web app của Aquanix, phục vụ qua CDN của Google, nên chuyện này áp dụng trực tiếp với tôi. Bản release mới chỉ hiện ra nhanh nếu file HTML trỏ đến bundle mới không bị cache lâu.

Know: Cache-Control: public, max-age=31536000, immutable for hashed assets; no-cache (revalidate) for HTML. Firebase Hosting headers are set in firebase.json, and a new Hosting release clears its CDN cache.

Trap: Caching responses that depend on the user (cookies, Authorization) at a shared edge.

Follow-up: "What else does a CDN give you?" TLS at the edge, compression, DDoS absorption, and often a WAF.

36Linux troubleshooting checklistSymptom, service, resources, network, logs, what changed.~63s✓

A Linux server is misbehaving. How do you troubleshoot it?

I start by pinning down the symptom: down, slow, a failed deploy, or one feature broken. Then I collect evidence before changing anything. Is the service running? systemctl status, then journalctl -u for its logs. Resources: df -h and df -i for disk, free -m for memory, uptime and top for load. Network: is it listening, with ss -tlnp, and does curl to localhost work from the box itself? Then the web server and app logs under /var/log. And always: what changed recently, such as a deploy, a package upgrade, or a config edit. I fix the safest thing that explains the evidence, verify from outside, and write down the check if the problem can come back. At Akktis this loop covered most issues on the Ubuntu and Debian servers: deploys, service restarts, and full disks. Rebooting first destroys the evidence and often just delays the same failure.

Một server Linux đang có vấn đề. Bạn xử lý thế nào?

Tôi bắt đầu bằng việc xác định rõ triệu chứng: sập hẳn, chậm, deploy lỗi, hay chỉ một chức năng hỏng. Rồi tôi thu thập bằng chứng trước khi thay đổi gì. Service có đang chạy không? Dùng systemctl status, rồi journalctl -u để xem log của nó. Tài nguyên: df -h và df -i cho ổ đĩa, free -m cho bộ nhớ, uptime và top cho tải. Mạng: service có đang lắng nghe không, xem bằng ss -tlnp, và curl đến localhost ngay trên máy có được không? Sau đó là log của web server và ứng dụng trong /var/log. Và luôn hỏi: gần đây có gì thay đổi, như một lần deploy, nâng cấp package, hay sửa cấu hình. Tôi sửa thứ an toàn nhất mà giải thích được bằng chứng, kiểm tra lại từ bên ngoài, và ghi lại bước kiểm tra nếu vấn đề có thể quay lại. Ở Akktis, vòng lặp này xử lý được phần lớn vấn đề trên server Ubuntu và Debian: deploy, restart service và đầy ổ đĩa. Reboot ngay từ đầu sẽ xóa mất bằng chứng và thường chỉ làm lỗi đó quay lại muộn hơn.

systemctl status nginx php8.3-fpm
journalctl -u nginx --since "30 min ago"
df -h; df -i; free -m; uptime
sudo ss -tlnp
curl -sI http://127.0.0.1/
tail -n 100 /var/log/nginx/error.log
grep -i "upgrade\|install" /var/log/dpkg.log | tail

Know: Which process holds port 8080: sudo ss -tlnp 'sport = :8080' or sudo lsof -i :8080.

Trap: Listing twenty commands with no order. The order is the answer.

Follow-up: "The disk is full. Now what?" See disk full. "CPU is high?" See high CPU.

37The disk is fulldf and df -i, du -x, deleted-but-open files, then the cause.~69s✓

A server's disk is full and the site has stopped working. What do you do?

I confirm it first with df -h, and df -i, because a disk can also run out of inodes while space is left. Then I find what grew, staying on that one filesystem: du -xh --max-depth=1 from the root, and down from there. Usually it is logs, old backups, or uploads. I free space safely: truncate or rotate known log files, vacuum the systemd journal to a size, and move old backups off the box. I never delete inside database directories. One trap: if you delete a log file that a process still has open, the space is not freed until that process closes it. lsof +L1 shows those files; then you truncate the file or restart the service. After that, I restart whatever failed, check that the site works, and fix the cause: logrotate, retention, or a bigger disk. At Akktis I handled disk-full incidents this way, and I noted the check afterwards so the next one would be caught earlier.

Ổ đĩa server bị đầy và site ngừng hoạt động. Bạn làm gì?

Tôi xác nhận trước bằng df -h, và cả df -i, vì ổ đĩa có thể hết inode trong khi vẫn còn dung lượng. Sau đó tôi tìm xem cái gì phình to, chỉ trong đúng filesystem đó: chạy du -xh --max-depth=1 từ thư mục gốc rồi đi dần xuống. Thường là log, bản backup cũ, hoặc file người dùng tải lên. Tôi giải phóng dung lượng một cách an toàn: truncate hoặc rotate các file log đã biết rõ, thu gọn journal của systemd theo dung lượng, và chuyển backup cũ ra khỏi máy. Tôi không bao giờ xóa gì trong thư mục của database. Có một cái bẫy: nếu xóa một file log mà process vẫn đang mở, dung lượng sẽ không được giải phóng cho đến khi process đó đóng file. Lệnh lsof +L1 liệt kê những file như vậy; khi đó ta truncate file hoặc restart service. Sau đó tôi khởi động lại service bị lỗi, kiểm tra site chạy bình thường, rồi xử lý nguyên nhân gốc: logrotate, chính sách lưu giữ, hoặc tăng ổ đĩa. Ở Akktis tôi xử lý các sự cố đầy ổ đĩa theo cách này, và sau đó ghi lại bước kiểm tra để lần sau phát hiện sớm hơn.

df -h; df -i
sudo du -xh --max-depth=1 / | sort -h | tail
sudo du -xh --max-depth=1 /var | sort -h | tail
sudo lsof +L1                       # deleted but still open
sudo truncate -s 0 /var/log/app/huge.log
sudo journalctl --vacuum-size=500M
sudo logrotate -f /etc/logrotate.d/nginx

Know: The CV wording: confirm with df and du, clear logs safely, restart, then note the check for next time.

Trap: rm on a log that is still open frees nothing. Deleting files under /var/lib/mysql corrupts the database.

Follow-up: "How do you stop it happening again?" logrotate with size and count, journald SystemMaxUse, backups shipped off the box, and an alert at 80 to 90 percent.

38High CPU or high loadLoad vs cores, user vs iowait vs steal, then what changed.~71s✓

A server has very high load or CPU. How do you investigate?

First I check whether it is really CPU. uptime shows the load average over 1, 5, and 15 minutes. On Linux, load counts processes waiting for the CPU and also those stuck waiting on disk, so I compare it with the number of cores. Then top or htop. If user time is high, a process is busy: I find it and look at its logs or what it is doing. If iowait is high, the CPU is idle and waiting on disk, so the real problem is disk I/O, maybe a heavy query or a backup, and iostat or iotop helps. If steal time is high on a VM, the host is overloaded. Then I ask what changed: new traffic, a deploy, a cron job, a runaway loop. On a PHP server, a common cause is too many workers for the memory, which pushes the machine into swap. I mitigate first, by restarting a stuck worker or pausing a job, and then fix the real cause.

Một server đang có load hoặc CPU rất cao. Bạn điều tra thế nào?

Đầu tiên tôi kiểm tra xem có thật là do CPU không. Lệnh uptime cho load average trong 1, 5 và 15 phút. Trên Linux, load tính cả process đang chờ CPU lẫn process đang bị kẹt chờ ổ đĩa, nên tôi so nó với số core. Sau đó dùng top hoặc htop. Nếu user time cao, có một process đang bận: tôi tìm ra nó và xem log hoặc xem nó đang làm gì. How do you work with SSH, file permissions, and systemd day to day?

SSH is how I work on servers, with keys only, no passwords, and no direct root login, using sudo when needed. For permissions, every file has an owner, a group, and read, write, and execute bits for each. The web server user, often www-data, needs to read the code and write only where the app writes, like storage or uploads. The fix for a permission error is the right owner or group, never chmod 777. systemd manages services. systemctl starts, stops, restarts, and reloads them, enable makes them start on boot, status shows whether they are running, and journalctl -u reads their logs. For web servers I prefer reload over restart, after testing the config, because reload keeps existing connections. A unit file can also restart a process automatically when it fails, which is how I'd keep a long-running process alive on a VM. At Akktis this was daily work on Ubuntu and Debian.

What is the difference between a 502 and a 504, and how do you debug each?

Both come from a proxy, like Nginx or a load balancer, reporting on its upstream. A 502 Bad Gateway means the proxy reached for the upstream and got nothing valid back: the connection was refused, the process crashed, or the response was broken. With PHP that is often PHP-FPM being down, or Nginx pointing at the wrong socket. A 504 Gateway Timeout means the upstream accepted the request but did not answer in time: a slow query, a stuck external call, or a timeout set lower than the work needs. So a 502 sends me to the upstream process and its logs, and a 504 sends me to whatever was slow. On Cloud Run the codes shift a little. A 503 usually means no instance could take the request, for example the container failed to start or the service hit max instances. A 504 means the request ran past the service's request timeout. Reloading Nginx alone rarely fixes either one.

502 và 504 khác nhau thế nào, và bạn debug từng loại ra sao?

Cả hai đều do một proxy như Nginx hoặc load balancer trả về, để báo về upstream phía sau nó. 502 Bad Gateway nghĩa là proxy gọi đến upstream nhưng không nhận được gì hợp lệ: kết nối bị từ chối, process bị crash, hoặc response bị hỏng. Với PHP, thường là PHP-FPM đang chết, hoặc Nginx trỏ sai socket. 504 Gateway Timeout nghĩa là upstream đã nhận request nhưng không trả lời kịp: một query chậm, một lần gọi ra ngoài bị treo, hoặc timeout đặt thấp hơn thời gian công việc cần. Nên gặp 502 thì tôi xem process upstream và log của nó, còn gặp 504 thì tôi tìm xem cái gì đang chậm. Trên Cloud Run thì các mã này hơi khác. 503 thường nghĩa là không có instance nào nhận được request, ví dụ container không khởi động được hoặc service đã chạm max instances. 504 nghĩa là request chạy quá request timeout của service. Chỉ reload Nginx thì hiếm khi sửa được lỗi nào trong hai lỗi này.

systemctl status php8.3-fpm
grep -i "connect() to unix" /var/log/nginx/error.log | tail
# 504
grep -i "upstream timed out" /var/log/nginx/error.log | tail
# relevant knobs: fastcgi_read_timeout / proxy_read_timeout, PHP max_execution_time

Know: Cloud Run's request timeout defaults to 5 minutes and can go up to 60. A 500 is the app itself failing.

Trap: Raising every timeout to hide a slow query. The 504 goes away and the slowness stays.

Follow-up: "Users see 502 only under load?" PHP-FPM pm.max_children reached, or the upstream crashing from memory.

44Cloud networking: VPC, subnets, firewallGCP VPC is global, AWS VPC is regional. Private by default.~66s✓

Explain cloud networking basics: VPCs, subnets, and firewalls.

A VPC is your private network in the cloud, split into subnets, with firewall rules that decide what traffic is allowed and routes that decide where it goes. One difference interviewers like to test: in Google Cloud, a VPC is global and each subnet is regional; in AWS, a VPC is regional and each subnet sits in one availability zone. The other key idea is public versus private. Only the entry point, usually a load balancer, should be reachable from the internet. App servers and databases sit on private addresses and reach the internet, if they need to, through Cloud NAT. Cloud Run is outside your VPC by default; to reach private resources it uses Direct VPC egress or a connector. My hands-on side of this is firewall rules: on the Akktis servers, I opened only the ports a service needed. Firewall rules are not the whole security story; IAM and app authentication still matter.

Bạn giải thích cơ bản về mạng trên cloud: VPC, subnet và firewall.

VPC là mạng riêng của ta trên cloud, được chia thành các subnet, có rule firewall quyết định traffic nào được phép và bảng định tuyến quyết định traffic đi đâu. Có một khác biệt người phỏng vấn hay hỏi: trên Google Cloud, VPC là global và mỗi subnet thuộc một region; còn trên AWS, VPC thuộc một region và mỗi subnet nằm trong một availability zone. Ý quan trọng thứ hai là công khai và riêng tư. Chỉ điểm vào, thường là load balancer, mới nên truy cập được từ internet. Server ứng dụng và database dùng địa chỉ nội bộ, và nếu cần ra internet thì đi qua Cloud NAT. Cloud Run mặc định nằm ngoài VPC; muốn truy cập tài nguyên nội bộ thì nó dùng Direct VPC egress hoặc một connector. Phần tôi làm thực tế là rule firewall: trên các server ở Akktis, tôi chỉ mở những port mà service cần. Firewall chưa phải là toàn bộ bảo mật; IAM và xác thực ở tầng ứng dụng vẫn quan trọng.

Know: GCP firewall rules apply to the whole VPC and target instances by network tag or service account. AWS has security groups (stateful, per instance) and NACLs (stateless, per subnet).

Trap: "Firewall equals security."

Follow-up: "Public vs private subnet?" A public subnet has a route to the internet gateway; a private one goes out only through NAT and cannot be reached from outside.

45IAM and least privilegePrincipal, role, resource. One service account per service.~66s✓

Explain IAM and least privilege. How do you apply them?

IAM answers who can do what on which resource. A principal, meaning a user, a group, or a service account, gets a role, which is a set of permissions, on a resource like a project or a bucket. Least privilege means the smallest role on the smallest scope that does the job. In practice, each service runs as its own service account, not the default Compute account with Editor. A Cloud Run service that reads two secrets and writes to one bucket gets Secret Accessor on those secrets and object access on that bucket, nothing project-wide. CI deploys with its own service account, not my personal credentials, so the audit log shows which pipeline did what. Humans get viewer access by default and elevated roles only when they need them. The red flag is Owner or Editor given to everyone "to make it work". That is how a small mistake becomes the incident story later.

Bạn giải thích IAM và nguyên tắc quyền tối thiểu. Bạn áp dụng chúng thế nào?

IAM trả lời câu hỏi ai được làm gì trên tài nguyên nào. Một principal, tức là user, group hoặc service account, được gán một role, là một tập quyền, trên một tài nguyên như project hoặc bucket. Quyền tối thiểu nghĩa là role nhỏ nhất, trên phạm vi nhỏ nhất, mà vẫn làm được việc. Thực tế, mỗi service chạy bằng service account riêng, chứ không dùng account Compute mặc định có quyền Editor. Một service Cloud Run đọc hai secret và ghi vào một bucket thì chỉ được Secret Accessor trên hai secret đó và quyền với object trên bucket đó, không có gì ở cấp project. CI deploy bằng service account riêng, không dùng thông tin đăng nhập cá nhân của tôi, để audit log cho thấy pipeline nào đã làm gì. Người dùng mặc định chỉ có quyền xem, và chỉ được nâng quyền khi thật sự cần. Dấu hiệu nguy hiểm là ai cũng được Owner hoặc Editor "cho chạy được". Đó là cách một lỗi nhỏ sau này trở thành câu chuyện sự cố.

49Terraform and infrastructure as codeDeclarative, init, plan, apply, modules. Studied, not owned.~65s✓

What is infrastructure as code? How does Terraform work?

Infrastructure as code means the infrastructure is defined in files, reviewed in pull requests, and created the same way every time, instead of clicked together in a console. Terraform is declarative: you describe the resources you want, and it works out what to create, change, or destroy. The workflow is terraform init to download providers and set up the state backend, terraform plan to show exactly what will change, and terraform apply to do it, ideally applying the same plan that was reviewed. Modules package a repeated pattern, like a Cloud Run service with its service account and secrets, so each environment calls the same module with different variables. My level is honest: I have studied Terraform, but I have not owned a Terraform codebase in production. On a team, I'd start by reading their modules and state setup, run plan in a safe environment first, and make small changes through review.

Infrastructure as code là gì? Terraform hoạt động thế nào?

Infrastructure as code nghĩa là hạ tầng được định nghĩa bằng file, được review qua pull request, và được tạo ra giống hệt nhau mỗi lần, thay vì bấm tay trên console. Terraform theo kiểu khai báo: ta mô tả các tài nguyên ta muốn, và nó tự tính cần tạo, sửa hay xóa gì. Quy trình là terraform init để tải provider và cấu hình nơi lưu state, terraform plan để thấy chính xác cái gì sẽ thay đổi, và terraform apply để thực hiện, tốt nhất là apply đúng bản plan đã được review. Module đóng gói một mẫu lặp lại, ví dụ một service Cloud Run kèm service account và secret, để mỗi môi trường gọi cùng một module với biến khác nhau. Tôi nói thật về trình độ của tôi: tôi đã học Terraform nhưng chưa phụ trách một codebase Terraform trên production. Khi vào team, tôi sẽ bắt đầu bằng việc đọc module và cách họ cấu hình state, chạy plan ở môi trường an toàn trước, và thay đổi từng phần nhỏ qua review.

Know: terraform plan -out=tfplan then terraform apply tfplan applies exactly what was reviewed. terraform fmt and validate belong in CI. OpenTofu is the open-source fork.

50Terraform state and driftRemote, locked, sensitive. Plan shows drift.~70s✓

What is Terraform state, and what is drift?

State is Terraform's record of which real resources belong to which blocks in the code, with their IDs and attributes. A plan compares three things: the code, the state, and what the cloud really has. On a team, state must be remote and locked. A Cloud Storage backend locks natively, and in recent Terraform versions the S3 backend can lock with a lock file in the bucket, so the old DynamoDB lock table is deprecated. Two people applying at once without a lock can corrupt the state. State also contains secrets in plain text, like generated passwords, so the bucket needs tight access, versioning, and encryption, and state never goes into Git. Drift is when someone changes a resource in the console and the code no longer matches. terraform plan shows it, and you either bring the change into code or revert it. Common mistakes are manual changes, giant applies, and editing state by hand. This is knowledge from study, not from running it.

Terraform state là gì, và drift là gì?

State là bản ghi của Terraform cho biết tài nguyên thật nào ứng với khối nào trong code, kèm ID và thuộc tính của chúng. Lệnh plan so sánh ba thứ: code, state, và những gì thực sự có trên cloud. Khi làm theo team, state phải để ở xa và có khóa. Backend Cloud Storage có cơ chế khóa sẵn, còn ở các phiên bản Terraform gần đây, backend S3 có thể khóa bằng một file khóa ngay trong bucket, nên bảng khóa DynamoDB kiểu cũ đã bị deprecated. Hai người cùng apply mà không có khóa có thể làm hỏng state. State còn chứa secret ở dạng văn bản thường, như mật khẩu được sinh ra, nên bucket phải giới hạn quyền chặt, bật versioning và mã hóa, và state không bao giờ được đưa vào Git. Drift là khi ai đó sửa tài nguyên trên console và code không còn khớp nữa. terraform plan sẽ cho thấy điều đó, và ta hoặc đưa thay đổi đó vào code, hoặc hoàn tác nó. Những lỗi hay gặp là sửa tay, apply một lần quá nhiều thứ, và sửa state bằng tay. Đây là kiến thức tôi học, chưa phải từ vận hành thực tế.

terraform {
  backend "gcs" {
    bucket = "my-tf-state"
    prefix = "prod"
  }
}
# S3: backend "s3" { bucket = "...", key = "...", use_lockfile = true }
terraform plan -refresh-only   # show drift without changing anything
terraform import ...           # adopt a resource created by hand

Know: S3 native locking (use_lockfile) arrived in Terraform 1.10 and is the recommended path from 1.11, where dynamodb_table is deprecated.

Trap: Sharing a local terraform.tfstate file over chat.

Follow-up: "How do you detect drift on a schedule?" A CI job that runs plan -detailed-exitcode and alerts on exit code 2.

51Logs, metrics, and tracesMetrics detect, logs explain, traces show where time went.~64s✓

What is the difference between monitoring, logging, and tracing? What do you use?

Metrics are numbers over time, such as request rate, error rate, latency, and memory. They are cheap to keep and good for alerts and trends. Logs are detailed events, and they explain what happened in one request. Traces follow one request across services and show where the time went. Metrics tell me something is wrong; logs and traces tell me why. On my own projects, Cloud Logging collects the Cloud Run request and app logs, and I filter them by revision after a deploy. On Aquanix, Sentry collects API errors with stack traces, grouped, so a new error after a release stands out. For the IELTS AI calls I use Langfuse tracing, which separates a bad model answer from an upstream failure. To make all of this useful, logs need structured JSON fields and a request ID, so I can search them instead of reading them line by line.

Monitoring, logging và tracing khác nhau thế nào? Bạn dùng những gì?

Metric là các con số theo thời gian, như số request, tỉ lệ lỗi, latency và bộ nhớ. Lưu metric rẻ, và phù hợp để cảnh báo và xem xu hướng. Log là các sự kiện chi tiết, giải thích chuyện gì đã xảy ra trong một request. Trace theo một request đi qua nhiều service và cho thấy thời gian bị tốn ở đâu. Metric cho tôi biết có gì đó sai; log và trace cho tôi biết vì sao. Ở các dự án của tôi, Cloud Logging gom log request và log ứng dụng của Cloud Run, và sau mỗi lần deploy tôi lọc chúng theo revision. Ở Aquanix, Sentry gom lỗi API kèm stack trace, được nhóm lại, nên lỗi mới sau một lần release sẽ nổi lên ngay. Với các lần gọi AI trong IELTS, tôi dùng tracing của Langfuse, giúp tách một câu trả lời tồi của model khỏi lỗi từ phía nhà cung cấp. Để những thứ này hữu ích, log cần có trường JSON có cấu trúc và một request ID, để tôi tìm kiếm được thay vì đọc từng dòng.

Know: Observability means you can answer new questions from the data you already collect, without shipping new code. OpenTelemetry is the standard way to emit traces and metrics.

Trap: Collecting logs with no alerts: you find out from users.

Follow-up: "What fields do you always log?" Timestamp, severity, request ID, route, status, latency, revision or version, and a user or tenant ID where allowed. Never secrets or tokens.

52What to alert on, and Prometheus with AlertmanagerGolden signals, actionable alerts. Prometheus evaluates, Alertmanager notifies.~64s✓

What would you alert on? How do Prometheus, Alertmanager, and Grafana fit together?

I alert on symptoms users feel, not on every cause. The four golden signals are a good start: latency, traffic, errors, and saturation, meaning CPU, memory, disk, or connection pools. A good alert is actionable. Someone has to do something when it fires, and it should link to a runbook. High CPU for two minutes is not worth waking someone up for, but a rising 5xx rate, or a disk at 90 percent and still filling, is. In the Prometheus stack the roles are split. Prometheus scrapes metrics from exporters and from the apps, stores them as time series, and evaluates the alert rules. Alertmanager receives the alerts that fire, groups them, removes duplicates, silences them during maintenance, and routes them to Slack, email, or a pager. Grafana draws the dashboards. I have not run a Prometheus setup myself. On Google Cloud, Cloud Monitoring alert policies do the same job.

Bạn sẽ đặt cảnh báo cho những gì? Prometheus, Alertmanager và Grafana kết hợp với nhau thế nào?

Tôi đặt cảnh báo cho những triệu chứng người dùng cảm nhận được, chứ không phải mọi nguyên nhân. Bốn tín hiệu vàng là điểm khởi đầu tốt: latency, traffic, lỗi, và mức bão hòa, tức là CPU, bộ nhớ, ổ đĩa hay connection pool. Một cảnh báo tốt phải hành động được. Khi nó kêu thì phải có người làm gì đó, và nó nên dẫn đến một runbook. CPU cao hai phút thì không đáng để đánh thức ai, nhưng tỉ lệ lỗi 5xx đang tăng, hay ổ đĩa ở 90% và vẫn đang đầy thêm, thì đáng. Trong bộ Prometheus, vai trò được tách riêng. Prometheus thu metric từ exporter và từ ứng dụng, lưu thành chuỗi thời gian, và tính các rule cảnh báo. Alertmanager nhận các cảnh báo đã kích hoạt, nhóm lại, loại bỏ trùng lặp, tắt tạm khi bảo trì, và gửi đến Slack, email hoặc hệ thống gọi trực. Grafana vẽ dashboard. Tôi chưa tự vận hành Prometheus. Trên Google Cloud, alert policy của Cloud Monitoring làm cùng một việc.

Know: An exporter exposes metrics for something that cannot itself (node_exporter for Linux hosts, mysqld_exporter for MySQL). Prometheus pulls; push is only for short jobs through the Pushgateway.

Trap: "Prometheus sends the alert." It evaluates rules; Alertmanager notifies. Grafana is not a log store.

53SLI, SLO, and error budgetMeasure, target, allowance. Budget gone means slow down.~59s✓

What is an SLI, an SLO, and an error budget?

An SLI is the measurement: success rate, latency, or how fresh a job's output is. An SLO is the target, for example 99.9 percent of requests succeeding under a latency we agreed on, over 30 days. The error budget is how much failure that target still allows. At 99.9 percent, that is about 43 minutes of full outage a month. While there is budget left, the team can ship faster and take risks. When the budget is gone, I slow risky releases and spend the time on reliability. I talk about it in operational terms: what should page someone at night, and what can wait until morning. I have not run a formal SRE program. My practice has been smaller: after an incident like a full disk, I wrote down the check that would have caught it earlier.

SLI, SLO và error budget là gì?

SLI là thứ được đo: tỉ lệ thành công, latency, hoặc độ mới của kết quả một job. SLO là mục tiêu, ví dụ 99,9% request thành công dưới mức latency đã thống nhất, tính trong 30 ngày. Error budget là phần lỗi mà mục tiêu đó vẫn cho phép. Với 99,9%, đó là khoảng 43 phút sập hoàn toàn mỗi tháng. Khi vẫn còn budget, team có thể release nhanh hơn và chấp nhận rủi ro. Khi hết budget, tôi làm chậm các release rủi ro lại và dành thời gian cho độ ổn định. Tôi nói về nó theo góc vận hành: cái gì cần gọi người dậy lúc nửa đêm, cái gì có thể chờ đến sáng. Tôi chưa chạy một chương trình SRE chính thức. Việc tôi làm nhỏ hơn: sau một sự cố như đầy ổ đĩa, tôi ghi lại bước kiểm tra lẽ ra đã giúp phát hiện sớm hơn.

Know: 99.9% over 30 days is 43.2 minutes; 99.99% is 4.3 minutes. An SLA is the contract with a penalty; the SLO should be stricter than the SLA.

Trap: 100% as a target. It blocks every release and is never true.

Follow-up: "How do you alert on an SLO?" Burn-rate alerts: page when the budget is being used fast, ticket when it is used slowly.

How would you centralize logs? Which tools would you choose?

First, logs belong in one searchable place, not on each box. On Cloud Run that comes built in: anything the app writes to stdout or stderr ends up in Cloud Logging, and if the app writes JSON lines, fields like severity and a request ID become searchable. A Compute Engine VM does not do that by itself. You install the Ops Agent, which ships system logs, the journal, and files like the Nginx logs to Cloud Logging, and collects metrics too. Outside Google Cloud, the common choice is the ELK stack, with Elasticsearch, Logstash, and Kibana. It is powerful for search but heavy to run. Grafana Loki is lighter because it indexes only labels, not the full text. Graylog is another option. I choose by log volume, how long logs must be kept, how they will be searched, and who will run the system. For a small product, the cloud provider's logging is enough.

Bạn sẽ gom log về một chỗ thế nào? Bạn chọn công cụ nào?

Trước hết, log phải nằm ở một chỗ tìm kiếm được, chứ không nằm rải rác trên từng máy. Trên Cloud Run thì có sẵn: mọi thứ app ghi ra stdout hoặc stderr đều vào Cloud Logging, và nếu app ghi theo từng dòng JSON thì các trường như severity và request ID sẽ tìm kiếm được. VM Compute Engine thì không tự làm việc đó. Ta cài Ops Agent, nó gửi log hệ thống, journal và các file như log Nginx lên Cloud Logging, và thu cả metric. Grafana Loki nhẹ hơn vì chỉ đánh index theo label, không đánh index toàn bộ nội dung. Graylog là một lựa chọn khác. Tôi chọn dựa trên lượng log, thời gian cần lưu, cách sẽ tìm kiếm, và ai sẽ vận hành hệ thống đó. Với một sản phẩm nhỏ, logging của nhà cung cấp cloud là đủ.

Know: Cloud Logging reads a JSON line's severity and message fields. Set retention per bucket; route long-term logs to Cloud Storage or BigQuery with a sink.

55Walk me through an incidentConfirm, mitigate, communicate, root cause, follow-up.~69s✓

Walk me through how you handle a production incident.

I go in this order. First, detect and confirm: what exactly is failing, for whom, and since when. Then I mitigate before looking for the root cause. If a release caused it, I roll back. If a disk is full, I free space. Users come first, and the perfect explanation can wait. While I work, I post short status updates, so nobody has to ask. When the service is stable, I find the root cause with evidence: what changed, what the logs say, and what I checked. Then the follow-up: a fix so it cannot happen the same way again, plus a check or alert that would have caught it earlier. A disk-full incident at Akktis followed this shape. I confirmed it with df and du, cleared logs safely, restarted the service, checked the site, and then noted the check for next time. Under pressure I keep the same four lines: what changed, what failed, what I verified, and what I changed.

Bạn đi qua cách bạn xử lý một sự cố production.

Tôi đi theo thứ tự này. Đầu tiên là phát hiện và xác nhận: chính xác cái gì đang lỗi, ai bị ảnh hưởng, và từ lúc nào. Sau đó tôi giảm thiệt hại trước khi tìm nguyên nhân gốc. Nếu do một lần release, tôi rollback. Nếu ổ đĩa đầy, tôi giải phóng dung lượng. Người dùng là ưu tiên, còn lời giải thích hoàn hảo có thể chờ. Trong lúc xử lý, tôi cập nhật tình hình ngắn gọn để không ai phải hỏi. Khi service đã ổn, tôi tìm nguyên nhân gốc bằng bằng chứng: cái gì đã thay đổi, log nói gì, và tôi đã kiểm tra những gì. Rồi đến phần tiếp theo: một bản sửa để lỗi không lặp lại theo cùng cách, cộng với một bước kiểm tra hoặc cảnh báo lẽ ra đã phát hiện sớm hơn. Một sự cố đầy ổ đĩa ở Akktis đi đúng theo trình tự đó. Tôi xác nhận bằng df và du, dọn log an toàn, restart service, kiểm tra site, rồi ghi lại bước kiểm tra cho lần sau. Khi bị áp lực, tôi giữ đúng bốn ý: cái gì đã thay đổi, cái gì lỗi, tôi đã kiểm tra gì, và tôi đã thay đổi gì.

Know: Severity first: how many users, which feature, is data at risk. One person leads, others help.

Trap: Guessing "maybe DNS" before reading logs, or debugging for an hour while users stay down.

Follow-up: "Incident vs known bug?" An incident is live user impact that needs action now; a known bug is tracked and scheduled.

56Postmortems and on-callBlameless, timeline, root cause, owned action items.~65s✓

How do you run a postmortem? What makes on-call work well?

A postmortem is a short written review after an incident, and it has to be blameless. The question is how the system let this happen, not who broke it. When people are blamed, they hide mistakes, and you lose the information you need. Mine covers the impact, meaning who was affected and for how long, and a timeline with times. Then the root cause and what contributed to it, what went well, what slowed us down, and a few action items, each with an owner and a date. The action items are the point; without them it is just a story. On-call works when alerts are few and actionable, each alert links to a runbook, and there is a clear handoff between shifts. 57Secrets managementOut of Git and images, least readers, rotate on leak. Env vs mounted on Cloud Run.~70s✓

How do you manage secrets?

Secrets never go in Git, in an image, or in a ticket screenshot. They live in a secret manager, like Google Secret Manager, or in the CI tool's encrypted secrets, and each workload can read only the secrets it needs. On Cloud Run there are two ways to use a secret, and the difference matters. As an environment variable, the value is read when the instance starts, so after rotating you need a new revision or new instances, even if you reference the latest version. As a mounted volume with latest, the app reads the file and gets the new value without a redeploy. In my own APIs the model keys stay on the server and are never shipped in the mobile app. If a secret leaks, I rotate it first and investigate second. Deleting the commit or the chat message is not enough, because the old value still works until it is revoked. And I make sure secrets never get printed in logs.

Bạn quản lý secret thế nào?

Secret không bao giờ nằm trong Git, trong image, hay trong ảnh chụp màn hình đính kèm ticket. Nó nằm trong một secret manager như Google Secret Manager, hoặc trong phần secret được mã hóa của công cụ CI, và mỗi workload chỉ đọc được những secret nó cần. Trên Cloud Run có hai cách dùng secret, và khác biệt này quan trọng. Nếu dùng dạng biến môi trường, giá trị được đọc lúc instance khởi động, nên sau khi đổi secret ta cần một revision mới hoặc instance mới, kể cả khi đang trỏ tới phiên bản latest. Nếu mount dạng volume với latest, app đọc file và nhận giá trị mới mà không cần deploy lại. Trong các API của tôi, key của model nằm trên server và không bao giờ được đóng gói vào app mobile. Nếu một secret bị lộ, tôi đổi nó trước rồi mới điều tra. Xóa commit hay xóa tin nhắn là chưa đủ, vì giá trị cũ vẫn dùng được cho đến khi bị thu hồi. Và tôi đảm bảo secret không bao giờ bị in ra log.

58Server hardening basicsKeys only, few ports, patches, ownership, TLS, and a runbook.~63s✓

How do you harden a Linux server?

I keep server hardening practical, and I write it down. For access: SSH keys only, password login off, no direct root login, and named accounts with sudo, so actions can be traced to a person. For the network: the firewall allows only what the server serves, usually 80 and 443, and SSH from trusted ranges where possible. Every open port is something I have to defend, and a "temporary" rule that opens everything is never temporary. For patching: security updates on a schedule, and bigger upgrades in a maintenance window. For the app: correct file ownership instead of 777, .env files outside the web root, and TLS everywhere. Then the documentation: how to deploy, where the logs are, and how the certificate renews. At Akktis I left a short runbook with each server change. I don't claim formal security audits. I claim the basics, applied consistently.

Bạn tăng cường bảo mật cho một server Linux thế nào?

Tôi làm việc tăng cường bảo mật theo hướng thực tế, và luôn ghi lại. Về truy cập: chỉ dùng SSH key, tắt đăng nhập bằng mật khẩu, không cho đăng nhập trực tiếp bằng root, mỗi người có tài khoản riêng dùng sudo, để hành động nào cũng truy được về một người. Về mạng: firewall chỉ cho phép những gì server phục vụ, thường là 80 và 443, còn SSH chỉ từ những dải địa chỉ tin cậy khi có thể. Mỗi port đang mở là một thứ tôi phải bảo vệ, và một rule "tạm thời" mở hết mọi thứ thì không bao giờ là tạm thời. Về vá lỗi: cập nhật bảo mật theo lịch, và các bản nâng cấp lớn thì làm trong khung giờ bảo trì. Về ứng dụng: đặt đúng chủ sở hữu file thay vì 777, file .env nằm ngoài thư mục web, và TLS ở mọi nơi. Cuối cùng là tài liệu: cách deploy, log nằm đâu, và certificate gia hạn thế nào. Ở Akktis, mỗi lần thay đổi server tôi đều để lại một runbook ngắn. Tôi không nhận là đã làm audit bảo mật chính thức. 59Backups, RPO, RTO, and restore testingA backup counts only after a restore. Real example: the MySQL cutover.~66s✓

How do you think about backups and disaster recovery? What are RPO and RTO?

RPO, the recovery point objective, is how much data you can afford to lose, measured in time. A daily backup means up to a day of lost writes. RTO, the recovery time objective, is how long the service can be down while you restore. The business sets both, and they drive the design. A nightly dump is cheap but has a large RPO. Binary logs or point-in-time recovery shrink it. A replica you can promote shrinks the RTO. The rule I care about most is that a backup only counts once you have restored it. So copies go off the server, and restores get tested on a schedule. My real example is the MySQL migration at Akktis. Before the cutover I took backups, so there was a known point to return to. After it, I validated that the application's reads and writes worked. The backup plus that validation was the safety net for the change.

Bạn nghĩ thế nào về backup và khôi phục sau thảm họa? RPO và RTO là gì?

RPO, tức recovery point objective, là lượng dữ liệu ta chấp nhận mất, tính bằng thời gian. Backup hằng ngày nghĩa là có thể mất đến một ngày dữ liệu ghi. RTO, tức recovery time objective, là service được phép ngừng bao lâu trong lúc khôi phục. Cả hai do phía kinh doanh đặt ra, và chúng quyết định cách thiết kế. Dump mỗi đêm thì rẻ nhưng RPO lớn. Binary log hoặc khôi phục theo thời điểm giúp thu nhỏ RPO. Một bản replica có thể nâng lên làm chính giúp thu nhỏ RTO. Nguyên tắc tôi coi trọng nhất là một bản backup chỉ có giá trị khi ta đã khôi phục được từ nó. Nên bản sao phải nằm ngoài server, và việc khôi phục phải được thử theo lịch. Ví dụ thật của tôi là lần migrate MySQL ở Akktis. Trước khi cutover, tôi backup để có một điểm chắc chắn có thể quay về. Sau đó, tôi kiểm tra các thao tác đọc và ghi của ứng dụng đều chạy đúng. Bản backup cùng bước kiểm tra đó là lưới an toàn cho thay đổi này.

mysqldump --single-transaction --routines --triggers appdb | gzip > appdb-$(date +%F).sql.gz
# restore test on another host
gunzip -c appdb-2026-01-01.sql.gz | mysql appdb_restore_test
mysql -e "SELECT COUNT(*) FROM appdb_restore_test.orders"

Know: 3-2-1: three copies, two media, one off-site. Firestore has scheduled backups and point-in-time recovery; Cloud Storage has versioning and soft delete.

Trap: A backup on the same disk as the database. Or a backup nobody has ever restored.

Follow-up: "What would you set for a small SaaS?" Ask the business. A common start: nightly full plus binary logs, copies off-site, a monthly restore drill.

60Keyless CI with Workload Identity FederationShort-lived OIDC tokens instead of a JSON key.~62s✓

How should a CI system authenticate to Google Cloud?

The old way to let CI deploy to Google Cloud was a service account JSON key stored as a CI secret. It is a long-lived credential: if it leaks, it works until someone deletes it. Workload Identity Federation removes the key. The CI provider, for example GitHub Actions, issues a short-lived OIDC token for each run. Google trusts that issuer, checks conditions such as the repository and the branch, and exchanges the token for short-lived Google credentials for one specific service account. Nothing long-lived is stored anywhere. With Cloud Build there is no key at all, because the build runs as a service account inside the project, which is part of why it is simple on my own projects. If I set up GitHub Actions to deploy Cloud Run today, I would use Workload Identity Federation, restricted to the main branch of one repository.

Một hệ thống CI nên xác thực với Google Cloud thế nào?

Cách cũ để CI deploy lên Google Cloud là lưu file JSON key của service account làm secret trong CI. Đó là thông tin xác thực sống lâu: nếu bị lộ, nó vẫn dùng được cho đến khi có người xóa. Workload Identity Federation bỏ được cái key đó. Nhà cung cấp CI, ví dụ GitHub Actions, cấp một OIDC token ngắn hạn cho mỗi lần chạy. Google tin nhà phát hành đó, kiểm tra các điều kiện như repo và nhánh, rồi đổi token lấy thông tin xác thực Google ngắn hạn cho đúng một service account. Không có gì sống lâu được lưu ở đâu cả. Với Cloud Build thì hoàn toàn không có key, vì bản build chạy bằng một service account ngay trong project, đó cũng là một phần lý do nó đơn giản với các dự án của tôi. Nếu hôm nay tôi cấu hình GitHub Actions để deploy Cloud Run, tôi sẽ dùng Workload Identity Federation, giới hạn cho nhánh main của đúng một repo.

# GitHub Actions
permissions:
  id-token: write
  contents: read
steps:
  - uses: google-github-actions/auth@v2
    with:
      workload_identity_provider: projects/123/locations/global/workloadIdentityPools/ci/providers/github
      service_account: deployer@PROJECT.iam.gserviceaccount.com

Know: The attribute condition (for example assertion.repository == 'org/repo') is what stops any other repository from using your pool.

Trap: A pool with no attribute condition: any GitHub repo could request tokens.

Follow-up: "And on AWS?" Same idea: an IAM OIDC provider and a role the workflow assumes.

61Encryption, CMEK, and Cloud ArmorDefault encryption, customer keys, edge WAF. Awareness level.~64s✓

What do you know about encryption at rest, CMEK, and Cloud Armor?

Google Cloud encrypts data at rest by default, with keys Google manages, and TLS protects data in transit. CMEK, customer-managed encryption keys, means the keys live in Cloud KMS under your control. You can rotate them, audit their use, and revoke them, and if you disable the key, the data becomes unreadable. That gives control, which regulated customers often require, and also responsibility, because a destroyed key means lost data. Cloud Armor is Google's edge protection on the external Application Load Balancer. It is a WAF with rules for common attacks like SQL injection, plus rate limiting and IP allow and deny lists. It needs a load balancer, so a plain Cloud Run URL does not get it. I have not operated CMEK or Cloud Armor in production. I know when to raise them in a design discussion, and I would learn the project's setup by reading it first.

Bạn biết gì về mã hóa dữ liệu lưu trữ, CMEK và Cloud Armor?

Google Cloud mặc định mã hóa dữ liệu lưu trữ bằng khóa do Google quản lý, còn TLS bảo vệ dữ liệu khi truyền đi. CMEK, tức khóa mã hóa do khách hàng quản lý, nghĩa là khóa nằm trong Cloud KMS dưới quyền kiểm soát của khách hàng. Khách hàng có thể xoay vòng khóa, kiểm tra ai dùng nó, và thu hồi nó; nếu tắt khóa, dữ liệu không đọc được nữa. Điều đó cho khách hàng quyền kiểm soát, thứ mà khách hàng trong ngành có quy định chặt thường yêu cầu, đồng thời cũng là trách nhiệm, vì khóa bị hủy nghĩa là mất dữ liệu. Cloud Armor là lớp bảo vệ ở biên của Google, gắn với Application Load Balancer bên ngoài. Nó là một WAF với các rule chặn kiểu tấn công phổ biến như SQL injection, kèm giới hạn tần suất và danh sách IP cho phép hoặc chặn. Nó cần có load balancer, nên một URL Cloud Run trần thì không có. Tôi chưa vận hành CMEK hay Cloud Armor trên production. Tôi biết khi nào nên nêu chúng ra trong một buổi thảo luận thiết kế, và tôi sẽ học cách dự án đang cấu hình bằng cách đọc nó trước.

Know: Envelope encryption: a data key encrypts the data, and the KMS key encrypts the data key. To force traffic through Cloud Armor, set Cloud Run ingress to internal and load balancer only.

Trap: Name-dropping CMEK without knowing who is responsible for the key.

Follow-up: "When would a customer ask for CMEK?" Compliance rules, or the need to revoke the provider's access to their data on demand.

What does your Cloud Build file look like for a Cloud Run service?

It has three steps: build the image tagged with the short commit SHA, push it to Artifact Registry, and deploy that exact tag to Cloud Run. Tagging by commit is what makes rollback and debugging simple, because I always know which code a revision runs.

File Cloud Build của bạn cho một service Cloud Run trông thế nào?

Nó có ba bước: build image gắn tag bằng short commit SHA, push lên Artifact Registry, rồi deploy đúng tag đó lên Cloud Run. Gắn tag theo commit giúp việc rollback và debug đơn giản, vì tôi luôn biết một revision đang chạy code nào.

substitutions:
  _IMAGE: REGION-docker.pkg.dev/PROJECT/REPO/api
  _REGION: REGION
steps:
  - name: gcr.io/cloud-builders/docker
    args: [build, -t, "${_IMAGE}:${SHORT_SHA}", .]
  - name: gcr.io/cloud-builders/docker
    args: [push, "${_IMAGE}:${SHORT_SHA}"]
  - name: gcr.io/google.com/cloudsdktool/cloud-sdk
    entrypoint: gcloud
    args: [run, deploy, api, "--image=${_IMAGE}:${SHORT_SHA}", "--region=${_REGION}"]
images: ["${_IMAGE}:${SHORT_SHA}"]
options:
  logging: CLOUD_LOGGING_ONLY

Know: User substitutions must start with an underscore. $SHORT_SHA is filled only for trigger runs; for manual gcloud builds submit pass it yourself.

How do you set up a Cloud Build trigger that deploys to Cloud Run? What permissions does it need?

A trigger connects the repository to Cloud Build, so a push to a branch runs the build file. The part people get wrong is permissions. The build's service account needs to push to Artifact Registry and deploy to Cloud Run, and it also needs Service Account User on the runtime service account, because deploying a service that runs as another account means acting as that account.

Bạn cấu hình trigger Cloud Build để deploy lên Cloud Run thế nào? Nó cần những quyền gì?

Trigger nối repo với Cloud Build, để mỗi lần push lên một nhánh thì file build được chạy. Phần hay bị sai là quyền. Service account của bản build cần push được lên Artifact Registry và deploy được lên Cloud Run, và còn cần role Service Account User trên service account runtime, vì deploy một service chạy bằng account khác nghĩa là đang hành động thay cho account đó.

B=build-sa@PROJECT.iam.gserviceaccount.com
R=api-runtime@PROJECT.iam.gserviceaccount.com

  --member=serviceAccount:$B --role=roles/artifactregistry.writer
gcloud iam service-accounts add-iam-policy-binding $R \
  --member=serviceAccount:$B --role=roles/iam.serviceAccountUser
gcloud builds triggers create github --name=api-dev --repo-owner=ORG --repo-name=api \
  --branch-pattern='^dev$' --build-config=cloudbuild.yaml --service-account=projects/PROJECT/serviceAccounts/$B

How do you read Cloud Run logs during an incident?

I filter logs by service, revision, and severity around the incident time, rather than scrolling. The revision label tells me whether the errors started with the new deploy, which decides between a rollback and a deeper look.

67Runbook: new VM and SSH accessOwn service account, gcloud ssh, keys only, keep a session open.~22s✓

How do you create a VM and lock down SSH?

I create the VM with a service account that has only what it needs, connect with gcloud compute ssh or OS Login, and then lock SSH down: keys only, no root login. I keep one session open while I change the SSH settings, and test a second login before closing the first.

Bạn tạo VM và khóa chặt SSH thế nào?

Tôi tạo VM với một service account chỉ có đúng quyền cần thiết, kết nối bằng gcloud compute ssh hoặc OS Login, rồi khóa SSH lại: chỉ dùng key, không cho đăng nhập bằng root. Tôi giữ một phiên đang mở trong lúc đổi cấu hình SSH, và thử đăng nhập phiên thứ hai trước khi đóng phiên đầu.

gcloud compute instances create app-1 --zone=$ZONE --machine-type=e2-small \
  --image-family=ubuntu-2404-lts-amd64 --image-project=ubuntu-os-cloud \
  --service-account=vm-sa@PROJECT.iam.gserviceaccount.com --scopes=cloud-platform
gcloud compute ssh app-1 --zone=$ZONE
# /etc/ssh/sshd_config.d/10-hardening.conf
PasswordAuthentication no
PermitRootLogin no
sudo sshd -t && sudo systemctl reload ssh

Know: On Ubuntu 22.10 and later, including 24.04, SSH is socket-activated: the port lives in ssh.socket, so change it with systemctl edit ssh.socket (ListenStream), then daemon-reload and restart the socket. The unit is ssh; sshd is only an alias.

Trap: Reloading SSH with a broken config and no second session open.

Follow-up: "How do you avoid a public SSH port?" IAP TCP forwarding: gcloud compute ssh --tunnel-through-iap, with port 22 open only to 35.235.240.0/20.

68Runbook: firewall with VPC rules and UFWNetwork tags in the cloud, UFW on the box, SSH first.~15s✓

How do you open only the ports a server needs?

On Google Cloud I open ports with VPC firewall rules aimed at a network tag, and on the server UFW adds a second layer. I always allow SSH before enabling UFW, or I lock myself out.

Bạn chỉ mở những port mà server cần bằng cách nào?

Trên Google Cloud tôi mở port bằng rule firewall của VPC, áp vào một network tag, còn trên server thì UFW thêm một lớp nữa. Tôi luôn cho phép SSH trước khi bật UFW, nếu không sẽ bị khóa ở ngoài.

gcloud compute firewall-rules create allow-web --network=default \
  --allow=tcp:80,tcp:443 --target-tags=web --source-ranges=0.0.0.0/0
gcloud compute firewall-rules create allow-ssh-iap --network=default \
  --allow=tcp:22 --target-tags=ssh --source-ranges=35.235.240.0/20
gcloud compute instances add-tags app-1 --tags=web,ssh --zone=$ZONE
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable && sudo ufw status verbose

Know: Check from outside: curl -I http://EXTERNAL_IP and nc -vz EXTERNAL_IP 22.

Trap: Docker-published ports skip UFW. Temporary 0.0.0.0/0 SSH rules that never get removed.

Follow-up: "Which wins, VPC rule or UFW?" Both must allow the traffic; either one can block it.

69Runbook: Nginx vhost for Laravel, and TLSsites-available, nginx -t, reload, certbot, check the timer.~23s✓

How do you put a new PHP site behind Nginx with HTTPS?

I write the site config in sites-available, link it into sites-enabled, test with nginx -t, and reload. For TLS, DNS must already point at the server; certbot gets the certificate and installs a renewal timer. I check that timer, because Let's Encrypt no longer emails expiry warnings and certificate lifetimes are getting shorter.

Bạn đưa một site PHP mới chạy sau Nginx với HTTPS thế nào?

Tôi viết cấu hình site trong sites-available, tạo link sang sites-enabled, kiểm tra bằng nginx -t rồi reload. Với TLS, DNS phải trỏ về server trước; certbot lấy certificate và cài sẵn một timer để gia hạn. Tôi kiểm tra timer đó, vì Let's Encrypt không còn gửi email báo hết hạn và thời hạn certificate đang ngắn dần.

server {
    listen 80;
    server_name example.com;
    root /var/www/app/public;
    index index.php;
    location / { try_files $uri $uri/ /index.php?$query_string; }
    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
    }
    location ~ /\. { deny all; }
}
sudo ln -s /etc/nginx/sites-available/app.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d example.com
systemctl list-timers | grep certbot
sudo certbot renew --dry-run

Know: Let's Encrypt stopped expiry emails in 2025 and is moving from 90-day to 45-day certificates by 2028, so renewal must be automatic and monitored. Ubuntu 24.04 ships PHP 8.3.

Trap: Editing a live config without nginx -t: one typo and the reload takes down every site on the box. Pointing root at the project folder instead of public exposes .env.

Follow-up: "Self-signed is fine?" For a lab, yes; public sites need a public CA.
