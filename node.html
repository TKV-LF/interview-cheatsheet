03Progress storage: hydrate, don't N+1JD: efficient APIs + client/server split.~37s✓

How do you store user progress between the app and the server?

Server is the source of truth in Firestore under user_data/{username}. On app open or after Google/Apple sign-in the client calls GET /api/storage and writes every key into AsyncStorage. After that, reading a skill topic is local — we don't fan out GET /storage/key/:key per topic. Writes still go to the server and update the cache. That was a product bug we fixed: opening a skill used to look like N+1 HTTP. Same efficiency rule as BaseVN reports — don't hide a chatty loop in the UI.

Bạn lưu tiến độ user giữa app và server thế nào?

Server là nguồn sự thật, lưu trên Firestore theo document của từng user. Khi mở app hoặc sau khi đăng nhập Google hay Apple, client gọi GET /api/storage một lần rồi ghi hết các key vào AsyncStorage. Sau đó, mở một topic là đọc local, không gọi lần lượt từng key lên server. Thao tác ghi vẫn gửi lên server rồi cập nhật cache. Đây là một bug thật chúng tôi đã sửa: trước đó mỗi lần mở một skill là một loạt request, giống N+1 nhưng qua HTTP. 05IAP: Apple and Google on ExpressMoney path. Server must be source of truth.~51s✓

How do in-app purchases work on IELTS?

The app talks to the store, but the server decides who is Pro. After a purchase the client sends the purchase to /api/iap on Express. The server verifies it with Apple or Google, then writes the entitlement and the transaction to Firestore. Pro access, ads, and daily quotas all read that server flag, so a modified app cannot unlock itself. Apple's signed data is a JWS, so I verify the certificate chain and pin the algorithm instead of trusting the decoded JSON. For Google, the server checks the purchase with the Play Developer API using a service account. I store the transaction id, so if the same purchase is verified twice it updates one entitlement instead of granting two.

In-app purchase trên IELTS hoạt động thế nào?

App nói chuyện với store, nhưng server mới là bên quyết định ai là Pro. Mua xong, client gửi giao dịch lên /api/iap của Express. Server verify với Apple hoặc Google, rồi ghi entitlement và transaction vào Firestore. Quyền Pro, quảng cáo và quota hằng ngày đều đọc cờ đó từ server, nên app bị sửa cũng không tự mở khóa được. Dữ liệu ký của Apple là JWS, nên tôi verify chuỗi certificate và cố định thuật toán, không tin JSON sau khi decode. Với Google, server kiểm tra giao dịch qua Play Developer API bằng service account. Tôi lưu transaction id, nên nếu cùng một giao dịch được verify hai lần thì chỉ cập nhật một entitlement, không cấp hai lần.

08The event loopMust-know. Phases, microtasks, the thread pool, and what blocks.~57s✓

How does the Node.js event loop work, and why does it matter?

Node runs my JavaScript on one thread. libuv handles the I/O, and when an operation finishes its callback is queued. The loop goes round in phases: timers run due setTimeout and setInterval callbacks, pending callbacks come next, poll waits for and runs I/O callbacks, check runs setImmediate, and then close callbacks. After each callback Node drains the microtasks: process.nextTick first, then promise callbacks. Some work that looks async uses the libuv thread pool, four threads by default: file system calls, dns.lookup, crypto like pbkdf2 or async bcrypt, and zlib. It matters because anything synchronous and CPU-heavy, like a huge JSON.parse or a sync hash, stops every other request on that instance. So in a route I await I/O, keep CPU work small, and move heavy work to a worker or a job.

Event loop của Node.js hoạt động thế nào, và vì sao nó quan trọng?

Node chạy JavaScript của tôi trên một thread. libuv lo phần I/O, xong việc thì callback được đưa vào hàng đợi. Vòng lặp đi qua các phase: timers chạy callback setTimeout và setInterval đến hạn, rồi pending callbacks, poll chờ và chạy callback I/O, check chạy setImmediate, rồi close callbacks. Sau mỗi callback, Node chạy hết microtask: process.nextTick trước, rồi đến callback của promise. Một số việc trông như async thật ra chạy trên thread pool của libuv, mặc định bốn thread: thao tác file, dns.lookup, crypto như pbkdf2 hay bcrypt bản async, và zlib. Nó quan trọng vì việc đồng bộ mà nặng CPU, như JSON.parse một chuỗi rất lớn hay hash đồng bộ, sẽ chặn mọi request khác trên instance đó. Nên trong route tôi await I/O, giữ phần CPU nhỏ, và đẩy việc nặng sang worker hoặc job.

Know: Phases: timers → pending → poll → check → close. Microtasks after each callback: nextTick, then promises. Thread pool (UV_THREADPOOL_SIZE, default 4): fs, dns.lookup, crypto, zlib. Network sockets do not use the pool.

Trap: Saying Node is multi-threaded, or that async/await makes CPU work non-blocking.

09nextTick vs setImmediate vs setTimeoutWhere each one runs in the loop. Then say you rarely need them.~56s✓

What is the difference between process.nextTick, setImmediate, and setTimeout?

They run at different points of the loop. process.nextTick runs right after the current operation, before promise callbacks and before the loop moves on. It is useful for calling back asynchronously while keeping order, but a recursive nextTick can starve I/O. Promise callbacks run next, as microtasks. setImmediate runs in the check phase, right after poll. setTimeout with zero really means at least one millisecond, in the timers phase. Inside an I/O callback, setImmediate always fires before setTimeout zero. From the main module the order of those two is not guaranteed, because it depends on how fast the loop starts. In application code I rarely need any of them. If a long loop must yield, I use setImmediate, but usually the better fix is to move that work off the request.

process.nextTick, setImmediate và setTimeout khác nhau thế nào?

Chúng chạy ở những thời điểm khác nhau trong vòng lặp. process.nextTick chạy ngay sau thao tác hiện tại, trước callback của promise và trước khi vòng lặp đi tiếp. Nó hữu ích khi cần gọi callback bất đồng bộ mà vẫn giữ thứ tự, nhưng gọi nextTick đệ quy có thể làm I/O không bao giờ được chạy. Callback của promise chạy ngay sau đó, dưới dạng microtask. setImmediate chạy ở phase check, ngay sau poll. setTimeout với 0 thực chất là ít nhất một mili giây, ở phase timers. Trong một callback I/O, setImmediate luôn chạy trước setTimeout 0. Còn ở module chính thì thứ tự hai cái này không chắc chắn, vì phụ thuộc vòng lặp khởi động nhanh hay chậm. Trong code ứng dụng tôi hiếm khi cần đến chúng. Nếu một vòng lặp dài phải nhường lượt, tôi dùng setImmediate, nhưng thường cách tốt hơn là đưa việc đó ra khỏi request.

Know: Order inside I/O callback: nextTick → promises → setImmediate → setTimeout(0). queueMicrotask() queues a promise-style microtask.

Trap: Saying setTimeout(fn, 0) runs immediately, or that the main-module order of setImmediate vs setTimeout is fixed.

10Many requests on one threadOne thread. I/O waits. CPU must not.~64s✓

Walk through what happens when a request hits your Node API, and when two arrive at once.

One JavaScript thread serves many requests, because most of a request is waiting.

1Accept

Cloud Run hands the request to the Node process.

↓
2Middleware

Parse JSON, check auth, attach a request id. If auth fails, stop here.

↓
3Handler

Call one service and await Firestore or the database. While it waits, the loop serves other requests.

↓
4Response

JSON back, or the error middleware returns a generic error and logs the real one.

So two requests at once are not two threads. The first one reaches an await, and Node starts the second while the database works. What breaks this is synchronous CPU work: a sync password hash, a huge JSON transform, a big loop. That blocks every request on the instance, so it goes to a worker or a job. That is how the PhysioFix, Aquanix, and IELTS APIs run on Cloud Run.

11Promises, async/await, and unhandled rejectionsSame model underneath. Know what crashes the process.~59s✓

How do promises, async/await, and errors fit together in Node?

async/await is syntax over promises, so the rules are the same. An async function always returns a promise, and a throw inside it becomes a rejection. I await anything that can fail inside try/catch, or let it reach one error handler. A floating promise, with no await and no catch, becomes an unhandled rejection, and since Node 15 the default is to crash the process. I want that to be loud: on Aquanix errors go to Sentry, and the platform restarts the instance rather than letting it run in an unknown state. For parallel work I use Promise.all when one failure should fail the whole thing, and Promise.allSettled when I want every result. A common bug is await inside a for loop when the calls are independent. That makes them run one by one for no reason.

Promise, async/await và lỗi ăn khớp thế nào trong Node?

async/await là cú pháp bên trên promise, nên quy tắc giống nhau. Hàm async luôn trả về promise, và throw bên trong nó trở thành rejection. Chỗ nào await có thể lỗi thì tôi để trong try/catch, hoặc cho nó đi tới một error handler chung. Promise bị bỏ trôi, không await cũng không catch, sẽ thành unhandled rejection, và từ Node 15 mặc định là process bị crash. Tôi muốn lỗi đó phải lộ ra: ở Aquanix lỗi được gửi về Sentry, và nền tảng khởi động lại instance thay vì để nó chạy tiếp trong trạng thái không rõ. Khi chạy song song, tôi dùng Promise.all nếu một lỗi phải làm hỏng cả nhóm, và Promise.allSettled khi cần kết quả của từng cái. Một bug hay gặp là await trong vòng for khi các lời gọi không phụ thuộc nhau, khiến chúng chạy tuần tự một cách vô ích.

Know: Node 15+: --unhandled-rejections=throw by default. process.on('unhandledRejection') is for logging, not for carrying on. Promise.any / race exist too.

Trap: Catching the rejection and swallowing it so the bug disappears.

What are streams in Node, and what is backpressure?

A stream lets me handle data in chunks instead of loading it all into memory. Readable, writable, and transform streams are the ones I use most. Backpressure is the important part. If the producer is faster than the consumer, write returns false, and the producer has to wait for the drain event, or memory keeps growing. I do not manage that by hand. I use pipeline from node:stream/promises, which respects backpressure and destroys every stream if one of them fails. A typical case is an export: read rows in batches, transform them to CSV, and pipe them into the response or a Cloud Storage upload. My big exports were in PHP, the 500,000-record tax reports at BaseVN, and the rule is the same in Node: never build the whole file in memory inside the request.

Stream trong Node là gì, và backpressure là gì?

Stream cho phép xử lý dữ liệu theo từng đoạn thay vì nạp hết vào bộ nhớ. Tôi hay dùng nhất là readable, writable và transform stream. Backpressure là phần quan trọng. Nếu bên đọc nhanh hơn bên ghi, hàm write trả về false, và bên đọc phải chờ sự kiện drain, nếu không bộ nhớ cứ tăng mãi. Tôi không tự xử lý chuyện đó bằng tay. Tôi dùng pipeline từ node:stream/promises, nó tôn trọng backpressure và hủy mọi stream nếu một stream lỗi. Ví dụ điển hình là export: đọc dữ liệu theo từng lô, chuyển sang CSV, rồi pipe vào response hoặc upload lên Cloud Storage. Các bản export lớn của tôi là ở PHP, báo cáo thuế hơn 500.000 bản ghi ở BaseVN, và nguyên tắc ở Node cũng vậy: không bao giờ dựng cả file trong bộ nhớ bên trong request.

13ES modules vs CommonJSHow Node decides, what breaks, what you pick.~60s✓

What is the difference between CommonJS and ES modules in Node?

CommonJS is the original Node module system: require and module.exports, loaded synchronously. ES modules use import and export, are the standard across browsers and Node, load asynchronously, and allow top-level await. Node decides per file. A .mjs file is ESM, a .cjs file is CommonJS, and a .js file follows the type field in package.json. ESM can import CommonJS. The other way used to need a dynamic import, but current Node, 22 and 24, can require an ES module that has no top-level await. Small differences catch people: there is no __dirname in ESM, so I use import.meta.dirname, and relative imports need the file extension. On a TypeScript server I set module to NodeNext so the compiler follows the same rules as Node. For a new service I pick ESM. For an existing one I follow what it already uses.

CommonJS và ES modules trong Node khác nhau thế nào?

CommonJS là hệ module gốc của Node: require và module.exports, load đồng bộ. ES modules dùng import và export, là chuẩn chung cho cả trình duyệt và Node, load bất đồng bộ, và cho phép top-level await. Node quyết định theo từng file. File .mjs là ESM, .cjs là CommonJS, còn .js thì theo field type trong package.json. ESM import được CommonJS. Chiều ngược lại trước đây phải dùng dynamic import, nhưng Node hiện tại, bản 22 và 24, đã require được một ES module không có top-level await. Vài khác biệt nhỏ hay làm vấp: ESM không có __dirname, nên tôi dùng import.meta.dirname, và import tương đối phải ghi rõ đuôi file. Ở server TypeScript, tôi đặt module là NodeNext để compiler theo đúng quy tắc của Node. Service mới thì tôi chọn ESM. Service có sẵn thì tôi theo cái nó đang dùng.

Know: require(esm) is on by default from Node 22.12 / 20.19. import.meta.dirname since Node 20.11. ESM imports are live bindings; CJS exports are a copied object.

16Middleware and the request pipelineExpress runs middleware in order. Nest has a fixed order: know it.~62s✓

Walk me through how a request runs through middleware in Express, and in Nest.

In Express everything is middleware, and it runs in the order I register it. Usually: security headers and CORS, the JSON body parser, a request id for logs, authentication, then the router, where a route can add its own validation and permission check before the handler. The error middleware, the one with four arguments, is registered last. If auth fails it responds 401 and never calls next, so the business code does not run. Nest has more named steps in a fixed order: middleware first, then guards that decide whether the request may continue, then interceptors before the handler, then pipes that validate and transform the input, then the controller. On the way out the interceptors run again, and exception filters turn any thrown error into the response. Either way, I make sure secrets never get logged and every path ends in one error shape.

Hãy đi qua cách một request chạy qua middleware trong Express, và trong Nest.

Trong Express mọi thứ là middleware, và chạy theo đúng thứ tự tôi đăng ký. Thường là: security header và CORS, body parser JSON, request id cho log, xác thực, rồi tới router, nơi từng route có thể thêm validation và kiểm tra quyền trước handler. Error middleware, loại có bốn tham số, được đăng ký cuối cùng. Nếu auth fail, nó trả 401 và không gọi next, nên code nghiệp vụ không chạy. Nest có nhiều bước có tên hơn, theo thứ tự cố định: middleware trước, rồi guard quyết định request có được đi tiếp không, rồi interceptor chạy trước handler, rồi pipe validate và biến đổi input, rồi tới controller. Trên đường ra, interceptor chạy lại lần nữa, và exception filter biến lỗi được throw thành response. Dù dùng cái nào, tôi đảm bảo secret không bao giờ vào log và mọi nhánh đều trả cùng một format lỗi.

What is the difference between OAuth 2, OpenID Connect, and JWT?

They answer different questions. OAuth 2 is delegated authorization: the user lets my app call an API for them, and my app gets an access token without seeing their password. OpenID Connect is a layer on top that adds login. It returns an id token, a JWT that says who the user is. JWT itself is only a token format. So Sign in with Google is OpenID Connect on OAuth 2.

1App

Opens Google sign-in with a PKCE challenge.

↓
2Google

User agrees. Google returns a one-time code.

↓
3App

Swaps the code and the PKCE verifier for tokens.

↓
4My API

Verifies the id token, finds or creates the user, issues its own session.

PKCE matters on mobile because a phone cannot keep a client secret. On IELTS my app is the client in this picture, and the server verifies the Google or Apple identity token. I have not built an authorization server.

OAuth 2, OpenID Connect và JWT khác nhau thế nào?

Chúng trả lời những câu hỏi khác nhau. OAuth 2 là ủy quyền: user cho phép app của tôi gọi một API thay họ, và app nhận access token mà không cần biết mật khẩu. OpenID Connect là lớp nằm trên, thêm phần đăng nhập. Nó trả về id token, một JWT cho biết user là ai. Còn JWT chỉ là một định dạng token. Nên Sign in with Google là OpenID Connect chạy trên OAuth 2.

1App

Mở trang đăng nhập Google kèm PKCE challenge.

↓
2Google

User đồng ý. Google trả về một code dùng một lần.

↓
3App

Đổi code cùng PKCE verifier lấy token.

↓
4API của tôi

Verify id token, tìm hoặc tạo user, cấp session của mình.

PKCE quan trọng trên mobile vì điện thoại không giữ được client secret. Ở IELTS, app của tôi là client trong hình này, và server verify identity token của Google hoặc Apple. Tôi chưa xây authorization server.

Know: OAuth 2 = authorization (access token). OIDC = authentication (id token, a JWT). PKCE = code_verifier / code_challenge, required for public clients. OAuth 1 signed every request; nobody starts there now.

Trap: Saying OAuth 2 proves who the user is. Saying JWT and OAuth are alternatives.

28How you check a JWTSignature with a pinned algorithm. Then exp, iss, aud. Then authorize.~63s✓

A client sends a JWT. What does the server do?

A JWT is three base64url parts: header, payload, signature. Anyone can decode the payload, so nothing in it counts until the signature checks out.

1Read

Take the Bearer token from the Authorization header.

↓
2Verify

Check the signature with the algorithm the server expects, never the one the header asks for.

↓
3Claims

Check exp, iss, and aud. Anything wrong is a 401.

↓
4Authorize

This user, this record. The token says who, not what.

Pinning the algorithm blocks the old tricks, like alg none, or a public key reused as an HMAC secret. I keep access tokens short and rotate refresh tokens. Logout revokes the refresh token on the server, because an issued JWT stays valid until it expires unless I keep a denylist. On Aquanix the token carries role and partnership, but the pond check still runs on every pond route.

Client gửi một JWT. Server làm gì?

JWT gồm ba phần base64url: header, payload, signature. Ai cũng decode được payload, nên chưa tin gì trong đó cho tới khi chữ ký hợp lệ.

1Đọc

Lấy Bearer token từ header Authorization.

↓
2Verify

Kiểm chữ ký bằng thuật toán server quy định, không theo thuật toán header yêu cầu.

↓
3Claim

Kiểm exp, iss và aud. Sai bất cứ cái nào là 401.

↓
4Phân quyền

User này, bản ghi này. Token nói là ai, không nói được làm gì.

Cố định thuật toán chặn được các mánh cũ, như alg none, hoặc dùng public key làm secret HMAC. Tôi để access token ngắn hạn và xoay vòng refresh token. Logout là thu hồi refresh token trên server, vì JWT đã cấp thì còn hiệu lực tới lúc hết hạn, trừ khi giữ một denylist. Ở Aquanix token có role và partnership, nhưng route nào của ao vẫn chạy kiểm tra quyền truy cập ao.

30Securing a webhookProve the sender, answer fast, expect duplicates.~61s✓

How do you secure and handle an incoming webhook?

A webhook is a public URL, so anyone can post to it. First I prove the sender. Many providers sign the raw body with a shared secret, an HMAC, so I compute it over the raw bytes before any JSON parsing and compare in constant time. Others sign with a key pair, like Apple's signed JWS, which I verify against their certificate chain. I also check the timestamp, so an old request cannot be replayed. A bad check is a 401 and nothing else runs. Second, I answer fast. On PhysioFix the xAI webhook is verified, returns 200, and only then opens the realtime socket, so the provider is not left waiting. Third, I assume it will arrive more than once. I store the provider's event id and skip one I have already handled, so a retry never grants or books twice.

Bạn bảo mật và xử lý một webhook gửi tới thế nào?

Webhook là một URL public, ai cũng gửi tới được. Việc đầu tiên là chứng minh bên gửi. Nhiều provider ký phần body gốc bằng secret dùng chung, gọi là HMAC, nên tôi tính chữ ký trên đúng byte gốc trước khi parse JSON và so sánh theo kiểu constant time. Một số khác ký bằng cặp khóa, như JWS của Apple, thì tôi verify theo chuỗi certificate của họ. Tôi cũng kiểm tra timestamp để một request cũ không bị gửi lại. Kiểm tra sai là 401 và không chạy gì thêm. Thứ hai, trả lời nhanh. Ở PhysioFix, webhook của xAI được verify, trả 200, rồi mới mở realtime socket, nên provider không phải chờ. Thứ ba, tôi coi như nó sẽ tới nhiều hơn một lần. Tôi lưu event id của provider và bỏ qua event đã xử lý, nên gửi lại không bao giờ cấp quyền hay đặt lịch hai lần.

Know: express.raw() on the webhook route, crypto.timingSafeEqual for the compare. Verify → 2xx fast → do the work → idempotent by event id.

Trap: Parsing JSON first and signing the re-serialized body. Doing slow work before answering, so the provider retries.

31Rate limiting429, an algorithm by name, and where the counter lives on Cloud Run.~60s✓

How do you rate-limit an API?

I limit anything public or expensive, especially routes that call a model, per user or per API key, and per IP on login. Over the limit is a 429 with a Retry-After header, and I log who hit it. The common algorithms are a fixed window, a sliding window, and a token bucket. Token bucket is my default because it allows a short burst and then a steady rate. Where the counter lives matters. On Cloud Run there are several instances, so an in-memory counter only limits one instance, and a client spread across instances gets several times the limit. A real limit needs a shared store like Redis, or a gateway in front. In-memory is only a cheap first guard. On IELTS the model keys sit on Express, so that is where a limit belongs, not in the app.

Bạn rate-limit API thế nào?

Tôi giới hạn mọi route public hoặc tốn kém, nhất là route gọi model, theo user hoặc theo API key, và theo IP với route đăng nhập. Vượt ngưỡng thì trả 429 kèm header Retry-After, và log lại ai chạm ngưỡng. Thuật toán hay dùng là fixed window, sliding window và token bucket. Tôi mặc định chọn token bucket vì nó cho phép một đợt ngắn rồi giữ tốc độ đều. Bộ đếm nằm ở đâu rất quan trọng. Trên Cloud Run có nhiều instance, nên bộ đếm trong memory chỉ giới hạn từng instance, và một client rải request qua các instance sẽ được gấp mấy lần ngưỡng. Muốn giới hạn thật thì cần kho dùng chung như Redis, hoặc một gateway phía trước. Bộ đếm trong memory chỉ là lớp chặn rẻ ban đầu. Ở IELTS, key model nằm ở Express, nên giới hạn phải đặt ở đó, không phải trong app.

33cluster, worker_threads, or more instances?Cores, CPU work, or traffic. On Cloud Run, usually more instances.~64s✓

When would you use cluster, worker_threads, or just run more instances?

They solve different problems. cluster forks several Node processes that share one port, so one machine can use all its cores. worker_threads run JavaScript on other threads inside one process, for CPU-heavy work like parsing a big file or resizing an image without blocking the event loop. child_process runs a separate program. On Cloud Run I usually need neither of the first two. The platform starts more instances when traffic grows, so I keep one Node process per container, keep it stateless, and tune concurrency and the maximum instance count. That is how my three Express APIs run. I would reach for a worker thread only when one request genuinely needs heavy CPU, and for a long job I would rather move it out of the request into a queue or a separate job. On a plain VM, PM2 or cluster is the usual way to use every core.

Khi nào bạn dùng cluster, worker_threads, hay chỉ chạy thêm instance?

Chúng giải quyết những vấn đề khác nhau. cluster tách ra nhiều process Node dùng chung một port, để một máy dùng hết các core. worker_threads chạy JavaScript trên thread khác bên trong một process, dành cho việc nặng CPU như parse file lớn hay resize ảnh mà không chặn event loop. child_process chạy một chương trình riêng. Trên Cloud Run tôi thường không cần hai cái đầu. Nền tảng tự bật thêm instance khi tải tăng, nên tôi giữ một process Node cho mỗi container, không lưu state, và chỉnh concurrency cùng số instance tối đa. Ba API Express của tôi chạy như vậy. Tôi chỉ dùng worker thread khi một request thật sự cần nhiều CPU, còn việc dài thì tôi đưa ra khỏi request, vào hàng đợi hoặc một job riêng. Trên một VM bình thường, PM2 hoặc cluster là cách phổ biến để dùng hết các core.

34Thousands of logins at onceYou have not had this spike. Say the shape, and be exact about hashing.~64s✓

How would you handle thousands of simultaneous login requests?

I have not had that spike, so I would describe the shape. The app is stateless, so more instances can take the load. Sessions or refresh tokens live in Redis or a database, not in the memory of one Node process, and the connection pool to that store is bounded. Password hashing is the CPU cost. 35Finding a memory leakProve it grows, compare two heap snapshots, bound the cache.~66s✓

How do you find a memory leak in a Node service?

First I confirm it is a leak and not just load. On Cloud Run that looks like memory climbing steadily across requests until the instance is killed for going over its limit, then starting again after every restart. Then I check the usual causes: a module-level cache or Map with no size limit, event listeners added per request and never removed, intervals never cleared, and closures holding large objects. To prove it, I reproduce locally with the same traffic, run node with --inspect, take a heap snapshot, run the load, take another, and compare them in Chrome DevTools to see which objects keep growing and what holds them. The fix is usually a bounded LRU cache or removing the listener, and the guard is a memory alert on the service. I have not had to chase a serious leak in my own APIs, so this is my method rather than a war story.

Bạn tìm memory leak trong một service Node thế nào?

Đầu tiên tôi xác nhận đó là leak chứ không phải chỉ do tải. Trên Cloud Run, dấu hiệu là memory tăng đều qua các request cho tới khi instance bị dừng vì vượt giới hạn, rồi lặp lại sau mỗi lần khởi động. Rồi tôi kiểm tra các nguyên nhân hay gặp: cache hoặc Map ở cấp module không giới hạn kích thước, event listener gắn theo mỗi request mà không gỡ, interval không clear, và closure giữ object lớn. Để chứng minh, tôi tái hiện ở local với cùng kiểu tải, chạy node với --inspect, chụp một heap snapshot, chạy tải, chụp thêm một cái, rồi so sánh trong Chrome DevTools để xem object nào cứ tăng và cái gì đang giữ nó. Cách sửa thường là cache LRU có giới hạn hoặc gỡ listener, và lớp bảo vệ là cảnh báo memory trên service. Tôi chưa phải truy một leak nghiêm trọng trong các API của tôi, nên đây là phương pháp của tôi chứ không phải câu chuyện thực tế.

Know: --inspect + heap snapshots (comparison view, retainers) · process.memoryUsage() · --heapsnapshot-signal · --max-old-space-size · MaxListenersExceededWarning is a hint.

Trap: Raising the memory limit and calling it fixed.

36Graceful shutdown on SIGTERMCloud Run sends SIGTERM, then about 10 seconds, then SIGKILL.~61s✓

How do you shut down a Node service gracefully?

Cloud Run sends SIGTERM before it stops an instance, on scale-down or a new deploy, and gives about ten seconds before SIGKILL. So I listen for SIGTERM and shut down in order. First stop taking new work: server.close stops accepting connections and lets in-flight requests finish. Then let running work complete, like a write to Firestore that a webhook still owes. Then close database connections, flush logs and Sentry, and exit with zero. I add a timer that forces exit if something hangs, so the platform does not kill the process in the middle of a write. The process must also receive the signal. I run node directly as the container's main process, not through npm start, which may not forward SIGTERM. PhysioFix is the case I think about most, because a live call holds an open socket that a deploy can cut.

Bạn tắt một service Node một cách an toàn thế nào?

Cloud Run gửi SIGTERM trước khi dừng một instance, khi giảm tải hoặc khi deploy bản mới, và cho khoảng mười giây trước khi gửi SIGKILL. Nên tôi bắt SIGTERM và tắt theo thứ tự. Trước hết ngừng nhận việc mới: server.close không nhận kết nối mới và để các request đang chạy làm xong. Rồi để việc đang dở hoàn tất, ví dụ một lần ghi Firestore mà webhook còn nợ. Rồi đóng kết nối database, đẩy hết log và Sentry, và thoát với mã 0. Tôi đặt thêm một timer buộc thoát nếu có gì bị treo, để nền tảng không phải kill process giữa lúc đang ghi. Process cũng phải nhận được tín hiệu. Tôi chạy node trực tiếp làm process chính của container, không qua npm start, vì npm có thể không chuyển tiếp SIGTERM. PhysioFix là trường hợp tôi nghĩ tới nhiều nhất, vì một cuộc gọi đang diễn ra giữ một socket mở mà một lần deploy có thể cắt ngang.

Know: SIGTERM → server.close() → finish in-flight → close pools → flush → process.exit(0), with a forced-exit timer under 10s. CMD ["node", "dist/server.js"]; PID 1 has no default signal handlers, so handle SIGTERM yourself (or use --init / tini).

Trap: process.exit() straight away, dropping in-flight requests. Long keep-alive connections holding server.close open (use closeIdleConnections).

Follow-up: How is this different on a VM with a supervisor? Same signal, but you choose the timeout.

Walk through deploying a Node API.

A push runs CI. Tests pass, then the pipeline builds a container image, pushes it to Artifact Registry, and deploys a new Cloud Run revision. On Aquanix that is Cloud Build on the dev branch. 38Upgrading Node and dependenciesAn upgrade is its own change: LTS, changelog, staging, cheap rollback.~62s✓

How do you upgrade Node or a major dependency safely?

I treat an upgrade as its own change, never mixed into a feature. I stay on an LTS line, today Node 22 or 24, and plan the move before the current one reaches end of life. I read the changelog for breaking changes, bump the version in one place, the Dockerfile base image and the engines field, run the tests, and deploy to staging first. For dependencies I keep a lockfile, use npm ci in CI, and take small updates one at a time so a failure points at one package. npm audit tells me about known vulnerabilities, but I check whether the vulnerable path is actually reachable before treating it as urgent. On Cloud Run the rollback is cheap, because the previous revision is still there, so I can ship the upgrade on a normal day and move traffic back if something breaks.

Bạn nâng cấp Node hoặc một dependency lớn một cách an toàn thế nào?

Tôi coi nâng cấp là một thay đổi riêng, không bao giờ trộn với tính năng. Tôi dùng bản LTS, hiện tại là Node 22 hoặc 24, và lên kế hoạch chuyển trước khi bản đang dùng hết hạn hỗ trợ. Tôi đọc changelog để tìm thay đổi phá vỡ, đổi version ở một chỗ, là base image trong Dockerfile và field engines, chạy test, rồi deploy lên staging trước. Với dependency, tôi giữ lockfile, dùng npm ci trong CI, và cập nhật từng chút một để nếu lỗi thì biết ngay do gói nào. npm audit báo các lỗ hổng đã biết, nhưng tôi kiểm tra đoạn code lỗi có thật sự được gọi tới không trước khi coi là khẩn cấp. Trên Cloud Run, rollback rất rẻ vì revision trước vẫn còn đó, nên tôi có thể ship bản nâng cấp vào một ngày bình thường và chuyển traffic về nếu có gì hỏng.

Know: Even-numbered releases become LTS · lockfile + npm ci · one change at a time · staging · rollback by revision.

How do you test a Node API?

I test where a mistake would hurt: validation, permission checks, and the paths that touch money or data. On PhysioFix, Jest covers the API. Pure logic, like mapping a webhook event or deciding what to send on the socket, gets plain unit tests with no network. Services get tests with the database or the provider faked at the boundary, so they stay fast. Then a smaller set of HTTP tests call real routes and check the status code and the JSON shape, including the error cases: no token is 401, someone else's record is 403, a bad body is 400. For things that go wrong in production, like a webhook arriving twice, I write that exact case. I do not chase a hundred percent coverage. The test I add after a bug is the most valuable one, because it guards a mistake that already happened.

Bạn test API Node thế nào?

40Testing an Express route with Jest and supertestExport the app, not the server. Test 401, 403, 400, then success.~63s✓

How would you test an Express route?

I split the app from the server. app.ts builds and exports the Express app, and server.ts is the only file that calls listen. Then supertest can call the app in memory, with no port and no deploy.

import request from 'supertest';
import { app } from '../src/app';

test('rejects a missing token', async () => {
  const res = await request(app).get('/api/items/1');
  expect(res.status).toBe(401);
});

For the happy path I sign a test token, and I replace Firestore or any outside API with a fake, through a Jest mock or by injecting the dependency, so the test is fast and needs no network. I check the status, the JSON shape, and that the fake was called with the right data. One test per rule I care about: missing token, wrong user, bad body, success. They run in CI before the image is built, so a broken route never reaches Cloud Run.
