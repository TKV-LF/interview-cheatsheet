Asked in round 1

What they asked. How JWT works; what you do when a user's token is stolen; “log out of all devices”; authorization and roles; and scenario questions around them. Expect a second round to go deeper on the same area, with follow-ups like “how fast does the cut-off happen?” and “doesn't that make JWT stateful again?”.

Answers. Full cards live on the Node page, so every interview can use them:

  • Access token and refresh token: the whole flow
  • A user's token was stolen. What do you do?
  • Log out of all devices
  • The JWT signing key leaked
  • How you design authorization
  • An admin removes a role, but the user still has access
  • A user changes the id in the URL and sees someone else's data
  • A user makes themselves admin through the profile form
  • One user, two organizations, two different roles

The spine to remember. Access token short and stateless; refresh token in the database, one row per device, rotated; revoke there. Token says who, the server decides what, per request and per record.

05NestJS or Hono? You use Express.Name the gap, then map Express to Nest in one minute.~64s✓

Have you used NestJS or Hono?

Not in production. My three APIs are Express with TypeScript. I have studied NestJS from its docs, so I know the shape, and I know where Express leaves me on my own.

In Express I already split each domain into a router, a service, and validation, and I put auth in middleware. NestJS makes that structure the default. A module groups a feature. Controllers take the request. Providers are services injected through the constructor. Guards decide whether the request may run, which is where my JWT and per-pond checks would go. Pipes validate and transform input. Interceptors wrap the call for logging or response shape, and exception filters turn errors into one response format.

Hono is the opposite direction: very small, built on the web-standard Request and Response, and it runs on Node, Bun, or Cloudflare Workers. It feels close to Express, so I would be productive in it quickly.

Bạn đã dùng NestJS hay Hono chưa?

Chưa dùng trên production. Ba API của tôi là Express với TypeScript. Tôi đã tìm hiểu NestJS qua tài liệu, nên tôi hiểu cấu trúc, và tôi biết Express để mình tự lo những phần nào.

Ở Express tôi đã tách mỗi domain thành router, service và phần validation, và đặt auth vào middleware. NestJS biến cấu trúc đó thành mặc định. Module gom một tính năng lại. Controller nhận request. Provider là các service được inject qua constructor. Guard quyết định request có được chạy hay không, đó là chỗ tôi sẽ đặt phần kiểm JWT và kiểm quyền theo từng ao. Pipe kiểm tra và chuyển đổi dữ liệu đầu vào. Interceptor bọc quanh lời gọi để log hoặc định dạng response, còn exception filter biến lỗi thành một format response thống nhất.

Hono thì ngược lại: rất nhỏ, xây trên Request và Response chuẩn của web, và chạy được trên Node, Bun hoặc Cloudflare Workers. Nó khá giống Express, nên tôi sẽ làm được việc với nó nhanh.

Know: Nest request order: middleware → guards → interceptors (before) → pipes → handler → interceptors (after) → exception filters. See also Express vs Nest.

Trap: Saying you “know Nest” and then being asked about providers' scopes or circular dependencies.

Follow-up: “How would you structure a Nest module for payments?” Controller, service, a provider for the payment SDK, a guard for auth, DTOs with class-validator.

06What is Hono, and when would you pick it?Web standards, many runtimes, typed RPC. Pick it for edge and small services.~63s✓

What is Hono, and when would you choose it over NestJS?

Hono is a small web framework built on the standard Request and Response objects. Because it does not depend on Node APIs, the same app runs on Cloudflare Workers, Bun, Deno, or Node. Routing and middleware look like Express, and it has helpers for validation with Zod, JWT, CORS, and a typed client, so the frontend can call routes with types taken from the server.

I would pick Hono for a small API, a webhook receiver, or anything that should run at the edge on Cloudflare, where cold start and bundle size matter. I would pick NestJS for a larger backend with many modules and several developers, where a fixed structure and dependency injection save time in review.

For a client MVP with a Next.js or TanStack frontend, Hono plus a typed client is a very fast way to keep one set of types across the stack.

Hono là gì, và khi nào bạn chọn nó thay vì NestJS?

Hono là một web framework nhỏ, xây trên Request và Response chuẩn của web. Vì không phụ thuộc vào API của Node, cùng một app có thể chạy trên Cloudflare Workers, Bun, Deno hay Node. Routing và middleware trông giống Express, và nó có sẵn helper cho validation bằng Zod, JWT, CORS, và một client có type, để frontend gọi route với type lấy thẳng từ server.

Tôi sẽ chọn Hono cho một API nhỏ, một service nhận webhook, hoặc thứ cần chạy ở edge trên Cloudflare, nơi thời gian khởi động và kích thước bundle quan trọng. Tôi chọn NestJS cho backend lớn hơn, nhiều module và nhiều developer, nơi cấu trúc cố định và dependency injection giúp review nhanh hơn.

Với một MVP cho khách có frontend Next.js hoặc TanStack, Hono cùng typed client là cách rất nhanh để giữ một bộ type chung cho cả stack.

Know: Web-standard Request/Response; runs on Workers, Bun, Deno, Node; middleware; zod-validator; hono/client RPC types.

Trap: Claiming production Hono. Say this is what you read and tried.

Follow-up: “How do you share types with the frontend?” Hono RPC client, or a shared package with Zod schemas.

08PostgreSQL, coming from MySQLMySQL is deep. Name what changes in Postgres.~60s✓

Our projects use PostgreSQL. What is your experience?

My production SQL is MySQL, and it is deep: at BaseVN I designed the schema and tuned indexes and queries for tax and reporting flows over 500,000 records. I have not run PostgreSQL in production, but most of that work carries over: indexes, reading the query plan, transactions, and avoiding N+1.

What I would watch in Postgres: it has richer types, such as JSONB with GIN indexes, arrays, and proper enums. Upsert is INSERT … ON CONFLICT, and RETURNING gives the written row back without a second query. Identity columns replace auto-increment. DDL runs inside a transaction, so a failed migration rolls back cleanly. Partial indexes, like an index only on active rows, are very useful. The default isolation is Read Committed, not Repeatable Read like MySQL InnoDB. And EXPLAIN ANALYZE runs the query and shows real timings.

Dự án bên tôi dùng PostgreSQL. Kinh nghiệm của bạn thế nào?

SQL tôi làm trên production là MySQL, và làm sâu: ở BaseVN tôi thiết kế schema, tối ưu index và query cho các luồng thuế và báo cáo trên hơn 500.000 bản ghi. Tôi chưa vận hành PostgreSQL trên production, nhưng phần lớn kinh nghiệm đó áp dụng được: index, đọc query plan, transaction, và tránh N+1.

Những điểm tôi sẽ để ý ở Postgres: kiểu dữ liệu phong phú hơn, như JSONB với GIN index, mảng, và enum đúng nghĩa. Upsert viết là INSERT … ON CONFLICT, và RETURNING trả lại dòng vừa ghi mà không cần query thứ hai. Identity column thay cho auto-increment. 16Keeping your database in step with the chainEvents, confirmations, reorgs, idempotency. Same discipline as webhooks.~77s✓

A smart contract emits events. How would your backend keep its database in sync?

I would treat the chain like a payment provider that sends webhooks, with two extra problems: events can arrive late, and recent blocks can be replaced in a reorg.

I have not built this on a chain. The idempotent worker, the checkpoint, and the reconciliation are what I do for webhooks and sync jobs already.

I log each request and response with an id, without secrets or personal data, so when the vendor says “we never got it”, I can show what I sent.

Anything that does not need to finish inside the user's request goes to a background job. At BaseVN the VietnamWorks and TopCV integration worked that way: candidate sync ran as jobs with retries, request logging, and monitoring, so a job board being down did not break our product.

18How you design an APIResources, one error shape, pagination, idempotency, versioning.~71s✓

How do you design a REST API for a new product?

I start from the screens and the jobs the client needs, not from the tables. Then I name resources as nouns, like /ponds/:id/readings, and use the methods for what they mean: GET reads, POST creates, PATCH changes part of a record, DELETE removes.

A few rules I keep on every API. One error shape everywhere, with a stable code, a message, and field errors for validation, and status codes that mean something: 400 for bad input, 401 for no login, 403 for logged in but not allowed, 404, 409 for a conflict. Lists are paginated from day one, with a cursor if the data changes often. Every POST that creates money or a record from an external event accepts an idempotency key. Input is validated at the edge with a schema, and the same schema gives the TypeScript type.

On Aquanix, the phone app and the web app call the same Express API and the same access check, so the rules live in one place.

Bạn thiết kế REST API cho một sản phẩm mới thế nào?

Tôi bắt đầu từ các màn hình và những việc khách cần làm, không phải từ các bảng dữ liệu. Sau đó tôi đặt tên resource bằng danh từ, như /ponds/:id/readings, và dùng method đúng nghĩa: GET để đọc, POST để tạo, PATCH để sửa một phần, DELETE để xóa.

Có vài quy tắc tôi giữ ở mọi API. Một format lỗi thống nhất, có mã lỗi ổn định, thông điệp, và lỗi theo từng field khi validate, và status code phải có ý nghĩa: 400 khi dữ liệu sai, 401 khi chưa đăng nhập, 403 khi đã đăng nhập nhưng không có quyền, 404, và 409 khi xung đột. Danh sách phải phân trang ngay từ đầu, dùng cursor nếu dữ liệu thay đổi thường xuyên. POST nào tạo ra tiền hoặc tạo bản ghi từ sự kiện bên ngoài thì nhận idempotency key. Dữ liệu đầu vào được validate ngay ở cửa vào bằng schema, và cũng chính schema đó sinh ra type TypeScript.

Ở Aquanix, app điện thoại và app web gọi cùng một API Express và cùng một lớp kiểm quyền, nên luật nằm ở một chỗ.

19Authentication and authorizationJWT with role, then a per-resource check. That is the part people forget.~65s✓

How do you handle authentication and authorization?

Authentication is who you are, and authorization is what you may touch. Most real bugs are in the second one.

On Aquanix, phone login issues a JWT that carries the user's role and partnership. Every pond route then checks that this member is assigned to that pond, so changing the id in the URL does not show someone else's data. Sensor readings are only attached after that check. The nightly job runs on a separate authenticated route, so a user token can never start the batch worker.

For the token itself: I verify the signature with a pinned algorithm and check expiry, issuer, and audience. Access tokens are short. For a browser, I prefer an HttpOnly, Secure cookie over localStorage, with CSRF protection. For “Sign in with Google” or Apple, which IELTS uses, the provider proves identity through OpenID Connect, and my server still issues its own session and owns the permissions.

Bạn xử lý xác thực và phân quyền thế nào?

Xác thực là bạn là ai, còn phân quyền là bạn được đụng vào cái gì. Phần lớn bug thật nằm ở phần thứ hai.

Ở Aquanix, đăng nhập bằng số điện thoại sẽ cấp một JWT chứa vai trò và partnership của người dùng. Mỗi route của ao đều kiểm tra thành viên này có được gán cho ao đó không, nên đổi id trên URL cũng không xem được dữ liệu của người khác. Dữ liệu cảm biến chỉ được gắn vào sau bước kiểm tra đó. Job chạy ban đêm dùng một route xác thực riêng, nên token của người dùng không bao giờ khởi động được worker xử lý hàng loạt.

Về bản thân token: tôi kiểm tra chữ ký với thuật toán cố định, và kiểm tra thời hạn, issuer và audience. Access token có thời hạn ngắn. Với trình duyệt, tôi ưu tiên cookie HttpOnly, Secure hơn là localStorage, kèm bảo vệ CSRF. Với “Đăng nhập bằng Google” hay Apple, mà IELTS có dùng, nhà cung cấp chứng minh danh tính qua OpenID Connect, còn server của tôi vẫn tự cấp session riêng và tự quản lý quyền.

Trap: Only checking “is logged in”. That is how IDOR bugs happen.

20Web security you check on every featureAccess per resource, input, secrets, rate limits, and the LLM-specific ones.~68s✓

What web security issues do you check for?

I go through a short list on every feature.

Broken access control first: can this user read or change this exact record? That is the Aquanix pond check. Then input: validate every body and query with a schema, use parameterized queries so SQL injection is not possible, and escape output so user text cannot become script. Secrets live in the secret manager, never in the repo, the app bundle, or the logs. Public endpoints like login or “send code” are rate limited per user and IP. Webhooks verify the signature before doing anything. CORS allows only the real frontends.

LLM features add two of their own. Prompt injection: text from a user or a web page can tell the model to do something else, so tools check permissions in code and the model cannot widen its own access. And server-side requests: if a tool fetches a URL, I block internal addresses so it cannot reach metadata or private services.
