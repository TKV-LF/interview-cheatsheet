08React component lifecycleClassic interview question.

What is the React component lifecycle?

In class components there are phases: mounting (constructor, render, componentDidMount), updating (render, componentDidUpdate), and unmounting (componentWillUnmount). In modern React with function components we mostly use hooks: first render + useEffect(() => {}, []) ≈ didMount; useEffect with deps ≈ didUpdate for those values; the cleanup function returned from useEffect ≈ willUnmount. I think in terms of “when does this run?” — after paint for effects, before leave for cleanup — rather than memorizing every old class method name.

Lifecycle của React component là gì?

Với class component có các phase: mounting (constructor, render, componentDidMount), updating (render, componentDidUpdate), và unmounting (componentWillUnmount). React hiện đại với function component chủ yếu dùng hooks: lần render đầu + useEffect(() => {}, []) ≈ didMount; useEffect có deps ≈ didUpdate theo giá trị đó; hàm cleanup return từ useEffect ≈ willUnmount. Tôi nghĩ theo “chạy khi nào?” — effect sau paint, cleanup trước khi rời — hơn là thuộc lòng mọi tên method class cũ.

Map: Mount → Update → Unmount. Hooks: [] mount, [deps] update, cleanup unmount.

Trap: Only listing class methods with no hooks mapping.

09useEffect lifecycle detailsMost asked follow-up.

How does useEffect relate to the lifecycle?

useEffect runs after the browser paints. With [] it runs once after mount — good for subscribe, initial fetch, or third-party chart init. With [a, b] it re-runs when a or b change. The function you return cleans up the previous effect before the next run and on unmount — cancel fetch, remove listener, dispose AnyChart. Missing deps causes stale bugs; wrong deps causes loops. For data fetching, also watch race conditions when the filter changes quickly.

useEffect liên quan lifecycle thế nào?

useEffect chạy sau khi browser paint. Với [] chạy một lần sau mount — hợp subscribe, fetch ban đầu, hoặc init chart. Với [a, b] chạy lại khi a hoặc b đổi. Hàm return cleanup effect trước đó trước lần chạy tiếp và khi unmount — hủy fetch, gỡ listener, dispose AnyChart. Thiếu deps gây bug stale; deps sai gây loop. Fetch data thì chú ý race khi filter đổi nhanh.

Know: after paint · deps · cleanup · stale vs infinite loop · race on fast filter change.

10Virtual DOMClassic concept.

What is the Virtual DOM, and why does React use it?

The Virtual DOM is React's in-memory description of the UI — a lightweight tree of React elements. When state changes, React creates a new virtual tree, diffs it with the previous one (reconciliation), and updates only the real DOM nodes that changed. That is usually cheaper than rewriting the whole page by hand. It is not “always faster than raw DOM”; it is a productive model so we describe UI as a function of state and let React apply the minimal updates.

Virtual DOM là gì và vì sao React dùng?

Virtual DOM là mô tả UI trong memory của React — cây element nhẹ. Khi state đổi, React tạo virtual tree mới, diff với tree trước (reconciliation), và chỉ update node DOM thật thay đổi. Thường rẻ hơn tự viết lại cả trang. Không phải “luôn nhanh hơn raw DOM”; đó là model hiệu quả: UI = f(state), React apply cập nhật tối thiểu.

Know: Describe UI → diff → patch real DOM. Not magic always-faster.

11Keys and list reconciliationClassic bug source.

Why do lists need a key in React?

Keys help React match list items between renders so it can reuse the right DOM nodes and keep local state on the correct row. Use a stable unique id from data — not the array index if the list can reorder, insert, or delete, because index keys make React confuse which item is which. Wrong keys cause weird UI bugs: wrong checkbox checked, input text jumping between rows.

Vì sao list trong React cần key?

Key giúp React khớp item giữa các lần render để tái sử dụng đúng DOM node và giữ state cục bộ đúng hàng. Dùng id ổn định từ data — không dùng index nếu list có thể reorder/thêm/xóa, vì index làm React nhầm item. Key sai gây bug UI lạ: checkbox sai, text input nhảy hàng.

Know: Stable unique key from data; index only for static lists.

12Props vs stateFundamentals.

What is the difference between props and state?

Props are inputs from the parent — read-only for the child. State is data owned by the component that can change over time with setState/useState and trigger a re-render. If many siblings need the same changing value, lift state up or use a shared store like Zustand. Don't mutate props; treat them as immutable configuration for this render.

Khác nhau giữa props và state?

Props là input từ parent — child chỉ đọc. State là data component sở hữu, đổi theo thời gian bằng setState/useState và gây re-render. Nếu nhiều sibling cần cùng giá trị đang đổi, lift state lên hoặc dùng shared store như Zustand. Không mutate props; coi props là cấu hình bất biến cho lần render đó.

Know: props in · state owned · lift or store when shared.

13Controlled vs uncontrolled inputsForm classic.

What is a controlled vs uncontrolled input in React?

Controlled: React state is the source of truth — value={state} and onChange updates state. Easy to validate and disable submit. Uncontrolled: the DOM holds the value; you read it with a ref when needed. React Hook Form leans more uncontrolled under the hood for performance. For dashboard filters I often use controlled inputs so chart and grid stay in sync with the same state.

Controlled và uncontrolled input khác nhau thế nào?

Controlled: state React là nguồn sự thật — value={state} và onChange update state. Dễ validate và disable submit. Uncontrolled: DOM giữ value; đọc bằng ref khi cần. React Hook Form nghiêng uncontrolled bên dưới để hiệu năng. Filter dashboard tôi hay dùng controlled để chart và grid đồng bộ cùng state.

Know: Controlled = React state drives value; uncontrolled = DOM/ref.

14What triggers a re-render?Performance awareness.

When does a React component re-render?

Typically when its state changes, when its parent re-renders and passes new props (by default), or when a context/store value it subscribed to changes. Re-render does not always mean the DOM changed — React may bail out if output is the same. To reduce unnecessary work: keep state local, split components, use selectors with Zustand, and memoize heavy children only when profiling shows a problem.

Component React re-render khi nào?

Thường khi state đổi, khi parent re-render và truyền props mới (mặc định), hoặc khi context/store nó subscribe đổi. Re-render không luôn nghĩa DOM đổi — React có thể bail out nếu output giống. Giảm việc thừa: giữ state local, tách component, dùng selector với Zustand, và memo child nặng chỉ khi profile chỉ ra vấn đề.

Know: state · parent · subscribed store/context. Measure before memo everywhere.

15Lifting state upClassic pattern.

What does “lifting state up” mean?

When two children need the same changing data, you move that state to their closest shared parent and pass it down as props (and setters). Example: a filter toolbar and a table both need dateRange — parent owns dateRange. If the tree gets too deep or many distant widgets share it, that's when Context or Zustand becomes cleaner than lifting to App.

“Lifting state up” nghĩa là gì?

Khi hai child cần cùng data đang đổi, bạn đưa state lên parent chung gần nhất và truyền xuống bằng props (và setter). Ví dụ: toolbar filter và bảng đều cần dateRange — parent own dateRange. Nếu cây quá sâu hoặc nhiều widget xa nhau share, lúc đó Context hoặc Zustand sạch hơn lift lên App.

Know: Shared need → closest parent. Too wide → Context/Zustand.

16useMemo and useCallbackClassic hooks question.

When do you use useMemo and useCallback?

useMemo caches an expensive calculated value between renders. useCallback caches a function reference so child memo components don't re-render for a new function identity every time. I don't wrap everything — only when the work is heavy or a memoized child depends on a stable callback. Premature memo makes code harder and can even cost more. Measure first on slow lists or heavy chart option objects.

Khi nào dùng useMemo và useCallback?

useMemo cache giá trị tính toán đắt giữa các lần render. useCallback cache reference hàm để child đã memo không re-render vì identity hàm mới mỗi lần. Không bọc hết — chỉ khi việc nặng hoặc child memo cần callback ổn định. Memo sớm làm code khó hơn và đôi khi tốn hơn. Đo trước trên list chậm hoặc object option chart nặng.

Know: Memo for proven cost; not default everywhere.

17React.memoPrevent child re-renders.

What does React.memo do?

React.memo wraps a component so it skips re-render when props are shallow-equal to the previous props. Useful for heavy pure widgets in a dashboard when the parent re-renders often but this widget's props did not change. It does not help if you pass new object/array/function props every render — then combine with useMemo/useCallback or pass primitives. Again: use when profiling shows the child is expensive.

React.memo làm gì?

React.memo bọc component để bỏ qua re-render khi props shallow-equal với props trước. Hữu ích cho widget thuần nặng trong dashboard khi parent hay re-render nhưng props widget không đổi. Không giúp nếu mỗi lần render truyền object/array/function mới — lúc đó kết hợp useMemo/useCallback hoặc truyền primitive. Dùng khi profile thấy child đắt.

Know: Shallow prop compare; unstable props defeat memo.

18Conditional renderingEveryday pattern.

How do you handle conditional rendering in React?

Common patterns: {condition && <Comp />}, ternary for if/else, early return of loading/error UI, or switch on status for workflow steps. Avoid rendering 0 by accident with {count && <X/>} when count can be 0 — use Boolean(count) or count > 0. For workflow UIs, map status to the right panel clearly so recruiters always see the current step.

Bạn xử lý conditional rendering trong React thế nào?

Pattern phổ biến: {condition && <Comp />}, ternary if/else, early return UI loading/error, hoặc switch theo status cho bước workflow. Tránh render nhầm 0 với {count && <X/>} khi count có thể 0 — dùng Boolean(count) hoặc count > 0. UI workflow: map status sang đúng panel để recruiter luôn thấy bước hiện tại.

Trap: {count && <X/>} renders 0.

19Class vs function componentsStill asked sometimes.

Class components vs function components — which do you use?

I use function components with hooks for new code — simpler and the modern standard. Class components still appear in older codebases; I can read lifecycle methods and map them to hooks. Error boundaries are still class-based in classic React (componentDidCatch), unless the team uses a library. I'd follow the team's React style — almost certainly hooks-first.

Class component vs function component — bạn dùng gì?

Code mới tôi dùng function component với hooks — đơn giản và chuẩn hiện đại. Class vẫn gặp ở codebase cũ; tôi đọc được lifecycle và map sang hooks. Error boundary vẫn thường là class (componentDidCatch), trừ khi team dùng lib. Tôi theo style của team — gần như chắc hooks-first.

Know: Hooks-first; can map class lifecycle; error boundary nuance.

35How Zustand works (mental model)Deeper mechanics.

How does Zustand work under the hood, in simple terms?

Simple mental model from the docs: Zustand creates a store object that holds current state and a list of listeners. When you call set, it updates state and notifies subscribers. The React hook useStore(selector) subscribes the component; when the selected value changes, that component re-renders. Unlike Context, the store is not a React provider wrapping the tree — it's an external store that React components hook into. That's why you don't need to wrap the whole app just to share filters. Again: research-level understanding, not production war stories.

Zustand hoạt động thế nào, nói đơn giản?

Khác Context, store không phải Provider bọc tree — nó là external store mà React component hook vào. Vì vậy không cần bọc cả app chỉ để share filter. 39Selectors in more detailRe-renders & pitfalls.

How should you use selectors in Zustand, and what can go wrong?

Best practice from research: select the smallest value — useStore(s => s.filter) not useStore(s => s) for the whole store. That way a layout change doesn't re-render the chart. 42Why not only useState?Core comparison.

Why use Zustand instead of useState?

useState is perfect for local state inside one component — open/closed modal, input draft, one toggle. The pain starts when many distant components need the same state: dashboard filters shared by chart + AG-Grid + workflow panel. With only useState you lift state to a parent and prop-drill, or wrap a huge tree in Context and often re-render too much. So: useState for local; Zustand when shared UI state crosses many siblings without a clean parent.

useState hoàn hảo cho state cục bộ trong một component — mở/đóng modal, draft input, một toggle. Zustand giữ shared client state trong một store ngoài tree; widget nào cũng subscribe đúng slice cần. Vậy: useState cho local; Zustand khi UI state share xuyên nhiều sibling mà không có parent gọn.

Khi nào React Flow là lựa chọn đúng cho workflow?

Nó có node, edge, zoom/pan, custom node UI. Không dùng cho wizard form ba bước. Trade-off là phức tạp: vẫn phải validate graph trên server. Common questions

78useRef versus useStateCommon hooks follow-up.

When do you use useRef instead of useState?

useState is for a value the screen must show. Changing it re-renders. useRef holds a mutable value that should not re-render by itself: a DOM node, a timer id, the previous value of a prop. If I put visible UI state in a ref, the screen will lie. If I put a timer id in state, I re-render for no reason.

Khi nào dùng useRef thay vì useState?

useState cho giá trị màn hình phải hiện. Đổi nó là re-render. useRef giữ giá trị mutable mà bản thân nó không cần re-render: DOM node, timer id, giá trị prop lần trước. Nhét UI state vào ref thì màn hình nói dối. Nhét timer id vào state thì re-render vô ích.

79Context APICommon, and the doorway into the Zustand comparison.

When is React Context the right tool?

Context is for data many children need, that changes rarely: theme, locale, the current user. If the value changes often, every consumer re-renders. I have mostly passed props and kept state local. For frequent UI state — a dashboard filter, a selected node — a selector store avoids waking the whole tree. Server data still belongs in the API layer, not in Context just because it is shared.

Khi nào React Context là tool đúng?

Context cho data nhiều component con cần, và ít đổi: theme, ngôn ngữ, user hiện tại. Nếu value đổi thường xuyên, mọi consumer re-render. Tôi chủ yếu truyền props và giữ state tại chỗ. Với UI state đổi liên tục — filter dashboard, node đang chọn — store có selector khỏi đánh thức cả cây. Data từ server vẫn thuộc lớp API, không nhét vào Context chỉ vì nó được share.

80Code splittingCommon performance question for large React apps.

How do you code-split a React app?

I split by route first. React.lazy and Suspense load a heavy screen when the user opens it, with a small fallback. A dashboard with charts or a big grid should not sit in the first bundle. After routes, I split a single heavy widget if the rest of the page is light. I measure before I split everything. Too many chunks can make navigation feel chatty.

Bạn code-split app React thế nào?

Tôi tách theo route trước. React.lazy và Suspense tải màn nặng khi user mở, kèm fallback nhỏ. Dashboard có chart hoặc grid lớn không nên nằm trong bundle đầu. Sau route, tôi tách một widget nặng nếu phần còn lại của trang nhẹ. Tôi đo trước khi tách tất cả. Quá nhiều chunk làm chuyển trang cảm giác phải chờ liên tục.
