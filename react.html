Which React libraries do you reach for, and how do you choose a new one?

Most React apps need the same few pieces: routing, data fetching, forms, a state tool if local state is not enough, and a component kit. In my own work routing is Expo Router on mobile and the Next.js router on the admin. Data comes from typed fetch helpers that call our Express APIs, and shared state like the signed-in user lives in Context. I know TanStack Query, React Hook Form with Zod, and Zustand well from study, but I haven't shipped them in production, and I say that.

To choose a library I ask four things. What problem does it solve that a small custom hook can't? Does the team already use something for this? How big is it, and is it maintained and typed? And how hard is it to remove later? If a page needs one table, I write a table. If users need sorting, filtering, and fifty thousand rows, a grid library earns its cost. On a team, I follow the house stack before I add mine.

04Virtual DOM and reconciliationRender builds a tree, React diffs it, commit touches only what changed.~69s✓

What is the Virtual DOM, and how does reconciliation work?

When a component renders, it returns React elements, which are plain objects that describe the UI. That tree is what people call the Virtual DOM. React compares the new tree with the previous one, and this step is called reconciliation. Then, in the commit phase, it changes only the real DOM nodes that differ.

The comparison uses two cheap rules. If the element type at a position changes, for example a div becomes a section, React throws away that subtree and builds a new one, including its state. If the type is the same, it keeps the node and updates its props. For lists it matches children by key.

The point is not that the Virtual DOM is faster than hand-written DOM code. It isn't always. The point is that I describe the UI as a function of state, and React works out the smallest set of changes. Rendering is pure work in memory. Only the commit touches the page.

Virtual DOM là gì, và reconciliation hoạt động thế nào?

Khi một component render, nó trả về các React element, tức là những object thường mô tả giao diện. Cây đó chính là cái người ta gọi là Virtual DOM. React so sánh cây mới với cây trước, bước này gọi là reconciliation. Sau đó, ở pha commit, nó chỉ sửa những node DOM thật nào khác đi.

Việc so sánh dựa trên hai quy tắc đơn giản. Nếu kiểu element ở một vị trí thay đổi, ví dụ div thành section, React bỏ cả nhánh đó và dựng lại, mất luôn state bên trong. Nếu cùng kiểu thì nó giữ node và chỉ cập nhật props. Với list thì nó ghép các phần tử con theo key.

Điểm chính không phải Virtual DOM nhanh hơn code DOM viết tay. Không phải lúc nào cũng vậy. Điểm chính là tôi mô tả giao diện như một hàm của state, còn React tự tính ra số thay đổi ít nhất. Render chỉ là tính toán trong bộ nhớ. Chỉ có commit mới chạm vào trang.

Know: Render phase (pure, can be interrupted in concurrent rendering) vs commit phase (DOM writes, then layout effects, then effects). Different type at the same position = remount and state loss.

Trap: "Virtual DOM is always faster than the real DOM." Or defining a component inside another component, which gives it a new type every render and remounts it.

05What triggers a re-render?State change, parent render, context change. Memo is the exception, not the rule.~69s✓

When does a React component re-render?

There are three triggers. Its own state changes. Its parent re-renders. Or a context it reads changes. The parent one surprises people: by default a child re-renders every time its parent renders, even if its props are exactly the same. Props changing is not the trigger. The parent rendering is.

There are two ways React skips work. If I call setState with a value that is the same as the current one, compared with Object.is, React bails out and doesn't re-render that component. And if a child is wrapped in memo and all its props are shallow-equal to last time, that child is skipped.

Also, a re-render is not a DOM update. React renders, compares the result, and if nothing differs it doesn't touch the DOM. So most re-renders are cheap. I only act when the Profiler shows a slow one. Then I move state down closer to where it's used, pass heavy children as children, or memoize that one component.

Khi nào một component React render lại?

Có ba nguyên nhân. State của chính nó thay đổi. Component cha render lại. Hoặc một context mà nó đọc thay đổi. Nguyên nhân thứ hai hay làm người ta bất ngờ: mặc định component con render lại mỗi lần cha render, kể cả khi props giống hệt. Không phải props đổi mới gây render, mà là việc cha render.

Có hai trường hợp React bỏ qua. Nếu tôi gọi setState với giá trị giống giá trị hiện tại, so bằng Object.is, React sẽ không render lại component đó. Và nếu component con được bọc memo và mọi props đều bằng nhau khi so nông với lần trước, component con đó được bỏ qua.

Ngoài ra, render lại không có nghĩa là cập nhật DOM. React render, so kết quả, và nếu không có gì khác thì không đụng vào DOM. Nên phần lớn các lần render lại là rẻ. Tôi chỉ xử lý khi Profiler cho thấy có lần render chậm. Lúc đó tôi đưa state xuống gần chỗ dùng, truyền phần nặng qua children, hoặc memo đúng component đó.

Know: Triggers: own state, parent render, context value. Bail-outs: same state via Object.is, memo with shallow-equal props. Render ≠ commit. Mutating an object and setting the same reference = no re-render (bug).

Trap: "A child re-renders only when its props change." Or "React skips the render if the output is the same." It doesn't compare output to skip rendering, it compares output to skip DOM writes.

06Props vs stateProps come in from the parent, read-only. State is owned and changed by the component.~64s✓

What's the difference between props and state?

Props are inputs. The parent passes them, and the child must treat them as read-only. State is memory that the component owns. It changes over time through the setter, and changing it causes a re-render.

A good test is to ask who is allowed to change the value. If the parent decides, it's a prop. If this component decides, it's state. If two siblings need the same changing value, the state moves up to their closest common parent, and it goes down to both as props, along with a callback to change it.

Two mistakes I watch for. Copying a prop into state with useState(props.value) means the copy goes stale when the parent changes it, so usually I just read the prop. And storing something I can calculate, like a filtered list or a full name, in state means two sources that can disagree. I calculate it during render instead.

Props và state khác nhau thế nào?

Props là đầu vào. Component cha truyền xuống, và component con phải coi nó là chỉ đọc. State là bộ nhớ mà component tự sở hữu. Nó thay đổi theo thời gian qua hàm setter, và mỗi lần đổi thì component render lại.

Một cách kiểm tra đơn giản là hỏi ai được quyền đổi giá trị này. Nếu cha quyết định thì đó là prop. Nếu chính component này quyết định thì đó là state. Nếu hai component anh em cần cùng một giá trị hay thay đổi, state được đưa lên component cha chung gần nhất, rồi truyền xuống cả hai dưới dạng props, kèm một callback để đổi nó.

Có hai lỗi tôi hay để ý. Copy prop vào state bằng useState(props.value) thì bản copy sẽ cũ đi khi cha đổi giá trị, nên thường tôi đọc thẳng prop. Và lưu vào state những thứ tính được, như list đã lọc hay họ tên đầy đủ, nghĩa là có hai nguồn dữ liệu có thể lệch nhau. Tôi tính nó ngay trong lúc render.

Know: Props: read-only inputs. State: owned, changes via setter, triggers re-render. Derive what you can calculate.

Trap: Mirroring a prop in state and wondering why it doesn't update. Mutating props.

07Lifting state upMove shared state to the closest common parent. Reach for Context or a store only when that gets painful.~69s✓

What does "lifting state up" mean?

When two components need the same changing value, I move the state to their closest common parent. The parent passes the value down as a prop and passes a function to change it. Now there's one source of truth, and both children always agree.

A simple example: a search box and a results list. If the search box keeps its own text in state, the list can't see it. Lift the text to the parent, give the box value and onChange, give the list the text, and they stay in sync.

The cost is prop drilling when the common parent is far up and the value passes through components that don't use it. Before I reach for Context or a store, I try composition: pass the ready-made child element down as children, so the middle layers don't need the prop at all. If many distant parts of the app still need it, then Context, or a store if it changes often.

"Lifting state up" nghĩa là gì?

Khi hai component cần cùng một giá trị hay thay đổi, tôi đưa state lên component cha chung gần nhất. Cha truyền giá trị xuống qua prop và truyền kèm một hàm để đổi nó. Như vậy chỉ có một nguồn dữ liệu, và hai component con luôn khớp nhau.

Ví dụ đơn giản: một ô tìm kiếm và một danh sách kết quả. Nếu ô tìm kiếm tự giữ chữ trong state của nó thì danh sách không nhìn thấy được. Đưa chữ đó lên cha, cho ô tìm kiếm value và onChange, cho danh sách đoạn chữ đó, thế là hai bên luôn đồng bộ.

Cái giá là prop drilling, khi cha chung nằm quá cao và giá trị phải đi qua những component không dùng tới nó. Trước khi dùng Context hay store, tôi thử composition: truyền sẵn component con xuống qua children, để các tầng ở giữa không cần biết prop đó. Nếu nhiều chỗ cách xa nhau trong app vẫn cần nó, lúc đó mới dùng Context, hoặc store nếu giá trị đổi thường xuyên.

Know: One source of truth at the closest common parent. Composition (children) before Context. Context before a store only if the value changes rarely.

Trap: Jumping straight to a global store for state two siblings share.

08Keys in listsStable id from the data, not the array index, when the list can change.~72s✓

Why does React need keys in lists?

Keys tell React which item is which between renders. When a list changes, React matches old and new children by key, so it can reuse the right DOM node and keep each row's state, like a checkbox or an input, with the right item.

So the key must be stable and unique among siblings, and it should come from the data, like a database id. The array index is fine only if the list never reorders, never inserts, and never deletes. Otherwise, if I delete the first row, every index shifts, React thinks the first row's state now belongs to the second item, and you get the classic bug where the text you typed jumps to another row. A random key from Math.random is worse: every render remounts every row.

Keys also have a second use. If I change a component's key, React treats it as a new component and resets its state. I use that to reset a form when the user switches to a different record.

Vì sao React cần key trong list?

Key cho React biết phần tử nào là phần tử nào giữa các lần render. Khi list thay đổi, React ghép con cũ với con mới theo key, nhờ vậy nó dùng lại đúng node DOM và giữ state của từng dòng, như checkbox hay ô input, đi theo đúng phần tử.

Vì thế key phải ổn định, không trùng giữa các phần tử anh em, và nên lấy từ dữ liệu, như id trong database. Dùng index của mảng chỉ ổn khi list không bao giờ đổi thứ tự, thêm hay xóa. Nếu không, khi tôi xóa dòng đầu tiên thì mọi index dịch lên, React tưởng state của dòng đầu giờ thuộc về phần tử thứ hai, và gặp lỗi kinh điển là chữ vừa gõ nhảy sang dòng khác. Dùng key ngẫu nhiên bằng Math.random còn tệ hơn: mỗi lần render, mọi dòng đều bị mount lại.

Key còn có công dụng thứ hai. Nếu tôi đổi key của một component, React coi đó là component mới và reset state của nó. Tôi dùng cách này để reset form khi người dùng chuyển sang bản ghi khác.

Know: Keys are per sibling list. Index keys break on reorder, insert, delete. Changing a key remounts and resets state.

Trap: Math.random() or Date.now() as key. Index keys on a sortable list.

09Controlled vs uncontrolled inputsControlled: React state is the source. Uncontrolled: the DOM is, read it when needed.~69s✓

What's the difference between controlled and uncontrolled inputs?

In a controlled input, React state is the source of truth. I pass value from state and update it in onChange. That makes it easy to validate as the user types, format the value, or disable the submit button until the form is valid.

In an uncontrolled input, the DOM keeps the value. I give it a defaultValue and read it when I need it, through a ref or from the form data on submit. There's less code and no re-render on every keystroke. React 19 makes this style more natural: a form can take an action, and the action receives FormData directly.

React Hook Form is mostly uncontrolled inside, which is why it stays fast on big forms. One bug to know: switching an input from uncontrolled to controlled, usually because the value starts as undefined, triggers a React warning. I start controlled values as an empty string. In my own screens, small forms like login and settings are controlled.

Input controlled và uncontrolled khác nhau thế nào?

Với input controlled, state của React là nguồn dữ liệu chính. Tôi truyền value từ state và cập nhật nó trong onChange. Nhờ vậy dễ kiểm tra hợp lệ ngay khi người dùng gõ, định dạng giá trị, hoặc khóa nút submit cho tới khi form hợp lệ.

Với input uncontrolled, DOM tự giữ giá trị. Tôi cho nó defaultValue và đọc ra khi cần, qua ref hoặc từ dữ liệu form lúc submit. Code ít hơn và không phải render lại mỗi lần gõ phím. React 19 làm cách này tự nhiên hơn: form có thể nhận một action, và action nhận thẳng FormData.

React Hook Form bên trong chủ yếu là uncontrolled, nên nó vẫn nhanh với form lớn. Có một lỗi nên biết: chuyển một input từ uncontrolled sang controlled, thường do value ban đầu là undefined, sẽ làm React cảnh báo. Tôi luôn khởi tạo value controlled bằng chuỗi rỗng. Trong các màn của tôi, form nhỏ như đăng nhập hay cài đặt thì dùng controlled.

Know: value + onChange vs defaultValue + ref or FormData. React 19 form actions read FormData.

How do you render things conditionally in React?

I use three patterns. For show or hide, condition && <Thing />. For one thing or another, a ternary. And when a whole component depends on a state like loading or error, an early return at the top, so the main JSX only handles the success case.

When there are more than two states, I model them as one status value, like idle, loading, error, or done, and switch on it. That's cleaner than several booleans that can contradict each other, like isLoading and isError both true.

The classic bug is with &&. If I write count && <Badge /> and count is zero, React renders the number 0 on screen, because zero is a value React prints. I write count > 0 instead. One more thing: hiding with a condition unmounts the component and loses its state. If I want to keep the state, for example a tab the user will come back to, I hide it with CSS instead, or use the Activity component in React 19.2.

Bạn render có điều kiện trong React thế nào?

Tôi dùng ba cách. Để hiện hoặc ẩn thì dùng condition && <Thing />. Để chọn giữa hai thứ thì dùng toán tử ba ngôi. Còn khi cả component phụ thuộc vào trạng thái như đang tải hay lỗi, tôi return sớm ở đầu hàm, để phần JSX chính chỉ lo trường hợp thành công.

Khi có nhiều hơn hai trạng thái, tôi gom thành một giá trị status, như idle, loading, error hoặc done, rồi switch theo nó. Cách này gọn hơn nhiều biến boolean có thể mâu thuẫn nhau, kiểu isLoading và isError cùng là true.

Lỗi kinh điển nằm ở &&. Nếu tôi viết count && <Badge /> mà count bằng không, React sẽ in số 0 ra màn hình, vì số không là giá trị React hiển thị. Tôi viết count > 0 thay vào đó. Thêm một điểm: ẩn bằng điều kiện thì component bị unmount và mất state. Nếu muốn giữ state, ví dụ một tab người dùng sẽ quay lại, tôi ẩn bằng CSS, hoặc dùng component Activity của React 19.2.

11Component lifecycleMount, update, unmount. With hooks, think in effects that sync with something outside React.~65s✓

What is the React component lifecycle?

A component mounts, updates zero or more times, and then unmounts. In class components each phase has a method: componentDidMount, componentDidUpdate, and componentWillUnmount.

With function components and hooks, the rough mapping is: an effect with an empty dependency array runs after mount, an effect with dependencies runs again when those values change, and the cleanup function runs before the next run and on unmount.

But I don't think of effects as lifecycle methods any more, and the React docs say the same. An effect is a way to keep the component in sync with something outside React: a socket, a timer, a subscription, a third-party widget. I ask, what does this connect to, and how do I disconnect? If I write the cleanup correctly, it doesn't matter how many times React mounts it. That's also why StrictMode in development mounts, unmounts, and mounts again: it checks that my cleanup is right.

Lifecycle của một component React là gì?

Một component được mount, cập nhật một số lần, rồi unmount. Với class component, mỗi giai đoạn có một method: componentDidMount, componentDidUpdate và componentWillUnmount.

Với function component và hook, có thể đối chiếu đại khái thế này: effect có mảng dependency rỗng chạy sau khi mount, effect có dependency chạy lại khi các giá trị đó đổi, và hàm cleanup chạy trước lần chạy tiếp theo và khi unmount.

Nhưng tôi không coi effect là lifecycle method nữa, và tài liệu React cũng nói vậy. Effect là cách giữ component đồng bộ với thứ nằm ngoài React: một socket, một timer, một subscription, một widget bên thứ ba. Tôi tự hỏi: nó kết nối tới cái gì, và ngắt kết nối thế nào? Nếu cleanup viết đúng thì React mount bao nhiêu lần cũng không sao. Đó cũng là lý do ở môi trường dev, StrictMode mount, unmount rồi mount lại: nó kiểm tra xem cleanup của tôi có đúng không.

Know: Mount, update, unmount. [] ≈ after mount, [deps] ≈ after those change, cleanup ≈ before next run and unmount. Effects synchronize, they are not lifecycle hooks.

Trap: Only reciting class methods. Saying an effect with [] is guaranteed to run once (not in StrictMode dev).

Class components or function components?

For new code, function components with hooks. They're shorter, logic is reused through custom hooks instead of higher-order components or render props, and every new React feature, like the compiler and the React 19 hooks, targets them.

I can still read class components, because older codebases have them. I know this.state and setState, the lifecycle methods, and the binding problems with this in event handlers. When I touch one, I don't rewrite it unless there's a reason, like adding a feature that's much easier with a hook.

13How state updates work: batching and the updater functionsetState schedules a render. Updates batch. Use the updater when the next value depends on the last.~72s✓

Is setState synchronous? What is batching?

Calling a state setter doesn't change the variable right away. It schedules a re-render, and in the current render the variable keeps its old value. So if I log count right after setCount, I still see the old number.

React also batches updates. Since React 18, several setState calls in the same event, timeout, or promise are grouped into one render. That's good for performance, but it means setCount(count + 1) three times in a row only adds one, because all three read the same old count. When the next value depends on the previous one, I pass a function: setCount(c => c + 1). React queues those and applies them in order.

The other rule is immutability. React compares state by reference, so I never mutate an array or object in place. I create a new one, with the spread operator, map, or filter. If I push into the existing array and set it again, the reference is the same, React bails out, and the screen doesn't update.

setState có đồng bộ không? Batching là gì?

Gọi hàm setter của state không đổi biến ngay lập tức. Nó lên lịch một lần render mới, còn trong lần render hiện tại biến vẫn giữ giá trị cũ. Nên nếu tôi log count ngay sau setCount thì vẫn thấy số cũ.

React còn gộp các cập nhật lại. Từ React 18, nhiều lần setState trong cùng một event, timeout hay promise được gộp thành một lần render. Điều đó tốt cho hiệu năng, nhưng nghĩa là gọi setCount(count + 1) ba lần liên tiếp chỉ cộng được một, vì cả ba đều đọc cùng một giá trị count cũ. Khi giá trị mới phụ thuộc vào giá trị trước, tôi truyền vào một hàm: setCount(c => c + 1). React xếp hàng các hàm đó và chạy lần lượt.

Quy tắc còn lại là không sửa trực tiếp. React so state theo tham chiếu, nên tôi không bao giờ sửa mảng hay object tại chỗ. Tôi tạo cái mới, bằng spread, map hoặc filter. Nếu tôi push vào mảng cũ rồi set lại, tham chiếu vẫn vậy, React bỏ qua, và màn hình không cập nhật.

Know: Automatic batching everywhere since React 18. Updater function for dependent updates. New references for objects and arrays. flushSync exists but is rarely needed.

Trap: Reading state right after setting it. push() then setItems(items).

15useEffect in detailRuns after paint. Deps decide when. Cleanup runs before the next run and on unmount.~78s✓

How does useEffect work, and what goes wrong with it?

useEffect runs after React commits the render and the browser paints. The dependency array decides when it runs again. No array means after every render. An empty array means after mount. An array with values means whenever one of those values changes, compared with Object.is.

The function I return is the cleanup. React calls it before the effect runs again and when the component unmounts. That's where I remove a listener, clear a timer, close a socket, or abort a request.

Three bugs come up a lot. Missing a dependency gives a stale value, because the effect still sees the old one. An object or function created during render as a dependency is new every time, so the effect runs every render, and if it sets state, it loops. And fetching without cleanup causes a race: the user changes the filter twice, the first response arrives last and overwrites the right one. I fix that with an AbortController in the cleanup, or an ignore flag. In development, StrictMode also runs the effect twice, which is a check that the cleanup works.

useEffect hoạt động thế nào, và hay sai ở đâu?

useEffect chạy sau khi React commit lần render và trình duyệt đã vẽ xong. Mảng dependency quyết định khi nào nó chạy lại. Không có mảng thì chạy sau mỗi lần render. Mảng rỗng thì chạy sau khi mount. Mảng có giá trị thì chạy lại khi một trong các giá trị đó đổi, so bằng Object.is.

Hàm tôi return là cleanup. React gọi nó trước khi effect chạy lại và khi component unmount. Đó là chỗ tôi gỡ listener, xóa timer, đóng socket, hoặc hủy request.

Có ba lỗi hay gặp. Thiếu dependency thì effect đọc phải giá trị cũ. Dùng object hay function tạo ra trong lúc render làm dependency thì mỗi lần nó là cái mới, nên effect chạy sau mọi lần render, và nếu nó set state thì sẽ lặp vô hạn. Còn fetch mà không cleanup thì bị race: người dùng đổi bộ lọc hai lần, response đầu về sau cùng và ghi đè lên kết quả đúng. Tôi xử lý bằng AbortController trong cleanup, hoặc một cờ ignore. Ở môi trường dev, StrictMode còn chạy effect hai lần, để kiểm tra cleanup có đúng không.

Know: After paint · deps compared with Object.is · cleanup before rerun and unmount · stale deps vs loops · fetch race fixed with AbortController or an ignore flag. eslint-plugin-react-hooks catches missing deps.

Trap: Silencing the exhaustive-deps lint rule instead of fixing the cause.

My API is called twice when the page loads. Why?

If it only happens in development, it's almost certainly StrictMode. In development, React 18 and 19 mount each component, run its effects, then simulate an unmount by running the cleanups, and then run the effects again. It also calls component functions and state initializers twice, to catch impure rendering. None of this happens in a production build.

The purpose is to find effects without proper cleanup. A real app remounts components all the time, like when a user navigates away and back. If my effect opens a subscription and never closes it, the double run makes that leak visible right away.

So the fix is not to remove StrictMode, and not to add a ref that says "already ran". The fix is a correct cleanup. For a fetch, I abort the first request in the cleanup, so only one result is used. For a subscription, I unsubscribe. If the double request itself is a problem, that's a sign the fetch should live in a data library or a route loader, which caches and dedupes it.

API của tôi bị gọi hai lần khi trang vừa tải. Vì sao?

Nếu chỉ xảy ra ở môi trường dev thì gần như chắc chắn là do StrictMode. Ở dev, React 18 và 19 mount từng component, chạy effect, rồi giả lập unmount bằng cách chạy cleanup, rồi chạy effect lần nữa. Nó còn gọi hàm component và hàm khởi tạo state hai lần, để bắt lỗi render không thuần. Build production thì không có chuyện này.

Mục đích là tìm ra những effect không có cleanup đúng. App thật lúc nào cũng mount lại component, ví dụ khi người dùng chuyển trang rồi quay lại. Nếu effect mở một subscription mà không bao giờ đóng, chạy hai lần sẽ làm lỗi rò rỉ đó lộ ra ngay.

Nên cách sửa không phải là bỏ StrictMode, cũng không phải thêm một ref đánh dấu "đã chạy rồi". Cách sửa là viết cleanup cho đúng. Với fetch, tôi hủy request đầu tiên trong cleanup để chỉ dùng một kết quả. Với subscription, tôi hủy đăng ký. Nếu bản thân việc gọi hai lần là vấn đề, đó là dấu hiệu nên chuyển việc fetch sang thư viện dữ liệu hoặc loader của route, vì chúng có cache và gộp request trùng.

What's the difference between useLayoutEffect and useEffect?

Both run after React updates the DOM. The difference is timing against the paint. useEffect runs after the browser has painted, so it never blocks the screen. useLayoutEffect runs synchronously after the DOM changes but before the browser paints.

That matters in one situation: when I need to measure the DOM and change something based on it before the user sees anything. A tooltip is the classic case. I render it, measure its height, and if it would go off screen I move it above the button. With useEffect, the user sees one frame in the wrong place and then a jump. With useLayoutEffect, they only see the final position.

The cost is that it blocks painting, so slow code there makes the page feel stuck. So useEffect is the default, and useLayoutEffect is only for measure-then-adjust. It also doesn't run on the server, so in server rendering I keep that logic in a client component. There's also useInsertionEffect, but that's for CSS-in-JS library authors.

useLayoutEffect và useEffect khác nhau thế nào?

Cả hai đều chạy sau khi React cập nhật DOM. Khác nhau ở thời điểm so với lúc vẽ màn hình. useEffect chạy sau khi trình duyệt đã vẽ, nên không bao giờ chặn màn hình. useLayoutEffect chạy đồng bộ ngay sau khi DOM đổi nhưng trước khi trình duyệt vẽ.

Điều đó quan trọng trong một tình huống: khi tôi cần đo DOM và thay đổi theo kết quả đo trước khi người dùng nhìn thấy. Tooltip là ví dụ kinh điển. Tôi render nó, đo chiều cao, và nếu nó tràn ra ngoài màn hình thì chuyển nó lên phía trên nút. Dùng useEffect thì người dùng thấy một khung hình ở sai chỗ rồi giật sang chỗ khác. Dùng useLayoutEffect thì họ chỉ thấy vị trí cuối cùng.

Cái giá là nó chặn việc vẽ, nên code chậm ở đó làm trang có cảm giác bị đơ. Vì vậy useEffect là mặc định, còn useLayoutEffect chỉ dùng cho việc đo rồi chỉnh. Nó cũng không chạy trên server, nên khi render phía server tôi để logic đó trong client component. Ngoài ra còn useInsertionEffect, nhưng cái đó dành cho người viết thư viện CSS-in-JS.

18useRef vs useStateState: the screen shows it. Ref: it must persist but must not re-render.~75s✓

When do you use useRef instead of useState?

useState is for values the screen shows. Changing it re-renders the component. useRef gives me a box with a current property that survives every render, and changing it doesn't re-render anything.

So refs are for two things. First, DOM nodes: I pass the ref to an element and later call focus or scrollIntoView on it. Second, mutable values that React doesn't need to know about: a timer id so I can clear it, an AbortController, a WebSocket instance, or the previous value of a prop.

The rule of thumb is: if changing it should change what the user sees, it's state. If I put visible data in a ref, the screen won't update and will show old data. If I put a timer id in state, I re-render for no reason. Also, I don't read or write ref.current during render, because the render should stay pure. I touch it in effects and event handlers. In React 19 a ref is also a normal prop on function components, so I don't need forwardRef to pass it down.

Khi nào bạn dùng useRef thay vì useState?

useState dành cho giá trị mà màn hình hiển thị. Đổi nó thì component render lại. useRef cho tôi một cái hộp có thuộc tính current, tồn tại qua mọi lần render, và đổi nó thì không có gì render lại.

Nên ref dùng cho hai việc. Thứ nhất là node DOM: tôi gắn ref vào một element rồi sau đó gọi focus hay scrollIntoView trên nó. Thứ hai là những giá trị thay đổi mà React không cần biết: id của timer để còn xóa, một AbortController, một kết nối WebSocket, hoặc giá trị trước đó của một prop.

Cách nhớ là: nếu đổi giá trị này mà người dùng phải thấy khác đi, thì đó là state. Nếu tôi để dữ liệu hiển thị trong ref, màn hình không cập nhật và sẽ hiện dữ liệu cũ. Nếu tôi để id timer trong state, component render lại vô ích. Ngoài ra tôi không đọc hay ghi ref.current trong lúc render, vì render phải thuần. Tôi chỉ dùng nó trong effect và event handler. Ở React 19, ref còn là một prop bình thường của function component, nên không cần forwardRef để truyền xuống nữa.

Know: Ref: DOM nodes and mutable values that must not re-render (timer ids, controllers, sockets, previous value). Don't read or write ref.current during render.

Trap: Visible data in a ref. A timer id in state.

19Rules of HooksTop level only, only in components or hooks. React matches hooks by call order.~78s✓

What are the Rules of Hooks, and why do they exist?

There are two rules. Call hooks only at the top level of a component or a custom hook, never inside a condition, a loop, or after an early return. And call them only from React function components or other custom hooks, not from normal functions or event handlers.

The reason is how React stores hook state. It doesn't know hooks by name. It keeps a list per component and matches each call by its position: the first useState is slot one, the second is slot two, and so on. If a condition skips a hook on one render, every hook after it reads the wrong slot, and state gets mixed up or React throws an error.

So when I need something conditional, I put the condition inside the hook, for example inside the effect, or I split the conditional part into its own component. The ESLint plugin for hooks catches these mistakes, so I keep it on. One exception in React 19 is use(): it can be called inside a condition or a loop, because it doesn't keep state the same way.

Rules of Hooks là gì, và vì sao có các quy tắc đó?

Nó giữ một danh sách cho mỗi component và ghép từng lần gọi theo vị trí: useState đầu tiên là ô số một, useState thứ hai là ô số hai, cứ thế. Nếu một điều kiện làm bỏ qua một hook ở một lần render, mọi hook phía sau sẽ đọc sai ô, state bị lẫn hoặc React báo lỗi.

Nên khi cần điều kiện, tôi đặt điều kiện bên trong hook, ví dụ bên trong effect, hoặc tách phần có điều kiện ra thành component riêng. Plugin ESLint cho hook bắt được những lỗi này, nên tôi luôn bật nó. Có một ngoại lệ ở React 19 là use(): nó được gọi trong điều kiện hay vòng lặp, vì nó không giữ state theo cách đó.

20Stale closures in hooksEach render sees its own props and state. Old callbacks see old values.~78s✓

What is a stale closure in React, and how do you fix it?

Every render is a snapshot. The functions created in that render, including effects and event handlers, close over that render's props and state. A stale closure is when an old function keeps running and reads old values.

The classic example is an interval. I start setInterval in an effect with an empty dependency array, and inside it I call setCount(count + 1). The callback was created in the first render, where count is zero, so it sets the count to one forever.

There are a few fixes, depending on the case. Use the updater form, setCount(c => c + 1), so the callback doesn't need to read count. Add the value to the dependencies so the effect restarts with fresh values. Or keep the latest value in a ref. And since React 19.2 there's useEffectEvent: I wrap the logic that needs the latest props in it, call it from the effect, and it always sees current values without being a dependency. That's the clean fix for something like logging the current theme when a socket connects, without reconnecting when the theme changes.

Stale closure trong React là gì, và sửa thế nào?

Mỗi lần render là một bản chụp. Các hàm tạo ra trong lần render đó, gồm cả effect và event handler, giữ lại props và state của đúng lần render đó. Stale closure là khi một hàm cũ vẫn chạy và đọc phải giá trị cũ.

Ví dụ kinh điển là interval. Tôi gọi setInterval trong một effect với mảng dependency rỗng, và bên trong gọi setCount(count + 1). Callback đó được tạo ở lần render đầu, lúc count bằng không, nên nó cứ đặt count bằng một mãi.

Có vài cách sửa tùy trường hợp. Dùng dạng updater, setCount(c => c + 1), để callback không cần đọc count. Thêm giá trị đó vào dependency để effect chạy lại với giá trị mới. Hoặc giữ giá trị mới nhất trong một ref. Và từ React 19.2 có useEffectEvent: tôi bọc phần logic cần props mới nhất vào nó, gọi nó từ trong effect, và nó luôn thấy giá trị hiện tại mà không phải là dependency. Đó là cách sửa gọn cho trường hợp như ghi log theme hiện tại khi socket kết nối, mà không phải kết nối lại mỗi khi đổi theme.

Know: Render = snapshot. Fixes: updater function, correct deps, latest-value ref, useEffectEvent (stable in React 19.2; don't pass it to other components or list it as a dep).

Trap: Removing the dependency to stop a re-run, which creates the stale closure.

21useMemo and useCallbackCache a value or a function between renders. With React Compiler, mostly automatic.~73s✓

When do you use useMemo and useCallback?

useMemo caches the result of a calculation between renders, and recalculates only when its dependencies change. useCallback is the same idea for a function: it returns the same function reference until the dependencies change.

I use them for two reasons only. One, the calculation is really expensive, like filtering and sorting thousands of rows, and the Profiler shows it. Two, referential stability: a memoized child, or an effect, depends on an object or function, and a new reference every render would defeat the memo or re-run the effect.

I don't wrap everything, because memoizing has a cost too: memory, a dependency comparison, and code that's harder to read. And in 2026 the question changes if the team uses React Compiler. It reached 1.0 in October 2025 and memoizes components and values automatically at build time. With the compiler on, I mostly stop writing useMemo and useCallback by hand. I keep a manual one only where I need to control an exact reference, for example a value used as an effect dependency.

Khi nào bạn dùng useMemo và useCallback?

useMemo lưu lại kết quả một phép tính giữa các lần render, và chỉ tính lại khi dependency đổi. useCallback là cùng ý tưởng nhưng cho hàm: nó trả về cùng một tham chiếu hàm cho tới khi dependency đổi.

Tôi chỉ dùng chúng vì hai lý do. Một là phép tính thực sự tốn kém, như lọc và sắp xếp hàng nghìn dòng, và Profiler cho thấy điều đó. Hai là giữ tham chiếu ổn định: một component con đã memo, hoặc một effect, phụ thuộc vào object hay hàm, và nếu mỗi lần render là tham chiếu mới thì memo vô tác dụng hoặc effect chạy lại.

Tôi không bọc mọi thứ, vì memo cũng tốn: bộ nhớ, một lần so dependency, và code khó đọc hơn. Và ở năm 2026, câu hỏi khác đi nếu team dùng React Compiler. Nó ra bản 1.0 vào tháng mười năm 2025 và tự memo component và giá trị lúc build. Khi bật compiler, tôi gần như không viết useMemo và useCallback bằng tay nữa. Tôi chỉ giữ lại chỗ nào cần kiểm soát chính xác một tham chiếu, ví dụ một giá trị dùng làm dependency của effect.

Know: useMemo = cached value, useCallback = cached function (useCallback(fn, deps) ≡ useMemo(() => fn, deps)). Two reasons: expensive work, referential stability. React Compiler 1.0 (Oct 2025) makes most of it automatic.

Trap: Memoizing cheap values. useCallback on a function passed to a child that is not memoized: no benefit.

22useReducer vs useStateReducer when several values change together or the next state depends on an event type.~72s✓

When would you use useReducer instead of useState?

useState is my default. I switch to useReducer when state has several fields that change together, or when there are many ways to update it and I want them in one place.

A reducer is a pure function that takes the current state and an action, like { type: 'submitted' }, and returns the next state. The component just dispatches what happened. All the rules about how state changes live in the reducer, which I can read in one place and test without rendering anything.

A good example is a multi-step form or an upload: status, progress, error, and the current step all move together. With four useState calls, it's easy to set status to done and forget to clear the error. With a reducer, each action sets a consistent state. In TypeScript I type the actions as a discriminated union, so a typo in the action type is a compile error. One more benefit: dispatch never changes identity, so I can pass it down without useCallback.

Khi nào bạn dùng useReducer thay vì useState?

useState là lựa chọn mặc định của tôi. Tôi chuyển sang useReducer khi state có nhiều trường thay đổi cùng nhau, hoặc khi có nhiều cách cập nhật và tôi muốn gom chúng vào một chỗ.

Reducer là một hàm thuần, nhận state hiện tại và một action, như { type: 'submitted' }, rồi trả về state tiếp theo. Component chỉ việc dispatch chuyện gì đã xảy ra. Mọi quy tắc về cách state thay đổi nằm trong reducer, đọc ở một chỗ và test được mà không cần render gì.

Ví dụ hợp là một form nhiều bước hoặc một lần upload: status, tiến độ, lỗi, và bước hiện tại đều đổi cùng nhau. Dùng bốn useState thì rất dễ đặt status là done mà quên xóa lỗi. Dùng reducer thì mỗi action tạo ra một state nhất quán. Trong TypeScript, tôi khai báo type cho action bằng discriminated union, nên gõ sai tên action là lỗi compile ngay. Thêm một lợi ích: dispatch không bao giờ đổi tham chiếu, nên tôi truyền nó xuống mà không cần useCallback.

Know: Related fields, many update paths, testable pure transitions, stable dispatch. Discriminated union actions in TS.

Trap: Using a reducer for one boolean. Side effects inside the reducer (it must stay pure; StrictMode calls it twice).

23You might not need an effectIf you can calculate it during render, don't sync it with an effect.~76s✓

When should you not use useEffect?

A lot of effects in real code shouldn't exist. The common one is syncing state with other state: I have items and a filter in state, and an effect that sets filteredItems whenever they change. That renders twice, and for a moment the two disagree. The fix is to calculate filteredItems during render. If it's slow, wrap it in useMemo.

The second is handling a user action in an effect. If something should happen because the user clicked submit, like sending a request or showing a toast, it belongs in the click handler, not in an effect that watches a flag. Effects are for things caused by the component being on screen, not by a specific event.

The third is resetting state when a prop changes. Instead of an effect that clears the form when userId changes, I give the form key={userId}, and React mounts a fresh one. So my checklist is: can I derive it? Is it really an event? Can a key reset it? Only if all three are no do I write an effect.

Khi nào không nên dùng useEffect?

Rất nhiều effect trong code thực tế lẽ ra không cần có. Trường hợp phổ biến là đồng bộ state với state khác: tôi có items và bộ lọc trong state, và một effect set filteredItems mỗi khi chúng đổi. Như vậy phải render hai lần, và có một khoảnh khắc hai giá trị lệch nhau. Cách sửa là tính filteredItems ngay trong lúc render. Nếu chậm thì bọc bằng useMemo.

Trường hợp thứ hai là xử lý hành động của người dùng trong effect. Nếu việc gì đó xảy ra vì người dùng bấm submit, như gửi request hay hiện thông báo, nó thuộc về click handler, không phải một effect theo dõi một cờ nào đó. Effect dành cho việc xảy ra vì component đang hiện trên màn hình, không phải vì một sự kiện cụ thể.

Trường hợp thứ ba là reset state khi prop đổi. Thay vì một effect xóa form khi userId đổi, tôi đặt key={userId} cho form, và React mount một form mới. Nên tôi tự hỏi: có tính ra được không? Có thật là một sự kiện không? Có reset bằng key được không? Chỉ khi cả ba đều không, tôi mới viết effect.

Know: Derive during render (useMemo if slow), events in handlers, reset with key, fetch in a data library. Effects for external systems only.

Trap: An effect chain: effect A sets state that triggers effect B that sets state.

How do you optimize a slow React component?

I find out why it's slow before I change anything. The React DevTools Profiler tells me which components render, how often, and how long each takes. The browser's Performance panel tells me if the time is in JavaScript, layout, or the network.

25React.memoSkips a re-render when props are shallow-equal. Useless if props are new objects every time.~72s✓

What does React.memo do, and when does it help?

memo wraps a component so that when its parent re-renders, React compares the new props with the old ones, shallowly, and skips rendering the child if they're all equal. Without memo, the child always renders with the parent.

It helps when the child is expensive to render, the parent renders often, and the child's props usually don't change. A heavy chart next to a text field is a typical case: every keystroke re-renders the parent, but the chart's data is the same.

It doesn't help if I pass a new object, array, or function every render, because shallow comparison sees a new reference and renders anyway. Then I either keep those props stable with useMemo and useCallback, pass primitives instead, or restructure so the heavy part doesn't sit under the changing state at all. Also, memo doesn't stop re-renders caused by the child's own state or by a context it reads. And with React Compiler turned on, the compiler does this automatically, so manual memo becomes rare.

React.memo làm gì, và khi nào nó có ích?

memo bọc một component để khi component cha render lại, React so props mới với props cũ theo kiểu so nông, và bỏ qua việc render component con nếu tất cả đều bằng nhau. Không có memo thì component con luôn render theo cha.

Nó có ích khi component con render tốn kém, cha render thường xuyên, và props của con thường không đổi. Một biểu đồ nặng nằm cạnh một ô nhập chữ là ví dụ điển hình: mỗi lần gõ phím, cha render lại, nhưng dữ liệu của biểu đồ vẫn vậy.

Nó vô tác dụng nếu mỗi lần render tôi truyền vào một object, mảng hay hàm mới, vì so nông thấy tham chiếu mới và vẫn render. Lúc đó tôi giữ các props đó ổn định bằng useMemo và useCallback, truyền giá trị nguyên thủy, hoặc sắp xếp lại để phần nặng không nằm dưới state hay thay đổi. Thêm nữa, memo không chặn được việc render do state của chính component con hay do context nó đọc. Và khi bật React Compiler, compiler tự làm việc này, nên memo bằng tay sẽ hiếm đi.

Know: Shallow prop comparison. Inline objects, arrays, and functions defeat it. Doesn't block own state or context updates. Optional custom compare function.

Trap: memo on a component whose props are always new. memo on cheap components.

How do you do code splitting in React?

The goal is that the first page doesn't download code for pages the user hasn't opened. I split by route first, because that's where the big wins are. With React.lazy and a dynamic import, a screen loads its JavaScript when the user goes there, and a Suspense boundary shows a fallback while it loads. I measure before and after with the bundle analyzer and the network tab, and I don't split everything. Too many tiny chunks means many round trips and loading spinners everywhere. Tôi đo trước và sau bằng bundle analyzer và tab network, và tôi không tách mọi thứ. Quá nhiều mảnh nhỏ nghĩa là nhiều lượt gọi mạng và chỗ nào cũng có vòng quay loading. 30Custom hooksReuse stateful logic, not state. Name it useX, return what the caller needs.~78s✓

What is a custom hook, and when do you write one?

A custom hook is a function whose name starts with use and that calls other hooks. It lets me reuse stateful logic between components. Each component that calls it gets its own state; the hook shares the logic, not the data.

I write one when the same combination of state and effects appears in two places, or when a component's logic hides what it renders. Two examples that fit my apps: a hook that reads the window width and returns whether the Aquanix layout is wide enough for the sidebar, and a hook that wraps the auth context and throws a clear error if it's used outside the provider.

A few rules I follow. The name says what it does, like useIsWideScreen, not useHelper. It returns only what the caller needs, often an object, so I can add fields later. Values it returns are stable when they can be, so callers can use them as dependencies. And I don't turn every three lines into a hook. If there's no hook inside, it's just a normal function and shouldn't start with use.

Custom hook là gì, và khi nào bạn viết một custom hook?

Custom hook là một hàm có tên bắt đầu bằng use và gọi các hook khác bên trong. Nó cho phép dùng lại logic có state giữa các component. Mỗi component gọi nó có state riêng; hook dùng chung logic, không dùng chung dữ liệu.

Tôi viết custom hook khi cùng một tổ hợp state và effect xuất hiện ở hai chỗ, hoặc khi logic của component che mất phần nó render. Hai ví dụ hợp với các app của tôi: một hook đọc chiều rộng cửa sổ và trả về layout Aquanix có đủ rộng để hiện sidebar hay không, và một hook bọc auth context, báo lỗi rõ ràng nếu bị dùng bên ngoài provider.

Tôi theo vài quy tắc. Tên phải nói nó làm gì, như useIsWideScreen, chứ không phải useHelper. Nó chỉ trả về những gì nơi gọi cần, thường là một object, để sau này thêm trường được. Giá trị trả về giữ ổn định khi có thể, để nơi gọi dùng làm dependency được. Và tôi không biến mọi ba dòng code thành hook. Nếu bên trong không có hook nào thì đó chỉ là hàm bình thường và không nên bắt đầu bằng use.

31Error boundariesCatch render errors in a subtree and show a fallback. Not for event handlers or async code.~76s✓

What is an error boundary, and what does it not catch?

An error boundary is a component that catches errors thrown while rendering its children, in lifecycle methods, and in constructors below it. Instead of the whole app going blank, it shows a fallback for that part of the screen. Since React 16, an uncaught render error unmounts the whole tree, so without boundaries one broken widget takes down the page.

It still has to be a class with getDerivedStateFromError and componentDidCatch, even in React 19. In practice I use react-error-boundary, which gives me an ErrorBoundary component with a fallback, a reset function, and an onError callback where I send the error to Sentry.

It doesn't catch errors in event handlers, in setTimeout or promises, or in the boundary itself. For those I use try and catch, show the error in state, and report it. I place boundaries around independent areas, like each panel or each route, so one failure stays local. In Next.js the App Router does this per route with an error.tsx file. React 19 also added onCaughtError and onUncaughtError on the root for central reporting.

Error boundary là gì, và nó không bắt được lỗi nào?

Error boundary là một component bắt lỗi xảy ra khi render các component con, trong lifecycle method, và trong constructor ở bên dưới nó. Thay vì cả app thành trang trắng, nó hiện một giao diện dự phòng cho phần màn hình đó. Từ React 16, một lỗi render không được bắt sẽ unmount cả cây, nên không có boundary thì một widget hỏng kéo sập cả trang.

Nó vẫn phải là class với getDerivedStateFromError và componentDidCatch, kể cả ở React 19. Thực tế tôi dùng react-error-boundary, nó cho tôi component ErrorBoundary có fallback, hàm reset, và callback onError để tôi gửi lỗi lên Sentry.

Nó không bắt lỗi trong event handler, trong setTimeout hay promise, và lỗi của chính boundary. Những lỗi đó tôi dùng try catch, đưa lỗi vào state để hiển thị, và báo cáo lên. Tôi đặt boundary quanh từng khu vực độc lập, như mỗi panel hay mỗi route, để một lỗi chỉ ảnh hưởng tại chỗ. Trong Next.js, App Router làm việc này cho từng route bằng file error.tsx. React 19 còn thêm onCaughtError và onUncaughtError ở root để báo lỗi tập trung.

Know: Class-only (getDerivedStateFromError, componentDidCatch). react-error-boundary in practice. Doesn't catch event handlers, async code, SSR, or itself. Next.js error.tsx. React 19 root options onCaughtError / onUncaughtError.

32Context and its pitfallsFor values many components need and that change rarely. Every consumer re-renders on change.~78s✓

When do you use Context, and what are its pitfalls?

Context passes a value to any component below a provider without threading props through every level. I use it for values many components need that change rarely: the signed-in user, theme, locale. In the IELTS app the auth context holds the user and the sign-in state after the app restores the session from storage.

The pitfalls are about re-renders. When the provider's value changes, every component that reads that context re-renders, and memo doesn't stop it. Two mistakes make this worse. First, passing a new object every render, like value={{ user, signOut }}, which changes on every provider render. I memoize that value, or the compiler does. Second, one giant context with everything in it, so a change to one field wakes every consumer. I split it: one context for the data, one for the actions, or one per concern.

Context isn't a state manager. It just passes a value. If something changes often and many components read different parts of it, I'd use a store with selectors. And server data belongs in the data layer, not in a context because it's shared.

Khi nào bạn dùng Context, và nó có những cạm bẫy gì?

Context truyền một giá trị tới mọi component bên dưới provider mà không cần truyền props qua từng tầng. Tôi dùng nó cho những giá trị nhiều component cần và ít khi đổi: user đang đăng nhập, theme, ngôn ngữ. Trong app IELTS, auth context giữ user và trạng thái đăng nhập sau khi app khôi phục phiên từ bộ nhớ máy.

Cạm bẫy nằm ở việc render lại. Khi value của provider đổi, mọi component đọc context đó đều render lại, và memo không chặn được. Có hai lỗi làm chuyện này tệ hơn. Thứ nhất là truyền một object mới mỗi lần render, như value={{ user, signOut }}, nên nó đổi mỗi khi provider render. Tôi memo giá trị đó, hoặc để compiler làm. Thứ hai là một context khổng lồ chứa mọi thứ, nên đổi một trường là đánh thức mọi component dùng nó. Tôi tách ra: một context cho dữ liệu, một cho các hàm xử lý, hoặc mỗi mối quan tâm một context.

Context không phải công cụ quản lý state. Nó chỉ truyền giá trị. Nếu thứ gì đó đổi thường xuyên và nhiều component đọc những phần khác nhau của nó, tôi sẽ dùng store có selector. Còn dữ liệu từ server thuộc về tầng dữ liệu, không bỏ vào context chỉ vì nó được dùng chung.

Know: Rarely changing, widely needed values. Memoize the value object; split contexts; a custom hook that throws outside the provider. React 19: <Context value> works as the provider; use(Context) can be conditional.

Trap: One AppContext with everything. A new value object every render. Calling Context a state manager.

I type props with a type or interface, and I let TypeScript infer the rest when it can. useState infers from the initial value; when it starts empty, I give it the type, like useState<User | null>(null). The biggest win in my work is the API contract. Our APIs are TypeScript and Express, so the response types for an assignment or a pond are defined once and the client uses the same shapes. When a field changes, the compiler shows me every screen that breaks. I still validate data that comes over the network at runtime, because types disappear after compile. And I avoid any. Với state có nhiều dạng, tôi dùng discriminated union: status đang tải, hoặc status lỗi kèm thông báo, hoặc status xong kèm dữ liệu. Như vậy TypeScript không cho tôi đọc dữ liệu trước khi kiểm tra status.

36What's new in React 19Actions, useActionState, useOptimistic, use(), ref as a prop, metadata, custom elements.~80s✓

What changed in React 19?

The biggest change is Actions. An async function can be passed to a transition or straight to a form's action prop, and React tracks the pending state, errors, and the form reset for me. Around that there are three hooks: useActionState returns the result of the last action and an isPending flag, useFormStatus lets a submit button know its form is submitting, and useOptimistic shows the expected result immediately and rolls back if the action fails.

There's also use(), which reads a promise or a context during render. With a promise, the component suspends until it resolves, and unlike other hooks, use can be called inside a condition.

Then smaller things that clean up code. A ref is now a normal prop on function components, so forwardRef isn't needed. A context can be rendered as its own provider. Ref callbacks can return a cleanup. A title or meta tag rendered anywhere is moved into the document head. And custom elements finally work properly. What do Suspense, useTransition, and useDeferredValue do?

When something inside it isn't ready, like a lazy component, a promise read with use(), or data from a library that supports Suspense, React shows the fallback for that area instead of the whole page. I place boundaries where a loading state makes sense to the user, like one per panel.

What are React Server Components?

42SSR, SSG, ISR, and streamingStatic when you can, dynamic when you must, and stream the slow parts.~81s✓

What's the difference between SSR, SSG, and ISR?

They answer one question: when is the HTML built? With static generation, SSG, the HTML is built once at build time and served from a CDN. It's the fastest and cheapest, and it fits pages that are the same for everyone, like marketing pages or docs. With server-side rendering, SSR, the HTML is built on every request, which you need when it depends on the user, a cookie, or data that must be fresh. ISR sits in between: the page is static, but it's regenerated in the background after a revalidate time or when I trigger it, so it stays mostly fresh without rebuilding the whole site.

In the App Router you don't choose these by name. A route is static unless it uses something dynamic, like cookies, headers, or uncached data, and then it renders per request. Revalidation gives you the ISR behavior. And streaming with Suspense lets a dynamic page send its shell right away while slow parts load.

Client-side rendering is still an option for screens behind a login that don't need SEO. An admin dashboard can be mostly client components after the first load.

SSR, SSG và ISR khác nhau thế nào?

Cả ba trả lời cùng một câu hỏi: HTML được tạo ra lúc nào? Với static generation, SSG, HTML được tạo một lần lúc build và phục vụ qua CDN. Cách này nhanh và rẻ nhất, hợp với những trang giống nhau cho mọi người, như trang giới thiệu hay tài liệu. Với server-side rendering, SSR, HTML được tạo ở mỗi request, cần khi nội dung phụ thuộc vào người dùng, cookie, hoặc dữ liệu phải luôn mới. Trong App Router, không cần chọn các chế độ này theo tên. Một route là tĩnh trừ khi nó dùng thứ gì đó động, như cookies, headers, hay dữ liệu không cache, lúc đó nó render theo từng request. 44Hydration and hydration errorsServer HTML and the first client render must match.~81s✓

What is hydration, and what causes a hydration mismatch?

When a page is server-rendered, the browser first gets plain HTML, so the user sees content fast. Then React loads on the client, renders the same tree, and attaches event handlers to the existing HTML instead of rebuilding it. That's hydration.

It only works if the first client render produces the same output as the server did. When they differ, React reports a hydration mismatch, and it may re-render that part on the client, which is slower and can flicker. The usual causes are values that differ between server and browser: Date.now or new Date formatted with the server's timezone, Math.random, reading window or localStorage during render, or checking typeof window to render different markup. Invalid HTML nesting, like a div inside a p, and browser extensions that edit the page cause it too.

The fixes: render the same thing on both sides and update in an effect after mount, for example show the local time after hydration. Hydration là gì, và vì sao bị hydration mismatch?

Khi một trang được render ở server, trình duyệt nhận HTML trước, nên người dùng thấy nội dung nhanh. Sau đó React tải ở client, render lại cùng cây đó, và gắn event handler vào HTML có sẵn thay vì dựng lại. Đó là hydration.

Nó chỉ chạy đúng khi lần render đầu ở client cho ra kết quả giống hệt server. Khi khác nhau, React báo hydration mismatch, và có thể render lại phần đó ở client, chậm hơn và có thể bị nháy. Nguyên nhân thường gặp là các giá trị khác nhau giữa server và trình duyệt: Date.now hay new Date định dạng theo múi giờ của server, Math.random, đọc window hay localStorage trong lúc render, hoặc kiểm tra typeof window để render markup khác. Cách sửa: render giống nhau ở cả hai phía rồi cập nhật trong effect sau khi mount, ví dụ hiện giờ địa phương sau khi hydrate xong. Can you use web components, or custom elements, in React?

47Where should this state live? When do you need a store?Local → lifted → Context → store. Server data is a separate thing.~77s✓

How do you decide where state lives, and when do you actually need a state library?

I go up a ladder and stop at the first step that works. First, local state in the component that uses it. Second, lift it to the closest common parent if siblings share it. Third, Context, for values many components need that rarely change, like the signed-in user or the theme. Fourth, a store, only when several things are true at once: many distant components read and write the same client state, it changes often, and Context would re-render too much.

Separately from that ladder, I ask whether the data comes from the server. Lists, records, and anything the API owns are server state. They need caching, refetching, and invalidation, which is a data-fetching library's job, not a store's. Filters that should survive a refresh or be shareable go in the URL.

In my own apps, local state plus an auth context has been enough, because most shared data is server data. I'd add a store for something like a complex editor, a multi-step flow shared across screens, or a dashboard where many widgets react to the same selection.

Bạn quyết định state nằm ở đâu thế nào, và khi nào thực sự cần một thư viện state?

Tôi đi theo từng bậc và dừng ở bậc đầu tiên đủ dùng. Thứ nhất, state cục bộ trong component dùng nó. Thứ hai, đưa lên component cha chung gần nhất nếu các component anh em cùng dùng. Thứ ba, Context, cho giá trị nhiều component cần và ít khi đổi, như user đang đăng nhập hay theme. Thứ tư, một store, chỉ khi nhiều điều cùng đúng: nhiều component cách xa nhau cùng đọc và ghi một state phía client, nó đổi thường xuyên, và dùng Context thì render lại quá nhiều.

Tách riêng khỏi các bậc đó, tôi hỏi dữ liệu này có đến từ server không. Danh sách, bản ghi, và mọi thứ API sở hữu là server state. Chúng cần cache, tải lại, và làm mới khi thay đổi, đó là việc của thư viện lấy dữ liệu, không phải của store. Bộ lọc cần giữ lại khi tải lại trang hoặc chia sẻ được thì để trên URL.

Trong các app của tôi, state cục bộ cộng một auth context là đủ, vì phần lớn dữ liệu dùng chung là dữ liệu server. 48Context vs Redux vs ZustandContext passes values, Redux is structured and team-scale, Zustand is a small store with selectors.~82s✓

Context, Redux, or Zustand: how do you choose?

They solve different problems. Context isn't really a state manager. It passes a value down the tree, and every consumer re-renders when it changes. It's right for things like the current user or the theme, and that's what I use in my own apps.

Redux, today meaning Redux Toolkit, is a single store where changes go through actions and reducers. That's more structure: every change is a named event you can trace in DevTools, which helps on a large app with many developers. RTK Query adds server-state caching on top.

Zustand is a small store you create with a hook. You write state and functions that call set, and components subscribe with a selector, so a component only re-renders when the slice it selected changes. There's no provider and much less ceremony than Redux.

My rule: Context for rarely changing values, Zustand when shared client state changes often and the team wants it light, Redux when the team already uses it or needs that structure. I'll be honest that I haven't used Zustand or Redux in production. I've studied both, and on a team I'd follow the existing store pattern first.

Context, Redux hay Zustand: bạn chọn thế nào?

Ba thứ này giải quyết các vấn đề khác nhau. Context thực ra không phải công cụ quản lý state. Nó truyền một giá trị xuống cây component, và mọi nơi dùng nó đều render lại khi giá trị đổi. Nó hợp với những thứ như user hiện tại hay theme, và đó là thứ tôi dùng trong các app của tôi.

Redux, ngày nay nghĩa là Redux Toolkit, là một store duy nhất nơi mọi thay đổi đi qua action và reducer. Như vậy có cấu trúc hơn: mỗi thay đổi là một sự kiện có tên và theo dõi được trong DevTools, có ích với app lớn có nhiều developer. RTK Query còn thêm phần cache dữ liệu server.

Zustand là một store nhỏ, tạo ra dưới dạng một hook. Ta viết state và các hàm gọi set, còn component đăng ký bằng selector, nên component chỉ render lại khi phần nó chọn thay đổi. Không cần provider và ít thủ tục hơn Redux nhiều.

Nguyên tắc của tôi: Context cho giá trị ít đổi, Zustand khi state dùng chung phía client đổi thường xuyên và team muốn gọn nhẹ, Redux khi team đã dùng sẵn hoặc cần cấu trúc đó. 49Server state vs client state, and TanStack QueryData the API owns needs caching and invalidation. That's a data library's job, not a store's.~84s✓

What's the difference between server state and client state? Why use TanStack Query?

Client state belongs to the UI: is the modal open, which tab is active, what's typed in a draft. The browser is its source of truth. Server state is a copy of data the server owns: a list of assignments, a pond's readings. It can go stale, other users change it, and several screens may need the same data.

Server state needs things a store doesn't give you: caching by key, deduping identical requests, refetching when the window regains focus or the network comes back, retries, and invalidating after a mutation. Writing that by hand in effects is where most fetching bugs come from.

TanStack Query does that. I call useQuery with a key like ['ponds', farmId] and a fetch function, and get data, error, and isPending. After a mutation, I invalidate that key and the screens refetch. staleTime controls how long data counts as fresh.

In my own clients I've used typed fetch helpers against our Express APIs, and the IELTS app loads progress once on sign-in and keeps it locally. I haven't used TanStack Query in production, but it's what I'd reach for on a screen-heavy web app, and the team's choice comes first.

Server state và client state khác nhau thế nào? Vì sao dùng TanStack Query?

Client state thuộc về giao diện: modal có đang mở không, tab nào đang chọn, bản nháp đang gõ gì. Trình duyệt là nguồn dữ liệu của nó. Server state là bản sao của dữ liệu do server sở hữu: danh sách bài tập, số đo của một cái ao. Nó có thể cũ đi, người khác có thể sửa nó, và nhiều màn hình có thể cần cùng dữ liệu đó.

Server state cần những thứ mà store không cho: cache theo key, gộp các request giống nhau, tải lại khi người dùng quay lại cửa sổ hoặc có mạng lại, thử lại khi lỗi, và làm mới sau khi có thay đổi. Tự viết những thứ đó bằng effect là nguồn gốc của phần lớn lỗi khi fetch.

TanStack Query làm những việc đó. Tôi gọi useQuery với một key như ['ponds', farmId] và một hàm fetch, rồi nhận về data, error và isPending. Sau khi thay đổi dữ liệu, tôi invalidate key đó và các màn hình tự tải lại. staleTime quyết định dữ liệu được coi là còn mới trong bao lâu.

50Zustand 5: store, selectors, and useShallowimport { create }, select the smallest slice, useShallow for objects.~78s✓

How do you create a Zustand store, and how do you avoid extra re-renders?

In Zustand 5 I write import { create } from 'zustand'. The default import was removed. create takes a function that receives set and get and returns the state and its actions, and it gives back a hook. With TypeScript it's create<State>() followed by the function. Inside an action, set({ status: 'open' }) merges a field, set(s => ({ count: s.count + 1 })) uses the previous value, and get() reads current state in an async action.

In a component I always pass a selector: useFilterStore(s => s.status). The component re-renders only when that value changes. Calling the hook with no selector subscribes to the whole store, so every change re-renders it.

The trap is a selector that returns a new object, like s => ({ status: s.status, range: s.range }). In version 5 that's a new reference every time, and it can cause an infinite loop with a "maximum update depth" error, not just extra renders. The fix is useShallow from zustand/react/shallow, which compares the fields, or two separate selectors. This is from the docs. I haven't shipped Zustand in production.

Bạn tạo store Zustand thế nào, và tránh render thừa ra sao?

Với Zustand 5, tôi viết import { create } from 'zustand'. Kiểu import default đã bị bỏ. create nhận một hàm có set và get, trả về state cùng các action, và nó trả lại một hook. Với TypeScript thì viết create<State>() rồi mới tới hàm đó. Trong action, set({ status: 'open' }) gộp một trường vào state, set(s => ({ count: s.count + 1 })) dùng giá trị trước đó, còn get() đọc state hiện tại trong một action async.

Trong component, tôi luôn truyền selector: useFilterStore(s => s.status). Component chỉ render lại khi giá trị đó đổi. Gọi hook mà không có selector là đăng ký cả store, nên mọi thay đổi đều làm nó render lại.

Cái bẫy là selector trả về một object mới, như s => ({ status: s.status, range: s.range }). Ở bản 5, mỗi lần đó là một tham chiếu mới, và có thể gây vòng lặp vô hạn với lỗi "maximum update depth", chứ không chỉ là render thừa. Cách sửa là useShallow từ zustand/react/shallow, nó so từng trường, hoặc dùng hai selector riêng. Phần này tôi biết qua tài liệu. Tôi chưa dùng Zustand trên production.

51What goes in a store, and what doesn'tUI coordination in the store, server data in the data layer, shareable filters in the URL.~81s✓

What would you put in a client store, and what would you keep out?

In a store I'd put client state that many parts of the screen coordinate on: the selected row or item, which panel is open, a multi-step draft that spans screens, layout preferences, and UI flags. Things the user creates on this device and the server doesn't know about yet.

I'd keep three things out. Server data, like lists and records, stays in the data layer with its cache and refetching. If I copy it into a store, I now have two copies that drift, and I have to sync them by hand. Derived values, like a filtered list or a total, are calculated from state, not stored. And filters, sort order, page number, and the active tab usually belong in the URL search params, so a refresh keeps them, the back button works, and a link can be shared.

So a filter change on a data-heavy screen goes like this: the filter updates the URL, the query key includes the filter, the data library fetches the new page from the API, and only components that read that data re-render. The store, if there is one, just holds the selection.

Bạn sẽ để gì trong store phía client, và để gì ra ngoài?

Trong store, tôi để state phía client mà nhiều phần của màn hình cùng phối hợp: dòng hay mục đang chọn, panel nào đang mở, một bản nháp nhiều bước kéo qua nhiều màn hình, tùy chọn layout, và các cờ giao diện. Tức là những thứ người dùng tạo ra trên thiết bị này mà server chưa biết.

Có ba thứ tôi để ra ngoài. Dữ liệu server, như danh sách và bản ghi, nằm ở tầng dữ liệu với cache và cơ chế tải lại của nó. Nếu copy vào store, tôi sẽ có hai bản sao lệch nhau và phải tự đồng bộ. Giá trị suy ra được, như danh sách đã lọc hay tổng tiền, thì tính từ state, không lưu lại. Còn bộ lọc, thứ tự sắp xếp, số trang và tab đang chọn thường nên để trên search params của URL, để tải lại trang vẫn giữ, nút quay lại vẫn chạy, và chia sẻ link được.

Nên khi đổi bộ lọc trên một màn hình nhiều dữ liệu, mọi thứ diễn ra thế này: bộ lọc cập nhật URL, query key có chứa bộ lọc, thư viện dữ liệu lấy trang mới từ API, và chỉ những component đọc dữ liệu đó mới render lại. Còn store, nếu có, chỉ giữ phần đang được chọn.

How do you add charts to a React app, and what goes wrong?

The hard part of a chart is usually the data, not the drawing. I have the server return the numbers already aggregated for the chart, like totals per day, instead of sending raw rows and summing them in the browser. How do you render a list with thousands of items without freezing the UI?

First I ask whether the user really needs thousands of items on one screen. Often pagination or infinite loading from the server is the real fix, because it also cuts the network and memory cost.

When the list really is long, I virtualize it. A virtualized list renders only the rows that are visible plus a small buffer, and swaps their content as you scroll. So ten thousand items cost about as much as thirty. On the web I'd use TanStack Virtual or react-window. On React Native, FlatList already does this, and FlashList from Shopify is faster for big lists because it recycles row views.

The details that matter: stable keys from ids, rows that are cheap and memoized, and known or measured row heights, because variable heights make scrolling jumpy if the library guesses wrong. On FlatList, I set keyExtractor, and getItemLayout if rows have a fixed height.

There are trade-offs to know. Off-screen rows don't exist in the DOM, so the browser's find-in-page can't see them, screen readers only see the rendered part, and restoring scroll position needs care. For a list of a hundred rows I wouldn't bother.

56React Native vs React on the webSame React, different host: native views, Flexbox styles, no DOM.~81s✓

How is React Native different from React on the web?

The React part is the same: components, props, state, hooks, context. What changes is what React renders into. On the web it creates DOM nodes. In React Native it creates real native views, a UIView on iOS and an Android View, through components like View, Text, Image, Pressable, and ScrollView. There's no HTML and no CSS file.

Styling is JavaScript objects with a subset of CSS and Flexbox layout, where the default direction is column, not row. Styles don't cascade, so text must be inside a Text component, and each component gets its own style. Lists use FlatList instead of mapping into a scroll view. Navigation is a stack of screens, not URLs, though Expo Router gives it file-based routes.

Under the hood, the New Architecture is now the default: JSI lets JavaScript call native code directly instead of sending messages over the old asynchronous bridge, Fabric is the new renderer, and Turbo Modules load native modules lazily. In practice, that means smoother interaction and synchronous calls where needed. And platform differences remain: I check keyboard handling, safe areas, back button behavior, and permissions on both iOS and Android.

React Native khác React trên web thế nào?

Phần React thì giống nhau: component, props, state, hook, context. Thứ khác là React render ra cái gì. Trên web nó tạo node DOM. Với React Native nó tạo view native thật, UIView trên iOS và View trên Android, qua các component như View, Text, Image, Pressable và ScrollView. Không có HTML và không có file CSS.

Style là object JavaScript với một phần của CSS và layout Flexbox, trong đó hướng mặc định là cột, không phải hàng. Style không kế thừa xuống, nên chữ phải nằm trong component Text, và mỗi component có style riêng. Danh sách dùng FlatList thay vì map vào một ScrollView. Điều hướng là một chồng màn hình, không phải URL, dù Expo Router cho phép định nghĩa route theo file.

Bên dưới, New Architecture giờ là mặc định: JSI cho JavaScript gọi thẳng code native thay vì gửi message qua cầu nối bất đồng bộ cũ, Fabric là bộ render mới, và Turbo Modules tải native module khi cần. Thực tế nghĩa là tương tác mượt hơn và có thể gọi đồng bộ khi cần. Còn khác biệt giữa các nền tảng vẫn có: tôi kiểm tra bàn phím, vùng an toàn, nút quay lại, và quyền truy cập trên cả iOS lẫn Android.

Where do you store data and tokens in a React Native app?

It depends on what the data is. Tokens and anything secret go in secure storage, like Expo SecureStore, which uses the Keychain on iOS and the Keystore on Android. AsyncStorage is a plain key-value store, unencrypted, so it's fine for preferences and cached app data, but not for secrets. For larger structured data or real offline use, SQLite or a sync library is a better fit.

For the IELTS app the important change was about loading, not just storage. The app used to make one request per topic to show progress. I replaced that with a single progress fetch on sign-in, saved locally, so screens read from the device and feel instant, and the server writes back as the user practices.

For offline, I decide per feature. Reading cached content offline is easy. Writing offline needs a queue: save the action locally, retry when the network returns, and make the server endpoint idempotent so a retry doesn't double-count. And entitlements like Pro access are always confirmed by the server, so clearing or editing local storage can't unlock anything.

Bạn lưu dữ liệu và token ở đâu trong app React Native?

Tùy dữ liệu đó là gì. Token và mọi thứ bí mật thì lưu trong bộ nhớ an toàn, như Expo SecureStore, dùng Keychain trên iOS và Keystore trên Android. 60Testing React with React Testing LibraryTest what the user sees: find by role, act with userEvent, assert on the screen.~83s✓

How do you test React components?

I use Jest or Vitest with React Testing Library. The idea is to test the component the way a user uses it, not its internals. I render it, find elements the way a person or a screen reader would, act on them, and check what's on screen.

So I query by role and accessible name first: getByRole('button', { name: 'Save' }), or getByLabelText for an input. If I can't find an element by role, that's often an accessibility problem in the component. I use userEvent, not fireEvent, because it simulates real typing and clicking, including focus. I don't test state values or which hooks were called, so the test survives a refactor.

The cases I care about most are the ones users hit: the form shows an error and doesn't submit when a field is empty, the button is disabled while saving, the error message shows when the API fails. For honesty: my Jest experience is mostly on the API side, like PhysioFix, and on helpers in the IELTS app, such as scoring and storage. I haven't written a large React Testing Library suite in production, but this is how I'd build one.

Bạn test component React thế nào?

Tôi dùng Jest hoặc Vitest với React Testing Library. Ý tưởng là test component theo cách người dùng dùng nó, không test phần bên trong. Tôi render nó, tìm các phần tử theo cách một người hoặc trình đọc màn hình sẽ tìm, thao tác lên chúng, rồi kiểm tra thứ hiện trên màn hình.

Nên tôi ưu tiên tìm theo role và tên có thể truy cập: getByRole('button', { name: 'Save' }), hoặc getByLabelText cho ô nhập. Nếu không tìm được phần tử theo role, đó thường là lỗi accessibility của component. Tôi dùng userEvent chứ không dùng fireEvent, vì nó giả lập việc gõ và bấm thật, kể cả focus. Tôi không test giá trị state hay hook nào đã được gọi, để test vẫn đúng khi refactor.

Những trường hợp tôi quan tâm nhất là những gì người dùng gặp: form báo lỗi và không gửi khi một trường bị trống, nút bị khóa trong lúc lưu, thông báo lỗi hiện ra khi API thất bại. Nói thật: kinh nghiệm Jest của tôi chủ yếu ở phía API, như PhysioFix, và ở các hàm hỗ trợ trong app IELTS, như chấm điểm và lưu trữ. Tôi chưa viết một bộ test React Testing Library lớn trên production, nhưng đây là cách tôi sẽ làm.

61Testing components that fetch dataMock the network, not the hook. findBy waits for the result.~80s✓

How do you test a component that calls an API?

I mock at the network boundary, not inside the component. Mock Service Worker, MSW, intercepts fetch requests in tests and returns the responses I define, so the component runs its real fetching code. If I later switch from fetch to a data library, the test doesn't change.

A typical test: I set up a handler that returns two assignments, render the screen, and use await findByText or findByRole, which waits until the element appears. Then I check the loading state disappeared. For the failure case, I override the handler in that one test to return a 500, and check that the error message shows and the retry button works. For an empty response, the empty state.

A few rules make these tests reliable. Each test gets a fresh query client or store, so cached data from one test doesn't leak into the next. I wait for what the user sees with findBy or waitFor, instead of fixed timeouts. And I reset handlers after each test. The same MSW handlers can also run in the browser during development, so the frontend can work before the API endpoint exists.

Bạn test một component có gọi API thế nào?

Tôi mock ở ranh giới mạng, không mock bên trong component. Mock Service Worker, MSW, chặn các request fetch trong test và trả về response tôi định nghĩa, nên component vẫn chạy code lấy dữ liệu thật của nó. Nếu sau này tôi đổi từ fetch sang một thư viện dữ liệu, test không cần sửa.

Một test điển hình: tôi tạo một handler trả về hai bài tập, render màn hình, rồi dùng await findByText hoặc findByRole, nó sẽ chờ tới khi phần tử xuất hiện. Sau đó tôi kiểm tra trạng thái loading đã biến mất. Với trường hợp lỗi, tôi ghi đè handler trong đúng test đó để trả về lỗi 500, rồi kiểm tra thông báo lỗi hiện ra và nút thử lại hoạt động. Với response rỗng thì kiểm tra trạng thái trống.

Vài quy tắc giúp test ổn định. Mỗi test có một query client hoặc store mới, để dữ liệu cache của test này không lọt sang test khác. Tôi chờ thứ người dùng nhìn thấy bằng findBy hoặc waitFor, thay vì chờ một khoảng thời gian cố định. Và tôi reset handler sau mỗi test. Cùng những handler MSW đó còn chạy được trên trình duyệt lúc phát triển, để frontend làm trước khi endpoint API có sẵn.

Know: MSW v2: http.get(url, () => HttpResponse.json(...)), server.use() to override per test, resetHandlers in afterEach. findBy* = getBy + waitFor. Fresh QueryClient per test with retry: false.

How do you decide what to test in a frontend app?

I spend tests where a bug would hurt most and where they're cheap to keep. Pure logic, like scoring, formatting, and validation rules, gets plain unit tests, because they're fast and never flaky. That's what I've done on the IELTS app with the scoring and storage helpers.

Components get tests through React Testing Library for the behavior users depend on: forms, error states, permissions that hide or disable actions. I don't test every presentational component.

Then a small number of end-to-end tests on the critical paths, the ones that would cost money or trust if they broke: sign in, the main create flow, and payment or purchase. For the web I'd use Playwright, which runs a real browser against a staging build. For React Native, Maestro or Detox do the same on a device or simulator. I keep these few, because they're slower and flakier.

Some things are better checked by tools than tests: TypeScript for contract mistakes, ESLint with the hooks rules, and an accessibility checker in CI. And when a bug reaches production, I add a test for it before I fix it.

Bạn quyết định test những gì trong một app frontend thế nào?

Tôi dồn test vào chỗ mà lỗi sẽ gây hại nhiều nhất và test dễ duy trì. Logic thuần, như chấm điểm, định dạng và quy tắc kiểm tra dữ liệu, thì viết unit test đơn giản, vì chạy nhanh và không bao giờ chập chờn. Đó là cách tôi đã làm ở app IELTS với các hàm chấm điểm và lưu trữ.

Component thì test bằng React Testing Library cho những hành vi người dùng dựa vào: form, trạng thái lỗi, phân quyền ẩn hoặc khóa thao tác. Tôi không test mọi component chỉ để hiển thị.

63Accessibility basics in ReactSemantic HTML first, labels, keyboard, focus, contrast. ARIA only to fill gaps.~84s✓

How do you make a React app accessible?

Most of it is using the right HTML. A button is a button element, not a div with onClick, because the real button gets keyboard focus, Enter and Space, and the right role for free. Links that navigate are anchors. Headings follow a real order, and pages have landmarks like main and nav.

Every input has a label, connected with htmlFor or by wrapping it, and errors are linked with aria-describedby so a screen reader reads them. Images have alt text, or empty alt if they're decorative. Everything works with the keyboard alone, focus is visible, and the color contrast is high enough. When content changes without a page load, like a saved message, I announce it with an aria-live region, and after navigation in a single-page app I move focus to the new heading.

ARIA is for gaps HTML can't fill, like a custom tab list, and the first rule is to avoid it when a native element exists, because wrong ARIA is worse than none. In React Native the same ideas use accessibilityLabel, accessibilityRole, and checking with VoiceOver and TalkBack. I test with the keyboard, an axe check, and a screen reader on key flows.

Bạn làm app React dễ tiếp cận cho mọi người dùng thế nào?

Phần lớn là dùng đúng HTML. Nút bấm phải là thẻ button, không phải div có onClick, vì button thật có sẵn focus bằng bàn phím, Enter và Space, và đúng role. Link dùng để chuyển trang thì là thẻ a. Tiêu đề đi đúng thứ bậc, và trang có các vùng mốc như main và nav.

Mỗi ô nhập có nhãn, gắn bằng htmlFor hoặc bọc bên ngoài, và lỗi được liên kết bằng aria-describedby để trình đọc màn hình đọc được. Ảnh có alt, hoặc alt rỗng nếu chỉ để trang trí. Mọi thứ dùng được chỉ bằng bàn phím, focus nhìn thấy được, và độ tương phản màu đủ cao. Khi nội dung thay đổi mà không tải lại trang, như thông báo đã lưu, tôi thông báo bằng vùng aria-live, và sau khi chuyển trang trong app một trang, tôi chuyển focus tới tiêu đề mới.

ARIA dành cho những chỗ HTML không làm được, như một danh sách tab tự làm, và quy tắc đầu tiên là không dùng nó khi đã có thẻ native, vì ARIA sai còn tệ hơn không có. Trong React Native, cùng những ý đó dùng accessibilityLabel, accessibilityRole, và kiểm tra bằng VoiceOver và TalkBack. Tôi test bằng bàn phím, công cụ axe, và trình đọc màn hình trên các luồng chính.

64Accessible modals and portalsPortal for stacking, the dialog element or a tested library, focus in and focus back.~79s✓

How do you build a modal in React, and make it accessible?

For rendering, a modal usually needs to escape its parent's overflow and z-index, so I render it with createPortal into document.body. Events still bubble through the React tree, not the DOM tree, which surprises people.

For behavior, a modal needs several things. Focus moves into the dialog when it opens, usually to the first field or the close button. Tab stays inside the dialog, the focus trap. Escape closes it. The page behind can't be scrolled or reached by a screen reader. And when it closes, focus goes back to the button that opened it. The dialog needs role dialog, aria-modal, and a label from its title.

Today the easiest correct way on the web is the native dialog element: calling showModal gives me the top layer, Escape handling, the backdrop, and makes the rest of the page inert. Otherwise I'd use a tested headless library like Radix UI or React Aria rather than writing focus trapping myself. On React Native, the Modal component handles the stacking, and I still set the accessibility label and make sure the screen reader focus moves into it.

Bạn làm modal trong React thế nào, và làm sao cho nó dễ tiếp cận?

Về hiển thị, modal thường phải thoát khỏi overflow và z-index của component cha, nên tôi render nó bằng createPortal vào document.body. Event vẫn nổi lên theo cây React, không theo cây DOM, điều này hay làm người ta bất ngờ.

Về hành vi, một modal cần nhiều thứ. Focus chuyển vào hộp thoại khi nó mở, thường là ô nhập đầu tiên hoặc nút đóng. Phím Tab chỉ chạy trong hộp thoại, gọi là focus trap. Phím Escape đóng nó. Trang phía sau không cuộn được và trình đọc màn hình không vào được. Và khi đóng, focus quay lại nút đã mở nó. Hộp thoại cần role dialog, aria-modal, và nhãn lấy từ tiêu đề của nó.

Ngày nay cách dễ nhất mà vẫn đúng trên web là thẻ dialog native: gọi showModal là có top layer, xử lý phím Escape, lớp nền mờ, và phần còn lại của trang không tương tác được. Nếu không, tôi dùng một thư viện headless đã được kiểm chứng như Radix UI hay React Aria, thay vì tự viết focus trap. Trên React Native, component Modal lo phần chồng lớp, và tôi vẫn đặt nhãn accessibility và đảm bảo focus của trình đọc màn hình chuyển vào trong.

Know: createPortal; events bubble through the React tree. Focus in, trap, Escape, inert background, return focus. <dialog> + showModal(). Radix UI, React Aria, Headless UI.

Trap: A div overlay with no focus management. Forgetting to return focus on close.
