How to talk

Structure, then stop. Let her pull detail.

  1. “A good example is…” / “The one that comes to mind is…”
  2. Situation in one sentence. Problem in one sentence.
  3. Two or three actions you personally took. Say “I”, then mention the team.
  4. Result. Number if you have one. If not, say the concrete change: fewer manual deploys, teachers could assign, sync no longer duplicated records.
  5. One lesson. Then stop.

Simple English is stronger. Do not say “I leveraged cross-functional collaboration.”

Story A. Be honest: mobile and CI/CD were new. LLMs helped you learn. You still owned the ship. This is exactly how Go1 says engineers should work.

A good example is the IELTS AI Tutor. We needed a real product: a React Native app on iOS and Android, a teacher workflow, a backend on Cloud Run, and a way to build and release it. Email theme 3

5. A challenging goal, or a moment you felt stuck, and the practical way forward

Story B. Follow-ups: What was the risk if you were wrong? Who did you involve?

At BaseVN I worked on HR, payroll, tax, and social insurance systems. Some workflows sat on more than 500,000 records, and data moved between systems.

I felt stuck because it was not one slow query. We had to know which system was the source of truth, what missing or duplicate records would do to payroll or reports, and which change was safe.

I made the problem visible first. I mapped the data flow, marked the important entities, checked the current schema and queries, and started with the highest-risk path — the one that could break money or compliance reporting — not the easiest refactor.

From there I improved structure and queries step by step instead of rewriting everything. The lesson: when a system feels too big, I need a picture of the dependencies before I change production data paths.

6b. Commit to a plan you did not initially agree with

Story F — Base PIT. Who decided = PO / tech lead. You feared a bad tax file on a large company. You still shipped their plan, then made it safer.

Around Base PIT launch, I wanted to move the heavy Excel/XML export off the request path first — background job, then download — because we already had more than 500,000 records. I was afraid the first real tax period on a big company would time out, blow memory, or worse, produce a file that looked fine and was wrong.

I committed. I did not keep arguing. The lesson: I push once, clearly, then I help the team win. I only escalate again if security, money, or users are in real danger.

If she asks “so you were right?” “Partly. The launch date was also right. My job after the decision was not to be right — it was to make their plan work and keep the risk visible.”

11. Decision with incomplete information

12. Disagreement / conflict

Different story from 6b. 6b = you lost and committed. This = two people, real tension, how it ended, relationship after. Use Akktis Friday deploy.

A good example is a Friday production push at Akktis. The client PM wanted a change live that evening. From their side that made sense: the customer was waiting, the diff looked small, and another weekend would slip the promise. Another engineer was ready to ship it.

I was not comfortable. We work across time zones. If staging was skipped and something broke after Europe logged off, I would be the one on the box, and rollback would be messy. My fear was not “process for process.” It was a Sunday incident with no one who knew the change still online.

I did not make it personal. I said their goal out loud — the customer should get the fix — then I said the risk: env drift, a missed variable, no clean rollback. I asked for a middle path: a short staging pass, a written rollback, then deploy. If staging was impossible, at least a health check and a way to turn the change off.

We did that. The change went out the same day, after a quick staging check. It held. After that, that PM still pushed for dates — that is their job — but they started asking for the rollback note. We could still work. Kind on the person, tough on the deploy.

If she asks “did you block the release?” “No. I would only hard-block for data loss or security. This was ‘slow down one hour so we can undo it.’”

Backup if she wants product, not ops: IELTS — a stakeholder wanted a broad “do everything” AI assistant for a date. I wanted a narrower flow plus Langfuse so we could judge quality. We shipped the narrow path. Relationship stayed fine because I showed a clickable version, not a lecture.

She will almost ask this

You wrote “optimized queries for 500,000+ records.” Walk me through it.

This is the money story from Base PIT (personal income tax). Correctness matters more than speed — wrong tax/payroll is worse than a slow screen. Follow-ups: EXPLAIN, indexes, why not load all rows in PHP, how you proved it.

Base PIT is a personal income tax product. It sat on more than 500,000 records and had to talk to HRM and Payroll. The painful parts were reporting and export — Excel and XML for tax-style compliance — plus screens that loaded or filtered a lot of employee and period data.

The first rule: I do not run a 500k-row report inside a user request. That will time out or blow memory. I treat heavy export and sync as a job path: chunk the work, write the file, then let the user download it.

Then I find the real slow query. I look at the slow query log or the query behind the slow screen, run EXPLAIN, and check whether it is a full scan, a bad join, or a missing index on the columns we actually filter — company, employee, period, that kind of key. I also look for SELECT * and N+1: one query per row in a loop will die at this size.

What I change is usually boring and safe: add or fix indexes that match the WHERE and JOIN, rewrite the query so it only fetches the columns and rows the report needs, and process in batches instead of loading everything into PHP memory. Sometimes the schema itself was the problem — types, keys, or a table that mixed too many concerns — so I adjust that carefully and re-test the export.

I always re-check correctness, not only speed. For tax data I compare a small known sample: same employees, same period, Excel/XML still matches HRM/Payroll. Fast and wrong is a worse launch than slow and right.

What I learned: at this size, schema and queries are infrastructure. “It works on my laptop” is not a plan.

If she asks “what index?” Say: indexes on the columns we filter and join — typically company / employee / tax period — so EXPLAIN stops doing a full table scan. I do not add an index on every column; unused indexes slow writes.

If she asks “how did you measure?” / “what improved?” Do not invent 3s → 300ms. Say: before, a heavy export on a large company could time out or run out of memory, and a list screen felt stuck because the query scanned too much. After indexes, narrower queries, and batching, the export finished and the screen was usable. I proved correctness on a small known sample — same employees, same period, Excel/XML still matched. Speed without a matching file is a failure.

How do you find a slow query? What does EXPLAIN tell you?

I start from the user symptom: which screen, which export, which company and period. Then I get the SQL — from logs, from the ORM, or by reproducing the action. I run EXPLAIN.

I look for type ALL or a huge rows count, no useful key, or a join that explodes. That usually means a missing index or a filter that cannot use an index — function on the column, bad types, or SELECT * plus a sort of the whole table.

I change one thing, measure again, and keep a copy of the old query. I do not “tune production” by guessing.

Would you return 500k rows to the API or the phone?

No. A list on a phone or a web table needs pagination and only the fields the screen needs. A full tax file is a background export, not a JSON dump. Same idea I use on IELTS: I do not hydrate a huge payload per topic if I can store progress locally and fetch what the screen needs.

Catch before it hurts

What is the most important issue you caught, and how did you fix it?

She wants: how you noticed, why it mattered, what you did before users or finance suffered. Pick silent sync as the main answer. PIT slowness is the backup if she wants performance.

The most important class of issue I have caught is a silent data mismatch, not a crash.

On Base VSS we synced Vietnam Social Security data with HRM and Payroll, and we exported Excel/XML for compliance. A crash is obvious. A sync that “succeeds” with the wrong mapping is worse — counts look fine until finance or the tax path notices.

How I catch it: I do not trust the job’s success log. I take a small known sample — a few employees I can check by hand — and I compare source fields vs destination fields vs the export. I check job order too: if Payroll reads before HRM has finished, you get yesterday’s truth.

How I fix it: correct the mapping or the transform rule, or fix the job order, then add a clearer validation step — row counts, required fields, or a checksum-style check on the sample — so the next failure is loud. Then I re-run on the sample before I touch the full set.

That is the issue I care about most: wrong money or compliance data that looks green. I would rather catch it on ten rows than explain it on 500,000.

Backup — caught before launch: On PIT, slow or memory-heavy exports showed up while we were still making the system launch-ready. Catching that before go-live meant we could change indexes and batch the export instead of discovering it on the first real tax period.

Backup — caught before users: Staging vs prod config, or Cloud Run up but Cloud SQL unreachable. I diff env, secrets, and IAM before I rewrite application code.

The hardest was Base PIT around launch. It was not one slow query. We had large data, reporting that had to be correct, Excel/XML that had to match HRM and Payroll, and a deadline. If I optimized the wrong path I could make exports fast and tax numbers wrong.

How you work

How do you estimate the time of a task?

Directors ask this to see if you hide uncertainty. Do not say “I just feel it.”

I do not estimate a blurry ticket as one number. I break it first.

One: what is already clear — screens, API, a query I have seen before. Two: what is unknown — data volume, a third-party API, missing env access, unclear rules. Three: test and release — especially if tax, sync, or production data is involved.

I estimate the known part from similar work. A normal CRUD feature is one thing. A PIT-style report on a large table is another, because I need time to profile, index, and verify a sample. A VietnamWorks-style integration needs time for auth, retries, and a failed-response path, not only the happy JSON.

I say my assumptions out loud: “This is three days if the mapping is documented and I can use a staging dump. If the dump is messy or the vendor API is different from the docs, I need a half-day spike and I will re-estimate.”

I also add a buffer for the risky slice only, not a secret 2x on everything. If I learn the task is bigger, I say so early — that matches the weakness I already told you. A late surprise is worse than a revised estimate on day one.

What if your estimate is wrong? How do you break a large task?

If I am slipping, I do not silently work late and hope. I say what is done, what is blocked, and the new date with a reason — “the export needs chunking, I did not see that in the spec.”

For a large task I cut a thin vertical slice we can demo: one company, one period, one export, or one student flow. Then I list the rest as follow-ups. That is how I keep velocity without hiding debt.

Example: for PIT I would not estimate “optimize the whole database.” I would estimate “make the period export finish and match a sample,” then a next slice for the next report.

How do you decide what to fix first when several things are slow or broken?

Impact and reversibility. Users blocked or data wrong goes first. Then launch-path reports. Then nice-to-have speed.

On PIT, a wrong XML for the tax authority beats a slightly slow list page. On IELTS, a failed STT that blocks speaking practice beats a slower animation. On a server, disk full or Cloud SQL unreachable beats a style bug.

Walk me through a data sync bug. · Third-party API. · Migration risk.

VSS sync: Silent mismatch. Reproduce on a tiny known set, diff source vs destination, check transform and job order, fix mapping, add validation, only then run the full job.

E-Hiring / VietnamWorks / TopCV: Failures are rate limits, expired auth, or a changed response. I make failure loud: retries where safe, request IDs in logs, monitoring on the sync job. I do not pretend the vendor is always up.

Legacy → MySQL/Apache: Hardest part is confidence. Backup and rollback first. After cutover I validate the app can read and write. I document the new path so the next person is not guessing.

A production issue you fixed · Something you caught in staging

Staging green, prod red: I diff commits, env vars, secrets, and service versions before I change code. Usually a missing variable, different web-server config, or a dependency only installed in one environment. Fix the config, redeploy, add it to the checklist.

Cloud Run up, DB down: Logs, then connection string, then network/socket, then service account permissions. Often identity or host setup, not “Node died.”

Linux disk full: df/du, free space safely, rotate logs, restart the service, then make disk visible in monitoring. I do not delete blindly under /var.

Pipeline red mid-release: Stop retry spam. Read which stage failed. Smallest fix. Promote only when green. Then make that failure louder earlier.

How do you test a report, export, or schema change?

I keep a fixture: a small company or a few employees whose numbers I already know. I run the old path and the new path and compare. For Excel/XML I check totals and a few line items, not only “file downloaded.”

For a schema or index change I check the write path too — inserts and the sync job — because a new index can slow writes. Then I run the heavy export once on a realistic volume if I have a staging dump, not first in production.
