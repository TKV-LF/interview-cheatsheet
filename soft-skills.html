How do you work with teammates day to day?

I try to make work visible: tickets with clear acceptance, small PRs, and status before people have to chase me. I ask early when the contract or design is unclear instead of building the wrong thing. I review others' code for risk, not style nits only. Bạn cộng tác với đồng nghiệp hằng ngày thế nào?

02. Two different solutions or ideas

Disagree on approach, not on people.

Answer EN

Answer VI

What do you do when you and a coworker have different technical solutions?

I put both options on the table with tradeoffs — time, risk, how hard it is to change later — and I ask what we optimize for this sprint. I don't need to 'win' the design. If we still disagree, I suggest a small spike or the reversible choice, and I commit to the team's decision. After we pick, I implement that path cleanly instead of half-building my idea in secret.

Khi bạn và đồng nghiệp khác giải pháp kỹ thuật, bạn làm gì?

Tôi đặt cả hai option lên bàn kèm tradeoff — thời gian, rủi ro, sau này sửa khó thế nào — và hỏi sprint này tối ưu gì. Tôi không cần 'thắng' design. Nếu vẫn khác ý, tôi đề xuất spike nhỏ hoặc lựa chọn đảo được, rồi commit theo quyết định của team. Sau khi chọn, tôi implement path đó sạch, không nửa vời cài ý mình.

Know: Tradeoffs · spike if stuck · commit after the decision

101. FE or BE? How do you decide?

Core method — memorize this.

Question EN
Answer EN
Question VI
Answer VI

How do you detect whether a bug is frontend or backend?

I reproduce first, then open DevTools Network. If the API response is already wrong — bad data, 4xx/5xx — it's backend or contract. If the API is correct but the UI shows wrong, it's frontend. If the request never leaves or is malformed, also frontend. I confirm with the same payload via curl or Postman to remove the UI from the equation.

Làm sao biết bug thuộc frontend hay backend?

Tôi reproduce trước, rồi mở DevTools Network. Nếu response API đã sai — data xấu, 4xx/5xx — là backend hoặc contract. Nếu API đúng mà UI sai — frontend. Nếu request không gửi hoặc malformed — cũng frontend. Tôi confirm cùng payload bằng curl/Postman để loại UI khỏi phương trình.

Know: Network tab is the judge between FE and BE.

Trap: Blaming FE or BE from a screenshot alone.

Follow-up: Show me how you'd prove an API is correct.

Practical steps.

What exactly do you look at in the Network tab?

Method and URL, status code, request headers/body, response JSON, and timing. I check if React called the endpoint I expect, with the params the backend needs. A 200 with wrong business data is still a backend bug. A 401 means auth. A CORS error is usually config between browser and API.

Bạn xem gì trong Network tab?

Method và URL, status, header/body request, JSON response, và timing. Tôi kiểm tra React có gọi đúng endpoint và param backend cần không. 200 mà data nghiệp vụ sai vẫn là bug backend. 401 là auth. Lỗi CORS thường là cấu hình giữa browser và API.

Know: Status + payload + timing + request shape.

Trap: Only watching Console and ignoring Network.

Why reproduce a bug with curl or Postman?

Because it answers: is the backend wrong without React? If curl gets the same bad data, I debug PHP/MySQL. If curl is correct but UI is wrong, I debug React state/render/mapping. It saves time and avoids arguments between FE and BE.

Vì sao reproduce bug bằng curl hoặc Postman?

Vì nó trả lời: backend có sai khi không có React không? Nếu curl ra data xấu giống vậy, tôi debug PHP/MySQL. Nếu curl đúng mà UI sai, tôi debug state/render/mapping React. Tiết kiệm thời gian và tránh cãi nhau FE–BE.

Know: Same request, no browser variables.

Trap: Different headers in curl than the app (false conclusion).

104. 4xx vs 5xx vs CORS

Quick triage.

Question EN
Answer EN
Question VI
Answer VI

How do status codes help you triage?

4xx usually means client/contract/auth — bad request, unauthorized, forbidden, not found. 5xx means server failure — exception, DB down, unhandled error. CORS failures often look like Network errors in the browser even when the server responded. I check the preflight and API CORS config before rewriting React code.

Status code giúp triage thế nào?

4xx thường là client/contract/auth — bad request, unauthorized, forbidden, not found. 5xx là lỗi server — exception, DB down, unhandled. CORS thường giống lỗi Network trên browser dù server có thể đã trả lời. Tôi kiểm tra preflight và cấu hình CORS trước khi viết lại React.

Know: 4xx client/contract; 5xx server; CORS is browser policy.

Trap: Treating every red Network row as backend is down.

The API is correct, but the UI is wrong. How do you debug?

I check mapping — wrong field names, timezone formatting, default values. Then React state: stale state, wrong dependency in useEffect, race condition from two fetches. Then render conditions — loading flag stuck, filtering out rows by mistake. React DevTools helps see props/state at the broken component.

API đúng nhưng UI sai. Bạn debug thế nào?

Tôi kiểm tra mapping — sai tên field, format timezone, default value. Rồi state React: state cũ, dependency useEffect sai, race từ hai lần fetch. Rồi điều kiện render — loading kẹt, filter mất row. React DevTools giúp xem props/state ở component đang hỏng.

Know: Mapping → state → effects → render conditions.

Trap: Rewriting the API when JSON was already right.

The UI is fine, but the API data is wrong or slow. How do you debug?

I reproduce the endpoint, read PHP logs, and inspect the SQL. Wrong data means business logic, joins, filters, or bad input validation. Slow means indexes, N+1, or heavy work in the request. I fix the query or logic, add a test when it's critical, and only then re-check from React.

UI ổn nhưng API sai hoặc chậm. Bạn debug thế nào?

Tôi reproduce endpoint, đọc log PHP, và xem SQL. Data sai nghĩa là business logic, join, filter, hoặc validation input. Chậm nghĩa là index, N+1, hoặc việc nặng trong request. Tôi sửa query/logic, thêm test nếu critical, rồi mới check lại từ React.

Know: Logs + SQL + reproduce payload.

Trap: Optimizing PHP loops before checking the query.

How do you balance a hotfix and a long-term fix?

If users are blocked, I ship the smallest safe mitigation first — feature flag, guard clause, rollback. Then I schedule the real fix: root cause, test, cleanup. I document both so we don't live on hotfixes forever. Globant's JD mentions long-term solutions — that matches how I like to work.

Bạn cân bằng hotfix và fix dài hạn thế nào?

Nếu user đang bị chặn, tôi ship mitigation nhỏ nhất an toàn trước — feature flag, guard, rollback. Rồi xếp lịch fix thật: root cause, test, dọn. Tôi ghi cả hai để không sống bằng hotfix mãi. JD Globant nói long-term solutions — khớp cách tôi muốn làm.

Know: Mitigate impact → root cause → prevent repeat.

Trap: Only hotfix and never follow up.

Walk me through debugging a production bug from UI to database.

User reports export shows wrong total. I reproduce on the screen, capture the API in Network — check payload. If API total is wrong, I hit the same endpoint via Postman, read PHP logs, inspect the SQL aggregate. Fix the query or business rule, verify API, then verify UI. If API was right, I fix the React mapping/format. Finally I add a check or test so it doesn't return quietly.

Hãy đi qua cách debug bug production từ UI tới database.

User báo export sai tổng. Tôi reproduce trên màn, bắt API trong Network — xem payload. Nếu API sai tổng, gọi cùng endpoint bằng Postman, đọc log PHP, xem SQL aggregate. Sửa query hoặc rule, verify API, rồi verify UI. Nếu API đúng, sửa mapping/format React. Cuối cùng thêm check hoặc test để không quay lại thầm lặng.

S: Wrong totals on an enterprise reporting screen.

T: Find which layer is lying.

A: UI reproduce → Network → Postman → PHP/SQL → fix → verify both layers.

R: Correct export + clearer ownership of the bug layer.

How do you approach solving a hard technical problem?

I clarify the symptom and the impact first. Then I reproduce it. Then I narrow the layer — FE, API, DB, or integration — with evidence from Network, logs, or SQL. I try the smallest safe fix, verify, and only then clean up or prevent repeats. I write down what I learned if it might come back.

Bạn tiếp cận giải quyết vấn đề kỹ thuật khó thế nào?

Tôi làm rõ triệu chứng và impact trước. Rồi reproduce. Rồi thu hẹp tầng — FE, API, DB, hay tích hợp — bằng bằng chứng từ Network, log, hoặc SQL. Thử fix nhỏ nhất an toàn, verify, rồi mới dọn hoặc phòng tái diễn. Tôi ghi lại nếu có thể quay lại.

Know: Symptom → reproduce → isolate layer → small fix → verify → prevent.

Trap: Changing five things at once.

What do you do when requirements are unclear?

I do not fake certainty. I ask what success looks like, what is in or out of scope, and what the edge cases are — empty data, permissions, large files. I propose a small first slice so we can demo early and adjust. In enterprise work, wrong assumptions are more expensive than one clarifying question.

Khi requirement không rõ bạn làm gì?

Tôi không giả vờ chắc chắn. Tôi hỏi success trông thế nào, in/out scope, và edge case — data trống, quyền, file lớn. Tôi đề xuất slice nhỏ đầu để demo sớm và chỉnh. Trong enterprise, giả định sai đắt hơn một câu hỏi làm rõ.

Know: Clarify success/scope/edges; ship a thin slice.

Question EN

Tell me about a technical tradeoff you made.

A common one: fix something fast for users versus making the perfect long-term design. If users are blocked, I ship a safe mitigation first, then schedule the cleaner fix. Another tradeoff: keep a sync flow synchronous for simplicity until it becomes slow, then move the heavy part to a job. I try to make the tradeoff explicit to the team.

Kể về một tradeoff kỹ thuật bạn từng chọn.

Một kiểu hay gặp: sửa nhanh cho user versus thiết kế dài hạn hoàn hảo. Nếu user đang bị chặn, tôi ship mitigation an toàn trước, rồi xếp lịch fix sạch hơn. Tradeoff khác: giữ sync đồng bộ cho đơn giản đến khi chậm, rồi đưa phần nặng sang job. Tôi cố nói rõ tradeoff với team.

S: Pressure between speed and design quality.

T: Unblock users without trapping the team in debt forever.

A: Mitigate first; document follow-up; move heavy work async when needed.

R: Users unblocked; debt tracked, not forgotten.

Say this: I make tradeoffs visible — not silent shortcuts.

How does your current team use Agile or Scrum day to day?

We work in sprints with a backlog of tickets. We plan what fits the sprint, have short daily standups for progress and blockers, and review/demo what we shipped. Tickets usually have acceptance criteria so “done” is clear. It's not ceremony for ceremony — the useful parts are shared priority, early blockers, and a demo of working software. Chúng tôi làm theo sprint với backlog ticket. Plan việc vừa sprint, standup ngắn về tiến độ và blocker, rồi review/demo phần đã ship. Ticket thường có acceptance criteria để “done” rõ. Không phải nghi thức vì nghi thức — phần hữu ích là ưu tiên chung, blocker sớm, và demo phần chạy được. Khi process nặng, tôi vẫn tập trung ship slice mỏng FE+BE hơn paperwork hoàn hảo.

113. Breaking down stories / estimation

How you plan work.

Question EN
Answer EN
Question VI
Answer VI

How do you break down a big feature into sprint work?

I split by user-visible value or risk: API contract first, then UI happy path, then edge cases, then polish. For a workflow feature that might mean: status model + transition API, then pipeline UI, then permissions, then reports. I avoid “all backend this sprint, all frontend next” when possible — a thin vertical slice is easier to demo and test. Estimation is a range with assumptions, not a promise to the minute.

Bạn tách feature lớn thành việc trong sprint thế nào?

Tôi tách theo giá trị user thấy hoặc rủi ro: contract API trước, rồi UI happy path, rồi edge case, rồi polish. Feature workflow có thể: model status + API transition, rồi UI pipeline, rồi permission, rồi report. Tránh “sprint này toàn BE, sprint sau toàn FE” nếu được — slice dọc mỏng dễ demo và test hơn. Estimate là khoảng có giả định, không hứa từng phút.

What do you do when you're blocked, or requirements change mid-sprint?

If blocked — say it in standup or ping ASAP: waiting on API, design, or access. Don't sit silent. During planning, how did you measure the complexity of a task? Story points?

Yes — usually relative sizing, often story points or a similar scale the team agrees on, not exact hours. I estimate by comparing to past tickets: uncertainty, how many layers (PHP API + React UI + DB), unknown third-party APIs, test effort, and risk of production impact. Khi planning, bạn đo độ phức tạp task thế nào? Story points?

Đổi text UI thì nhỏ; sync mapping nhiều edge case và report thì lớn. Team dùng Fibonacci story points thì tôi ổn. Nếu chưa rõ, tôi xin spike hoặc tách story trước khi commit số lớn.

What does clean, maintainable code mean to you?

Names that match reality, small functions, clear module boundaries, and tests on the risky parts. If a new teammate can change one feature without breaking five others, that's maintainable. Clever code that only I understand is not a win.
